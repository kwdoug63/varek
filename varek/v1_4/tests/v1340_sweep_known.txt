# v1340_sweep_known.txt — the checks of the suites that differ when each
# agent runs as a pod's container under the node agent (tests/v1340_sweep.sh),
# each with its reason. One a line, tab-separated: the suite, a regular
# expression on the check's text (its figures masked as #), the reason, and
# optionally a regular expression the node run's log (or its calls' reasons)
# must hold for the line to apply (step 8 review: a suite listed whole holds
# only while its runs are refused for what is not carried yet). A
# difference not listed here fails the sweep; a line no difference matches is
# said, so the list stays true. Found October 21, 2026 (Central), each cause
# read in the node run's own logs and streams (VAREK_SWEEP_KEEP=1).
#
# The kinds (the reason says which, by its first word):
#  AS-USER   under the node agent every file is opened as the container's
#            user, whatever the policy's version (step 2's review, "Files
#            opened as the node's root"); on a host a policy before 1.29 has
#            the Warden open allowed files as root. The suites' directories
#            and files are root's, so the agent (65534) cannot create or
#            write there, and what follows from a file it could not make
#            differs too.
#  OWN-PID   in the container's PID namespace the agent is PID 1: /proc/1 is
#            its own, decided as /proc/self/... (another process's
#            /proc/<pid> is refused under both; measured).
#  STREAM    in a pod the node agent's stream is a file on the node, outside
#            every pod, and the container's standard error is the kubelet's
#            log; the stand-in writes both on its standard error, so a
#            suite's "verdict stream" file is only that copy (not protected,
#            not the stream the node agent writes, no [agent] prefix).
#  RUNTIME   the runtime, not the node agent, starts the container and is
#            its parent: no exit status in run_end, no "agent killed by
#            signal", no network namespace of the Warden's (netns=on), the
#            runtime's own session (setsid), its own /dev.
#  LINE      the node agent's status lines differ in wording from the
#            Warden's ("supervising container ... pid=N ... uid=N", "held by
#            the launcher's Landlock"), which a check greps for.
#  D4        a pod's writable volumes are noexec as a whole (the plugin) and
#            the node agent refuses a container that could run a file it can
#            write; the Warden's per-directory noexec mounts (v1.27.1) are not
#            the node agent's. The suites' programs and scripts under /tmp
#            (the container's volume) cannot run; the stand-in moves the
#            program it is given into the image (/varek-sweep/NAME), so its
#            path differs.
#  LAUNCHER  the launcher runs first in every container and applies Landlock,
#            whatever the policy says of launches, and refuses to run without
#            Landlock; its refusals are its own (exit 126, its message).
#  NOT-YET   not carried in pods yet, refused at deploy (the webhook) and at
#            the start (--oci-filter names it); none from v1.36 step 6.
#            Credentials are carried from v1.36 step 4 (the stand-in gives
#            each to its namespace and sets the placeholders, as a cluster
#            does), sub-agents and confined MCP servers from step 5 (the
#            stand-in binds each program the policy names under /tmp
#            read-only at its path, as a pod's read-only volume holds one),
#            the on-behalf-of chain from step 6 (the stand-in puts the token
#            where the kubelet keeps the pod's varek-obo volume and gives
#            the SVID by a stand-in varek-svid), the dry run and trust
#            bundles from step 7 (the stand-in annotates the container as
#            the plugin does for a VarekPolicy saying them; a flow policy
#            checks a plan, and the stand-in gives no pod one).
#  OBO       v1.36 step 6 (D5): a pod's user's token and its agent's SVID are
#            the node agent's, read from the kubelet's copy and SPIRE's
#            answer outside the container and copied to its own files: its
#            refusals name those copies, and say a pod names no token
#            (varek.dev/on-behalf-of) where a host's say to give
#            --on-behalf-of FILE; the file a suite gave the Warden is not
#            the pod's token, so a policy naming it does not bear on it.
#  FIRST     v1.36 step 5 (D3, M1): the container's first process stays in
#            the container's group, so a sub-agent it launches itself is
#            refused (subagent_first_process); one launched by any other
#            process of the container runs, as on a host. The suite's agent
#            launches its sub-agents itself (exec), so each of those runs,
#            and what is read from their streams later, differs.
#  STAND-IN  how the stand-in differs from a pod in a way that does not bear
#            on the node agent (named in the reason).
#  D6A       v1.36 step 7 (D6a): in a pod a dry run refuses a connect the
#            policy refuses all the same (its network is the cluster's), the
#            record the policy's refusal, enforced, with dry_run_refused; on
#            a host the Warden dials it, recorded not enforced.
