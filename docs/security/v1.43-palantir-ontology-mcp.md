## Why

Palantir's Ontology MCP (OMCP) is a Developer Console feature. It exposes
an application's ontology resources (object types, action types and query
functions) as Model Context Protocol (MCP) tools, so that external agents
can read and write production ontology data. It authenticates with the
application's own OAuth 2.0 client: the authorization code grant for an
agent acting for a user, and the client credentials grant for a service
user. Agents connect over HTTP with a bearer token.

That is the setup VAREK is built for. An agent calls Palantir's tools,
and VAREK decides each call ALLOW or DENY at the run's boundary, with the
same SMT decision procedure and the same independent certificate check as
every other call. A read of an object type is allowed. An action type
that writes is held for a person (v1.42's STEP UP). A call the policy
does not name is refused. Every call and every approval is in the signed
stream. It is the pattern of the Falcon Foundry integration, aimed at the
platform the Department of War runs its data on (the Maven Smart System,
Army Vantage, Air Force Envision), and a recorded run is the proof point
for Palantir's FedStart program and for CDAO.

## What VAREK already does, and what is missing

- **Open-source build: most of it.** v1.31 decides MCP calls over HTTP
  under inspecting mode: `allow|deny mcp URL METHOD [NAME]`, the body read
  with a strict JSON parser, the `Mcp-Method` and `Mcp-Name` headers
  checked against it, the object `mcp:URL#METHOD/NAME`. v1.31's MCP tokens
  hold an access token and release it only into calls to its server.
  v1.42 holds an MCP call for an approver (`step_up mcp ... mode=hold`).
  An agent pointed at an OMCP server through a VAREK run with
  `proxy inspect` is decided today, if the agent trusts the run's CA.
- **Missing: the policy.** OMCP's tool names come from the application's
  ontology. Palantir's documentation shows `search-osdk-todo-task` and
  `create-osdk-todo-task` but states no naming rule, so a glob such as
  `tools/call search-*` cannot be trusted to mean "reads only". The policy
  has to name each tool the server lists.
- **Missing: the Defense build.** The Defense build (`make DEFENSE=1`,
  v1.41) leaves inspecting mode out, and MCP tool-call rules with it
  (`docs/security/v1.41-cryptography.md`, open item 2). For CDAO and
  FedStart, the Defense build is the one that matters.
- **Missing: tokens.** VAREK does not refresh tokens itself (v1.31's D8).
  An OMCP client credentials token expires, and whether a Foundry token is
  a JWT whose `aud` holds the MCP server's URL is not documented.
- **Missing: a test environment.** There is no public Maven Smart System
  sandbox. The free AIP Developer Tier (capacity-limited, commercial cloud,
  test data only) is the closest Palantir platform VAREK can be tested
  against. Whether Developer Tier offers OMCP has to be measured.

## Decisions

- **D1. Scope.** (a) The policy writer (D2), gateway mode (D3), the
  tokens (D4) and the Palantir integration folder, tested against a
  stand-in in CI and against a live enrollment at the ship gate; (b) the
  integration folder alone, on today's inspecting mode, with the Defense
  build later. *Recommended: (a).* (b) is a demo, not a product: it needs
  the agent to trust a minted CA and leaves out the build CDAO would run.

- **D2. The policy, written from the server's own tool list.** `varek mcp
  tools URL [--credential NAME] [--write-policy FILE]` calls `initialize`
  and `tools/list` once, through a run with only those two methods
  allowed, recorded as any run is, and writes one exact rule per tool. A
  tool goes to `allow` only when its MCP annotations say `readOnlyHint:
  true` and not `destructiveHint: true`. Every other tool, unannotated
  included, goes to `step_up ... mode=hold`. A person edits the file
  before it is used. Alternatives: (b) globs over Palantir's apparent
  naming; (c) rules written by hand from Developer Console. *Recommended:
  (a), with no globs over tool names.* An annotation is the server's claim
  about itself: it can move a tool to a person, never past one. The
  writer records the tool list's SHA-256 in the policy's header, and
  `varek mcp tools --check FILE` fails when the server's list has changed.

- **D3. Gateway mode, so the Defense build can decide MCP calls.** `mcp
  gateway NAME upstream URL [credential=NAME]`: warden-proxy listens for
  the run on loopback (`http://127.0.0.1:PORT/NAME`, the address given to
  the agent's MCP client in place of the server's URL). Each request is
  parsed and decided exactly as v1.31 decides an inspected one, against
  the same object `mcp:URL#METHOD/NAME` with the upstream's URL, so one
  policy reads the same in both modes. A call that is allowed is sent to
  the upstream over warden-proxy's own TLS client: the host's OpenSSL 3,
  the system trust store, the upstream's certificate verified against its
  host name. The response, streamed (SSE) or not, passes back unchanged,
  as v1.31's responses do. No certificate is minted and the agent trusts
  no CA, so gateway mode is not TLS interception. Alternatives: (b) wait
  for counsel on inspecting mode in the Defense build; (c) open-source
  build only. *Recommended: (a), in both builds.* In the Defense build it
  adds a TLS client to the egress proxy, a change to the cryptography
  inventory: the amended inventory goes to the outside export-control firm
  before any Defense claim names it (see "Rules for external material").

- **D4. Tokens.** (a) The client credentials grant for a service user,
  the token fetched by a small refresher outside the Warden
  (`varek/v1_4/integrations/palantir/omcp_token.py`, writing a file store, mode 600),
  read again by warden-secrets before it expires; VAREK stays no OAuth
  client, as v1.31 decided. The token is a v1.31 MCP credential:
  `audience=URL` when step 1 finds it is a JWT whose `aud` holds the MCP
  server's URL, `opaque` otherwise. (b) The authorization code grant, for
  an agent acting for a user, through v1.28.1's on-behalf-of and v1.31's
  `trust mcp-resource`, if step 1 finds OMCP publishes protected resource
  metadata (RFC 9728). *Recommended: (a) in v1.43.0, (b) after it.* The
  agent never holds the token in either.

- **D5. Writes held for a person.** Action types write ontology data. The
  example policy holds every action tool (`step_up mcp URL tools/call
  NAME mode=hold approvers=GROUP timeout=N`), and an approval is a v1.42
  grant: this tool, this many times, until this time. The demo shows a
  read allowed, a write approved, a write denied by the approver, a write
  that times out, and a tool the policy does not name refused.
  *Recommended: as written.*

- **D6. Arguments are not decided.** v1.31 decides the method and the
  tool, not the arguments, and does not record them. For an ontology
  action the arguments say which object it changes. Deciding named
  arguments (`arg project_id=...`) would be new grammar in both parsers,
  the cross-check's oracle and the checker. *Recommended: not in v1.43.0;
  named as a known limit, a candidate after it.* The approver sees the
  tool, not its arguments, until then; v1.42's `--intent` gives the
  approver the user's request.

- **D7. The ship gate.** (a) The full suite against the stand-in in CI;
  a live run against a Palantir enrollment with OMCP (Developer Tier, if
  step 1 finds OMCP there), recorded; the 24-hour soak against the
  stand-in, since Developer Tier's capacity is capped; and, for the
  Defense build, the RHEL 9 FIPS-mode acceptance of v1.41, extended to
  gateway mode. (b) Ship on the stand-in alone. *Recommended: (a).* If
  Developer Tier has no OMCP, the live run waits for an enrollment that
  has it (FedStart, or a partner's), and v1.43.0 waits with it.

- **D8. The live enrollment's data.** Test data only: a small ontology
  made for the run (Palantir's OSDK to-do example, a task object type, a
  create action, a search). No CUI, no government data, nothing
  export-controlled on Developer Tier. *Recommended: as written.*

- **D9. The recording.** Before a recording of the live run is published,
  Developer Tier's terms are read for any limit on publishing results.
  *Recommended: as written.*

## Implementation plan

1. **Measure (live; waits on a Developer Tier account).** Whether
   Developer Tier offers OMCP; the server URL's form; the MCP revision and
   transport; the token's form (JWT or opaque, `aud`, lifetime); whether
   OMCP publishes protected resource metadata; `tools/list` for one object
   type, one action type and one query function, with any annotations.
   Recorded in this note, then D2, D4 and D7 decided. The measurement is
   `varek/v1_4/integrations/palantir/omcp_measure.py` (standard library
   only, read-only: a token by the client credentials grant, discovery,
   `initialize` and `tools/list`; no tool is called, and neither the
   token nor the secret is printed or written).
2. **A stand-in OMCP server** for the tests (`tests/` and
   `varek/v1_4/tests/`), from step 1's measurements: streamable HTTP, the
   2025-06-18 and 2026-07-28 revisions, Palantir-style tool names, bearer
   tokens.
3. **`varek mcp tools`**: the policy writer and `--check` (D2).
4. **Gateway mode** in warden-proxy, open-source build (D3): the grammar
   in both parsers and the cross-check's oracle, under `require warden
   1.43`; the listener, the upstream TLS client, the decision, the
   credential, the records (`net.mcp` with `mode: gateway`).
5. **`varek/v1_4/integrations/palantir/`**: the example policy, the token refresher
   (D4), MCP client configurations pointing at the gateway (Claude Agent
   SDK, VS Code `mcp.json`, a headless agent), and the runbook.
6. **The live run** (D7, D8), recorded, and the demo script.
7. **The Defense build**: gateway mode on the FIPS provider, the RHEL 9
   FIPS-mode acceptance extended, `docs/security/v1.41-cryptography.md`'s
   inventory amended.
8. **Release v1.43.0**: release notes, the 24-hour soak, and the
   materials updated on every release.

## Tests (beyond v1.31's and v1.42's, run again in gateway mode)

- The policy writer: annotated read-only tools allowed, unannotated and
  destructive tools held, a changed tool list failing `--check`.
- Gateway mode: every v1.31 parser and header test through the gateway;
  the same policy deciding the same objects in inspecting and gateway
  mode; an upstream certificate for another host refused; the token
  released only to its upstream; SSE responses streamed unchanged; a
  refused call never reaching the stand-in; the agent unable to reach the
  upstream except through the gateway.
- Holds: an action tool held, approved, denied and timed out, each in the
  signed stream and replayed by the audit.
- The Defense build: gateway mode on a RHEL 9 host in FIPS mode, refusing
  to start without the FIPS provider active.

## Known limits (as planned)

- Arguments are not decided (D6).
- Responses are not decided: an object's data returned by a read passes
  as it is.
- A stdio MCP server's calls are not decided (v1.31); OMCP is over HTTP.
- Nothing here gives VAREK access to the Maven Smart System. Getting
  there is a government program office's decision, through CDAO's Open
  DAGIR third-party onboarding.
