# v1.26.1 — the egress proxy's inspecting mode: deciding every request (plan)

Status: **in progress**, target **v1.26.1**. Decided 2026-10-08: the
recommendation for each decision below. Built so far: steps 1 and 2, the grammar and `warden-proxy`
(see "As built" under it).
Builds on v1.26.0 (the egress proxy in SNI mode, [design](./v1.26-egress-proxy.md)),
whose sections 3 and 4 sketched this mode. Where this plan departs from
that sketch it says so (see "Changes from the v1.26 sketch"). Each section
ends with what must be tested before it ships.

## What SNI mode leaves open

SNI mode decides each connection on the name the client asks for. Inside
TLS it reads only the ClientHello, so:

1. **Domain fronting.** A request inside TLS can carry a `Host` for another
   site on the same content network. It reaches only the server the
   allowed name resolved to, but that server may serve the other site.
2. **Kept-open connections.** Later requests on a TLS connection can name
   another host, with the same limit.
3. **What is asked.** The method and path of each request are the agent's
   choice. `allow host api.example.com:443` allows `DELETE /v1/projects/*`
   as much as `GET /v1/models`.

Inspecting mode closes all three on the hosts it inspects. It does so by
terminating the agent's TLS in the proxy, which means the agent's
traffic to those hosts is in clear inside the proxy. That is the cost, and
it is why the mode is opt-in.

## 1. Policy

    require warden 1.26
    proxy inspect
    allow host api.example.com:443
    allow request GET  https://api.example.com/v1/models
    allow request POST https://api.example.com/v1/chat/completions max_body=256k
    deny  request *    https://api.example.com/v1/admin/*
    proxy passthrough host pinned.example.net

- `proxy inspect` turns the proxy on in inspecting mode. It takes the
  place of `proxy on`, and `proxy ports` and `proxy upstream` work with it
  as in v1.26.0.
- `allow request` and `deny request` take a method (`*`, or 1 to 20
  letters A-Z) and a URL: `https://` or `http://`, a host as in host rules
  (exact, or `*.` over a suffix of at least two labels), an optional port
  (default 443 or 80), and a path. The path may contain the glob forms the
  string fragment already decides (`*`, which stops at `/`, `**`, and
  `[...]`). `?` is the query's own `?`, never a wildcard.
- Options: `max_body=N` (bytes, with `k` and `m` suffixes) refuses a
  request whose body is longer.
- `proxy passthrough host NAME` (exact names only) keeps that host in SNI
  mode: its connections are decided on the SNI and relayed without
  decrypting. A request rule may not name a passthrough host. This is for
  clients that pin certificates and hosts that need a client certificate.
- **Version.** `require <major>.<minor>` has no patch part, so the new forms
  need `require warden 1.26` and are new in 1.26.1. A v1.26.0 Warden already
  refuses `proxy inspect` ("refused until v1.26.1") and refuses `allow
  request` as an unknown rule, so a v1.26.1 policy fails closed on it.
  Requiring `proxy inspect` for request rules keeps it that way.
- Refused at load: request rules without `proxy inspect`; `proxy on` and
  `proxy inspect` together; a request rule on a port that is not proxied;
  `max_body` on a deny; `passthrough` for a name a request rule matches.
  A request rule whose host no host rule allows on its port can never be
  reached: the Warden warns and `vdp_check lint` fails, as for any rule
  that can never fire.

The three policy parsers (the SMT decision procedure's, the certificate
checker's and the cross-check oracle's) read all of this independently and
must agree, as for every earlier form.

*Tests:* each form and each refusal in all three parsers; `varek policy
show` lists request rules and passthrough hosts; `make crosscheck` with
request rules in the fuzzed policies, 0 disagreements; a v1.26.0 Warden
refuses each new form.

## 2. What is decided

A connection is decided on its SNI `name:port` exactly as in SNI mode
(host rules, certified). Then each request on it is decided, in order,
before any of it is sent to the server.

- **The object.** `METHOD scheme://name:port/path?query`, for example
  `GET https://api.example.com:443/v1/models?limit=10`. The name and port
  are the connection's (the SNI's), not the client's: the request's `Host`
  must equal them or the request is refused. The method, path and query
  are the request's own bytes, unchanged.
- **Rules as globs.** Each request rule becomes a glob over that object
  (`GET https://api.example.com:443/v1/models`; a `*` method is a glob over
  one HTTP token), so it is decided, certified, checked for reachability
  and fuzzed with the existing matcher, as v1.25 did for wildcards. The
  first rule that matches decides. A request that matches no request rule
  is refused: in inspecting mode a host rule lets the agent connect, and
  only request rules let it ask. `varek policy check` warns about an
  inspected host with no request rule.
- **The query is matched.** An exact rule matches no query; to allow one,
  end the rule with `*` or name it. A query can carry data out, so the
  default does not admit it silently.
- **Objects over 4,095 bytes** (the string fragment's bound) are refused,
  not truncated.
- **Paths read one way.** A server and the matcher must not read a path
  differently, so the proxy refuses rather than normalizes a target that
  some servers would read as another path: `.` or `..` segments, `//`,
  a backslash, `;`, a NUL or other control byte, a byte over 0x7E, a
  percent-encoded unreserved character (`%2e`, `%41`), a percent-encoded
  `/`, a bad percent escape, and anything but origin-form (absolute-form is
  allowed when it names the connection's own scheme and authority, and
  then is matched as origin-form). What is left is matched byte for byte.
- **Headers are not decided**, beyond the framing and `Host` rules SNI mode
  already applies. Request heads stay within 8 KB.
- **Bodies are not decided.** Their length is counted against `max_body`,
  and their length and SHA-256 are recorded; their contents are not stored.

*Tests:* method, path and query matching, first match wins, default refusal;
each refused path form, including the encodings that would reach a deny
rule's path on a common server (`/v1/%61dmin/x`, `/v1/admin;x/y`,
`/v1/./admin/x`); `Host` differing from the SNI (domain fronting) refused;
a later request naming another host on a kept-open connection refused;
an object at 4,095 and 4,096 bytes; `max_body` with `Content-Length` and
with a chunked body.

## 3. Terminating TLS

- **A CA per run.** At startup the proxy generates an ECDSA P-256 CA key in
  its own memory and sends the Warden only the CA certificate. The key is
  never written anywhere, is held in locked memory, and dies with the
  proxy: there is nothing to store, protect or rotate. The certificate is
  valid from a few minutes before the run starts for at most the run's
  limit, and carries critical name constraints permitting only the
  policy's inspected names and wildcard suffixes, so a client that checks
  them refuses any other name even if the key were taken. Its SHA-256 is
  in `run_start`.
- **The agent trusts it.** The Warden serves the agent a CA bundle view:
  the host's own bundle followed by the run's CA certificate, at the usual
  bundle paths (as the v1.24 hosts view is served) and named by
  `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE` and
  `NODE_EXTRA_CA_CERTS` in the agent's environment. Java needs a trust
  store; how to serve one is a decision below.
- **Leaf certificates.** For each name it inspects, the proxy issues an
  ECDSA P-256 certificate for exactly that name, signed by the run's CA, and
  keeps it for the run.
- **The client side.** TLS 1.2 and 1.3, ALPN `http/1.1` only (a decision
  below), no 0-RTT data accepted, no session tickets across runs (the CA is
  new each run anyway).
- **The server side.** A new TLS connection to the address the Warden
  dialed (or through the upstream's `CONNECT`), SNI the decided name, TLS 1.2
  or 1.3, ALPN `http/1.1`, verified against the host's trust store (not the
  agent's view) with the name checked. Any verification failure refuses the
  connection and is recorded with OpenSSL's reason; it is never passed
  through. The certificate the server presented is recorded by its SHA-256.
- **Client certificates** cannot be forwarded through a terminated
  connection; a host that needs one must be a passthrough host.

*Tests:* curl, Python `requests` and `urllib`, Node `https` and `fetch`,
Go `net/http` and Java `HttpClient` reach an inspected host through the
view with no other settings; the agent cannot read the proxy's memory or
any CA key file (there is none); the CA certificate's name constraints and
lifetime; a server with an expired, self-signed or wrong-name certificate
is refused, never passed through; a passthrough host is relayed without
decrypting and recorded as such; a client that pins fails cleanly.

## 4. The proxy and the Warden

The split stays as in v1.26.0: the proxy parses, the Warden decides.

- For each request the proxy sends the Warden the connection id, the
  request's sequence number on it, the method, the target and the body
  length if known (`WP_MSG_HTTPREQ`). The Warden checks the report (one
  per sequence number, in order, on a connection it passed on in
  inspecting mode), decides the object with the SMT decision procedure,
  requires the certificate checker to accept the certificate, records it,
  and answers. Only then does the proxy send the request head to the
  server.
- A refused request gets a `403` with a one-line reason, and the
  connection ends after it (what came before has been answered), as SNI
  mode does at a request for another host.
- After the body, the proxy reports its length and SHA-256; the Warden
  records them. A body that passes `max_body` mid-stream ends the
  connection, and the server sees an incomplete request.
- The Warden never blocks on the proxy, and anything malformed from it
  stops the run, as now.
- **A separate binary.** Terminating TLS needs OpenSSL in the proxy. The
  Warden does not link OpenSSL and should not have to: the proxy (both
  modes) becomes its own binary, `warden-proxy`, which the Warden opens at
  startup, records by SHA-256 in `run_start`, and starts with `fexecve` as
  it starts the proxy today. The Warden's own trusted computing base gains
  no TLS code.

*Tests:* a proxy that reports a request twice, out of order, on a
connection in SNI mode, or never, stops the run (with the reviewers'
harnesses from v1.26.0 extended); the Warden's time per request decision;
`warden-proxy` replaced on disk after startup is not what runs.

## 5. Records and audit

- One `net.request` record per request, chained: connection id, sequence
  number, the object, the decision, the rule line, the certificate, and
  (after the body) `body_len` and `body_sha256`.
- `proxy_close` gains `requests` (how many were decided on the connection)
  and `inspected` (false for a passthrough host).
- `net.proxy` decisions in inspecting mode carry `inspected` and the
  server certificate's SHA-256.
- `varek_audit.py` checks that each `net.request` belongs to an inspected
  connection that was passed on, in sequence, each certificate re-checked,
  the object's name and port equal to the connection's, no request after a
  refused one on the same connection, `max_body` held, and the close's
  `requests` equal to the records. `run_start` names the CA certificate's
  hash and `warden-proxy`'s.
- `varek refusals` explains a refused request with its rule line, and the
  CycloneDX export carries request records.
- **What is in the stream.** The path and query are recorded as sent, as
  file paths are. Where a query carries a secret (an API key in the URL),
  so does the stream; the stream is the operator's, signed and anchored
  as before. Bodies are never recorded.

*Tests:* forged streams the audit must refuse: a request on a passthrough
connection, a sequence gap, a request after a refusal, an allowed request
the policy refuses, a body over its rule's limit, a close whose count
disagrees.

## 6. Cost and real traffic

Terminating TLS adds a handshake between the agent and the proxy and a
per-request round trip to the Warden. `varek bench` gains the proxied kinds
deferred from v1.26.0 (an HTTPS request in SNI mode and in inspecting mode),
`tests/latency_v1261.sh` repeats the v1.26.0 table with inspecting mode, and
a 24-hour soak runs the v1.26.0 harness in inspecting mode with request
rules, a fronting probe and a refused-path probe.

## Changes from the v1.26 sketch

- **A CA per run, not per installation.** The sketch had `varek init`
  create a CA kept on disk, readable only by the proxy's user, with a
  rotation procedure. A per-run CA in the proxy's memory has no key at rest
  and nothing to rotate, and its name constraints can follow the policy.
  The cost is that its certificate changes each run, which matters only to
  a client that caches trust across runs; the view is served each run.
- **No content-type rule.** The sketch had `deny content application/zip`.
  The agent writes the `Content-Type` header, so such a rule decides
  nothing the agent cannot choose; it is dropped rather than shipped as a
  control.
- **HTTP/1.1 only, for now.** The sketch tested HTTP/2. Offering only
  `http/1.1` in ALPN keeps HPACK and HTTP/2 framing, a large parser, out of
  this release; common clients fall back. gRPC needs HTTP/2 and does not
  work inspected (use a passthrough host). See the decisions below.
- **A separate proxy binary**, so the Warden does not link OpenSSL.

## Decisions before building

A recommendation for each; each is to be decided before step 1.

1. **HTTP/2.** Recommended: HTTP/1.1 only in v1.26.1; HTTP/2 later, as its
   own release, with its own fuzzed parser. Alternative: HTTP/2 now, using
   a library for framing and HPACK.
2. **A request with no request rule.** Recommended: refused (in inspecting
   mode, request rules are an allowlist). Alternative: a host with no
   request rules allows every request, as in SNI mode, which makes
   switching on inspecting mode easier but lets an unlisted host go
   unchecked.
3. **Java's trust store.** Recommended: serve a PKCS#12 trust store built by
   the Warden from the same bundle and set `JAVA_TOOL_OPTIONS`
   (`-Djavax.net.ssl.trustStore=...`). Alternative: document Java as a
   passthrough-only client in v1.26.1.
4. **Name constraints.** Recommended: put them on the CA, and test which
   clients enforce them and which refuse a constrained CA outright. If one
   the buyers need refuses it, allow no constraints only by a policy
   option, recorded.
5. **The proxy as its own binary.** Recommended, as above. Alternative:
   link OpenSSL into the Warden's binary and keep `--proxy-helper`, which is
   simpler to ship but puts TLS code in the binary that holds the signing
   key.

## Implementation plan

Each step lands with its tests in `make test-v1261`.

1. **Grammar** (done). `proxy inspect`, request rules, `max_body`, `proxy
   passthrough host`, in the three parsers, with their refusals and
   `varek policy show`; `vdp_cert_check`'s `proxy` mode reports the mode.
   As built (`smt_decide.c`, `checker/vdp_checker.c`,
   `tools/smt_crosscheck.py`; the grammar is in `smt_decide.h`):
   - A request rule is a new kind (`request`) held as a glob over the
     object, `METHOD scheme://host:port/path?query`: a `*` method is the
     glob `*` (no request target holds a space), a wildcard host is
     `?*.<suffix>` as for v1.25 host wildcards, the port is filled in, and
     each `?` of the URL is escaped. It is then decided, certified, checked
     for reachability and fuzzed as any glob, with no new matcher.
   - The rule's own path is held to the same forms the proxy will refuse
     in requests (no `.` or `..` segment, no `//`, `\`, `;` or `#`, bytes
     0x21 to 0x7e, no percent-encoded `/` or unreserved byte, no bad
     escape), since a rule written in a form no request takes could never
     fire.
   - The shared-domain refusals of v1.25 are not applied to a request
     rule's wildcard: request rules only narrow what host rules let the
     agent connect to, and the host rules are refused as in v1.25.
   - The Warden checks the two C parsers agree on every request rule (its
     glob and `max_body`), on inspecting mode and on the passthrough hosts,
     and warns about a request rule no host rule reaches. Until requests
     are decided (step 6), it refuses to run a `proxy inspect` policy, and
     `--check-startup` says so too: running it as SNI mode would allow
     requests the request rules refuse.
   - `vdp_cert_check <policy> proxy` prints `inspect` in place of `on`,
     then `passthrough NAME...`; its `rules` mode has a new field, a
     request rule's `max_body` (kind `r`), which `varek_audit.py` reads.
   - `make test-v1261` (section 1, 78 checks): each form and each refusal
     in both C parsers, the globs, ten requests decided and their
     certificates checked, lint, `varek policy show` and the Warden.
     `make crosscheck` fuzzes inspecting-mode policies with request rules,
     valid and malformed.
2. **`warden-proxy`** (done). Move the proxy into its own binary, started by
   `fexecve` and recorded by hash; SNI mode behaves exactly as in v1.26.0
   (`make test-v1260` passes unchanged).
   As built (`warden_proxy_helper.c`, `warden_proxy.c`):
   - The proxy's code (and `proxy_parse.c`) is now only in `warden-proxy`,
     which links libc alone; the Warden keeps only the side that starts the
     proxy and talks to it, and has no `--proxy-helper` mode. The
     `warden-proxy UID:GID` program drops to that user itself (no
     supplementary groups, an empty bounding set, no capabilities,
     no-new-privileges) and serves its control socket on descriptor 3; run
     any other way, it exits.
   - The Warden finds it beside its own binary, or at `--proxy-bin PATH`.
     It refuses one that is not a regular file, is writable by its group or
     by others, or is not an ELF executable (a script would run code the
     hash does not cover), and refuses to start without it when the policy
     turns the proxy on (`--check-startup` too).
   - Rather than check the file and run it by path, the Warden copies it
     into a memfd, hashing as it copies, seals the copy (no write, grow or
     shrink, no further seals) and starts the proxy from that copy with
     `fexecve`. What runs is exactly what was hashed, whatever happens to
     the file afterwards; `/proc/<pid>/exe` of the proxy is
     `/memfd:warden-proxy`. The copy's descriptor is close-on-exec, so the
     proxy holds the same six descriptors as in v1.26.0.
   - `run_start` carries `"proxy_binary_sha256"` beside its `proxy` object
     (the object itself is unchanged), and the audit requires it, as a
     SHA-256, exactly when the policy turns the proxy on.
   - `make install` installs `warden-proxy` beside `warden`; `varek doctor`
     and the AMI build check for it.
   - `make test-v1261` section 2 (16 checks): the program refusing to run
     by hand, its libraries, the hash in run_start equal to the file's,
     the memfd, the file replaced mid-run without effect, each refused
     binary, and two forged run_starts.
3. **The run's CA and the trust views.** The CA in the proxy, its
   certificate to the Warden, the bundle views and environment, Java's
   store if decided.
4. **Terminating TLS.** Client side and server side with OpenSSL, leaf
   certificates, verification, passthrough hosts; requests still relayed
   whole, so this step is tested against SNI mode's decisions.
5. **The request parser.** The target rules of section 2 in `proxy_parse.c`,
   bounded and fuzzed with the others.
6. **Request decisions.** `WP_MSG_HTTPREQ`, the Warden's decision and
   certificate, `net.request` records, refusals, `max_body`, body hashes.
7. **Audit and tools.** The section 5 checks, `varek refusals`, the
   CycloneDX export.
8. **Bench, latency and soak.** Section 6.

Then the review by AI review agents, the regression count against v1.26.0,
the README, threat model and spec paper, and the release.
