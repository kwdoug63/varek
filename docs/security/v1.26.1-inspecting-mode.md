# v1.26.1 — the egress proxy's inspecting mode: deciding every request (plan)

Status: **in progress**, target **v1.26.1**. Decided 2026-10-08: the
recommendation for each decision below. Built: steps 1 to 8, the grammar,
`warden-proxy`, the run's CA, terminating TLS, the request parser, request
decisions, the audit and tools, and the bench, latency and soak harnesses
(see "As built" under each). Left: the 24-hour soak on the droplet, the
review, and the release.
Builds on v1.26.0 (the egress proxy in SNI mode, [design](./v1.26-egress-proxy.md)),
whose sections 3 and 4 sketched this mode. Where this plan departs from
that sketch it says so (see "Changes from the v1.26 sketch"). Each section
ends with what must be tested before it ships.

## What SNI mode leaves open

SNI mode decides each connection on the name the client asks for. Inside
TLS it reads only the ClientHello, so:

1. **Domain fronting.** A request inside TLS can carry a `Host` for another
   site on the same content network. It reaches only the server the
   allowed name resolved to, but that server may serve the other site.
2. **Kept-open connections.** Later requests on a TLS connection can name
   another host, with the same limit.
3. **What is asked.** The method and path of each request are the agent's
   choice. `allow host api.example.com:443` allows `DELETE /v1/projects/*`
   as much as `GET /v1/models`.

Inspecting mode closes all three on the hosts it inspects. It does so by
terminating the agent's TLS in the proxy, which means the agent's
traffic to those hosts is in clear inside the proxy. That is the cost, and
it is why the mode is opt-in.

## 1. Policy

    require warden 1.26
    proxy inspect
    allow host api.example.com:443
    allow request GET  https://api.example.com/v1/models
    allow request POST https://api.example.com/v1/chat/completions max_body=256k
    deny  request *    https://api.example.com/v1/admin/*
    proxy passthrough host pinned.example.net

- `proxy inspect` turns the proxy on in inspecting mode. It takes the
  place of `proxy on`, and `proxy ports` and `proxy upstream` work with it
  as in v1.26.0.
- `allow request` and `deny request` take a method (`*`, or 1 to 20
  letters A-Z) and a URL: `https://` or `http://`, a host as in host rules
  (exact, or `*.` over a suffix of at least two labels), an optional port
  (default 443 or 80), and a path. The path may contain the glob forms the
  string fragment already decides (`*`, which stops at `/`, `**`, and
  `[...]`). `?` is the query's own `?`, never a wildcard.
- Options: `max_body=N` (bytes, with `k` and `m` suffixes) refuses a
  request whose body is longer.
- `proxy passthrough host NAME` (exact names only) keeps that host in SNI
  mode: its connections are decided on the SNI and relayed without
  decrypting. A request rule may not name a passthrough host. This is for
  clients that pin certificates and hosts that need a client certificate.
- **Version.** `require <major>.<minor>` has no patch part, so the new forms
  need `require warden 1.26` and are new in 1.26.1. A v1.26.0 Warden already
  refuses `proxy inspect` ("refused until v1.26.1") and refuses `allow
  request` as an unknown rule, so a v1.26.1 policy fails closed on it.
  Requiring `proxy inspect` for request rules keeps it that way.
- Refused at load: request rules without `proxy inspect`; `proxy on` and
  `proxy inspect` together; a request rule on a port that is not proxied;
  `max_body` on a deny; `passthrough` for a name a request rule matches.
  A request rule whose host no host rule allows on its port can never be
  reached: the Warden warns and `vdp_check lint` fails, as for any rule
  that can never fire.

The three policy parsers (the SMT decision procedure's, the certificate
checker's and the cross-check oracle's) read all of this independently and
must agree, as for every earlier form.

*Tests:* each form and each refusal in all three parsers; `varek policy
show` lists request rules and passthrough hosts; `make crosscheck` with
request rules in the fuzzed policies, 0 disagreements; a v1.26.0 Warden
refuses each new form.

## 2. What is decided

A connection is decided on its SNI `name:port` exactly as in SNI mode
(host rules, certified). Then each request on it is decided, in order,
before any of it is sent to the server.

- **The object.** `METHOD scheme://name:port/path?query`, for example
  `GET https://api.example.com:443/v1/models?limit=10`. The name and port
  are the connection's (the SNI's), not the client's: the request's `Host`
  must equal them or the request is refused. The method, path and query
  are the request's own bytes, unchanged.
- **Rules as globs.** Each request rule becomes a glob over that object
  (`GET https://api.example.com:443/v1/models`; a `*` method is a glob over
  one HTTP token), so it is decided, certified, checked for reachability
  and fuzzed with the existing matcher, as v1.25 did for wildcards. The
  first rule that matches decides. A request that matches no request rule
  is refused: in inspecting mode a host rule lets the agent connect, and
  only request rules let it ask. `varek policy check` warns about an
  inspected host with no request rule.
- **The query is matched.** An allow rule without a `?` matches no query,
  not even an empty one; to allow one, name it (`?limit=*`, or `?*` for
  any). A deny rule without a `?` denies its paths with any query. A query
  can carry data out, so the default does not admit it silently. (As
  first built, a rule's `*` could stretch across the query's `?`, and a deny
  rule for a path could be passed by adding one; the review found both.
  See "The review".)
- **Objects over 4,095 bytes** (the string fragment's bound) are refused,
  not truncated.
- **Paths read one way.** A server and the matcher must not read a path
  differently, so the proxy refuses rather than normalizes a target that
  some servers would read as another path: `.` or `..` segments, `//`,
  a backslash, `;`, a NUL or other control byte, a byte over 0x7E, a
  percent-encoded unreserved character (`%2e`, `%41`), a percent-encoded
  `/`, a bad percent escape, and anything but origin-form (absolute-form is
  allowed when it names the connection's own scheme and authority, and
  then is matched as origin-form). What is left is matched byte for byte.
- **Headers are not decided**, beyond the framing and `Host` rules SNI mode
  already applies. Request heads stay within 8 KB.
- **Bodies are not decided.** Their length is counted against `max_body`,
  and their length and SHA-256 are recorded; their contents are not stored.

*Tests:* method, path and query matching, first match wins, default refusal;
each refused path form, including the encodings that would reach a deny
rule's path on a common server (`/v1/%61dmin/x`, `/v1/admin;x/y`,
`/v1/./admin/x`); `Host` differing from the SNI (domain fronting) refused;
a later request naming another host on a kept-open connection refused;
an object at 4,095 and 4,096 bytes; `max_body` with `Content-Length` and
with a chunked body.

## 3. Terminating TLS

- **A CA per run.** At startup the proxy generates an ECDSA P-256 CA key in
  its own memory and sends the Warden only the CA certificate. The key is
  never written anywhere, is held in locked memory, and dies with the
  proxy: there is nothing to store, protect or rotate. The certificate is
  valid from a few minutes before the run starts for at most the run's
  limit, and carries critical name constraints permitting only the
  policy's inspected names and wildcard suffixes, so a client that checks
  them refuses any other name even if the key were taken. Its SHA-256 is
  in `run_start`.
- **The agent trusts it.** The Warden serves the agent a CA bundle view:
  the host's own bundle followed by the run's CA certificate, at the usual
  bundle paths (as the v1.24 hosts view is served) and named by
  `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE` and
  `NODE_EXTRA_CA_CERTS` in the agent's environment. Java needs a trust
  store; how to serve one is a decision below.
- **Leaf certificates.** For each name it inspects, the proxy issues an
  ECDSA P-256 certificate for exactly that name, signed by the run's CA, and
  keeps it for the run.
- **The client side.** TLS 1.2 and 1.3, ALPN `http/1.1` only (a decision
  below), no 0-RTT data accepted, no session tickets across runs (the CA is
  new each run anyway).
- **The server side.** A new TLS connection to the address the Warden
  dialed (or through the upstream's `CONNECT`), SNI the decided name, TLS 1.2
  or 1.3, ALPN `http/1.1`, verified against the host's trust store (not the
  agent's view) with the name checked. Any verification failure refuses the
  connection and is recorded with OpenSSL's reason; it is never passed
  through. The certificate the server presented is recorded by its SHA-256.
- **Client certificates** cannot be forwarded through a terminated
  connection; a host that needs one must be a passthrough host.

*Tests:* curl, Python `requests` and `urllib`, Node `https` and `fetch`,
Go `net/http` and Java `HttpClient` reach an inspected host through the
view with no other settings; the agent cannot read the proxy's memory or
any CA key file (there is none); the CA certificate's name constraints and
lifetime; a server with an expired, self-signed or wrong-name certificate
is refused, never passed through; a passthrough host is relayed without
decrypting and recorded as such; a client that pins fails cleanly.

## 4. The proxy and the Warden

The split stays as in v1.26.0: the proxy parses, the Warden decides.

- For each request the proxy sends the Warden the connection id, the
  request's sequence number on it, the method, the target and the body
  length if known (`WP_MSG_HTTPREQ`). The Warden checks the report (one
  per sequence number, in order, on a connection it passed on in
  inspecting mode), decides the object with the SMT decision procedure,
  requires the certificate checker to accept the certificate, records it,
  and answers. Only then does the proxy send the request head to the
  server.
- A refused request gets a `403` with a one-line reason, and the
  connection ends after it (what came before has been answered), as SNI
  mode does at a request for another host.
- After the body, the proxy reports its length and SHA-256; the Warden
  records them. A body that passes `max_body` mid-stream ends the
  connection, and the server sees an incomplete request.
- The Warden never blocks on the proxy, and anything malformed from it
  stops the run, as now.
- **A separate binary.** Terminating TLS needs OpenSSL in the proxy. The
  Warden does not link OpenSSL and should not have to: the proxy (both
  modes) becomes its own binary, `warden-proxy`, which the Warden opens at
  startup, records by SHA-256 in `run_start`, and starts with `fexecve` as
  it starts the proxy today. The Warden's own trusted computing base gains
  no TLS code.

*Tests:* a proxy that reports a request twice, out of order, on a
connection in SNI mode, or never, stops the run (with the reviewers'
harnesses from v1.26.0 extended); the Warden's time per request decision;
`warden-proxy` replaced on disk after startup is not what runs.

## 5. Records and audit

- One `net.request` record per request, chained: connection id, sequence
  number, the object, the decision, the rule line, the certificate, and
  (after the body) `body_len` and `body_sha256`.
- `proxy_close` gains `requests` (how many were decided on the connection)
  and `inspected` (false for a passthrough host).
- `net.proxy` decisions in inspecting mode carry `inspected` and the
  server certificate's SHA-256.
- `varek_audit.py` checks that each `net.request` belongs to an inspected
  connection that was passed on, in sequence, each certificate re-checked,
  the object's name and port equal to the connection's, no request after a
  refused one on the same connection, `max_body` held, and the close's
  `requests` equal to the records. `run_start` names the CA certificate's
  hash and `warden-proxy`'s.
- `varek refusals` explains a refused request with its rule line, and the
  CycloneDX export carries request records.
- **What is in the stream.** The path and query are recorded as sent, as
  file paths are. Where a query carries a secret (an API key in the URL),
  so does the stream; the stream is the operator's, signed and anchored
  as before. Bodies are never recorded.

*Tests:* forged streams the audit must refuse: a request on a passthrough
connection, a sequence gap, a request after a refusal, an allowed request
the policy refuses, a body over its rule's limit, a close whose count
disagrees.

## 6. Cost and real traffic

Terminating TLS adds a handshake between the agent and the proxy and a
per-request round trip to the Warden. `varek bench` gains the proxied kinds
deferred from v1.26.0 (an HTTPS request in SNI mode and in inspecting mode),
`tests/latency_v1261.sh` repeats the v1.26.0 table with inspecting mode, and
a 24-hour soak runs the v1.26.0 harness in inspecting mode with request
rules, a fronting probe and a refused-path probe.

## Changes from the v1.26 sketch

- **A CA per run, not per installation.** The sketch had `varek init`
  create a CA kept on disk, readable only by the proxy's user, with a
  rotation procedure. A per-run CA in the proxy's memory has no key at rest
  and nothing to rotate, and its name constraints can follow the policy.
  The cost is that its certificate changes each run, which matters only to
  a client that caches trust across runs; the view is served each run.
- **No content-type rule.** The sketch had `deny content application/zip`.
  The agent writes the `Content-Type` header, so such a rule decides
  nothing the agent cannot choose; it is dropped rather than shipped as a
  control.
- **HTTP/1.1 only, for now.** The sketch tested HTTP/2. Offering only
  `http/1.1` in ALPN keeps HPACK and HTTP/2 framing, a large parser, out of
  this release; common clients fall back. gRPC needs HTTP/2 and does not
  work inspected (use a passthrough host). See the decisions below.
- **A separate proxy binary**, so the Warden does not link OpenSSL.

## Decisions before building

A recommendation for each; each is to be decided before step 1.

1. **HTTP/2.** Recommended: HTTP/1.1 only in v1.26.1; HTTP/2 later, as its
   own release, with its own fuzzed parser. Alternative: HTTP/2 now, using
   a library for framing and HPACK.
2. **A request with no request rule.** Recommended: refused (in inspecting
   mode, request rules are an allowlist). Alternative: a host with no
   request rules allows every request, as in SNI mode, which makes
   switching on inspecting mode easier but lets an unlisted host go
   unchecked.
3. **Java's trust store.** Recommended: serve a PKCS#12 trust store built by
   the Warden from the same bundle and set `JAVA_TOOL_OPTIONS`
   (`-Djavax.net.ssl.trustStore=...`). Alternative: document Java as a
   passthrough-only client in v1.26.1.
4. **Name constraints.** Recommended: put them on the CA, and test which
   clients enforce them and which refuse a constrained CA outright. If one
   the buyers need refuses it, allow no constraints only by a policy
   option, recorded.
5. **The proxy as its own binary.** Recommended, as above. Alternative:
   link OpenSSL into the Warden's binary and keep `--proxy-helper`, which is
   simpler to ship but puts TLS code in the binary that holds the signing
   key.

## Implementation plan

Each step lands with its tests in `make test-v1261`.

1. **Grammar** (done). `proxy inspect`, request rules, `max_body`, `proxy
   passthrough host`, in the three parsers, with their refusals and
   `varek policy show`; `vdp_cert_check`'s `proxy` mode reports the mode.
   As built (`smt_decide.c`, `checker/vdp_checker.c`,
   `tools/smt_crosscheck.py`; the grammar is in `smt_decide.h`):
   - A request rule is a new kind (`request`) held as a glob over the
     object, `METHOD scheme://host:port/path?query`: a `*` method is the
     glob `*` (no request target holds a space), a wildcard host is
     `?*.<suffix>` as for v1.25 host wildcards, the port is filled in, and
     each `?` of the URL is escaped. It is then decided, certified, checked
     for reachability and fuzzed as any glob, with no new matcher.
   - The rule's own path is held to the same forms the proxy will refuse
     in requests (no `.` or `..` segment, no `//`, `\`, `;` or `#`, bytes
     0x21 to 0x7e, no percent-encoded `/` or unreserved byte, no bad
     escape), since a rule written in a form no request takes could never
     fire.
   - The shared-domain refusals of v1.25 are not applied to a request
     rule's wildcard: request rules only narrow what host rules let the
     agent connect to, and the host rules are refused as in v1.25.
   - The Warden checks the two C parsers agree on every request rule (its
     glob and `max_body`), on inspecting mode and on the passthrough hosts,
     and warns about a request rule no host rule reaches. Until requests
     are decided (step 6), it refuses to run a `proxy inspect` policy, and
     `--check-startup` says so too: running it as SNI mode would allow
     requests the request rules refuse.
   - `vdp_cert_check <policy> proxy` prints `inspect` in place of `on`,
     then `passthrough NAME...`; its `rules` mode has a new field, a
     request rule's `max_body` (kind `r`), which `varek_audit.py` reads.
   - `make test-v1261` (section 1, 78 checks): each form and each refusal
     in both C parsers, the globs, ten requests decided and their
     certificates checked, lint, `varek policy show` and the Warden.
     `make crosscheck` fuzzes inspecting-mode policies with request rules,
     valid and malformed.
2. **`warden-proxy`** (done). Move the proxy into its own binary, started by
   `fexecve` and recorded by hash; SNI mode behaves exactly as in v1.26.0
   (`make test-v1260` passes unchanged).
   As built (`warden_proxy_helper.c`, `warden_proxy.c`):
   - The proxy's code (and `proxy_parse.c`) is now only in `warden-proxy`,
     which links libc alone; the Warden keeps only the side that starts the
     proxy and talks to it, and has no `--proxy-helper` mode. The
     `warden-proxy UID:GID` program drops to that user itself (no
     supplementary groups, an empty bounding set, no capabilities,
     no-new-privileges) and serves its control socket on descriptor 3; run
     any other way, it exits.
   - The Warden finds it beside its own binary, or at `--proxy-bin PATH`.
     It refuses one that is not a regular file, is writable by its group or
     by others, or is not an ELF executable (a script would run code the
     hash does not cover), and refuses to start without it when the policy
     turns the proxy on (`--check-startup` too).
   - Rather than check the file and run it by path, the Warden copies it
     into a memfd, hashing as it copies, seals the copy (no write, grow or
     shrink, no further seals) and starts the proxy from that copy with
     `fexecve`. What runs is exactly what was hashed, whatever happens to
     the file afterwards; `/proc/<pid>/exe` of the proxy is
     `/memfd:warden-proxy`. The copy's descriptor is close-on-exec, so the
     proxy holds the same six descriptors as in v1.26.0.
   - `run_start` carries `"proxy_binary_sha256"` beside its `proxy` object
     (the object itself is unchanged), and the audit requires it, as a
     SHA-256, exactly when the policy turns the proxy on.
   - `make install` installs `warden-proxy` beside `warden`; `varek doctor`
     and the AMI build check for it.
   - `make test-v1261` section 2 (16 checks): the program refusing to run
     by hand, its libraries, the hash in run_start equal to the file's,
     the memfd, the file replaced mid-run without effect, each refused
     binary, and two forged run_starts.
3. **The run's CA and the trust views** (done). The CA in the proxy, its
   certificate to the Warden, the bundle views and environment, Java's
   store if decided.
   As built (`proxy_ca.c`, `warden_trust.inc.c`):
   - `warden-proxy` links OpenSSL (libssl, libcrypto); the Warden does not.
     Before the agent starts, the Warden sends the proxy the run id, the
     host's trust bundle (the first of `/etc/ssl/certs/ca-certificates.crt`,
     `/etc/pki/tls/certs/ca-bundle.crt`,
     `/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem`, `/etc/ssl/cert.pem`
     that is a file) and the names the CA may sign for: every host name an
     allow rule lets the agent reach on a proxied port and every wildcard's
     suffix, without passthrough hosts. The proxy makes the CA and sends
     back its certificate (PEM) and a PKCS#12 trust store.
   - The CA: ECDSA P-256, a random serial, `CN=VAREK run CA <run id>`,
     basicConstraints critical CA:TRUE pathlen 0, keyUsage critical
     keyCertSign and cRLSign, and critical name constraints permitting those
     names (a dNSName subtree also covers the names under it; with none,
     only `invalid`). Valid from five minutes before the run for seven days:
     a run longer than that will have its new leaf certificates refused
     (step 4).
   - Its key is made in OpenSSL's secure heap where the memory-lock limit
     allows (locked, wiped when freed; run_start's `ca_key_locked` says
     whether it was), and the proxy is not dumpable, so no process of its
     own user can read its memory or take a core. Nothing is written to disk.
   - The trust store holds the host's roots and the CA, each a trusted
     certificate entry with the attribute Java reads (OpenSSL 3.2's
     `-jdktrust`), unencrypted and with no MAC, so it opens without a
     password; Java 21 reads it as such.
   - The Warden checks the certificate is one PEM certificate (and records
     the SHA-256 of its DER) and the store is DER. It serves, read-only, the
     host's bundle with the CA after it at each of the four bundle paths and
     `/etc/varek/run-bundle.pem` (and any spelling that resolves to them),
     the CA alone at `/etc/varek/run-ca.pem`, and the store at
     `/etc/varek/run-trust.p12`, whether or not those files exist on the
     host. An open that could write any of them is refused. The agent's
     environment sets `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE` and
     `CURL_CA_BUNDLE` to the bundle, `NODE_EXTRA_CA_CERTS` to the CA, and
     adds the store to `JAVA_TOOL_OPTIONS` after any options already there.
     A client that reads a hashed certificate directory (`CApath`) instead
     of a bundle file does not see the CA.
   - run_start's proxy is in mode `inspect`, and `"trust"` records the
     host's bundle and its SHA-256, how many roots it holds, the CA's
     SHA-256, how many names it may sign for, the store's SHA-256, whether
     the key is locked, and the passthrough hosts. The audit checks each
     against the policy, and that trust views are answered only in
     inspecting mode and only at their paths.
   - Until requests are decided (step 6), a connection to a host that is not
     a passthrough host is refused, recorded `inspect_not_built`, after the
     decision on its name, rather than relayed in SNI mode, which would let
     through requests the request rules refuse. A passthrough host is
     relayed in SNI mode, as it will be. The step 1 refusal to run a `proxy
     inspect` policy at all is gone.
   - `make test-v1261` section 3 (17 checks): the proxy's memory, each view,
     their read-only answers, the environment, Python's default context
     trusting the CA, the CA's form, name constraints and validity, the
     hashes in run_start, Java opening the store, an inspected host refused
     and a passthrough host relayed, the audit accepting the run and
     refusing four forged streams.
4. **Terminating TLS** (done). Client side and server side with OpenSSL, leaf
   certificates, verification, passthrough hosts; requests still relayed
   whole, so this step is tested against SNI mode's decisions.
   As built (`proxy_ca.c`, `warden_proxy_helper.c`, `warden_pxdecide.inc.c`):
   - Changed from the plan: requests are not relayed whole. Relaying them
     before step 6 would let through requests the request rules refuse, so
     until then the proxy answers every inspected request `403` (a short
     text body) after reading its head, and sends the server nothing. The
     TLS on both sides is built and tested now; relaying, with each request
     decided, is step 6.
   - The Warden decides the SNI name as in SNI mode, then marks a host that
     is not a passthrough host `"inspected":true` and passes the socket it
     dialed with the inspect flag. Plain HTTP to such a host has no TLS to
     terminate and is refused (`inspect_not_built`) until step 6.
   - The proxy verifies the server first, over the dialed socket (or inside
     the upstream's CONNECT tunnel): TLS 1.2 or later, SNI the name decided,
     verified against the roots the run trusts (the host's bundle, or
     `--trust-bundle PATH`, a new Warden option for a bundle of one's own,
     such as a corporate CA's), the name checked without partial
     wildcards, ALPN `http/1.1`. A server that fails is refused before the
     client's handshake begins: the client gets a handshake_failure alert,
     and the close is `server_tls` with OpenSSL's reason (`certificate:
     hostname mismatch`, `certificate: self-signed certificate`, ...).
   - Then the client's handshake, from the ClientHello already read, with a
     leaf for the name: one P-256 key for every leaf, `CN` (when it fits)
     and the subject alternative name the name alone, CA:FALSE,
     digitalSignature, serverAuth, an authority key identifier, valid until
     the CA is; made once a name and kept (4,096 names, then made again).
     TLS 1.2 or later, ALPN `http/1.1` chosen, a client that offers ALPN
     without it (h2 alone) refused, no session tickets, no session cache, no
     early data, no renegotiation. A client that does not trust the CA, or
     offers only h2, fails its handshake: the close is `client_tls` with the
     reason (`tlsv1 alert unknown ca`, `no application protocol`).
   - `proxy_close` for an inspected connection carries `"inspected":true`,
     the server certificate's SHA-256 when it presented one, and
     `"tls_error"`; its reasons add `server_tls`, `client_tls`,
     `tls_timeout` (a handshake over 10 s; once relaying, the 1 h idle limit) and
     `inspect_not_built`. The Warden refuses (and stops the run on) a close
     report that marks inspected a connection it did not pass on to be
     inspected, or the reverse, gives a TLS reason for one that is not, or
     counts bytes relayed to an inspected server before step 6.
   - Found while testing Java: it checks the trust store exists before
     opening it, and `/etc/varek/run-trust.p12` is a view, not a file. A
     read-type lookup (`stat`, `statx`, `access` without W_OK or X_OK) of a
     trust view is now answered from the view (`view_metadata`): a regular
     file of the view's size.
   - The audit checks each inspected decision and close against these
     rules: inspected exactly when the host is not passthrough, the TLS
     reasons only for inspected connections, no bytes relayed, a SHA-256
     where one is given, `view_metadata` only for trust views in
     inspecting mode.
   - `make test-v1261` section 4 (24 checks): a verifying Python client, the
     leaf's form and its reuse, ALPN, a client that pins its own root, TLS
     inside CONNECT, a server of the wrong name and a self-signed one, a
     passthrough host, plain HTTP, the close records, the store's
     metadata, curl, Node.js and Java with no settings of their own, a Squid
     upstream, and forged streams. The suite also passes with
     `warden-proxy` built under ASan and UBSan.
5. **The request parser** (done). The target rules of section 2 in `proxy_parse.c`,
   bounded and fuzzed with the others.
   As built (`pp_request` in `proxy_parse.c`; its contract is in
   `proxy_parse.h`):
   - It reads one request of an inspected connection as plain HTTP's heads
     are read (CRLF only, within 8 KB, one `Host`, the body framed by
     `Content-Length` or chunked, no upgrade), allocates nothing, and gives
     the method, the object `METHOD https://name:port/path?query` (name and
     port the connection's, method and target the request's own bytes),
     the head's length and the body's framing.
   - Refused: a method that is not 1 to 20 letters A-Z (plain HTTP's
     request line now takes 20 too, from 16, to match the rules), CONNECT, a
     `Host` other than the connection's name (or its port, if it gives one;
     a trailing dot and capitals are read as the name), an absolute-form
     target for another scheme or authority or without a path, `OPTIONS *`,
     and the target forms of section 2. One more than the plan:
     a percent-encoded backslash (`%5C`), which some servers read as a path
     separator; the three rule parsers refuse it in a rule too, so a rule
     is still held to the forms a request can take.
   - An object over 4,095 bytes is refused, not cut.
   - The proxy now reads an inspected connection's first request with it.
     One it refuses is answered `403` with the reason and recorded
     `refused_request`, with `"request_error"` in the close (domain
     fronting, `..`, `%61dmin` and the like); one it reads is still
     answered `403` and recorded `inspect_not_built` until step 6.
   - `make fuzz-proxy-parse`: 40 request vectors, an object at the bound
     and one byte over, a request read a byte at a time, and requests among
     the mutated inputs (about 18,000 of 4,000,000 read as whole requests),
     each result checked against the contract, under ASan and UBSan.
   - `make test-v1261`: four more checks, a fronting request, a `..`
     segment and an escaped letter inside TLS refused and recorded, and an
     absolute-form request read; and `%5C` refused in a rule.
6. **Request decisions** (done). `WP_MSG_HTTPREQ`, the Warden's decision and
   certificate, `net.request` records, refusals, `max_body`, body hashes.
   As built (`warden_proxy_helper.c`, `px_httpreq` and `px_httpbody` in
   `warden_pxdecide.inc.c`):
   - The proxy relays an inspected connection both ways through a gate on
     the client's side. The gate reads each request's head with
     `pp_request`, sends the Warden its object and its body's framing
     (`WP_MSG_HTTPREQ`, numbered 1, 2, ... on the connection), and lets
     nothing of it through until the verdict (`WP_MSG_REQVERDICT`). An
     allowed request's head is sent, then its body as framed; the next
     head is read after it, so pipelined and kept-alive requests are each
     decided in turn. The server's answers are relayed as they come.
   - The Warden checks each report (a connection passed on to be
     inspected, the next number, no body of the last request still
     unreported, an object for that connection's scheme, name and port of
     printable bytes) and stops the run on anything else. It decides the
     object with the decision procedure (kind `request`), and the checker
     must accept the certificate. A `Content-Length` over the allowing
     rule's `max_body` is refused (`max_body`) before a byte is sent. Each
     decision is a chained `net.request` record: `proxy_conn`,
     `request_seq`, the object, the rule (`request_allowed`,
     `policy_match`, `default_deny_unknown`, `certificate_refused`,
     `max_body`), `policy_line`, the certificate, the body's framing and
     declared length, and an allowed request's `max_body`.
   - At a refusal, by the Warden or by the parser, the gate stops: nothing
     of that request or after it is sent, the server is told no more
     requests are coming (close_notify, or a half-close), its answers to
     the requests before are still relayed (10 s at most), and then the
     client gets `403` with a one-line reason (`the policy denies it (line
     8)`, `no request rule allows it`, `its body is over max_body=1024
     (policy line 5)`, or the parser's reason). The close is
     `refused_request`.
   - Bodies: the proxy counts and hashes (SHA-256) the bytes of each
     allowed request's body as it sends them (a chunked body's framing
     included), and reports them after the body (`WP_MSG_HTTPBODY`), which
     the Warden records as a chained `request_body`. A chunked body that
     passes `max_body` is sent only up to it; then the connection is cut
     (no close_notify, so the server sees an incomplete request), the
     body is recorded `"exceeded_max_body":true` at exactly `max_body`
     bytes, and the close is `max_body`. Bodies are never stored.
   - Plain HTTP to an inspected host is no longer refused outright: it is
     relayed through the same gate, each request decided on its
     `http://` object.
   - `inspect_not_built` is gone. The Warden's close checks now allow
     bytes to an inspected server only after a request was allowed, and a
     `max_body` close only after a body that passed it.
   - The audit (ahead of step 7) checks each `net.request`: a connection
     passed on to be inspected, numbered in order with none after a
     refusal and none before the last body, an object of that connection,
     a rule the Warden writes, an allowed request certified again by the
     checker with its rule's `max_body`; and each `request_body`: after
     its allowed request, once, within `max_body` unless marked as passing
     it, and then at exactly `max_body`.
   - `make test-v1261` section 5 (17 checks), against a TLS and a plain
     keep-alive server that hash what they receive: a kept-alive
     connection (two allowed, one denied, one never sent), pipelining, a
     request no rule allows, a query, a later request for another `Host`,
     a body within `max_body` (the recorded SHA-256 equal to the
     server's), one declared over it, a chunked one passing it, a chunked
     one with no limit, plain HTTP, and four forged streams. Sections 1 to
     4 now expect allowed requests to reach their servers. The suite passes
     with `warden-proxy` under ASan and UBSan.
7. **Audit and tools** (done). The section 5 checks, `varek refusals`, the
   CycloneDX export.
   As built (`tools/varek_audit.py`, `tools/varek`, `tools/varek_cyclonedx.py`):
   - `proxy_close` for an inspected connection carries `"requests"`, how
     many requests the proxy reported on it. The Warden stops the run on a
     close report whose count is not the number it decided on that
     connection (or is not zero for one not inspected), and the audit
     requires it to equal the `net.request` records of the connection.
   - The audit asks the policy again about each refused request (the
     checker's `holds` mode, the first request rule in policy order that
     matches the object): a `policy_match` refusal must be a deny rule at
     its `policy_line`, a `default_deny_unknown` one must have no rule that
     matches, and a `max_body` one must be an allow rule at its line whose
     `max_body` is under the declared length. An allowed request is still
     re-checked by its certificate.
   - `varek refusals` lists a refused request with its rule line and text
     (`UNSATISFIED`, `UNKNOWN`, or `MAX_BODY` with the declared length; the
     agent got `403 Forbidden` and the connection ended), then the
     connections the proxy ended itself: a request its parser refused
     (`REFUSED`, with the reason), a server that failed verification
     (`SERVER_TLS`), the agent's failed handshake (`CLIENT_TLS`, with a hint
     about the CA and http/1.1), `TLS_TIMEOUT`, and a body cut at
     `max_body`. A close after the Warden's own refusal is not listed twice.
   - The CycloneDX export names the proxy's mode and `warden-proxy`'s
     SHA-256 and, in inspecting mode, the run's CA (its SHA-256, how many
     names it may sign for, whether its key was locked), the trust store's
     and host bundle's SHA-256, the passthrough hosts, and the counts:
     requests allowed and refused (and for `max_body`), refused by the
     parser, bodies recorded and cut, failed TLS handshakes. The
     attestation says each request was decided before any of it was sent
     and that bodies are recorded by length and SHA-256, never their
     contents. Each allowed request's object is an authorized component, as
     a file is. Trust views are counted as views, not decisions, so the

   - `make test-v1261` section 6 (8 checks): the close counts, four forged

8. **Bench, latency and soak** (done). Section 6.

## The review

Four AI review agents reviewed 2259655..20533cf on 2026-10-08, each over one
part: TLS termination and the run's CA; the request parser and the gate; the
grammar and the Warden's request decisions; the audit and the tools. Each
finding was reproduced (a script and its output) before it was reported,
then fixed and given a check in `make test-v1261` (sections 1 and 7). The
parser and gate review found nothing; it compared the proxy's reading of
smuggling and framing vectors with a Python and a Go server, and ran the
parser fuzzer under ASan and UBSan.

**Critical**, fixed:
- *A rule's wildcard stretched across the query's `?`.* `allow request
  DELETE https://h/v1/items/*/tag` allowed `DELETE /v1/items/42?/tag`,
  which a server reads as `/v1/items/42`; `[!s]` matched the `?` of
  `/v1/user?`, and `/a/**/info` matched `/a/secret?x=/info`. Now a request
  URL has at most one `?`, and so has a request the proxy reads, so a rule's
  `?` can meet only the request's; and an allow rule without a `?` holds on
  no request with one. In the three parsers (`smt_decide.c`,
  `checker/vdp_checker.c`, `tools/smt_crosscheck.py`, which also says it to
  its SMT solver), so decisions, certificates and the cross-check agree.
- *A deny rule for a path was passed by adding a query.* `deny request GET
  https://h/v1/secret` before `allow request GET https://h/v1/**` let
  `/v1/secret?` and `/v1/secret?x=1` through. A deny rule without a `?` now
  holds when its glob matches the request up to its `?`.
- *The audit passed an allowed request declaring a body over its rule's
  max_body*, and *one in a path form the proxy must refuse* (`%61dmin`,
  `/./`, `//`). The audit now applies section 2's target rules to every
  request, and so does the Warden, written again rather than taking the
  proxy's word (differential-tested against `proxy_parse.c` and the audit
  over 200,000 targets).

**High and medium**, fixed:
- An allowed body with no `request_body`, so a cut body could be recorded as
  sent whole. The proxy now reports what was sent of a body when the
  connection ends first (`"incomplete":true`); the Warden requires a report
  for every allowed body (a declared length sent whole, or less if
  incomplete) and stops the run on a close with one unreported; the audit
  checks requests, bodies and closes in stream order, so also a request
  after its connection's close.
- A server's TLS ending without close_notify (a crash, or a forged FIN or
  RST) reached the agent as a clean close, so a body read to the end could be
  cut short unseen. The agent now gets no close_notify either, and the close
  says why (`tls_error`).
- `view_metadata` answered where a deny rule holds, or for `access(W_OK)`,
  passed the audit.

**Low**, fixed: the CA's name constraints now exclude every IP address and
the passthrough hosts (a wildcard's suffix covered them); a chunked body cut
at max_body is sent up to the limit first (the server got nothing, the
record said it got the limit); a client's TCP half-close no longer loses the
answer; trust views stat as 0444; a server name is checked in the subject
alternative name only, never the CN; the Warden refuses a request after a
body cut at max_body and stops on a malformed report while the run ends
(`run_end` says `"proxy_failed":true`, and the Warden exits 1); lint reports
a wildcard request rule no host rule reaches; the audit checks the CA's name
count, refuses trust views outside inspecting mode in the export, and
recorded bodies larger than the bytes relayed; no traceback on malformed
fields (the audit, the export, `varek refusals`, the soak checker).

**Stated, not changed**: a chunked body's framing counts against max_body
(the proxy bounds and hashes what it sends); run_start's `host_roots` and
`ca_key_locked` are the Warden's reports of its host, which the audit cannot
recompute; a passthrough host stays in SNI mode, so fronting through it to an
inspected name on the same CDN is not inspected (by design: section 3).

**Found by the cross-check, after the review.** `make crosscheck` on the
final grammar found the reachability analysis still reading each request
rule as its glob alone: it called `deny request PUT https://h/v1/**` dead
behind `allow request PUT https://h/v1/**`, though the deny holds on
`/v1/x?q` and the allow does not. Decisions and certificates were not
affected (they use the rules' holds), but lint's "can never fire" could
have hidden a live deny rule. The analysis now compiles a rule without a
`?` with no wildcard taking `?` (and, for a deny rule, a second automaton
for its path followed by a query) and searches those; `make test-v1261`
section 1 checks the case.

## Regression against v1.26.0

`make test-v1261` (192 checks, all passing on this branch) was run against
the v1.26.0 Warden, parsers, audit, exporter and `varek` command (commit
2259655, which reports itself as `1.26.0`), with this branch's
`warden-proxy` placed beside the old Warden so that no section is skipped:

- **187 checks fail.** v1.26.0 has no inspecting mode: it refuses every
  `proxy inspect` policy, so no request is decided, no CA is made and no
  trust view is served. 51 of the failures are grammar checks of refused
  forms: v1.26.0 refuses those policies too, but as an unknown kind
  (`request`) or directive, not for the reason the check names. The
  review's checks all fail on it: 12 in section 1 and the 16
  checks of section 7 (whose 8 forgeries also have no stream to edit, 8
  failures more, so the run reports 195).
- **2 pass:** the audit accepts section 2's run, which is in SNI mode, as
  v1.26.0 has it; and "the refused request never reached the server" holds
  trivially, as v1.26.0 refused the whole policy.
- **3 are not counted:** they test the `warden-proxy` binary itself (it
  will not run by hand or without the Warden's control socket, and links
  neither libseccomp nor libsodium), which v1.26.0 does not have; with this
  branch's binary placed beside it they pass, and say nothing of v1.26.0.

The earlier suites pass unchanged on this branch: `make test-v1260` (SNI
mode), `test-v1250`, `test-v1240`, `test-cli` (64 tests) and
`fuzz-proxy-parse`. `make crosscheck` passes with 0 disagreements, with
request rules (valid and malformed, queries among them) in the fuzzed
policies and the review's semantics in its SMT encoding.
