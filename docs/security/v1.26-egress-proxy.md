# v1.26 — the egress proxy: deciding on the name the agent asks for (plan)

Status: **planned**, target **v1.26.0** (decided 2026-10-05; this is the
"v1.21 stage 3" item of earlier roadmaps). Builds on v1.24.0 (exact host
names, [design](./v1.21-stage2-host-names.md)) and v1.25.0 (wildcards,
[design](./v1.25-wildcard-host-names.md)); nothing below is implemented. Each
section ends with what must be tested before it ships.

## What v1.24 and v1.25 leave open

Both decide a connect on the address dialed and the names that resolved to
it. Two things are outside that:

1. **Shared addresses.** On a content network one address serves many sites.
   Allowing `api.example.com` lets the agent reach any other site on the same
   address by sending another name in TLS SNI or the HTTP `Host` header.
2. **What is sent.** An allowed host is a channel: the method, path and body
   of each request are the agent's choice.

v1.26 adds a Warden-owned egress proxy that sees the name the client asks the
server for, and, in an opt-in inspecting mode, the request itself.

## 1. How traffic reaches the proxy

- No client configuration is needed. Since v1.21.0 the Warden dials every
  allowed connect itself and hands the agent the socket. With the proxy on,
  for a connect whose port is in the policy's `proxy ports` (default 80 and
  443), the Warden hands the agent a socket connected to the proxy instead,
  and tells the proxy the original destination. Clients that honour
  `HTTPS_PROXY` are also served (`CONNECT host:port`).
- The proxy runs as its own unprivileged user, outside the agent's network
  namespace, started and stopped with the Warden (lifecycle coupling as in
  v1.9.3). The agent cannot connect to it except through the Warden.
- Ports outside `proxy ports` are decided as today (numeric, exact-name and
  wildcard rules), for databases and other non-HTTP services.
- Policy: `proxy on` (SNI mode, section 2) or `proxy inspect` (section 4);
  `require warden 1.26`.

*Tests:* curl, Python `requests`, Node `https`, Go `net/http` and Java
`HttpClient` reach an allowed name with no proxy settings; the same with
`HTTPS_PROXY` set; a non-HTTP port bypasses the proxy and is decided as
before; the agent cannot reach the proxy's address directly.

## 2. SNI mode (default when the proxy is on)

- For TLS, the proxy reads the ClientHello without decrypting anything and
  decides on the SNI name and port, with the same rules as v1.24/v1.25 (exact
  names, wildcards, the shared-domain refusals, first match wins). The
  certificate is over `name:port`, the record carries the SNI, the address
  dialed and bytes each way.
- The proxy resolves the name itself and dials it. The agent needs no DNS at
  all, so wildcards work without the v1.25 stub and without its name channel.
- A ClientHello with no SNI, an SNI that differs from the `CONNECT` name, an
  IP literal in SNI, or Encrypted Client Hello is refused (the proxy cannot
  see the name it would be deciding on). Clients fall back or fail; which do
  is documented.
- For plain HTTP, the decision is on the `Host` header, and a request whose
  `Host` differs from the connected name is refused.
- What SNI mode cannot see: inside TLS, a request can carry a `Host` header for
  another site on the same content network (domain fronting). Most networks
  now refuse that themselves; the threat model says so, and inspecting mode
  (section 4) closes it.

*Tests:* the shared-address escape from v1.24 (another site on the same CDN
address by SNI) is refused; SNI/CONNECT mismatch, missing SNI, IP SNI and ECH
are refused; wildcard decisions with no agent DNS; records and audit.

## 3. Rules on requests

New rule forms, decided per request:

    allow request GET    https://api.example.com/v1/models
    allow request POST   https://api.example.com/v1/chat/*
    deny  request *      https://api.example.com/v1/admin/*

- Method, scheme, host and path, matched by the existing string fragment
  (prefix, suffix, glob), first match wins, certified like any rule.
- In SNI mode only the host is visible, so request rules apply only in
  inspecting mode; a policy with request rules and `proxy on` is refused at
  load with that reason.

*Tests:* both parsers agree; matching on method and path; refusals carry the
rule line; `varek refusals` explains them.

## 4. Inspecting mode (opt-in)

- `proxy inspect` terminates TLS in the proxy with a per-installation CA that
  `varek init` creates (key readable only by the proxy's user, never by the
  agent), adds its certificate to the agent's trust (an `SSL_CERT_FILE` view
  and the system bundle path, served like the v1.24 hosts view), and opens a
  new TLS connection to the real server with full verification.
- Each request is decided on method, host (the `Host` header must equal the
  SNI name) and path. Bodies are not stored; their size and SHA-256 are
  recorded.
- Optional body limits per rule (`max_body=64k`) and a refused-content-type
  list (`deny content application/zip`).
- Certificate pinning in a client breaks inspection; such hosts are listed in
  the policy as `passthrough host <name>` and fall back to SNI mode, which the
  record shows.
- This mode sees the agent's traffic in clear inside the proxy. It is off by
  default, and the deployment guide states what it sees, where the CA key
  lives and how to rotate it.

*Tests:* request rules allow and refuse as written; domain fronting refused;
upstream certificate errors refused, never passed through; the CA key is not
readable as the agent; passthrough hosts; HTTP/1.1 and HTTP/2 (HTTP/3 is
refused, so clients fall back to TCP).

## 5. Using a customer's proxy

Some buyers already run an egress proxy or DLP tool. `proxy upstream
http://proxy.corp:3128` makes the Warden's proxy forward to it after deciding,
so both apply; the record notes the upstream used.

*Tests:* chained to a Squid instance; refusals happen before the upstream sees
the request.

## 6. Cost and real traffic

`varek bench` gains proxied kinds (an allowed HTTPS request in SNI mode and in
inspecting mode), so the added time per request is measured like every other
call. Before v1.26 ships, an agent runs for 24 hours against Fastly-,
Cloudflare- and CloudFront-hosted APIs in both modes, with no refused request
that the policy allows and every request recorded.

## 7. What changes for operators

- `proxy on` closes the shared-address gap and makes wildcards DNS-free.
- `proxy inspect` adds rules on method and path, at the cost of terminating
  TLS inside the host.
- Policies without `proxy` behave exactly as on v1.25.

## Open questions

- Should `proxy on` become the default for new policies once v1.26 has run in
  the field for a release?
- HTTP/3 (QUIC): refuse and let clients fall back (planned), or decide QUIC
  Initial packets' SNI in a later release?
- Size: if inspecting mode delays the release, it ships as v1.26.1 after SNI
  mode, rather than holding SNI mode back.
