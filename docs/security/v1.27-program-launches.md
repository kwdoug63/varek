# v1.27 — decided program launches (plan)

Status: **planned**, nothing below is implemented. The target is **v1.27.0**
if the first buyers' agents mostly call APIs, or **v1.25.0** (moving the two
network releases up one each) if they are coding or tool-using agents. That
question is open. Each section ends with what must be tested before it ships.

## What v1.9.1 to v1.26 leave closed

The agent's own launch, the program the operator names on the command line,
is allowed once (`bootstrap_exec_allow`). Every later `execve`/`execveat` is
refused, whatever `allow exec` says (`deny_only_nonfile_v191` in `warden.c`).

Answering an allowed launch with `SECCOMP_USER_NOTIF_FLAG_CONTINUE` would let
the kernel read the path argument a second time, from the agent's memory, after
the Warden decided. Another thread could swap that path in between, so the
kernel would launch something the Warden never decided. Opens and connects
avoided the race because the Warden carries them out itself and hands over a
descriptor. There is no equivalent for `execve`: the new program has to replace
the agent's own image, so the kernel has to perform the launch.

The result: a coding or tool-using agent cannot run `git`, `python3` or a
compiler, even when the policy names them.

## The design in one paragraph

The kernel enforces the allowed set, and the Warden decides and records each
launch. Before the agent starts, the Warden builds a Landlock ruleset that
handles `LANDLOCK_ACCESS_FS_EXECUTE` and grants it only on the exact files the
policy's `allow exec` rules name (after its denies) that exist at startup. The
agent runs inside that Landlock domain. A launch the Warden allows is then
answered with CONTINUE. If another thread swaps the path, the kernel checks the
file it actually opens against the ruleset, so a swap can only reach another
allowed program. After the launch the Warden reads `/proc/<pid>/exe` and checks
that it is the file it decided on.

## 1. The ruleset

- At startup, after the policy loads, the Warden resolves every `allow exec`
  constant to a canonical path. Each one is an exact path, as exec rules are by
  default. Matcher rules (`prefix`, `glob`, …) are expanded against the files
  that exist, and a rule matching more than 256 files is refused with that
  reason. A path that a deny rule earlier in the policy decides is left out.
- Each file is opened `O_PATH` and added as a `LANDLOCK_RULE_PATH_BENEATH`
  rule, granting `LANDLOCK_ACCESS_FS_EXECUTE` on that file only. A directory is
  never added.
- The dynamic loader of each dynamically linked program (its `PT_INTERP`,
  usually `/lib64/ld-linux-x86-64.so.2`) is added too: the kernel opens it for
  execution as part of the launch. The policy check reports these additions.
  Shared libraries are mapped with `mmap(PROT_EXEC)`, which Landlock does not
  govern; they stay governed by the file-open rules as today.
- For a script, the kernel opens both the script and the interpreter named on
  its `#!` line for execution. Both must be in the allowed set, or the launch
  fails.
- The program the operator names on the command line, and its loader, are
  added, since its launch is authorized by being named.
- The ruleset is applied in the agent's process, after `PR_SET_NO_NEW_PRIVS`
  (already set for seccomp) and before the bootstrap `execve`. Every process
  the agent starts inherits it.
- Each file's device, inode and SHA-256, and the Landlock ABI version, go in
  `run_start`. So do the policy's `allow exec` rules and the files each one
  became.

*Tests:* the ruleset contents for exact, prefix and glob rules; a deny that
removes a file; the loader and interpreter additions; a rule matching too many
files is refused; `run_start` lists the files and hashes.

## 2. Deciding a launch

- An `execve` or `execveat` from the agent (not the bootstrap) is decided as
  today: on the path, by the SMT decision procedure, with a certificate the
  checker must accept. A relative path or an `execveat` dirfd is resolved like
  an open.
- **ALLOW:** the canonical path must be one of the ruleset's files, the same
  device and inode as at startup. The Warden then answers CONTINUE and records
  the launch with the file's identity and startup hash. A path the policy
  allows but that was not in the ruleset (created after startup) is refused:
  `exec_not_in_ruleset`.
- **DENY / UNKNOWN:** refused, as today.
- **After a CONTINUE:** the Warden reads `/proc/<pid>/exe` once the launch has
  happened, by `pidfd` and the next notification from that process, or a short
  poll. It compares the device and inode with the decided file. On a mismatch
  (which needs a kernel or Landlock bug, given the ruleset) it kills the
  process and records `exec_identity_mismatch`.
- The plan gate decides `process_exec` steps as before, now SATISFIED when the
  policy allows the path and it is in the ruleset.

*Tests:* allowed and denied launches; the certificate; the identity record; a
file created after startup is refused; the plan gate.

## 3. What stays true

- **Launched programs are fully mediated.** The seccomp filter, the user-notify
  listener and the Landlock domain are all inherited by the new program, and
  `no_new_privs` neutralizes setuid and file capabilities.
- **No write-then-execute.** A file the agent creates during the run is never
  in the ruleset, so the kernel refuses to execute it, whatever the policy's
  path rules allow it to write.
- **Fail closed.** Without Landlock (a kernel before 5.13, Landlock not in the
  active LSM list, or an ABI too old), launches stay refused exactly as in
  v1.26. The Warden says so at startup, `varek doctor` reports Landlock's
  availability and ABI, and a policy with `allow exec` rules gets a load-time
  note on such a host.
- **Invariant.** No extension may move a genuinely unsafe action to SATISFIED.
  A launch the policy does not allow is still refused, now by the kernel as
  well as by the Warden.

## 4. Stated limits

- **Arguments are not decided.** They are in the agent's memory and cannot be
  read race-free, the same problem as the path. `allow exec /usr/bin/git`
  allows `git` with any arguments. Rules on arguments would need the program
  launched by the Warden itself, with arguments copied once; that is left for a
  later release.
- **Interpreters and shells are broad.** `allow exec /usr/bin/python3` lets the
  agent run any Python code it can read. The launched program is still
  contained by the file and network rules, but the policy check warns when a
  shell or general-purpose interpreter is allowed.
- **A file changed in place.** If an allowed file is modified in place after
  startup (same inode), the startup hash no longer describes it. The record
  says so: the hash is the one taken at startup. The agent itself cannot do
  this unless the policy lets it write the file, and the policy check warns
  when a path is both executable and writable.

## 5. Needs

- Linux 5.13 or later with Landlock enabled. Amazon Linux 2023 ships 6.1
  kernels. **Before this is promised on the AMI, confirm on a real instance**
  that `landlock` is in `/sys/kernel/security/lsm`. Add it to `harden.sh` if it
  is not.
- `varek doctor` and `tools/varek_preflight.sh` report the Landlock ABI.

## 6. Ship gates

- A race harness: one thread swaps the path during an allowed `execve`, with
  zero launches of a non-allowed program in 20,000 attempts, and allowed
  launches that succeed (against v1.26 those launches all fail:
  `deny_only_nonfile_v191`).
- Write-then-execute refused: an agent writes a binary into an allowed
  directory, and launching it fails.
- Scripts and their interpreters; a script whose interpreter is not allowed
  fails.
- Child processes are still mediated: a launched program's opens and connects
  are decided and recorded.
- The identity check, and a forced mismatch (test build) killed and recorded.
- Without Landlock, launches are refused and the reason is reported.
- `make test-v1270`, and a regression suite that fails against v1.26.

## Open questions

- Should the ruleset be rebuilt when an allowed file is replaced (package
  upgrades during a long run)? The plan is no: such a file is refused until the
  next run.
- `execveat(AT_EMPTY_PATH)` on a descriptor the agent holds: decide on the
  descriptor's file. This needs the same identity check, and is simpler than a
  path.
