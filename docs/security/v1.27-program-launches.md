# v1.27 — decided program launches (plan)

Status: **in progress**, target **v1.27.0** (the alternative of shipping it as
v1.25.0 ahead of the network releases is moot: v1.24.0 to v1.26.1 have
shipped). Decided 2026-10-10: the recommendation for each decision below.
Built: steps 1 and 2, the grammar and the opt-in, and the launch set (see
"As built" under each). Each
section ends with what must be tested before it ships.

## What v1.9.1 to v1.26 leave closed

The agent's own launch, the program the operator names on the command line,
is allowed once (`bootstrap_exec_allow`). Every later `execve`/`execveat` is
refused, whatever `allow exec` says (`deny_only_nonfile_v191` in `warden.c`).

Answering an allowed launch with `SECCOMP_USER_NOTIF_FLAG_CONTINUE` would let
the kernel read the path argument a second time, from the agent's memory, after
the Warden decided. Another thread could swap that path in between, so the
kernel would launch something the Warden never decided. Opens and connects
avoided the race because the Warden carries them out itself and hands over a
descriptor. There is no equivalent for `execve`: the new program has to replace
the agent's own image, so the kernel has to perform the launch.

The result: a coding or tool-using agent cannot run `git`, `python3` or a
compiler, even when the policy names them. The shipped policy packs
(healthcare, finance, cybersecurity, national defense) already say
`allow exec /usr/bin/python3`; under v1.26 those rules never take effect.

## The design in one paragraph

The kernel enforces the allowed set, and the Warden decides and records each
launch. Before the agent starts, the Warden builds a Landlock ruleset that
handles `LANDLOCK_ACCESS_FS_EXECUTE` and grants it only on the exact files the
policy's `allow exec` rules name (after its denies) that exist at startup. The
agent runs inside that Landlock domain. A launch the Warden allows is then
answered with CONTINUE. If another thread swaps the path, the kernel checks the
file it actually opens against the ruleset, so a swap can only reach a file in
the ruleset. Before the Warden answers anything more from the launched
process, it reads `/proc/<pid>/exe` and checks that it is the file it decided
on; a process that is not is killed.

## What was measured before deciding

On this container's kernel (6.18, Landlock ABI 7), in a Landlock domain whose
ruleset handles `LANDLOCK_ACCESS_FS_EXECUTE` and grants it on `/usr/bin/true`
and the dynamic loader only (`tests/` will carry the probe as a check):

| Launch | Result |
|---|---|
| `/usr/bin/true` (in the ruleset) | runs |
| `/usr/bin/false` (not in the ruleset) | refused, `EACCES` |
| a file written during the run | refused, `EACCES` |
| an `O_TMPFILE` file, through `/proc/self/fd/N` | refused |
| an unlinked file, through `/proc/self/fd/N` | refused |
| a file in `/dev/shm` | refused |
| a memfd made with `MFD_NOEXEC_SEAL` | refused |
| **a plain memfd** (`execveat(AT_EMPTY_PATH)` or `/proc/self/fd/N`) | **runs** |
| **the loader, given a written file** (`ld.so ./written`) | **runs** |

Two findings change the design:

1. **Landlock does not govern a memfd.** A swap to `/proc/self/fd/N` naming a
   memfd would launch code that was never a file. This is already closed:
   `memfd_create` is in the baseline filter's hard-deny set
   (`warden_baseline_filter.c`), so the agent cannot make one, and the views
   the Warden serves are memfds of mode 0444, which the kernel will not
   execute. v1.27 makes that load-bearing: a check fails the build if
   `memfd_create` leaves the hard-deny set, and `make test-v1270` launches a
   memfd through each route to confirm the refusal.
2. **The loader runs any file it can read.** It has to be in the ruleset (the
   kernel opens it to launch every dynamically linked program), so a swap to
   its path passes Landlock, and the loader then maps whatever file its
   arguments name, including one written during the run. A direct launch of
   the loader is refused by the Warden (the policy does not allow it); the
   swap is the only route. The identity check closes it: the loader must open
   the file it is to run, an `openat` the Warden mediates, and the Warden
   checks `/proc/<pid>/exe` before it answers any call from a launched
   process. A process whose image is not the file decided is killed before
   the file is opened.

## 1. Opt-in: `require warden 1.27`

Launches after the first are decided only in a policy with
`require warden 1.27` (or later). Under any earlier `require` (or none), a
policy behaves exactly as on v1.26: every later launch is refused,
`deny_only_nonfile_v191`. The packs' `allow exec /usr/bin/python3` lines keep
their v1.26 meaning until a pack says `require warden 1.27`. The grammar of
`allow exec` and `deny exec` is unchanged: an exact path by default, and the
matchers (`prefix`, `glob`, ...) the parsers already accept.

*Tests:* a v1.26 policy with `allow exec` refuses later launches as before;
the same policy with `require warden 1.27` allows them.

## 2. The ruleset

- At startup, after the policy loads, the Warden resolves every `allow exec`
  constant to a canonical path. Each one is an exact path, as exec rules are by
  default. Matcher rules (`prefix`, `glob`, ...) are expanded against the files
  that exist, and a rule matching more than 256 files is refused with that
  reason. A path that a deny rule earlier in the policy decides is left out.
  Only regular files with an execute bit are added.
- Each file is opened `O_PATH` and added as a `LANDLOCK_RULE_PATH_BENEATH`
  rule, granting `LANDLOCK_ACCESS_FS_EXECUTE` on that file only. A directory is
  never added.
- The dynamic loader of each dynamically linked program (its `PT_INTERP`,
  usually `/lib64/ld-linux-x86-64.so.2`, read with a bounded ELF parser) is
  added too: the kernel opens it for execution as part of the launch. The
  policy check reports these additions. Shared libraries are mapped with
  `mmap(PROT_EXEC)`, which Landlock does not govern; they stay governed by the
  file-open rules as today.
- For a script, the kernel opens both the script and the interpreter named on
  its `#!` line for execution. Both must be allowed by the policy; the
  interpreter is not added for it. `#!/usr/bin/env python3` needs `env` and
  `python3` both allowed, and `env`'s own launch of `python3` is decided like
  any other.
- The program the operator names on the command line, its loader, and (for a
  script) its interpreter and that interpreter's loader, are added, since its
  launch is authorized by being named.
- The ruleset is applied in the agent's process, after `PR_SET_NO_NEW_PRIVS`
  (already set for seccomp) and before the bootstrap `execve`. Every process
  the agent starts inherits it. The Warden's own helpers (the resolver,
  `warden-proxy`) run outside it.
- Each file's device, inode and SHA-256, why it is there (`rule` with the line,
  `loader`, `bootstrap`), and the Landlock ABI version, go in `run_start`.

*Tests:* the ruleset contents for exact, prefix and glob rules; a deny that
removes a file; the loader and interpreter additions; a rule matching too many
files is refused; `run_start` lists the files and hashes.

## 3. Deciding a launch

- An `execve` or `execveat` from the agent (not the bootstrap) is decided as
  today: on the path, by the SMT decision procedure, with a certificate the
  checker must accept. A relative path or an `execveat` dirfd is resolved like
  an open. `execveat(fd, "", AT_EMPTY_PATH)` is decided on the descriptor's
  file (the descriptor is in a register; its table entry can be swapped like a
  path, and the identity check covers it the same way).
- **ALLOW:** the canonical path must be one of the ruleset's files, the same
  device and inode as at startup. The Warden then answers CONTINUE and records
  the launch with the file's identity and startup hash. A path the policy
  allows but that is not in the ruleset (created or replaced after startup) is
  refused: `exec_not_in_ruleset`.
- **DENY / UNKNOWN:** refused, as today.
- **The identity check.** After a CONTINUE the Warden holds the launch
  pending, keyed by the thread group (a launch from a thread that is not the
  leader takes over the group's pid). Before answering any notification from
  that group it compares `/proc/<pid>/exe` with the decided file:
  - the decided file: the launch happened; recorded, pending cleared;
  - the image from before the launch: not launched yet, or the launch failed
    (the kernel returned an error); answered, still pending;
  - anything else: the process is killed (`SIGKILL` by pidfd) and
    `exec_identity_mismatch` recorded, before the call is answered.
  A launched program that makes no mediated call before it exits is checked
  by a short poll, for the record only: a swap could reach only a file in the
  ruleset, and the loader (the one ruleset file the policy may not allow)
  must open its target, a mediated call.
- The plan gate decides `process_exec` steps as before, now SATISFIED when the
  policy allows the path and it is in the ruleset.
- **Arguments are not recorded.** They are in the agent's memory, and another
  thread may change them after the Warden reads them; a record of them would
  claim what it cannot know.

*Tests:* allowed and denied launches; the certificate; the identity record; a
file created after startup is refused; `execveat` by descriptor; a launch from
a thread that is not the leader; a failed launch (no record of a launch, no
kill); the plan gate.

## 4. What stays true

- **Launched programs are fully mediated.** The seccomp filter, the user-notify
  listener and the Landlock domain are all inherited by the new program, and
  `no_new_privs` neutralizes setuid and file capabilities.
- **No write-then-execute.** A file the agent creates during the run is never
  in the ruleset, so the kernel refuses to execute it, whatever the policy's
  path rules allow it to write; the loader cannot be made to run one (the
  identity check); and the agent cannot make a memfd.
- **Fail closed.** Without Landlock (a kernel before 5.13, Landlock not in the
  active LSM list, or an ABI too old), launches stay refused exactly as in
  v1.26, with `exec_no_landlock`. The Warden says so at startup, `run_start`
  records `landlock: null`, `varek doctor` reports Landlock's availability and
  ABI, and a policy with `require warden 1.27` and `allow exec` rules gets a
  load-time note on such a host. A failure to build or apply the ruleset
  refuses the run.
- **Invariant.** No extension may move a genuinely unsafe action to SATISFIED.
  A launch the policy does not allow is still refused, now by the kernel as
  well as by the Warden.

## 5. Stated limits

- **Arguments are not decided.** They are in the agent's memory and cannot be
  read race-free, the same problem as the path. `allow exec /usr/bin/git`
  allows `git` with any arguments. Rules on arguments would need the program
  launched by the Warden itself, with arguments copied once; that is left for a
  later release.
- **Interpreters and shells are broad.** `allow exec /usr/bin/python3` lets the
  agent run any Python code it can read. The launched program is still
  contained by the file and network rules, but the policy check warns when a
  shell or general-purpose interpreter is allowed.
- **A file changed in place.** If an allowed file is modified in place after
  startup (same inode), the startup hash no longer describes it. The record
  says so: the hash is the one taken at startup. The agent itself cannot do
  this unless the policy lets it write the file, and the policy check warns
  when a path is both executable and writable.
- **A swap between allowed programs is killed, not prevented.** A swap can
  only reach a file in the ruleset; the identity check then kills it. The
  launched program may run until its first mediated call.

## 6. Needs

- Linux 5.13 or later with Landlock enabled. Amazon Linux 2023 ships 6.1
  kernels. **Before this is promised on the AMI, confirm on a real instance**
  that `landlock` is in `/sys/kernel/security/lsm`. Add it to `harden.sh` if it
  is not. The droplet the soaks run on is checked the same way.
- `varek doctor` and `tools/varek_preflight.sh` report the Landlock ABI.

## 7. Ship gates

- A race harness: one thread swaps the path during an allowed `execve`, among
  allowed programs, the loader and a written file, with zero launches of a
  program not decided in 20,000 attempts that survive past their first
  mediated call, zero runs of the written file, and allowed launches that
  succeed (against v1.26 those launches all fail: `deny_only_nonfile_v191`).
- Write-then-execute refused: an agent writes a binary into an allowed
  directory, and launching it fails, directly, through `/proc/self/fd`,
  through the loader, and as a memfd.
- Scripts and their interpreters; a script whose interpreter is not allowed
  fails.
- Child processes are still mediated: a launched program's opens and connects
  are decided and recorded.
- The identity check, and a forced mismatch (test build) killed and recorded.
- Without Landlock, launches are refused and the reason is reported.
- `make test-v1270`, and a regression suite that fails against v1.26.1.
- A 24-hour soak on the droplet with an agent that launches `git`, `python3`
  and a compiler, with probes that must be refused.

## Decisions before building

1. **Version.** Recommended: v1.27.0, as above.
2. **Opt-in.** Recommended: `require warden 1.27` turns launches on (section
   1). Alternative: every policy's `allow exec` takes effect, which would
   change what the shipped packs allow without anyone choosing it.
3. **The loader.** Recommended: in the ruleset, guarded by the identity check
   before any call is answered (section 3). Alternative: refuse dynamically
   linked programs, which would refuse nearly everything.
4. **Rebuilding the ruleset when an allowed file is replaced** (a package
   upgrade during a long run). Recommended: no; such a file is refused
   (`exec_not_in_ruleset`) until the next run.
5. **`execveat(AT_EMPTY_PATH)` on a descriptor.** Recommended: decided on the
   descriptor's file, with the same identity check (section 3).
6. **Arguments.** Recommended: neither decided nor recorded in v1.27.0
   (sections 3 and 5).

## Implementation plan

1. **Grammar and opt-in** (done). `require warden 1.27` in both C parsers
   and the cross-check oracle; launches decided only under it; `vdp_check
   lint` notes for interpreters and shells, and for a path both executable
   and writable. `run_start` reports the Warden as 1.27.0 when the release is
   cut.
   As built:
   - The decision procedure and the certificate checker implement grammar
     1.27 (`VDP_WARDEN_MINOR`, `VDPC_GRAMMAR_MINOR`) and refuse a later
     `require`. Each sets the policy's `launches` flag when the highest
     `require warden` is 1.27 or later; no decision depends on it.
     `vdp_check P launches` and `vdp_cert_check P launches` print it, and
     the cross-check compares both with its own parse on every policy (its
     fuzzer now writes `require warden 1.27` among the valid directives and
     1.28 among the refused).
   - `vdp_exec_advisory` (in `smt_decide.c`, for lint and the Warden):
     an allow exec rule whose basename is a shell or general-purpose
     interpreter (sh, bash, python3, python3.12, node, perl, ruby, java,
     awk, ...), and an exact allow exec rule whose path the policy also lets
     the agent open for writing (`O_WRONLY` or `O_RDWR`, with or without
     `O_TRUNC`/`O_CREAT`). Matcher rules get the same notes per file when
     the Warden expands them (step 2). Without the opt-in, lint and the
     Warden note once that exec rules decide only the agent's own launch.
     Notes never fail lint.
   - `varek policy show` says whether launches are decided, refused for
     want of the opt-in, or decided with no exec rule allowing one.
   - The Warden prints the notes at load and reports the grammar it
     implements from `smt_decide.h` (it said "v1.26" as a copy before).
     Launches after the first stay refused (`deny_only_nonfile_v191`) until
     steps 2 to 4; the shipped packs keep launches off.
   - The v1.24, v1.25 and v1.26 suites' "a later `require` is refused"
     checks now use 1.28.
   - `make test-v1270` section 1 (34 checks with the loader note, in CI).
2. **The ruleset** (done). Expansion of `allow exec` rules (256-file cap,
   denies first), the bounded ELF `PT_INTERP` reader, the bootstrap's
   additions, hashing; Landlock applied in the agent before the bootstrap
   launch; `run_start`'s `exec_ruleset` and `landlock`; `exec_no_landlock`
   when it is missing; a test hook to act as if it were missing.
   As built (`warden_exec.inc.c`):
   - Only with `require warden 1.27`; otherwise nothing is built and the
     run is as in v1.26.
   - **Names and files.** The policy decides a launch on the path as the
     agent names it, as before (so `allow exec /usr/bin/python3` means the
     name packs use, though it is a symlink to `python3.11`). The set is of
     files: each admitted name is opened (following symlinks), and held by
     device and inode with its canonical path and SHA-256, read from the
     one descriptor that also names the file. The Landlock rule is added on
     a descriptor of the same file, checked to be the same device and inode.
   - **Expansion.** An exact rule's constant is a candidate. A prefix rule
     walks the directory its constant ends in; a glob rule, the directory
     before its first wildcard; both recurse into real directories (not
     symlinks to them) up to 16 levels and 200,000 entries. Every candidate
     is decided by the decision procedure as a launch of that name, so a
     deny rule earlier in the policy keeps a file out and one after an
     allow does not. Only regular files with an execute bit are added; a
     rule that admits more than 256 names is refused at startup. A suffix or
     contains rule, or a glob that starts with a wildcard, cannot be
     expanded to a bounded set and is refused at startup. An exact rule for
     a file that is not there gets a note and adds nothing.
   - **The loader.** Each ELF file's `PT_INTERP` (64- and 32-bit,
     little-endian, at most 512 program headers) is added as `loader`; a
     malformed header refuses the start. The loader named in a rule gets
     the interpreter note: it runs any ELF file it can read.
   - **The bootstrap.** The program the operator names is added as
     `bootstrap`, and a script's `#!` interpreter as `interpreter` (with its
     loader).
   - **Notes at startup** for files a matcher admits: an interpreter or
     shell; a file the policy also lets the agent open for writing; a script
     whose interpreter is not in the set (launching it will fail).
   - **Landlock.** The ABI is probed at startup; the ruleset handles
     `LANDLOCK_ACCESS_FS_EXECUTE` and grants it on each file. The agent's
     process sets `no_new_privs` and enters the domain after dropping its
     privileges and before its seccomp filter (which does not admit the
     call) and its own launch. A failure to build or enter it stops the
     run. Without Landlock (or with `VAREK_WARDEN_TEST_NO_LANDLOCK=1`), the
     set is still built and recorded, no domain is applied, and the Warden
     says later launches will be refused.
   - `run_start` gains `landlock` (`{"abi":N}` or `null`) and
     `exec_ruleset`: each file's name, path, device, inode, SHA-256, why
     (`rule` with its `policy_line`, `loader`, `bootstrap`, `interpreter`).
     `--check-startup` lists the set.
   - Launches after the first stay refused (`deny_only_nonfile_v191`) until
     step 3; the kernel's refusal of a file outside the set is tested there,
     once a launch can reach the kernel.
   - `make test-v1270` section 2 (35 checks): expansion by exact, prefix and
     glob rules, symlinks, denies before and after, files without an
     execute bit and directories, loaders, the 256-file cap, unexpandable
     rules, a malformed ELF header, missing files, the notes, and real runs:
     `run_start`'s Landlock ABI and each file's identity and hash checked
     against the file, the bootstrap and a script with its interpreter
     running in the domain, a run without the opt-in, one without Landlock,
     and the audit accepting each.
3. **Deciding launches.** CONTINUE for an allowed launch in the ruleset;
   `exec_not_in_ruleset`; `execveat` by descriptor; the records.
4. **The identity check.** Pending launches by thread group, checked before
   any answer; kill and `exec_identity_mismatch`; the poll; a test build that
   forces a mismatch.
5. **Audit and tools.** `varek_audit.py` checks each launch against the
   policy and `run_start`'s ruleset, each identity record, and that no
   launch follows a mismatch; `varek refusals` explains the new refusals; the
   CycloneDX export lists the ruleset and the launched programs;
   `varek doctor` and the preflight report Landlock; `varek policy show`
   lists the ruleset a policy would build on this host.
6. **Tests.** `make test-v1270`: the measured table above as checks, the
   race harness, scripts, children mediated, the identity check, no
   Landlock, forged streams the audit must refuse; the regression count
   against v1.26.1; the build check on the hard-deny set.
7. **Bench, latency and soak.** `varek bench` gains a launch kind (fork and
   launch of an allowed program, natively and under the Warden); the 24-hour
   soak on the droplet.
8. **Review by AI review agents**, fixes, README, threat model, spec paper,
   release notes.
