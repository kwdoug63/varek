# v1.39.0 — Security operations (plan)

Status: **in progress**, target **v1.39.0** (planned as v1.36.0, then
v1.37.0, then v1.38.0; `docs/roadmap/v1.36-v1.37.md`). Section 1, the
OpenTelemetry export, is built (November 14, 2026); sections 2 to 4 wait on
an instance of each tool. Developed on branches from main; each section
ends with what must be tested before it ships.

v1.31.0's OCSF export makes a run's evidence available as events. This
release delivers it where security teams already look: an OpenTelemetry
collector (and through it Datadog, Grafana, Honeycomb, Elastic and the
rest), Splunk, Microsoft Sentinel, CrowdStrike Falcon and Wiz.

**Ship gate** (`docs/roadmap/v1.32-v1.35.md`): a refusal appears in each
tool within a minute, with the policy line that decided it, each tested
against a real instance: an OpenTelemetry collector, a Splunk instance, a
Sentinel workspace, a Falcon tenant and a Wiz tenant.

## The design in one paragraph

Every integration starts from the OCSF events (`tools/varek_ocsf.py`), so
each sees the same evidence, audited first: the record's decision, its
three-state verdict, the policy line and its text, the run, the agent, and
the link back to the stream. An integration translates and delivers; it
decides nothing and drops nothing the OCSF event carries (the whole event
travels with each record where the tool allows it). `varek export --format
FORMAT` names each: `ocsf` (a file, v1.31), `otlp` (a collector, section
1), and later the vendors'.

## 1. OpenTelemetry export (built)

`tools/varek_otel.py` reads OCSF events, one per line, from a file or
standard input as they arrive, and sends each as an OTLP log record to a
collector over OTLP/HTTP with the JSON encoding. `varek export --format otlp
[LOG]` sends a finished run; `varek export --format otlp --follow STREAM`
sends a live one as it goes (the OCSF export's `--follow`, piped in).

A record:

| OTLP | From the OCSF event |
|---|---|
| `timeUnixNano` | `time` (the decision's); `observedTimeUnixNano` is when it was read |
| `severityNumber` / `severityText` | `severity_id`: Informational INFO (9), Low INFO2 (10), Medium WARN (13: a refusal), High ERROR (17: a failed audit), Critical and Fatal FATAL (21); the text is the short name (`INFO`, `WARN`, ...), which backends read a level from, and OCSF's word is in `ocsf.severity` |
| `body` | `Blocked: File System Activity: Open /etc/shadow (policy line 91: deny  path /etc/shadow)`: the disposition, the class and activity, the object, and the policy line with its text (or the rule, for a default deny) |
| attributes | `event.name` (`varek.decision`, `varek.run_start`, `varek.audit`, ...); `ocsf.class_uid`, `ocsf.class_name`, `ocsf.activity_name`, `ocsf.type_uid`, `ocsf.action`, `ocsf.disposition`, `ocsf.status`, `ocsf.severity`, `ocsf.metadata.uid`; `varek.verdict` (SATISFIED, UNSATISFIED, UNKNOWN), `varek.decision` (ALLOW, DENY), `varek.rule`, `varek.policy.line`, `varek.policy.text`, `varek.policy.name`, `varek.policy.sha256`, `varek.report_id`, `varek.seq`, `varek.mode` (dry run), `varek.agent`, `varek.agent.type`, `varek.target`; `process.pid`, `user.id`; `varek.audit.passed`; and `ocsf.event`, the whole OCSF event as the line read |
| resource | `service.name` `varek-warden`, `service.version` (the Warden's), `host.name`, `varek.run` |
| scope | `varek.ocsf`, version 1.9.0 |

Decisions (made November 14, 2026, while building):

- **D1. Logs, not spans or metrics.** A decision is an event at a moment,
  with no duration of its own; a span would invent one. Counts (refusals a
  minute) are the backend's to make from the logs. A trace context could
  be added later if an agent framework passes one down.
- **D2. OTLP/HTTP with JSON, no SDK.** The standard library only: no
  protobuf or gRPC dependency in the runtime, and every collector and most
  vendors' endpoints take OTLP/HTTP JSON. The endpoint and headers follow
  OpenTelemetry's own variables (`OTEL_EXPORTER_OTLP_LOGS_ENDPOINT`,
  `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_HEADERS`).
- **D3. From the OCSF events, not the stream.** The OCSF export audits the
  stream before it writes (in `--follow`, record by record, with the whole
  stream's audit as the last event), so nothing reaches a collector that
  the audit has not seen; and one mapping, OCSF's, is kept, not two.
- **D4. Keys never on a command line.** `--header NAME=ENVVAR` (and
  `varek export --otlp-header`) take a header's value from the environment,
  never from an argument `ps` and a shell's history show.
- **D5. Refusals and failures end the export.** A batch a collector
  refuses for a reason a retry can mend (429, 502, 503, 504, no answer) is
  sent again, up to `--retries` times, backing off (or as `Retry-After`
  says); any other refusal, or a partial success that rejects records,
  ends it with exit 1, so a lost event is never silent.

Tested (November 14, 2026):

- `tests/test_varek_otel.py` (in `make test-cli`): the mapping (a refusal
  a WARN naming its policy line; a default deny naming its rule and no
  line; severities; a failed audit an ERROR); one resource entry for each
  run; the endpoint and headers from the environment; a stand-in collector:
  batches, the header from the environment and never in the output, a 503
  and a 429 sent again, a 400 and a partial rejection ending the export
  (exit 1), input that is not OCSF refused (exit 2).
- Against the OpenTelemetry Collector (`otel/opentelemetry-collector-contrib`
  0.120.0, an OTLP/HTTP receiver and a file exporter), on this host: a
  run's 219 events, the refusals among them (`/etc/shadow`, policy line
  91; a connect refused by the default deny), all accepted and written by
  the collector as sent; and `varek export --format otlp --follow` on a
  live run: each refusal read 0.02 to 0.08 s after it was decided and at
  the collector within the exporter's one-second batch interval (the ship
  gate's minute).

- Through a vendor's OTLP endpoint: Grafana Cloud's (its free tier; the
  logs in Loki), November 14, 2026. `varek export --format otlp --follow`
  on a live run, run `9df79a46d8231cde112f1135a40dbe64`: 228 records
  accepted, and the six refusals (three opens of `/etc/shadow`, policy
  line 91; three connects to 1.1.1.1:443, the default deny) shown in
  Grafana with their fields, each sent within about a second of its
  decision. The key was the session's (Basic auth added on the way), not
  `--otlp-header`, which the stand-in collector tests.

  Found there, and fixed: `severityText` carried OCSF's word, so Loki,
  which reads the level from it, showed the refusals at no level ("Medium"
  is none it knows); it now carries the short name. And a record named
  its three-state verdict but not the final decision, so `varek.decision`
  was added. Sent again after the fix: run
  `2c92e010517a595722e0695be9300987`, 228 records accepted; in Loki,
  `varek_decision="DENY"` on that run returned the six refusals, each at
  level warn.

## 2. Splunk (planned)

A Splunk app: the OCSF events sent to the HTTP Event Collector (sourcetype
`varek:ocsf`), field extractions and a dashboard (refusals by policy line,
by agent, by run; dry runs; failed audits). Needs a Splunk Enterprise
instance under a developer license.

## 3. Microsoft Sentinel (planned)

A data connector: the OCSF events sent through the Azure Monitor Logs
Ingestion API (a data collection rule and a custom table), with analytics
rules and a workbook. Needs an Azure subscription and a Sentinel workspace.

## 4. CrowdStrike Falcon Foundry and Wiz (planned)

The integrations already in progress, released as supported. Each needs a
partner tenant (CrowdStrike's technology partner program; the Wiz
Integration Network).
