## The design in one paragraph

Every integration starts from the OCSF events (`tools/varek_ocsf.py`), so
each sees the same evidence, audited first: the record's decision, its
three-state verdict, the policy line and its text, the run, the agent, and
the link back to the stream. An integration translates and delivers; it
decides nothing and drops nothing the OCSF event carries (the whole event
travels with each record where the tool allows it). `varek export --format
FORMAT` names each: `ocsf` (a file, v1.31), `otlp` (a collector, section
1), `splunk` (section 2), and later the others.

## 1. OpenTelemetry export (built; v1.39.0)

`tools/varek_otel.py` reads OCSF events, one per line, from a file or
standard input as they arrive, and sends each as an OTLP log record to a
collector over OTLP/HTTP with the JSON encoding. `varek export --format otlp
[LOG]` sends a finished run; `varek export --format otlp --follow STREAM`
sends a live one as it goes (the OCSF export's `--follow`, piped in).

A record:

| OTLP | From the OCSF event |
|---|---|
| `timeUnixNano` | `time` (the decision's); `observedTimeUnixNano` is when it was read |
| `severityNumber` / `severityText` | `severity_id`: Informational INFO (9), Low INFO2 (10), Medium WARN (13: a refusal), High ERROR (17: a failed audit), Critical and Fatal FATAL (21); the text is the short name (`INFO`, `WARN`, ...), which backends read a level from, and OCSF's word is in `ocsf.severity` |
| `body` | `Blocked: File System Activity: Open /etc/shadow (policy line 91: deny  path /etc/shadow)`: the disposition, the class and activity, the object, and the policy line with its text (or the rule, for a default deny) |
| attributes | `event.name` (`varek.decision`, `varek.run_start`, `varek.audit`, ...); `ocsf.class_uid`, `ocsf.class_name`, `ocsf.activity_name`, `ocsf.type_uid`, `ocsf.action`, `ocsf.disposition`, `ocsf.status`, `ocsf.severity`, `ocsf.metadata.uid`; `varek.verdict` (SATISFIED, UNSATISFIED, UNKNOWN), `varek.decision` (ALLOW, DENY), `varek.rule`, `varek.policy.line`, `varek.policy.text`, `varek.policy.name`, `varek.policy.sha256`, `varek.report_id`, `varek.seq`, `varek.mode` (dry run), `varek.agent`, `varek.agent.type`, `varek.target`; `process.pid`, `user.id`; `varek.audit.passed`; and `ocsf.event`, the whole OCSF event as the line read |
| resource | `service.name` `varek-warden`, `service.version` (the Warden's), `host.name`, `varek.run` |
| scope | `varek.ocsf`, version 1.9.0 |

Decisions (made November 14, 2026, while building):

- **D1. Logs, not spans or metrics.** A decision is an event at a moment,
  with no duration of its own; a span would invent one. Counts (refusals a
  minute) are the backend's to make from the logs. A trace context could
  be added later if an agent framework passes one down.
- **D2. OTLP/HTTP with JSON, no SDK.** The standard library only: no
  protobuf or gRPC dependency in the runtime, and every collector and most
  vendors' endpoints take OTLP/HTTP JSON. The endpoint and headers follow
  OpenTelemetry's own variables (`OTEL_EXPORTER_OTLP_LOGS_ENDPOINT`,
  `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_HEADERS`).
- **D3. From the OCSF events, not the stream.** The OCSF export audits the
  stream before it writes (in `--follow`, record by record, with the whole
  stream's audit as the last event), so nothing reaches a collector that
  the audit has not seen; and one mapping, OCSF's, is kept, not two.
- **D4. Keys never on a command line.** `--header NAME=ENVVAR` (and
  `varek export --otlp-header`) take a header's value from the environment,
  never from an argument `ps` and a shell's history show.
- **D5. Refusals and failures end the export.** A batch a collector
  refuses for a reason a retry can mend (429, 502, 503, 504, no answer) is
  sent again, up to `--retries` times, backing off (or as `Retry-After`
  says); any other refusal, or a partial success that rejects records,
  ends it with exit 1, so a lost event is never silent.

## 2. Splunk (built; v1.39.0)

`tools/varek_splunk.py` reads OCSF events as `varek_otel.py` does and sends
each to a Splunk HTTP Event Collector (HEC), batched, over HTTPS.
`varek export --format splunk [LOG]` sends a finished run; `--follow
STREAM` a live one. The Splunk app, `integrations/splunk/varek/`, names
the events' fields and gives an overview; `integrations/splunk/README.md`
says how to install it, make the index and token, and export.

An HEC event:

| HEC | From the OCSF event |
|---|---|
| `time` | `time` (the decision's), in seconds to the millisecond |
| `host` | `device.hostname` |
| `source`, `sourcetype` | `varek-warden`, `varek:ocsf` |
| `index` | `--splunk-index`, else the token's |
| `event` | the OCSF event, whole |
| `fields` (indexed) | `varek_run`, `varek_decision` (ALLOW, DENY), `ocsf_class_uid` |

The app:

- **`props.conf`**, the sourcetype: JSON at search time (`KV_MODE =
  json`); short names for the VAREK fields (`varek_verdict`, `varek_rule`,
  `varek_policy_line`, `varek_policy_text`, `varek_report_id`,
  `varek_agent`, `varek_mode`, ...); `varek_target`, what the decision was
  about; `varek_decided_by`, the policy line and its text, or the rule for
  a default deny.
- **`macros.conf`**: `varek_events` (the index and sourcetype) and
  `varek_refused` (a DENY not let through by a dry run).
- **The dashboard, *VAREK: the Warden's decisions*** (Simple XML), for a
  time range, a run and a host:
  - counts: refused, decisions, runs, let through in dry runs, failed
    audits;
  - refusals over time, by what decided them;
  - refusals by policy line, and by agent;
  - the runs, each with its refusals, decisions, dry run, audit and policy;
  - the latest refusals;
  - what dry runs let through;
  - the failed audits.

Decisions (made November 15, 2026, while building):

- **S1. The HEC's event endpoint, the OCSF event as the body.** The events
  are pushed from the host, as to a collector (section 1), not pulled by a
  Splunk add-on, so nothing on the Splunk side needs the host's files.
  The body is the whole OCSF event, so nothing is lost and Splunk's JSON
  extraction names every field.
- **S2. The time is the decision's, set by the sender.** Splunk parses no
  timestamp, so an event's `_time` is when it was decided, to the
  millisecond, however late it arrives.
- **S3. Three fields indexed, the rest at search time.** The run, the
  decision and the class are indexed, for `tstats` over every event;
  every other name is the app's, at search time, so a later app can change
  them without re-indexing.
- **S4. The token from the environment, the certificate always checked.**
  As D4: `--hec-token-env` names a variable, never the token. The HEC's
  TLS certificate is checked, its name too; `--ca` trusts a private CA,
  and there is no option to skip the check.
- **S5. Indexer acknowledgement, when asked.** An HEC's 200 says a batch
  was received; `--hec-ack` waits for Splunk to say it was indexed, and a
  batch not acknowledged within 120 s ends the export with exit 1.
  Retries are as D5; a refusal names the first event the HEC did not
  take.
- **S6. A dry run's calls are not refusals.** A dry run records DENY for
  what it lets through (its disposition `Detected`, not `Blocked`); the
  dashboard counts those apart (`varek_refused`).

Tested (November 15, 2026):

- `tests/test_varek_splunk.py` (in `make test-cli`), against a stand-in
  HEC:
  - the mapping, and the endpoints;
  - batches with the token, the token never in the output;
  - no token, or no URL, refused (exit 2);

  - a 400 naming the first event not taken, and a 403, ending the export

## 3. Microsoft Sentinel (released in v1.40.0)

`tools/varek_sentinel.py` reads OCSF events as `varek_otel.py` does and
sends each as a row of the custom table `VarekOCSF_CL` in Sentinel's Log
Analytics workspace, through the Azure Monitor Logs Ingestion API and a
data collection rule. `varek export --format sentinel [LOG]` sends a
finished run; `--follow STREAM` a live one. `integrations/sentinel/` holds
two deployment templates and `README.md`, the steps:

- `azuredeploy.json`: the table (30 columns), the data collection rule
  (kind Direct: its own ingestion endpoint; its stream `Custom-VarekOCSF`
  passed to the table unchanged), and, given a principal, its Monitoring
  Metrics Publisher role on the rule; its outputs, the endpoint and the
  rule's immutable id, are what the export needs;
- `sentinel-content.json`: three analytics rules (a refusal, Medium, an
  incident for each run, agent and policy line; a failed audit, High; a
  dry run's let-through calls, Informational, no incident) and a workbook
  with the Splunk dashboard's panels. v1.42 adds a fourth: an approval
  nobody gave in time (Medium, an incident for each run, agent and policy
  line; `docs/security/v1.42-step-up-defer.md`, step 8).

A row: `TimeGenerated` (the decision's time), `Decision`, `Verdict`,
`Rule`, `PolicyLine`, `PolicyText`, `PolicyName`, `PolicySha256`, `Mode`,
`Target`, OCSF's class, activity, action, disposition, status and
severity, `RunId`, `ReportId`, `Seq`, `Agent`, `AgentType`, `Computer`,
`ProcessId`, `UserId`, `WardenVersion`, `EventName`, `AuditPassed`, and
`OcsfEvent`, the whole OCSF event (dynamic).

Decisions (made November 15, 2026, while building):

- **T1. The Logs Ingestion API and a custom table, not the HTTP Data
  Collector API**, which Microsoft has deprecated, nor an agent on the host. A
  Direct data collection rule needs no data collection endpoint.
- **T2. The columns are VAREK's, with the OCSF event whole beside them.**
  Sentinel's normalized schemas (ASIM) are its parsers' to map to; the
  table keeps every field the OCSF event has, and names the ones a query
  needs.
- **T3. The token is Entra ID's, its secret from the environment.** A
  client secret (the `AZURE_*` variables Azure's own tools read; the
  secret never on a command line), an Azure VM's managed identity (no
  secret), or a token had before. The identity's only role is Monitoring
  Metrics Publisher on the one rule.
- **T4. Refusals and failures end the export, as D5.** 429 and 5xx sent
  again (`Retry-After` read); a batch too large (413) split; a 401 gets a
  new token once; any other refusal exit 1. Rows are sent gzipped, each
  request under the API's 1 MB.
- **T5. The templates are generated from one list of columns**, and a
  test checks the table, the rule's stream and the rows agree, and that
  every name the rules' and workbook's KQL reads is a column.

Tested (November 15, 2026), against a stand-in Azure
(`tests/test_varek_sentinel.py`, in `make test-cli`): the row; the
templates' agreement; batches under the limit; the client secret's token
request (the tenant, the client, the scope) and one token kept; a managed
identity's (the metadata header, the resource); a token from the
environment; a 503 and a 429 sent again; a 413 split; a 401 mended once;
a 400 and a second 401 ending the export (exit 1); a refused secret
(exit 1, the secret never printed); missing settings (exit 2). And
`varek export --format sentinel` on a live run's stream: its 228 rows,
the six refusals with their policy line or rule.

Tested live (November 16, 2026), in a Log Analytics workspace with
Sentinel (East US), from a RHEL 9 host on #193's head: **the ship gate
passes.**

- **The templates** deployed on the first attempt, unchanged:
  `azuredeploy.json` in 34 s, `sentinel-content.json` in 34 s.
- **The rows:** a live run's 142 events, sent with `--follow` (9
  requests), all 142 in `VarekOCSF_CL`; the run's audit passed.
- **A refusal within a minute, with its policy line:** each of the run's
  19 refusals in the workspace 7.3 to 24.5 s after its decision; those
  decided by a policy line (`/etc/shadow`, `/etc/hostname`,
  `/root/.bash_history`, line 54 or 55) with `PolicyLine` and
  `PolicyText` filled.
- **The rules and the workbook:** the refusal rule raised an incident
  (Medium, two alerts: "VAREK refused python3.9 on ...: line 55: deny

  failed-audit rule was not exercised that day (no stream was tampered

- **The first rows to a new table and rule were slow:** on the first
  run, 18 of its 19 refusals reached the workspace 349 to 375 s after
  their decisions, all at once, with no error or retry in the export;
  forty minutes later, the second run's all within 25 s. Azure Monitor's

Found there and fixed: when the sender failed (Entra ID refusing a
wrongly pasted secret during `--follow`), the reader died on the closed
pipe with a traceback that buried the sender's message, and `varek
export` blamed the audit. The reader now exits quietly (exit 3), stopped
when the sender stops, and the CLI says the send failed, with the
sender's exit code (`test_a_refused_secret_is_the_send_failing_not_the_audit`,
the same for `--format otlp` and `splunk`, which share the path).

Worth a look, not blocking: 15 of the 19 refusals were Python 3.9's own
start-up lookups of paths that do not exist (12 `resolution_failed`, 3
`default_deny_unknown`), which fill the refusal incident and the
workbook's refusals over time; whether the rule should leave out
`resolution_failed`, or the sector packs allow Python's start-up lookups,
is a decision for v1.40.0. And the packs' `allow exec /usr/bin/python3`
on RHEL 9, where it is a link to `python3.9`, is to be checked (the test
ran the agent as `/usr/bin/python3.9`, with that path allowed).

*Answered* (November 18, 2026):
- **The start-up refusals: the packs, not the rule.** A rule can't tell
  them apart. A refusal says EACCES whether or not the file exists, and
  Python's `pyvenv.cfg` read is an open like any agent's. Leaving out
  `resolution_failed` would also miss most of them: under the packs at
  `require warden 1.27` there are none, and the same reads are refused as
  `default_deny_unknown` or by `deny path /etc/`. So the packs allow them,
  read-only (the loader's, the C library's and Python's). A bare Python
  agent's start-up went from 19 refusals to none
  (`test_a_python_agent_starts_under_each_pack_refused_nothing`, which CI
  runs on Ubuntu, Rocky Linux 9 and Amazon Linux 2023).
- **The python3 link.** The agent's own program needs no rule: it is
  allowed once, `bootstrap_exec_allow`. Under the packs' old `require
  warden 1.14`, every launch after it was refused whatever `allow exec`
  said. From 1.27, which the packs now say, the rule covers the file the
  link reaches: a launch of `/usr/bin/python3`, here a two-step link
  through `/etc/alternatives`, was allowed by the pack's line and ran.

Tested live (November 19, 2026), in the same workspace, from the same
RHEL 9 host (Amazon EC2) on main at `e1c0994`: **the failed-audit rule
raises its incident.**

- **A tampered stream:** a fresh run's first refusal edited into an allow,
  then sent as a live run is (`--follow`). The 6 events before the edited
  record reached `VarekOCSF_CL`, then the audit's verdict (7 rows): `AuditPassed`
  false, High, its problem `...-tampered.log:16: hash chain broken`. The
  row arrived 38 s after the run.
- **The incident:** "VAREK: the audit of run ... failed", High, created
  10 min 25 s after the run (the rule runs every 5 minutes; Sentinel then
  makes the incident).
- **The same stream sent whole** (no `--follow`): the audit refused it
  first, and no row was sent.

Found there and fixed: with `--follow`, the reason (the broken line)
reached Sentinel but not the screen; the whole-stream audit named the
exporter's private copy of the stream (`/tmp/varek-ocsf-.../stream.log`)
instead of the file given; and after a stream the audit refused, `varek
export` said "what it wrote before was sent" even when nothing was. The
reason is now printed too, the file given is named, and the CLI says
"nothing was sent" or "the events it wrote before it stopped were sent"
(`test_a_refused_stream_says_why_and_what_was_sent`).

**The rules now judge a row when it arrives.** As tested, each rule ran
every 5 minutes over the last 5 minutes of `TimeGenerated`, the decision's
time: a run exported live, or within minutes of its end, raised its
incidents, and one exported later reached the table and the workbook but
raised none. Ken decided on November 20 that the rules should look back by
arrival instead. Each now runs every 5 minutes over a day of
`TimeGenerated` and keeps the rows that arrived in the last 6 minutes
(`ingestion_time() > ago(6m)`), Microsoft's pattern for ingestion delay:
a run exported within a day of its decisions raises its incidents. A day,
not more: Sentinel runs a solution's rule that looks back 2 days or more
at most hourly (`test_the_rules_judge_each_row_when_it_arrives`).

Tested live (November 20, 2026), the rules deployed again in the same
workspace (replaced in place: still three), from the same RHEL 9 host on
main at `c09e42b`: two runs exported 8 minutes after their decisions, past
the old rules' window. The refusals of the one sent whole raised the
Medium incident, 5 min 40 s after its rows arrived; the tampered one sent
with `--follow` raised the High incident, 50 s after its row arrived.
Neither would have under the old rules.

Found there and fixed:
- **The same failed audit raised two alerts**, 5 minutes apart: two runs
  of the rule both counted its row. Sentinel's runs are not exactly 5
  minutes apart, so a 5-minute arrival window overlaps the next run's
  when they are closer, and leaves a gap, a row no run judges, when they
  are further. The window is now 6 minutes: no gap; a row in the overlap
  raises a second alert, which the incident's grouping by run joins to the
  first (as it did here: one incident, two alerts).
- **The refusal alerts spanned the whole day** the rule looks over: the
  refusal and dry-run rules summarize without a `TimeGenerated`, so the
  alert took the query's period. Each now gives `TimeGenerated =
  max(TimeGenerated)`, the latest decision, as the failed-audit rule's
  rows already did.

Tested live again after both fixes (November 20, 2026, the rules deployed

### 4a. Falcon Next-Gen SIEM export (built against a stand-in; in the code from v1.41.0, supported in v1.44.0)

`tools/varek_falcon.py` reads OCSF events as `varek_otel.py` does and
sends each to a Next-Gen SIEM HTTP Event Collector (HEC) data connector.
`varek export --format falcon [LOG]` sends a finished run; `--follow
STREAM` a live one; `--from-position N` the rest of one that failed.

- **The connector's URL and API key.** The URL is the one the Falcon
  console shows on the connector's page (`--endpoint`, default
  `FALCON_HEC_URL`); `/services/collector` is added to a URL that ends in
  no collector path (`/services/collector`, its `/event` or `/raw`, or
  LogScale's `/api/v1/ingest/hec`, or its `/raw`). The key is read from
  the environment (`FALCON_HEC_API_KEY`, or the variable
  `--falcon-key-env` names), never the command line, and sent as
  `Authorization: Bearer`.
- **An event is the Splunk export's** (section 2): `time` (the
  decision's, in seconds, to the millisecond), `host`, `source`
  `varek-warden`, `sourcetype` `varek:ocsf`, `event` (the whole OCSF
  event) and `fields` (`varek_run`, `varek_decision`, `ocsf_class_uid`,
  flat strings). Events go one a line, several in a request. To the raw
  endpoint (`.../services/collector/raw`), each OCSF event goes as one
  line, alone.
- **Sending:** only a 200 is taken (LogScale: committed, not to be
  resent). 429, any 5xx, and a 2xx other than 200 or a 3xx (not
  followed: urllib would send a POST's redirect on as a GET, without its
  events) are sent again, `Retry-After` read; a batch too large (413)
  split; any other refusal ends the export with exit 1, naming where the
  events not sent begin. A 200 whose answer is the HEC's with a code
  other than 0 is a refusal. A request stays under 900 KB. An event over
  1 MB is not sent and ends the export so: the connector would answer 200
  and keep it truncated, its fields dropped.

## 5. A failed export resumed (released in v1.40.0)

An export that fails partway (a refusal the sender cannot mend, a lost
connection, an expired secret) has sent some of the run's events. Through
v1.39.0 the only way to send the rest was to export the run again, so a
SIEM got every event it already had a second time. Now the sender's
message says where the events it did not send begin:

```
varek_sentinel: HTTP 400 ... (500 rows sent before; those not sent begin at position 512: `varek export --from-position 512` sends them)
```

and the same export with `--from-position 512` sends the rest.

- **The position is the record's.** Every OCSF event already names the
  position of the record it came from, in `unmapped.varek.position`. A
  decision's `seq` would not do: only decisions have one, and a run's
  start, its checkpoints and its DNS answers are events too.
- **The stream is audited whole.** `--from-position` changes which events
  are written, not what is checked: the export still audits the whole
  stream (record by record in `--follow`), and a stream the audit refuses
  writes nothing, whatever the position. The audit's verdict event is
  always written.
- **None from there on is left out.** Events come out in their records'
  order, since an event waiting for a record that folds into it holds back
  those after it. So the export writes from the first event at or past
  the position, and everything after it, including an event `finish()`
  adds at the end with an earlier position. What can happen is an event
  sent twice: a split Sentinel batch whose first half was accepted is
  named from its first row, and the run's last event shares its position
  with the audit's verdict.
- **Where the rest begins, for each sender:** the first event of the batch
  refused (OTLP, Splunk, Sentinel); with `--hec-ack`, the first event of
  the earliest batch Splunk received but did not acknowledge as indexed.
  A sender that failed before it read anything names no position: the
  export is then made again whole.
- **For `--format ocsf, otlp, splunk, sentinel`**, with a finished run's
  stream or `--follow`. Not with `--verify`, which checks a whole export,
  nor for CycloneDX, which is one document.

Tested (November 18, 2026):

- `tests/test_varek_export_resume.py` (in `make test-cli`):
  - events in their records' order, a launch holding back the open behind
    it until its `exec_result` folds in;
  - `--from-position` keeping every event from the first at or past it;
  - on a real run's stream: the export from the middle equal to the whole
    export's events from there, by `--log` and by `--follow`; a record
    before the position edited, and nothing written; `--verify`, CycloneDX
    and position 0 refused;
  - a Sentinel send refused (a stand-in Azure) naming the position, and
    the same export with `--from-position` sending exactly the whole
    export's rows from there.
- `test_varek_otel.py`, `test_varek_splunk.py`, `test_varek_sentinel.py`:
  the first batch taken and the second refused names the second's first
  position; Splunk's unacknowledged batch; Sentinel's split batch named
  from its first row; an event with no position naming none.

## 6. Google Security Operations (planned; v1.43.0)

Added November 24, 2026, from Google's *Google Security Operations Build
Partner Content Guide* (H1 2026, Rev. 1.0; a partner-shared PDF, not in
this repository). The guide asks a partner for three things:

- **logs in**, preferably as UDM (Google's Unified Data Model) events;
- **detection content**: YARA-L rules and dashboards, kept in the
  partner's own repository;
- **optionally, a SOAR Response Integration**, sent to Google's Content
  Hub.

Like Falcon and Wiz, this waits on an instance of the tool. Here that's
Google's development license, offered to "Build" partners in Google Cloud
Partner Advantage.

Today Google SecOps appears only in `docs/security/v1.31-standards.md`,
as a SIEM that maps from OCSF.

### What it adds

**`tools/varek_secops.py`** reads OCSF events as `varek_sentinel.py`
does: audited first, translating and delivering, deciding nothing,
dropping nothing the OCSF event carries. It sends each event as a UDM
event to the instance's Chronicle API.

- `varek export --format secops [LOG]` sends a finished run.
- `--follow STREAM` sends a live one.
- `--from-position N` resumes, as section 5 describes.

**`integrations/secops/`**, installed in `/opt/varek/integrations` like
`sentinel/` and `splunk/`, holds:

- **three YARA-L rules**, one for each Sentinel analytics rule:
  - an agent's action refused (Medium);
  - a run's audit failed (High);
  - a dry run's let-through calls (Informational).

  Each rule names the policy line in its outcome and groups by run.
- **a dashboard** with the Splunk dashboard's and the Sentinel
  workbook's panels:
  - refusals by policy line, agent and run, over time;
  - the latest refusals;
  - dry-run let-throughs, counted apart from refusals;
  - failed audits.

  It's built from YARA-L searches in the development instance and
  exported from there, as the guide asks.
- **`README.md`**: the service account and its permission, the export
  command, and how to import the rules and the dashboard.

### Decisions (decided November 24, 2026)

G2's endpoint, body and permission, and G4's field names, are checked
against Google's reference pages in the development instance before the
export is built against them; a difference found there changes the
detail, not the decision.

- **G1. UDM events, not raw OCSF through Google's OCSF parser.** Google
  SecOps has a default parser for the log type `OCSF`, so VAREK's OCSF
  events could go in as raw logs today. But Google says a default parser
  "might map a subset of core values from the raw log". A value it doesn't
  map stays in the raw log, not the UDM record, and no rule or dashboard
  can read it. VAREK's policy line and its text, the three-state verdict
  and the policy's SHA-256 are the values most likely to be left out.
  - The export therefore writes the UDM itself, as Sentinel's writes its
    own columns (T2).
  - The README says what the raw-OCSF route loses, for a customer who
    sends raw OCSF anyway. That list gets measured in the development
    instance: send the same run both ways and record which fields the
    default parser fills.
- **G2. The Chronicle API's `events:import`, not the older Ingestion
  API.** The guide recommends the Chronicle API's ingestion methods for
  new integrations, "to future-proof". Endpoint, body and permission, as
  Google's own sample code calls it:
  - **Endpoint:** `POST https://{region}-chronicle.googleapis.com/v1alpha/projects/{project}/locations/{region}/instances/{customer_id}/events:import`.
  - **Body:** `{"inline_source": {"events": [{"udm": {...}}, ...]}}`.
  - **Auth:** OAuth scope `https://www.googleapis.com/auth/cloud-platform`.
  - **Permission on the instance:** `chronicle.events.import`.
  - **Sources:** `chronicle/api-samples-python`,
    `ingestion/v1alpha/create_udm_events.py`; Google's SecOps SDK,
    `secops` 0.44.1, `chronicle/log_ingest.py` (`ingest_udm`).
  - **Not yet checked:** Google's reference pages couldn't be reached
    from where this was written, so the first test in the instance
    checks these.
  - **The version is a setting** (`--api-version`, default `v1alpha`).
    The method is a preview, and when Google moves it to `v1beta` or
    `v1`, changing over is a flag, not a release.
  - **The fallback** is the Ingestion API's
    `POST https://malachiteingestion-pa.googleapis.com/v2/udmevents:batchCreate`
    (`{"customerId": ..., "events": [...]}`, scope
    `https://www.googleapis.com/auth/malachite-ingestion`, a JSON key
    Google issues). It gets built only if `events:import` isn't available
    to the development instance.
- **G3. The credential is the customer's own Google Cloud identity**, as
  Sentinel's is Entra ID's (T3). It comes from one of:
  - the VM's service account, through the metadata server, with no
    secret on the host;
  - a service-account key file named by `GOOGLE_APPLICATION_CREDENTIALS`;
  - a token from the environment.

  The credential is never on the command line. The identity needs only
  `chronicle.events.import` on the one instance; a custom role with that
  single permission is the least.
- **G4. The UDM event.** The mapping below is checked against Google's
  UDM field list in the instance before it's fixed.
  - **`metadata`:**
    - `event_type` comes from OCSF's class and activity: file activity
      gives `FILE_OPEN`, `FILE_CREATION`, `FILE_MODIFICATION` or
      `FILE_DELETION`; a launch gives `PROCESS_LAUNCH`; network activity
      gives `NETWORK_CONNECTION`; the egress proxy's HTTP activity gives
      `NETWORK_HTTP`; anything else gives `GENERIC_EVENT`.
    - `vendor_name` is "Sober Agentic Infrastructure", `product_name`
      "VAREK", `product_version` the Warden's version, and
      `event_timestamp` the decision's time.
    - `product_event_type` is OCSF's class and activity.
    - `description` is the one line the OTLP export writes ("Blocked:
      File System Activity: Open /etc/shadow (policy line 91: ...)").
    - `product_log_id` is the run and the record's position, so an event
      sent twice (section 5) can be told apart from two events.
  - **`principal`:** the host, and the agent's process (pid, command
    line, user).
  - **`target`:** what was decided. That's `target.file.full_path` for a
    file, `target.process` for a launch, or `target.hostname`, `ip`,
    `port` and `url` for the network.
  - **`security_result`:**
    - `action` is `ALLOW` or `BLOCK`;
    - `rule_name` is the policy line;
    - `summary` is the line's text;
    - `severity` is `MEDIUM` for a refusal, `HIGH` for a failed audit
      and `INFORMATIONAL` for a dry run's let-through;
    - `description` names the three-state verdict.
  - **`additional.fields`:** `varek_decision`, `varek_verdict`,
    `varek_mode`, `varek_policy_name`, `varek_policy_sha256`,
    `varek_run`, `varek_agent` and `varek_position`, plus the whole OCSF
    event as JSON in `ocsf_event`, as the other exports carry it. Keys
    use underscores, so a YARA-L rule reads them plainly
    (`$e.additional.fields["varek_verdict"]`).
  - **A failed audit** is its own `GENERIC_EVENT`, at `HIGH`.
  - **When an event lacks a required noun.** UDM refuses an event type
    whose required nouns are missing (a `FILE_OPEN` with no
    `target.file`, for one). So an OCSF event without the object goes
    out as `GENERIC_EVENT` rather than be refused.
- **G5. Refusals and failures end the export, as Sentinel's do (T4).**
  - A 429 or a 5xx is sent again with back-off.
  - A request over the size limit is split; the limit is measured in the
    instance.
  - A 401 gets a new token once.
  - Any other refusal exits 1, naming where the events not sent begin
    (section 5).
- **G6. The rules read only what the export writes.** A test checks
  every UDM field and `additional` key the rules and dashboard read, as
  T5 does for Sentinel's KQL.
- **G7. A Response Integration is later, and optional, not v1.43.0.**
  - **What it would add:** actions for an analyst on a case ("get a
    run's evidence", "verify a run's audit") and an ontology mapping
    (agent, host, file and URL as entities). It's the same idea as
    section 4's Falcon Foundry app, which it should share a design with.
  - **What it needs:** a VAREK API that SecOps' SOAR can reach. Whether
    that's the Verdict Service or the customer's own is a decision for
    then.
  - **The payoff:** the Content Hub takes these as a pull request, and
    Google publishes them to every SecOps customer within a day of
    approval. The Content Hub doesn't take rules or parsers yet, so
    the rules and the dashboard stay in this repository either way.

**Not needed:**
- reading SecOps data through the Chronicle API, since VAREK doesn't
  read it;
- a webhook feed, since `events:import` covers ingestion;
- a new log type, since UDM needs none and `OCSF` already exists.

### Before it ships

**Built against a stand-in first**, as Sentinel and Falcon were:
`tests/test_varek_secops.py`, in `make test-cli`. It covers:

- the UDM event for each OCSF class;
- the `GENERIC_EVENT` fallback;
- the request's URL and body;
- the metadata server's token, a key file's token, and one token kept;
- a 429 and a 503 sent again;
- a request too large, split;
- a 401 mended once;
- a 400 ending the export (exit 1) with the position;
- missing settings (exit 2).

**The ship gate**, in the development instance (`docs/roadmap/v1.32-v1.35.md`):

- a refusal appears in Google SecOps within a minute, with the policy
  line that decided it;
- each YARA-L rule raises its detection live, as Sentinel's rules did
  on November 19 and 20;
- the dashboard is imported and shows a live run.

Whether a UDM event can be searched within a minute of its import hasn't
been measured; it's the gate's first question.

**What the export needs from the development instance:**

1. Its customer ID, the Google Cloud project it's bound to, and its
   region (`us`; the guide asks for US).
2. The Chronicle API enabled on that project, and `events:import`
   available to the instance. Ask Google whether the preview method is
   open to a development license, and for its limits: request size,
   events per request, and the requests-per-minute quota.
3. A service account in that project with `chronicle.events.import`,
   and a reader role for checking what arrived.
4. A VM in that project to run the export from, so G3's no-secret path
   is what gets tested.
5. Rights to create YARA-L rules and dashboards, and to export them.
   The guide's three Chronicle roles cover this.
6. The Ingestion API's JSON key as well, so that if the preview isn't
   open to the instance, G2's fallback doesn't cost another wait.
