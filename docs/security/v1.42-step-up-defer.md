# v1.42: human approval (STEP_UP) and deferral (DEFER)

Status: design draft (November 23, 2026), not built. Decisions marked **(open)** are Ken's to make before building.

## Why

VAREK decides each mediated call ALLOW or DENY. An undecidable call (UNKNOWN) is refused. The AARM specification's Core level (`docs/security/aarm-mapping.md`) needs three more decisions:
- **STEP_UP:** hold the call until a person approves or refuses it.
- **DEFER:** hold it until the context it needs arrives.
- **MODIFY:** carry it out changed.

STEP_UP and DEFER are the gap that blocks Core: AARM's R4, and its DEFER clauses in R1, R3, R5 and R6. They suit VAREK's design, because the kernel already holds every mediated call (seccomp user-notify) until the Warden answers. Holding it longer is a change in the Warden, not in the kernel interface. A general MODIFY is out of scope here (see the end).

## What it does

1. **A rule can say `step_up`.** A call it matches is held, and a request is put to an approver:

   ```
   require warden 1.42
   step_up connect host api.payments.example port 443 timeout=300 reason="payments API"
   step_up open path prefix /srv/records/ write timeout=120
   ```

   The match is the same as an `allow` rule's. A call the policy would refuse anyway is refused; `step_up` never widens the policy.
2. **DEFER holds a call while the decision lacks context, then decides again:**
   - **a call that is UNKNOWN** (outside the decidable fragment), with `on unknown defer timeout=N` (the default stays `on unknown deny`);
   - **a call no plan step covers,** under `--hold-to-plan` with `on outside_plan defer timeout=N`. If the planner extends the plan (`varek plan extend RUN FILE`, checked by the plan gate as any plan is), the held call is decided against the new plan;
   - **a rule that names its own condition:** `defer ... until=FILE` waits for a file (a ticket, a change window's marker) to exist and pass the rule's check.

   If a deferral can't be resolved this way, it becomes a STEP_UP when the rule says `escalate`. Otherwise it is refused at its timeout.
3. **Timeouts always refuse.** Each held call has one (default 300 s; at most 3,600 s). When it expires, the call is refused, and the refusal is recorded. There is no fail-open, and no setting makes one. If the Warden stops, the agent is killed, as today.
4. **A bounded number of held calls.** `max_held N` (default 8) caps the calls held at once in a run. One more is refused at once, rather than piling up unbounded state, as AARM's R4 requires.
5. **Ordering.**
   - **Same thread:** a held call blocks only the thread that made it. The thread's later calls wait behind it, so a call that depends on the held one waits too.
   - **Other threads and processes:** they go on, as AARM says independent actions should.
   - **Cross-thread dependencies:** VAREK can't see a dependency across threads (one thread waiting on another's held write). A policy that needs that should hold the whole run (`step_up ... scope=run`) **(open)**.

## Approvers

- **The command line:** `varek pending` lists a run's held calls. Each shows:
  - the action and its resolved object;
  - the rule and policy line;
  - on whose behalf (`obo`);
  - the plan step, if any, and the run's recent decisions;
  - the time left.

  `varek approve RUN ID [--reason TEXT]` and `varek deny RUN ID` answer through the run's control socket (`/run/varek/<run>.ctl`, root's, as `varek revoke` uses).
- **Who may approve:** the approver is the Unix user making the request, taken from the socket's peer credentials. `approvers=GROUP` on the rule limits approval to that group's members, so root alone is not an approver by default **(open: or an identity provider's group, verified as v1.28.1 verifies a token)**.
- **Notification:** `notify=URL` posts each request, without the call's data, to a webhook (Slack, Teams, a ticketing system). The webhook only notifies; it can't approve **(open: whether v1.42 includes it)**.
- **Approval fatigue:** keep `step_up` to the calls that need a person (destructive writes, payments, data leaving), as AARM advises. `varek policy suggest` doesn't propose `step_up` rules.

## The kernel side

- **Holding:** a held call is a seccomp notification the Warden hasn't answered. The kernel keeps the thread waiting indefinitely.
- **Signals:** where the kernel supports `SECCOMP_FILTER_FLAG_WAIT_KILLABLE_RECV` (Linux 5.19 and later), only a fatal signal ends the wait. On older kernels a signal can interrupt it, and the call then fails with `EINTR` without taking effect. Either way it is recorded as `abandoned`. Before answering, the Warden checks the notification is still valid (`SECCOMP_IOCTL_NOTIF_ID_VALID`), as today.
- **Network requests and MCP tool calls:** in the egress proxy these are held the same way: the request is not forwarded until it is decided.
- **The Warden's own work:** it goes on serving other notifications while calls are held. Held calls are kept in a table, not on the Warden's stack.

## The record (AARM R5 and R6)

- **When a call is held:** a record with `decision_raw: "STEP_UP"` or `"DEFER"`, a `held` id, the reason and the timeout. It carries the same fields and `obo` as any decision, chained like the rest.
- **When it ends:** a second record naming the `held` id, with:
  - `decision_final` (ALLOW or DENY);
  - how it ended: `approved`, `denied`, `resolved` (context arrived), `timeout` or `abandoned`;
  - for an approval: the approver (uid and name, and the group the rule named), the reason given, and the time.
- **Identity:** the user, agent and sub-agent are those of the original call, preserved through the hold.
- **The audit (`varek_audit.py`):**
  - every held id has exactly one ending, after it and within its timeout;
  - an ALLOW after STEP_UP names an approver the rule allowed;
  - an ALLOW after DEFER was decided again, with its certificate, under the context that resolved it;
  - a held call's ending isn't missing at `run_end`.
- **The export:** `STEP_UP` and `DEFER` appear in OCSF and in the Splunk, Sentinel and OpenTelemetry exports. The Sentinel rules gain one for timed-out approvals.

**A trust change:** an ALLOW after STEP_UP rests on a person's approval, not on a certificate the checker verified. The record says so, and the audit counts such calls separately. The threat model gains the approver as a principal: approvers can be deceived or coerced, as AARM also notes.

## Not in v1.42

- **A general MODIFY.** Rewriting a system call's arguments in the kernel's view risks a time-of-check race. A narrow form, for example dropping an MCP call's argument the policy forbids, is a candidate for later, kept to changes the certificate checker can verify. Credential release (v1.28) stays the one MODIFY.
- **Semantic drift (AARM R7).**
- **The user's original request (AARM R2).** A `--intent FILE` recorded in `run_start` and shown to approvers is small, and could ride along **(open)**.
- **Context across runtime calls** (a read of sensitive data refusing a later send). That is the cross-action data-flow candidate (v1.11).

## Tests (`make test-v1420`) and ship gate

- **Each decision:** ALLOW, DENY, STEP_UP approved, STEP_UP refused, DEFER resolved by a plan extension, DEFER resolved by its file, DEFER escalated, UNKNOWN deferred. Each comes with its records and the audit passing.
- **Timeouts** refuse. `max_held` refuses the next call. A thread's later calls wait behind its held one, and other threads go on.
- **Robustness:**
  - a signal during a hold;
  - the agent exiting during a hold;
  - the Warden killed during a hold (the agent gone, no effect carried out);
  - an approver outside `approvers=GROUP` refused;
  - an approval for a call that has ended refused.
- **The audit's forgeries:**
  - an ending without its hold, or a hold without its ending;
  - an approval with no approver or the wrong group;
  - an ending after the timeout;
  - an ALLOW after DEFER without a certificate.
- **Latency:** a call that is not held is decided no slower than in v1.41 (`make latency-*`).
- **Ship gate:** the suites, the cross-check, the 24-hour soak with a STEP_UP approved by a script every turn and a DEFER timing out every tenth, and AARM's R1 to R6 conformance tests run and recorded in `docs/security/aarm-mapping.md`.
