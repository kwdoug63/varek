## What v1.29 and v1.31 leave open

The Warden runs only on Linux, and only on x86-64. A Mac runs neither: an
agent on a developer's Mac runs with the developer's full reach.

## What v1.30 gains

An agent on a Mac runs inside a lightweight Linux VM, under the Warden as it
is on Linux, with the same three-state decisions, records and audit. The
Mac's files outside what is shared with the VM are out of the agent's reach
whatever the policy says.

## The design in one paragraph

On a Mac with Apple silicon the VM runs arm64 Linux, so the Warden is built
for arm64 (step 1), from the same source as for x86-64: one program, two
architectures, the same policies, certificates and records. VAREK's
encoding of open flags stays x86-64's on both, and the Warden translates
arm64's where they are decided and recorded. The VM runs on Apple's
Virtualization framework, launched by `vfkit` (Red Hat's), with a RHEL 9
arm64 guest (9.6 or later), the project directory shared and nothing else;
`varek` on the Mac starts it and runs `varek run` inside. Every layer is a
US vendor's: Apple's hypervisor, Red Hat's launcher and operating system. Testing needs a Mac only for the VM: the arm64 Warden is built and
tested on an arm64 Linux host (an AWS Graviton instance), and the VM on a
rented Mac (Amazon EC2 Mac, in a US region).

## 1. The arm64 Warden

What differs from x86-64, and how each is handled:

- **System calls.** arm64 has only the `*at` forms of `open`, `stat`,
  `lstat`, `access`, `readlink`, `unlink`, `rmdir`, `mkdir`, `rename` and
  `chmod`. The Warden decides the `*at` forms on both architectures; the
  legacy forms are decided where they exist (x86-64, for musl), and on
  arm64 a number no call carries stands in for each, so nothing changes in
  how a call is decided.
- **The filter.** libseccomp builds it by system-call name, for the
  architecture it runs on; a name arm64 lacks gets no rule that can match.
  A call from another ABI (arm64's 32-bit compat, as x86-64's i386 and x32)
  kills the process, as before.
- **Open flags.** Four bits differ: `O_DIRECTORY`, `O_NOFOLLOW`, `O_DIRECT`
  and `O_LARGEFILE` (and with them `O_TMPFILE`). Rules, certificates, the
  cross-check oracle, the audit and every recorded `open_flags` use x86-64's
  values (D3), so the Warden keeps an action's flags as the kernel's and
  translates them where they are decided (the decision procedure, the
  certificate checker), recorded, and read from a plan. The four bits are
  permuted among themselves, so the translation is exact both ways.
- **Unchanged:** the system calls' argument order for everything the
  Warden reads (`clone`'s flags, `socket`, `connect`, the `*at` calls),
  `clone3` and `io_uring_setup`'s numbers (the same on both), Landlock,
  seccomp user-notify, pidfds and cgroup v2.

**Tests:** every suite on an arm64 host (`tests/arm64_sweep.sh`: the build,
every `make test-*` target, `make test-cli` and `make crosscheck`, each
logged, then a summary); `make test-v1300-oflags` on both architectures.

## 2. The VM

- `vfkit` (Red Hat's open-source launcher for Apple's Virtualization
  framework, the one `podman machine` uses on a Mac), with a RHEL 9 arm64
  guest image VAREK prepares: the Warden installed, the share mounted, a
  user for the agent. RHEL 9.6 or later, which has Landlock (Red Hat added
  it in 9.6); the kernel features the Warden needs (seccomp user-notify,
  Landlock, cgroup v2) checked by `varek doctor` inside the VM. Lima stays
  an option for development, being quicker to set up.
- RHEL's terms: the guest runs RHEL, so a user needs a RHEL entitlement
  for it (Red Hat's no-cost developer subscription covers an individual
  developer). For users without one, the same image built on a rebuild of
  RHEL 9 (AlmaLinux or Rocky Linux) or on CentOS Stream 9 is the
  alternative to decide when the image is built.
- Shared with the VM: the project directory only (read-write), never the
  home directory. The agent's network is the VM's, under the Warden's
  egress proxy as on Linux.
- `varek` on the Mac: starts the VM if needed, then runs `varek run` inside
  it on the shared project, and prints its summary; the verdict stream is
  kept in the VM and copied to the project.

**Tests:** on an EC2 Mac: the suites inside the VM; the agent cannot read
or write a file on the Mac outside the shared project; a 6-minute soak
trial; the VM's start time.

## 3. Audit and tools

- `run_start` names the architecture (`"arch": "aarch64"`), and the audit
  reports it; a stream reads the same on both otherwise (D4).
- `varek doctor` on the Mac: the VM, its kernel's features, the share.

## Decisions

- **D1. The VM: `vfkit` with a RHEL 9 guest** (decided October 14, 2026).
  Every layer is a US vendor's (Apple's Virtualization framework, Red Hat's
  launcher and operating system), which matters to defense buyers, and the
  guest lines up with the RHEL 9 certification and the OpenShift step in
  `docs/roadmap/v1.32-v1.35.md`. It costs more work than Lima (VAREK
  prepares and sets up the guest image itself); Lima, open source under the
  CNCF and the first recommendation, stays an option for development.
  Apple's Containerization framework needs macOS 26 and brings its own
  minimal kernel, which would have to be shown to have Landlock and cgroup
  v2 delegation: a later option.
- **D2. One source for both architectures,** not a separate port: every
  change is built and tested on both (D5) (decided October 14, 2026).
- **D3. VAREK's open-flag encoding is x86-64's on every architecture**
  (as built; decided October 14, 2026). The alternative, each architecture's own values in rules and
  records, would make a stream's meaning depend on where it was recorded,
  and the checker, the oracle and the audit each need both tables.
- **D4. `run_start` names the architecture**, and the audit reports it
  (built, step 3).
- **D5. Arm64 in CI** (built, step 2): a job on GitHub's arm64 Linux runners
  (`ubuntu-24.04-arm`), as the x86-64 one, so the Graviton instance is
  needed only to bring the port up.
- **D6. Testing on a Mac:** an Amazon EC2 Mac (a bare-metal Mac mini on a
  dedicated host, by the hour with a 24-hour minimum), in a US region; an
  M1 or M2 is enough (decided October 14, 2026).

4. **The VM** (started; built, not yet run on a Mac). As built:
   - `tools/varek_vm.py`, as `varek vm`:
     - `varek vm init --image FILE` makes the VM from a RHEL 9 aarch64
       KVM guest image, which the user downloads from Red Hat with their
       own login. It converts the image to raw with `qemu-img`, since
       Apple's framework boots raw disks, and grows it to 20 GiB. It makes
       an ed25519 key for the VM alone and writes cloud-init's files: a
       user `varek` with that key, sudo, no password, and nothing else.
     - The first boot shares the VAREK checkout (`varek-src`), for the
       guest to build from. If the guest is not registered, `varek vm
       init` stops and says how to register it (`sudo subscription-manager
       register` in `varek vm ssh`, with the user's own login), then
       carries on with `--resume`. An organization's activation key can be
       given instead (`--rh-org`, `--rh-activation-key-file`). varek never
       asks for or holds a Red Hat password.
     - `varek vm start [DIR]` boots it with DIR shared over virtio-fs and
       mounted at the same path inside, so the policy's paths, the
       records and the Mac's paths agree. The share is refused for `/`,
       the home directory or any directory holding it, and `/Users`,
       with links resolved.
     - `varek vm run ARGS -- CMD` (and `varek run` itself, on a Mac) runs
       `sudo varek run ARGS -- CMD` inside, in the working directory, as
       the VM's user. The run's verdict stream is copied to
       `.varek/` in the project.
     - `varek vm ssh`, `stop` and `status` do what they say.
   - vfkit's command line: EFI boot (a variable store made on the first
     boot), the raw disk over virtio-blk, NAT networking with a locally
     administered MAC of the VM's own, an entropy source, a serial log
     and each share over virtio-fs. cloud-init's files are given on the
     first boot only (`--cloud-init`). The VM's address comes from
     vmnet's DHCP leases (`/var/db/dhcpd_leases`), by its MAC, and ssh
     pins the VM's key in a `known_hosts` of its own.
   - `packaging/vm/provision.sh`, run as root inside by `varek vm init`:
     - It refuses anything but RHEL 9.6 or later, registered, or a
       rebuild of RHEL 9 (AlmaLinux, Rocky Linux, CentOS Stream 9).
     - It installs the build's packages, with libsodium from EPEL (RHEL
       does not ship it; EPEL needs CodeReady Builder, or CRB on the
       rebuilds).
     - It builds and installs the Warden from a copy of the source in
       `/opt/varek-src`.
     - If the kernel's LSM list lacks Landlock it adds it, effective at
       the next boot, and it runs `varek doctor`.
   - `tests/test_varek_vm.py` (in `make test-cli`): the parts that need
     no Mac. That covers the share's refusals, links included; the MAC;
     the leases, whose octets lose their leading zeros; cloud-init's
     files (the key, no password, no injected lines); vfkit's and ssh's
     command lines; and the refusal on any host but a Mac with Apple
     silicon.
   - Before a Mac, on AWS: `provision.sh` and every suite on a Graviton
     instance running RHEL 9.6 or later for arm64. This answers on AWS
     whether RHEL 9.6's kernel has Landlock and whether the build and
     install work there (EPEL's libsodium, RHEL 9's Python 3.9). The script
     takes a cloud's own RHEL image, whose repositories are the cloud's
     RHUI, as well as a registered system. `arm64_sweep.sh --deps` knows
     dnf as well as apt-get.
     Done on an x86-64 instance of AWS's own RHEL 9 image (October 15,
     2026; the architecture is not what this checks, arm64 having been
     checked on Ubuntu): `provision.sh` ran to the end. It enabled
     CodeReady Builder from AWS's RHUI, installed libsodium from EPEL,
     and built and installed the Warden; gcc 11 gives one warning there,
     at `checker/vdp_checker.c:800`. `varek` goes in `/usr/bin`, since
     RHEL leaves `/usr/local/bin` out of sudo's and root's path; that
     was found here. `varek doctor` on RHEL 9.8's kernel
     (5.14.0-687.10.1.el9_8): Landlock ABI 6, on by default; seccomp
     user-notify; mount namespaces for the noexec mounts; cgroup v2. Its
     one failure, no `/etc/varek/varek.conf`, is expected, since `varek
     run` works without one.
     The suites there (`arm64_sweep.sh` on the same instance, October 15
     and 16, 2026). The first sweep's failures were the build's static and
     sanitizer libraries (`glibc-static`, `libasan`, `libubsan`, from
     CodeReady Builder; `--deps` now installs them) and the following.
     Three were in the Warden:
     - RHEL 9's glibc (2.34) calls `pipe(2)` for `pipe()`, where Ubuntu's
       calls `pipe2`; the Warden refused it, and bash's command
       substitution failed. `pipe` is now admitted with `pipe2`.
     - RHEL's `/bin/sh` is bash, which calls `getpgrp`; it was admitted

       policy.

       saw a reset, not the end of the connection. It now shuts down its

       sees a FIN. This is on this branch only: v1.26.1 to v1.31 still

       unread (RHEL 9 here) the server sees a reset.
