## What there was before v1.36

v1.34 put the Warden on a node, as a DaemonSet that supervises the agent
containers of annotated pods from outside them. v1.35 added plans to it
(its D11). The node agent refuses a pod whose policy or run needs what it
does not carry. The refusals are in `warden_node.inc.c`
(`node_unsupported`, `node_policy_why`, `node_plan_carried`). Today it
refuses a pod for any of these:

| What the pod needs | On a host since | Refused by the node agent as |
|---|---|---|
| Credentials (`credential NAME from ...`) | v1.28 | "credentials" |
| Sub-agents (`subagent=`) and the MCP servers confined by them | v1.28.1, v1.31 | "sub-agents" |
| `require on-behalf-of`, a user's token, an SVID | v1.28.1 | "the on-behalf-of chain" |
| A dry run | v1.29 | "a dry run" |
| A plan step of kind `mcp_call`, `subagent` or `credential` | v1.35 | "the node agent does not carry ... steps yet" |
| A flow policy (`--flow-policy`) | v1.18 | "a flow policy" |
| A trust bundle (`--trust-bundle`: the roots trusted in place of the host's) | v1.26.1 | "a trust bundle" |

The last two are not in the roadmap's list. They were found in drafting
this note, from the code, and D7 decides them.

Beyond these refusals, v1.34's Known limits leave four more things:

- The node image and the DaemonSet are amd64 only.
- The exporter audits each stream whole, about 3.7 KB of memory a record,
  so at most about 550,000 records. Streams are not rotated on the node.
- The node's signing key is one Secret given to every node.
- The supported runtimes are named, but CI runs only `kind` with
  containerd 2.3 and no SELinux. That is why step 9 of v1.34 found its
  three faults on OpenShift and not before (the roadmap lists them).

## What v1.36 gains, and what it does not

- **Parity:** every policy and every plan that runs on a host runs under
  the node agent, decided the same way. If something cannot be carried
  into a pod from outside, the pod is still refused, never run with less.
- **arm64:** the node image built for both architectures, and the
  DaemonSet placed on both.
- **An audit in bounded memory:** a stream of any length audited in fixed
  memory, and streams rotated on the node.
- **A key for each node:** one node's key cannot sign as another node.
- **The supported platforms, tested:** each runtime and host that the
  README calls supported is run in CI. What the matrix does not cover is
  not called supported.

It does not change a decision procedure, a rule or a record's meaning.
The Warden's grammar stays as it is (D12).

## The design in one paragraph

Each carried feature is the host's code, run by the supervisor that the
node agent forks for each container, with one change: where the host's
Warden takes an input from its command line or its own files, the
supervisor takes it from the node. It never takes it from the agent's pod,
so the agent never holds it. The inputs are a credential's value, a
user's token, an SVID, a trust bundle and a flow policy. A sub-agent's
control group is made by the supervisor from the node's cgroup tree,
under the container's own group, as v1.34's step 1 measured possible. The
supervisor opens what is the node's before it enters the container's mount
and network namespaces, as it does now for the policy, the signing key and
the stream. So it is the node's network, under the DaemonSet's identity,
that fetches a credential from Vault or AWS Secrets Manager. The
credential's value is swapped into the agent's request by the proxy in the
pod's network namespace, as on a host.

## Decisions before building

- **D1. Where a credential's value comes from.** On a host,
  `credential NAME from file:PATH | vault:... | aws-sm:...` is read by
  warden-secrets as the Warden's user.
  - (a) warden-secrets runs in the supervisor before it enters the pod's
    namespaces. `file:` names a path under one directory that the chart
    mounts into the node agent from Secrets in VAREK's own namespace,
    which the operator lists in the chart's values. `vault:` and
    `aws-sm:` are reached from the node's network, under the DaemonSet's
    identity (EKS Pod Identity or IRSA for AWS; Vault's Kubernetes auth
    with the node agent's service account). The NRI plugin sets the
    credential's placeholder in the container's environment, as v1.34's
    step 2 planned.
  - (b) The node agent reads the Kubernetes Secret named by the policy,
    from the pod's own namespace. That needs `get` on Secrets in every
    namespace.

  *Decided (a)* (October 26, 2026). The value never enters the agent's pod or its
  namespace. The node agent's grant stays read-only and limited to its own
  namespace. (As built, the DaemonSet's account reads no Secret anywhere;
  it also gets pods in every namespace, for a flow policy's session (D7b),
  and creates `VarekNodeKey`s (D10). Step 11.) (b) would let any policy's author reach any Secret on the
  cluster through VAREK.

- **D2. Who may name a credential.** A `VarekPolicy` is namespaced, so a
  team that may write policies in its namespace could name a credential
  that is another team's.
  - (a) A cluster-scoped resource, `VarekCredential`, names each
    credential's source and the namespaces whose policies may name it. The
    webhook refuses a policy that names a credential its namespace is not
    given, and the node agent refuses such a pod at the start, so a
    webhook that is down or bypassed is not enough.
  - (b) The chart's values hold the same list.
  - (c) Any policy may name any credential.

  *Decided (a)* (October 26, 2026). A credential is given to a namespace by a cluster
  administrator, through the cluster's review flow, as policies are
  (v1.34's D7). (b) puts it in the chart's release instead, which a GitOps
  flow reviews less often.

- **D3. A sub-agent's control group.** On a host, the Warden makes
  `varek-<run>` under its own group, and makes `NAME-<n>` for each launch
  of a sub-agent. v1.34's step 1 measured on `kind` that the node can make
  a group under a container's group, move the container's process into it
  and back, and enable `pids` below it.
  - (a) The container's own group stands for the run's group. The
    supervisor makes each sub-agent's group under it, from the node's
    cgroup2 mount, and attributes each call by the calling thread's group,
    as on a host. Nothing is delegated to the pod, and the pod gets no
    capability.
  - (b) A group made inside the pod, through v1.32.1's bind remount. That
    needs CAP_SYS_ADMIN in the pod, which is what v1.34 exists to avoid.

  *Decided (a)* (October 26, 2026), to be measured first (step 1) under the systemd
  cgroup driver, which EKS's Amazon Linux 2023 nodes and OpenShift use,
  where the container's group is a systemd scope. The roadmap's "a
  delegated cgroup" is not needed if (a) holds: the supervisor writes from
  the node, not from the pod. Also to be measured: that the runtime still
  ends the container, sub-agents included, when its group has groups
  below it (on cgroup v2, `cgroup.kill` ends every group below; whether
  runc and crun use it is to be measured), and that the kubelet's
  accounting of the pod's resources is unchanged. *Measured* (M1, step
  1): (a) holds on CRI-O and containerd under systemd, with one rule
  found: the supervisor never moves the container's first process below
  the scope, or a process exec'd into the container lands in that
  sub-agent's group.

- **D4. Confined MCP servers.** A confined stdio server (v1.31) is a
  sub-agent with its own rules, so it comes with D3. A plan's `mcp_call`,
  `subagent` and `credential` steps (v1.35) are carried when their
  subjects are (D1, D3).
  - (a) All three plan kinds carried in v1.36, and the node agent's
    refusal of them (`node_plan_carried`) removed.
  - (b) As (a), but `mcp_call` to an unconfined stdio server stays
    UNKNOWN, as on a host.

  *Decided (b)* (October 26, 2026). It is (a) with the host's rule kept: a stdio
  server's calls are not decided on a host (v1.31.0's Known limits), so a
  step for one is UNKNOWN there too, and parity means the same answer on
  both.

- **D5. The on-behalf-of chain: the user's token and the agent's SVID.**
  On a host, the Warden is given the user's token by `--on-behalf-of
  FILE`, and the agent never holds it.
  - (a) The user's token is a Secret volume in the pod that no container
    mounts. The node agent reads it from the kubelet's directory for the
    pod (`/var/lib/kubelet/pods/<uid>/volumes/`), by the pod's uid from
    the container's state. The SVID comes from the node's SPIRE agent
    (its Workload API), attested as the pod.
  - (b) The token is a file in the agent's container, which the Warden
    refuses the agent to open.

  *Decided (a)* (October 26, 2026), to be measured first (step 1): that the kubelet
  mounts a volume no container names, and how SPIRE attests a pod to a
  process that is not in it. *Changed for the token* (October 26, 2026,
  after M2): the kubelet mounts no volume that no container names, so the
  Secret volume is mounted by an init container that VAREK's admission
  webhook adds to the pod. It mounts the volume read-only, runs `true`
  and ends before the agent's container starts. The kubelet keeps the
  volume on the node while the pod runs, out of the agent's container,
  and the node agent reads it there (M2b, measured on CRI-O and
  containerd). The SVID half holds as decided (M3): the node agent, an
  authorized delegate of the node's SPIRE agent, gets the pod's SVID by
  the pod's process id through the Delegated Identity API. In (b) the token sits in the pod's file
  system, where the pod's other containers can read it. As on a host, a
  run is on behalf of one user: a pod serves one chain, so a long-lived
  agent pod that serves many users is not carried. A Job for each task
  is.

- **D6. The dry run in a pod.** A dry run lets a refused call through and
  records it, so that `varek policy suggest` can write a policy. On a host,
  the agent's empty network namespace stops a refused connect. In a pod,
  the connect would reach the cluster's network: other pods, the API
  server, the instance metadata service.
  - (a) Carried, but a connect the policy refuses is refused in a dry run
    too, and recorded as a dry run's refusal, so suggest still sees it.
    Every other call is let through as on a host.
  - (b) Carried as on a host, the record saying that the connect reached
    the cluster's network.
  - (c) Not carried: dry runs on a host or in v1.32's image.

  *Decided (a)* (October 26, 2026). An agent whose policy is not yet written should not
  reach the cluster's network. An agent may behave differently when its
  connect fails, and the dry run's records say which connects were
  refused.

- **D7. Flow policies and trust bundles.** Both are refused by the node
  agent today. Neither is in the roadmap.
  - (a) Both carried in v1.36. The flow policy and the trust bundle are
    files the Warden reads at its start. Each would come from a cluster
    resource, as the policy does: a flow policy in the `VarekPolicy`, a
    trust bundle in a ConfigMap in VAREK's namespace named by the chart.
  - (b) Both stated as limits, carried later.

  *Decided (a)* (October 26, 2026), if step 1 shows each is only the input's plumbing.
  "At parity" with two refusals left would not be parity, and the release
  notes would have to say so. Step 1 (M5) showed it for trust bundles, and
  not for flow policies, whose breaker keeps state across runs (D7b).

- **D7b. A flow policy's breaker in a cluster** (added October 26, 2026,
  from step 1's M5).
  - (a) Carried, with the breaker kept on each node (a host path, as the
    streams are). The session is taken from the pod's namespace and
    service account, which the node agent reads from the container's
    state, never from an annotation the pod's author writes. The release
    notes say the budget bounds each node, not the cluster.
  - (b) Carried, with the breaker kept for the whole cluster: a resource
    the node agents update under optimistic concurrency, the gate failing
    closed when it cannot.
  - (c) Not carried in v1.36: a pod whose policy needs a flow policy is
    still refused, said in the release notes.

  *Decided (a)* (October 26, 2026). It is the host's model, one table per Warden's
  machine, with the session out of the pod's reach. (b) adds a write to
  the API server at every gated start, and a way for the gate to fail when
  the API server is slow. If a cluster-wide bound turns out to be needed,
  it can follow on (a)'s records.

- **D8. arm64.**
  - (a) The node image built natively on GitHub's arm64 hosted runners
    and published as one multi-architecture image. The DaemonSet placed
    on `amd64` and `arm64` nodes, and the suites run on the arm64 runner
    as on amd64.
  - (b) Built under QEMU emulation on the amd64 runners.

  *Decided (a)* (October 26, 2026). The suites must run on arm64, not only the build,
  and under QEMU they are slow and do not test the real kernel. v1.30's
  Graviton sweep fixed the host side already.

- **D9. An audit in bounded memory.** The audit (`tools/varek_audit.py`)
  reads the whole stream, then checks it.
  - (a) A one-pass audit. Its state is bounded by the policy's and the
    plan's size, not by the stream's: the hash chain, counters, and the
    few running tables the checks need (open launches, pending
    sub-agents, the plan's steps). A check that today looks back over the
    stream is restated as running state. The node agent rotates streams
    at a size the chart sets, and each segment's first record carries the
    previous segment's last hash, so the chain runs across files.
  - (b) Rotation only, each segment audited whole.

  *Decided (a)* (October 26, 2026). (b) bounds a file but not the audit: a check that
  spans segments would need them all again. The test is the ship gate's:
  a stream of over 1,000,000 records audited, its memory flat from the
  first record to the last, and the same verdict as today's audit on
  every stream in the suites.

- **D10. A key for each node.**
  - (a) Each node agent makes its own key at its first start and keeps it
    on the node (mode 0400, root's). It publishes the public key as a
    cluster-scoped `VarekNodeKey` named for its node. The webhook admits
    that write only from the node agent on that node, by the node's name
    in its bound service account token. The audit trusts a stream's key
    if it is the one listed for that stream's node, and the list goes out
    with the anchor.
  - (b) Each node's key signed by a cluster key, held by a signing
    service that VAREK runs in the cluster.
  - (c) As now: one Secret.

  *Decided (a)* (October 26, 2026). (b) adds a service holding a key that signs for
  every node, which is the same single key in a different place. In (a), a
  node that is taken over signs only as itself, and the list of keys is
  in the cluster's own records.

  *A rebuilt node's key, decided* (October 28, 2026): each key is its own
  `VarekNodeKey`, named for its node and the key. When a node's new key
  is admitted, the key before it is retired at the new one's
  `creationTimestamp`: a time the cluster sets, not the node. The audit
  trusts the old key only for runs that began before then. The time a
  run began is the anchor host's when the anchor holds the run's
  `run_start`; otherwise it is the node's own claim, and the audit says
  so. The other choices were to keep old keys trusted without limit (a
  stolen old key would go on signing for the node) or to refuse them at
  once (every stream they signed would have to be audited before the
  rebuild).

- **D11. The matrix, and what it costs.** This is the roadmap's open
  decision. GitHub's hosted runners are Ubuntu.
  - (a) On every pull request, on the hosted runners:
    - `kind` with containerd 2.2 and 2.3 (`kind` node images by version);
    - CRI-O 1.35, 1.36 and 1.37, each under runc and crun, on a one-node
      cluster made by kubeadm on the runner itself (no virtual machine);
    - amd64 and arm64.

    For each release, and for each pull request that touches the Warden,
    the node agent or the chart:
    - one node with SELinux enforcing;
    - the hosts (RHEL 9, Amazon Linux 2023, Ubuntu 24.04);

    each in a virtual machine on the runner if step 1 shows the runner
    allows nested virtualization (KVM), else on small cloud instances run
    for a few hours.
  - (b) All of it on cloud instances, for each release only.
  - (c) A self-hosted runner.

  *Decided (a)* (October 26, 2026). Most cells cost nothing, and the cells that need
  SELinux or a real host are the ones that found v1.34's faults, so they
  run before a release, not after. (c) puts a runner VAREK must keep up
  and secure into the release path. The cost of (a)'s cloud fallback is
  to be measured in step 2. It should be well under the ship gate's
  (about $25 for the day, plus a Graviton node).

- **D12. The version and the grammar.**
  - (a) The Warden reports 1.36.0. The grammar is unchanged: every carried
    feature is written as it is on a host. A pod that needs a feature
    carried only from v1.36 is refused by a 1.35 node agent during an
    upgrade, never run with less. `VarekCredential` (D2) and
    `VarekNodeKey` (D10) are cluster resources, not policy lines.
  - (b) A `require warden 1.36` for policies that use a newly carried
    feature.

  *Decided (a)* (October 26, 2026). A 1.35 node already refuses each of them (see the
  table above), so (b) would add a line that changes no outcome.

## Implementation plan

1. **Measure.** Each finding settles the parts marked *to be measured*.
   The runbook: `varek/v1_4/tests/measure_v1360/README.md` (October 26,
   2026), M1 to M4 as a workflow on GitHub's hosted runners, M5 and M6
   here, M7 (OpenShift) only if M1 leaves a doubt:
   - D3 under the systemd cgroup driver, on CRI-O 1.35 (single-node
     OpenShift) and containerd 2.2 (`SystemdCgroup = true`): a sub-agent's
     group under a container's, a call attributed by it, and the container
     ended with groups below its own;
   - D5: whether the kubelet mounts a Secret volume that no container
     names, and SPIRE's attestation of a pod's process to the node agent;
   - D7: what a flow policy and a trust bundle need beyond their input;
   - D11: kubeadm with CRI-O on a hosted runner, and KVM on a hosted
     runner;
   - D9: where the audit's 3.7 KB a record goes, check by check.

   **M5, measured** (October 26, 2026, Central; from the code, `warden.c`
   and `warden_trust.inc.c`):
   - **A trust bundle is its input only.** `--trust-bundle` is read once,
     by `trust_setup`, which runs in the supervisor before
     `node_supervise` enters the container's namespaces. So the file is
     read from the node, and the bundle is held in memory and served
     through the trust views from then on. Carrying it is plumbing: a file
     on the node (a ConfigMap mounted into the node agent) and a way to
     name it for a pod (a field of the `VarekPolicy`, not a policy line, as
     D12 keeps the grammar).
     Found on the way: without `--trust-bundle`, inspecting mode under the
     node agent takes the roots from the node agent's own image (the first
     of `kHostBundles` it finds), not from the agent's container. An agent
     whose image adds a company's CA loses it from the bundle the views
     serve. Carrying the trust bundle is the fix for that too, and the
     release notes should say so.
   - **A flow policy is not its input only.** `flow_setup` also opens a
     state directory (`/var/lib/varek` by default), a lock file and the
     breaker table. The table persists across runs, and counts a plan's
     refusals per plan and per session (`session_refusal_budget`, which the
     Warden requires). It is read and written at the gate, under the lock,
     at the run's start. On a host one Warden keeps one table. In a cluster
     each node would keep its own, so a pod scheduled on another node
     starts its counts again. The session has to come from somewhere the
     pod's author cannot choose: the threat model already says the breaker
     "bounds a host only if that host cannot choose" the session and the
     file. So D7 (a) does not hold for flow policies as written ("only the
     input's plumbing"), and returned for decision, as D7b below
     (decided (a) the same day). Trust bundles stay at D7 (a).

   **M6, measured** (October 26, 2026, Central;
   `tests/measure_v1360/m6_audit_memory.py`, here, x86_64). The Warden 1.35.0
   wrote a stream of 1,008,566 records (534 MB) in 103 s: an agent held to
   its plan, with allowed opens, opens the policy refuses (83,336), opens
   refused outside the plan (83,334) and 1,667 launches. `varek audit
   --plan` passed it in 93 s, its resident memory peaking at 3,629,356 kB:
   3.6 KB a record, v1.34's 3.7 KB. Where it goes:
   - **85% is the parsed stream itself.** `_parse_log` keeps every record
     as a Python dict for the whole audit: 3,084,872 kB, about 2.9 KB a
     record in objects, and its time is 53 of the 93 s.
   - **About 10% is the main loop's own lists** (the views, the proxy's
     hand-offs, the rows for the certificate checker, the cited lines),
     built in `main` between the checks: about 360 MB.
   - **The checks hold little.** The most any one adds while it runs is
     `check_requests` (132 MB at its peak, 31 MB kept), then
     `check_changes` (79 MB), `check_credentials` (61 MB), `check_chain` and
     `check_dry` (41 MB each). The other 30 functions add nothing
     measurable. What they hold is what they collect as they go (records
     by id, a launch's pending result, a connection's hand-off), not the
     stream. That is to be confirmed check by check when D9 is built.

   So D9 (a) holds. A one-pass audit that keeps each check's own running
   state, and drops each record once the checks have seen it, is bounded by
   that state, not by the stream. The work is `_parse_log` and `main`'s
   loop, rather than the checks one by one. Not measured: the certificate
   checker's memory (a process of its own, fed rows as it goes), and a mix
   with proxied requests and MCP calls, whose state `check_requests` keeps.

   **M4, M1 and M2, measured** (October 26, 2026, Central; the workflow
   `measure_v1360.yml`, run 40362696887 on GitHub's `ubuntu-24.04`
   runners, Linux 6.17, systemd 255, cgroup v2; Kubernetes 1.35.9 by
   kubeadm with the systemd cgroup driver):
   - **M4a and M4b: every cell comes up.** CRI-O 1.35.10, 1.36 and 1.37,
     each under runc and under crun, and containerd 2.2.10 and 2.3 under
     runc with `SystemdCgroup = true`: a Ready node in about 40 s and a
     running pod in about 50 s from nothing, on a hosted runner. So D11's
     matrix runs on hosted runners. Three things were ours to get right:
     CRI-O's own runc and crun (the runner's crun 1.14.1, podman's, never
     started the control plane), cri-tools (CRI-O's packages bring no
     crictl), and Kubernetes pinned to the cell's minor (the image's
     newer kubectl is downgraded).
   - **M4c** (run 40357754301): `/dev/kvm` is usable on a hosted runner,
     and a Fedora Cloud VM booted under KVM in 15 s with SELinux
     `Enforcing`. So D11 (a) holds: the matrix's SELinux cell is a VM on
     the runner.
   - **M1: D3 (a) holds under systemd**, on CRI-O 1.35.10 and containerd
     2.2.10, both with runc 1.5.2, the same on each. The container's group
     is a systemd scope (`crio-<id>.scope`, `cri-containerd-<id>.scope`).
     From the node: a group `varek-sub-1` made below it, the container's
     process moved into it, and `pids` enabled below; the kernel's cgroup
     id through a pidfd is `varek-sub-1`'s, as the Warden attributes a
     call; `systemctl daemon-reload` leaves the group where it was; the
     kubelet's working set counts 60 MB held below; and deleting the pod
     ends every process below and removes the scope and its groups.
     Found: a process started in the container (`kubectl exec`) while a
     controller is enabled below lands in `varek-sub-1`, the group of the
     container's first process, not in the scope, which may then hold no
     process of its own. So the supervisor never moves the container's
     first process below; only a sub-agent's launch goes below, and the
     first process and anything exec'd stay with the run. **The memory
     limit holds below** (run 40365721974, both runtimes): with
     `memory.max` 128 MiB and `memory.oom.group` 1 on the scope, a
     process moved below that went past the limit was killed with the
     whole container, which the kubelet reports as `OOMKilled` and
     restarts in a new group. So a sub-agent that runs out of memory ends
     the run, as one does on a host.
   - **M2: the kubelet mounts no volume that no container names**, on
     either runtime: only the service account's token. D5 (a) as written
     fails. **M2b**: the same Secret mounted by an init container that
     ends before the pod's container is on the node while the pod runs
     (tmpfs), its token matches, it is not in the pod container's mounts,
     and it is removed with the pod. D5's token half is changed to that
     (above).

5. **Sub-agents and confined MCP servers** (D3, D4).

   **As built** (October 27, 2026):
   - **The run's group is the container's own** (D3 (a)). The node
     agent's pod has a cgroup namespace of its own, so its cgroup
     filesystem does not show the container's group. The supervisor joins
     the node's cgroup namespace (by the node's init, `/proc/1/ns/cgroup`,
     which `hostPID` reaches; not needed where it is in the initial one
     already, told by its fixed inode), reads the container's group from
     its first process's `/proc/<pid>/cgroup`, and mounts the cgroup
     filesystem detached (`fsopen`, `fsmount`: `nosuid`, `nodev`,

     mount; neither the node's mounts nor the container's change. The
     container's group is neither made nor removed. Each sub-agent's
     `NAME-<n>` is made below it, or below its launcher's, with no
     controller enabled, and removed at the run's end, the deepest first.

     cgroup id through a pidfd (Linux 6.13), or its `/proc/<tid>/cgroup` as
     the node names it.

     sub-agent launched by that process itself is refused
     (`subagent_first_process`, after the refusals a host makes, so a
     threaded launcher is still `subagent_threaded`); one launched by any
     other process of the container runs. So a process started in the
     container later (`kubectl exec`) lands in the container's group, the
     agent's. An agent that `exec`s itself into a sub-agent, rather than
     starting one, does not run its sub-agent in a pod.

     node agent refuses anyway); a policy that could write `cgroup.procs`,
     `cgroup.threads`, `cgroup.freeze`, `cgroup.kill` or

     API.

6. **The on-behalf-of chain** (D5).

   **As built** (October 27, 2026):
   - **The user's token** is a Secret the pod names
     (`varek.dev/on-behalf-of: SECRET`, key `token`). The webhook's new
     mutating hook (`/pod-mutate`, a MutatingWebhookConfiguration, never
     reinvoked) gives a pod that names a policy and a Secret two things.
     One is a Secret volume, `varek-obo`, of that key alone. The other is
     an init container that alone mounts it: the node image, `/bin/true`,
     not root, no privilege, every capability dropped, a read-only root,
     the runtime's default seccomp profile. The validating hook holds the
     pod to what the mutating hook gave. A field it does not give (an
     environment, a lifecycle hook, `restartPolicy`, a writable mount) is
     refused. So is another container mounting the volume, including an
     ephemeral one added later (the pod hooks now get
     `pods/ephemeralcontainers` too). The annotation is fixed after the
     pod is created, as the policy's is. A pod naming no Secret under a
     policy that says `require on-behalf-of` is refused at deploy.
   - **The node agent reads the kubelet's copy** (M2b). The NRI plugin
     copies the Secret's name to each container's annotations, and removes
     one that a pod acting for no one carries. The node agent finds
     `pods/<uid>/volumes/kubernetes.io~secret/varek-obo/token` under
     `--node-kubelet` (the chart mounts the kubelet's `pods/` read-only
     with HostToContainer propagation, since the kubelet mounts each
     volume after the DaemonSet starts). The pod's uid is checked across
     the plugin's annotation and the runtime's own. The node agent
     resolves the volume and keeps the key's target inside it, and opens
     it `O_NOFOLLOW`. It must be a regular file of root's, at most 64 KiB.
     The node agent copies it to a file of its own (root's, 0600, in its
     socket's directory), because warden-secrets refuses a file others
     may read and the kubelet makes a Secret's files group-readable under
     `fsGroup`. That copy is passed as `--on-behalf-of` is on a host, and
     removed once warden-secrets has read it and when the supervisor ends.
     The plugin lets the init container through as it is: its name, its
     command alone, and its image (`-obo-image`, by digest or by the name
     the runtime resolves) where the runtime says it. It runs no agent.
   - **The agent's SVID** (M3) comes from `varek-svid`, a new helper in
     the node image. The node agent runs it for a policy that trusts a
     SPIFFE trust domain when it is given the SPIRE agent's admin socket
     (`--node-spire-socket`, the chart's `spire.adminSocket`). It asks the
     Delegated Identity API by the container's process id
     (`SubscribeToX509SVIDs`), leaves out the node agent's own ID
     (`--node-spire-self`, `spire.self`: M3's finding), and needs exactly
     one SVID left. Departure from M3, which took the SVID SPIRE gave: an
     entry selected by the DaemonSet's uid alone matches the pods'
     processes too, so the node agent's own is left out first. The one
     left is not checked against an expected ID here; warden-secrets
     verifies it against the policy's trust domain and bundle, as on a
     host. It writes the chain and key (PKCS #8) to a new file
     (root's, 0600), passed as `--agent-svid` is on a host and removed in
     the same way.
   - **What is now the node agent's**: `--on-behalf-of`, `--agent-svid`
     and `--on-behalf-of-expiry` given to the node agent itself are
     refused (exit 2: each pod names its own). `--oci-filter`, and so the
     plugin and the webhook, carries `require on-behalf-of`. A policy that
     says it under a pod naming no token is refused at the start
     (`node_fail`, a refusal with its reason). The token is verified as on
     a host. The issuer's CA comes from `onBehalfOf.issuerCaConfigMap`
     (`oidc_ca` in warden-secrets' configuration; `kube-root-ca.crt` for
     the cluster's own service account issuer). It and the SPIRE bundle
     are mounted as projected volumes: a ConfigMap's own volume is a
     directory on the node's disk that the kubelet makes writable by all,
     which warden-secrets refuses for a trust file's (the first kind run
     of this step). And warden-secrets now asks an issuer for
     `application/json, application/jwk-set+json`: the Kubernetes API
     server serves its keys as the key set's own type (RFC 7517) only, and
     answered 406 to a request for JSON alone (the second kind run;
     `test_v1281` now has a stand-in issuer route that does the same, 217
     pass). `run_start` names the user
     and the agent, and every decision is the user's, as on a host.
   - **SPIRE's attestation timing**: the node agent asks for the SVID as
     the container's first process starts. A Kubernetes workload attestor
     that also waits for the container's status (image or container-name
     selectors) can miss that moment, and the start is then refused. With
     `disable_container_selectors = true` it attests from the pod alone,
     by namespace, service account and labels. This is stated in the

9. **A key for each node** (D10).

   **As built** (October 28, 2026):
   - **The node agent's key.** `--node-key FILE` is the node agent's own
     signing key. At its first start the node agent makes it: an Ed25519
