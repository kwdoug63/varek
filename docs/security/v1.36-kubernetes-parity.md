# v1.36.0 — Kubernetes at parity, and the platforms VAREK supports (plan)

Status: **a draft for decision**, not built. Drafted October 25, 2026
(Central), during v1.35's 24-hour soak. Each decision below (D1 to D12)
has a recommendation, and none is decided yet. The roadmap entry is in
`docs/roadmap/v1.36-v1.37.md`. v1.36 starts after v1.35.0, except its CI
matrix (D11), which the roadmap has built during v1.35 because it is
v1.36's ship gate.

Ship gate (the roadmap's): every cell of the matrix green on the release
commit. Then 24 hours each on Amazon EKS (amd64 and Graviton nodes) and on
single-node OpenShift, under a policy that names a credential, a
sub-agent, a confined MCP server and a plan. Each node's stream is audited
under that node's own key, and a stream of over 1,000,000 records is
audited in fixed memory.

## What there was before v1.36

v1.34 put the Warden on a node, as a DaemonSet that supervises the agent
containers of annotated pods from outside them. v1.35 added plans to it
(its D11). The node agent refuses a pod whose policy or run needs what it
does not carry. The refusals are in `warden_node.inc.c`
(`node_unsupported`, `node_policy_why`, `node_plan_carried`). Today it
refuses a pod for any of these:

| What the pod needs | On a host since | Refused by the node agent as |
|---|---|---|
| Credentials (`credential NAME from ...`) | v1.28 | "credentials" |
| Sub-agents (`subagent=`) and the MCP servers confined by them | v1.28.1, v1.31 | "sub-agents" |
| `require on-behalf-of`, a user's token, an SVID | v1.28.1 | "the on-behalf-of chain" |
| A dry run | v1.29 | "a dry run" |
| A plan step of kind `mcp_call`, `subagent` or `credential` | v1.35 | "the node agent does not carry ... steps yet" |
| A flow policy (`--flow-policy`) | v1.18 | "a flow policy" |
| A trust bundle (`--trust-bundle`: the roots trusted in place of the host's) | v1.26.1 | "a trust bundle" |

The last two are not in the roadmap's list. They were found in drafting
this note, from the code, and D7 decides them.

Beyond these refusals, v1.34's Known limits leave four more things:

- The node image and the DaemonSet are amd64 only.
- The exporter audits each stream whole, about 3.7 KB of memory a record,
  so at most about 550,000 records. Streams are not rotated on the node.
- The node's signing key is one Secret given to every node.
- The supported runtimes are named, but CI runs only `kind` with
  containerd 2.3 and no SELinux. That is why step 9 of v1.34 found its
  three faults on OpenShift and not before (the roadmap lists them).

## What v1.36 gains, and what it does not

- **Parity:** every policy and every plan that runs on a host runs under
  the node agent, decided the same way. If something cannot be carried
  into a pod from outside, the pod is still refused, never run with less.
- **arm64:** the node image built for both architectures, and the
  DaemonSet placed on both.
- **An audit in bounded memory:** a stream of any length audited in fixed
  memory, and streams rotated on the node.
- **A key for each node:** one node's key cannot sign as another node.
- **The supported platforms, tested:** each runtime and host that the
  README calls supported is run in CI. What the matrix does not cover is
  not called supported.

It does not change a decision procedure, a rule or a record's meaning.
The Warden's grammar stays as it is (D12).

## The design in one paragraph

Each carried feature is the host's code, run by the supervisor that the
node agent forks for each container, with one change: where the host's
Warden takes an input from its command line or its own files, the
supervisor takes it from the node. It never takes it from the agent's pod,
so the agent never holds it. The inputs are a credential's value, a
user's token, an SVID, a trust bundle and a flow policy. A sub-agent's
control group is made by the supervisor from the node's cgroup tree,
under the container's own group, as v1.34's step 1 measured possible. The
supervisor opens what is the node's before it enters the container's mount
and network namespaces, as it does now for the policy, the signing key and
the stream. So it is the node's network, under the DaemonSet's identity,
that fetches a credential from Vault or AWS Secrets Manager. The
credential's value is swapped into the agent's request by the proxy in the
pod's network namespace, as on a host.

## Decisions before building

- **D1. Where a credential's value comes from.** On a host,
  `credential NAME from file:PATH | vault:... | aws-sm:...` is read by
  warden-secrets as the Warden's user.
  - (a) warden-secrets runs in the supervisor before it enters the pod's
    namespaces. `file:` names a path under one directory that the chart
    mounts into the node agent from Secrets in VAREK's own namespace,
    which the operator lists in the chart's values. `vault:` and
    `aws-sm:` are reached from the node's network, under the DaemonSet's
    identity (EKS Pod Identity or IRSA for AWS; Vault's Kubernetes auth
    with the node agent's service account). The NRI plugin sets the
    credential's placeholder in the container's environment, as v1.34's
    step 2 planned.
  - (b) The node agent reads the Kubernetes Secret named by the policy,
    from the pod's own namespace. That needs `get` on Secrets in every
    namespace.

  *Recommended: (a).* The value never enters the agent's pod or its
  namespace. The node agent's grant stays read-only and limited to its own
  namespace. (b) would let any policy's author reach any Secret on the
  cluster through VAREK.

- **D2. Who may name a credential.** A `VarekPolicy` is namespaced, so a
  team that may write policies in its namespace could name a credential
  that is another team's.
  - (a) A cluster-scoped resource, `VarekCredential`, names each
    credential's source and the namespaces whose policies may name it. The
    webhook refuses a policy that names a credential its namespace is not
    given, and the node agent refuses such a pod at the start, so a
    webhook that is down or bypassed is not enough.
  - (b) The chart's values hold the same list.
  - (c) Any policy may name any credential.

  *Recommended: (a).* A credential is given to a namespace by a cluster
  administrator, through the cluster's review flow, as policies are
  (v1.34's D7). (b) puts it in the chart's release instead, which a GitOps
  flow reviews less often.

- **D3. A sub-agent's control group.** On a host, the Warden makes
  `varek-<run>` under its own group, and makes `NAME-<n>` for each launch
  of a sub-agent. v1.34's step 1 measured on `kind` that the node can make
  a group under a container's group, move the container's process into it
  and back, and enable `pids` below it.
  - (a) The container's own group stands for the run's group. The
    supervisor makes each sub-agent's group under it, from the node's
    cgroup2 mount, and attributes each call by the calling thread's group,
    as on a host. Nothing is delegated to the pod, and the pod gets no
    capability.
  - (b) A group made inside the pod, through v1.32.1's bind remount. That
    needs CAP_SYS_ADMIN in the pod, which is what v1.34 exists to avoid.

  *Recommended: (a)*, to be measured first (step 1) under the systemd
  cgroup driver, which EKS's Amazon Linux 2023 nodes and OpenShift use,
  where the container's group is a systemd scope. The roadmap's "a
  delegated cgroup" is not needed if (a) holds: the supervisor writes from
  the node, not from the pod. Also to be measured: that the runtime still
  ends the container, sub-agents included, when its group has groups
  below it (on cgroup v2, `cgroup.kill` ends every group below; whether
  runc and crun use it is to be measured), and that the kubelet's
  accounting of the pod's resources is unchanged.

- **D4. Confined MCP servers.** A confined stdio server (v1.31) is a
  sub-agent with its own rules, so it comes with D3. A plan's `mcp_call`,
  `subagent` and `credential` steps (v1.35) are carried when their
  subjects are (D1, D3).
  - (a) All three plan kinds carried in v1.36, and the node agent's
    refusal of them (`node_plan_carried`) removed.
  - (b) As (a), but `mcp_call` to an unconfined stdio server stays
    UNKNOWN, as on a host.

  *Recommended: (b).* It is (a) with the host's rule kept: a stdio
  server's calls are not decided on a host (v1.31.0's Known limits), so a
  step for one is UNKNOWN there too, and parity means the same answer on
  both.

- **D5. The on-behalf-of chain: the user's token and the agent's SVID.**
  On a host, the Warden is given the user's token by `--on-behalf-of
  FILE`, and the agent never holds it.
  - (a) The user's token is a Secret volume in the pod that no container
    mounts. The node agent reads it from the kubelet's directory for the
    pod (`/var/lib/kubelet/pods/<uid>/volumes/`), by the pod's uid from
    the container's state. The SVID comes from the node's SPIRE agent
    (its Workload API), attested as the pod.
  - (b) The token is a file in the agent's container, which the Warden
    refuses the agent to open.

  *Recommended: (a)*, to be measured first (step 1): that the kubelet
  mounts a volume no container names, and how SPIRE attests a pod to a
  process that is not in it. In (b) the token sits in the pod's file
  system, where the pod's other containers can read it. As on a host, a
  run is on behalf of one user: a pod serves one chain, so a long-lived
  agent pod that serves many users is not carried. A Job for each task
  is.

- **D6. The dry run in a pod.** A dry run lets a refused call through and
  records it, so that `varek policy suggest` can write a policy. On a host,
  the agent's empty network namespace stops a refused connect. In a pod,
  the connect would reach the cluster's network: other pods, the API
  server, the instance metadata service.
  - (a) Carried, but a connect the policy refuses is refused in a dry run
    too, and recorded as a dry run's refusal, so suggest still sees it.
    Every other call is let through as on a host.
  - (b) Carried as on a host, the record saying that the connect reached
    the cluster's network.
  - (c) Not carried: dry runs on a host or in v1.32's image.

  *Recommended: (a).* An agent whose policy is not yet written should not
  reach the cluster's network. An agent may behave differently when its
  connect fails, and the dry run's records say which connects were
  refused.

- **D7. Flow policies and trust bundles.** Both are refused by the node
  agent today. Neither is in the roadmap.
  - (a) Both carried in v1.36. The flow policy and the trust bundle are
    files the Warden reads at its start. Each would come from a cluster
    resource, as the policy does: a flow policy in the `VarekPolicy`, a
    trust bundle in a ConfigMap in VAREK's namespace named by the chart.
  - (b) Both stated as limits, carried later.

  *Recommended: (a)*, if step 1 shows each is only the input's plumbing.
  "At parity" with two refusals left would not be parity, and the release
  notes would have to say so.

- **D8. arm64.**
  - (a) The node image built natively on GitHub's arm64 hosted runners
    and published as one multi-architecture image. The DaemonSet placed
    on `amd64` and `arm64` nodes, and the suites run on the arm64 runner
    as on amd64.
  - (b) Built under QEMU emulation on the amd64 runners.

  *Recommended: (a).* The suites must run on arm64, not only the build,
  and under QEMU they are slow and do not test the real kernel. v1.30's
  Graviton sweep fixed the host side already.

- **D9. An audit in bounded memory.** The audit (`tools/varek_audit.py`)
  reads the whole stream, then checks it.
  - (a) A one-pass audit. Its state is bounded by the policy's and the
    plan's size, not by the stream's: the hash chain, counters, and the
    few running tables the checks need (open launches, pending
    sub-agents, the plan's steps). A check that today looks back over the
    stream is restated as running state. The node agent rotates streams
    at a size the chart sets, and each segment's first record carries the
    previous segment's last hash, so the chain runs across files.
  - (b) Rotation only, each segment audited whole.

  *Recommended: (a).* (b) bounds a file but not the audit: a check that
  spans segments would need them all again. The test is the ship gate's:
  a stream of over 1,000,000 records audited, its memory flat from the
  first record to the last, and the same verdict as today's audit on
  every stream in the suites.

- **D10. A key for each node.**
  - (a) Each node agent makes its own key at its first start and keeps it
    on the node (mode 0400, root's). It publishes the public key as a
    cluster-scoped `VarekNodeKey` named for its node. The webhook admits
    that write only from the node agent on that node, by the node's name
    in its bound service account token. The audit trusts a stream's key
    if it is the one listed for that stream's node, and the list goes out
    with the anchor.
  - (b) Each node's key signed by a cluster key, held by a signing
    service that VAREK runs in the cluster.
  - (c) As now: one Secret.

  *Recommended: (a).* (b) adds a service holding a key that signs for
  every node, which is the same single key in a different place. In (a), a
  node that is taken over signs only as itself, and the list of keys is
  in the cluster's own records. To be decided with (a): what a node's new
  key means after it is rebuilt (a new `VarekNodeKey`, the old one kept
  for the streams it signed).

- **D11. The matrix, and what it costs.** This is the roadmap's open
  decision. GitHub's hosted runners are Ubuntu.
  - (a) On every pull request, on the hosted runners:
    - `kind` with containerd 2.2 and 2.3 (`kind` node images by version);
    - CRI-O 1.35, 1.36 and 1.37, each under runc and crun, on a one-node
      cluster made by kubeadm on the runner itself (no virtual machine);
    - amd64 and arm64.

    For each release, and for each pull request that touches the Warden,
    the node agent or the chart:
    - one node with SELinux enforcing;
    - the hosts (RHEL 9, Amazon Linux 2023, Ubuntu 24.04);

    each in a virtual machine on the runner if step 1 shows the runner
    allows nested virtualization (KVM), else on small cloud instances run
    for a few hours.
  - (b) All of it on cloud instances, for each release only.
  - (c) A self-hosted runner.

  *Recommended: (a).* Most cells cost nothing, and the cells that need
  SELinux or a real host are the ones that found v1.34's faults, so they
  run before a release, not after. (c) puts a runner VAREK must keep up
  and secure into the release path. The cost of (a)'s cloud fallback is
  to be measured in step 2. It should be well under the ship gate's
  (about $25 for the day, plus a Graviton node).

- **D12. The version and the grammar.**
  - (a) The Warden reports 1.36.0. The grammar is unchanged: every carried
    feature is written as it is on a host. A pod that needs a feature
    carried only from v1.36 is refused by a 1.35 node agent during an
    upgrade, never run with less. `VarekCredential` (D2) and
    `VarekNodeKey` (D10) are cluster resources, not policy lines.
  - (b) A `require warden 1.36` for policies that use a newly carried
    feature.

  *Recommended: (a).* A 1.35 node already refuses each of them (see the
  table above), so (b) would add a line that changes no outcome.

## Implementation plan

1. **Measure.** Each finding settles the parts marked *to be measured*:
   - D3 under the systemd cgroup driver, on CRI-O 1.35 (single-node
     OpenShift) and containerd 2.2 (`SystemdCgroup = true`): a sub-agent's
     group under a container's, a call attributed by it, and the container
     ended with groups below its own;
   - D5: whether the kubelet mounts a Secret volume that no container
     names, and SPIRE's attestation of a pod's process to the node agent;
   - D7: what a flow policy and a trust bundle need beyond their input;
   - D11: kubeadm with CRI-O on a hosted runner, and KVM on a hosted
     runner;
   - D9: where the audit's 3.7 KB a record goes, check by check.
2. **The matrix** (D11), first, so that every later step runs on it.
   The README gets the table of supported platforms, and each cell links
   to its CI job.
3. **arm64** (D8): the image, the DaemonSet, the suites on the arm64
   runner.
4. **Credentials** (D1, D2): warden-secrets in the supervisor,
   `VarekCredential`, the webhook's and the node agent's checks, and the
   placeholder set by the NRI plugin.
5. **Sub-agents and confined MCP servers** (D3, D4).
6. **The on-behalf-of chain** (D5).
7. **The dry run, flow policies and trust bundles** (D6, D7), and the
   plan's remaining kinds (D4). After this step, `node_unsupported`
   refuses nothing that a host runs.
8. **The audit in bounded memory and the rotation** (D9).
9. **A key for each node** (D10).
10. **Tests:** `test_v1340`'s node sections extended for each carried
    feature, the sweep against a supervised container, and the regression
    count against v1.35.0.
11. **Review by AI review agents**, the fixes, and the release notes
    (draft).
12. **The ship gate's runs:** EKS (amd64 and Graviton node groups in one
    cluster) and single-node OpenShift, 24 hours each.
