# v1.28.0 — credential release: the agent holds only placeholders (plan)

Status: **in progress**, target **v1.28.0**. Decided 2026-10-12: the
recommendation for each decision below (D1 to D7). Built: steps 1 to 3
(see "As built"). Each section ends with what must be tested before it ships. The roadmap entry is in
`docs/roadmap/v1.28-v1.31.md`.

## What v1.27.1 leaves open

An agent that calls an API needs its credential: an API key, a bearer
token, a cloud secret. Today the operator puts that credential where the
agent can read it (its environment, a file the policy lets it read). From
then on the credential is the agent's. The Warden decides which hosts, and
in inspecting mode (v1.26.1) which methods, paths and queries, the agent
may reach, but a credential the agent holds can be:

- sent to any request the policy allows, including one the operator did
  not mean it for (the same host, another path);
- written into a file, a query or a body, and so into any allowed
  channel;
- kept and used after the run, from anywhere, since a secret that has
  been read cannot be taken back.

## What it gains, and what it does not

With credential release, the agent holds a **placeholder** for each
credential, made fresh for the run. The real value is put into a request
only by the egress proxy, after the Warden has decided that request
SATISFIED, and only where the deciding rule says it may go. So:

- **The secret never enters the agent's process.** Nothing the agent
  writes, sends or keeps can carry it; a placeholder outside its run, or
  outside the request it was meant for, is a meaningless string.
- **A credential is used only for a decided action.** "The agent called
  the API with the key" now means a request the Warden decided, certified
  and recorded, on the host, method and path a rule names.
- **Revocation is real.** The run can be revoked: every later decision is
  UNSATISFIED, and the proxy forgets every value it holds.

It does not:

- stop the server the request goes to from echoing the credential back
  (an endpoint that returns the request's headers); the rule must not
  allow such an endpoint (Known limits);
- protect a credential the operator also puts where the agent can read it;
- recall a request already sent.

## Why the proxy

The swap has to happen where the request head is in clear text after the
Warden's decision and before the server sees it. In inspecting mode that
is `warden-proxy`: it terminates the agent's TLS with the run's CA, holds
each request until the Warden answers (`WP_MSG_HTTPREQ`,
`WP_MSG_REQVERDICT`), and only then writes the head to the server. The
Warden does not link OpenSSL and never sees a request's headers; the agent
never sees the server's side of the connection. A credential can
therefore be added where nothing else can see it: in the proxy, between
the verdict and the write.

## The design in one paragraph

Under `require warden 1.28` a policy names each credential and its store,
and a request rule names the credential it may carry and the header it
goes in. At startup a small new helper, `warden-secrets`, fetches each
value from its store (a file the operator owns, HashiCorp Vault, or AWS
Secrets Manager) and hands it to `warden-proxy` over a private socket; the
Warden records each credential's name and store version, never its value.
The agent's environment gets one placeholder per credential, a random
token made for the run. When the Warden allows a request whose rule names
a credential, its verdict tells the proxy which; the proxy finds the
placeholder in that header, alone and exactly, replaces it with the
value, and writes the head. A placeholder anywhere else is sent as it is.
`varek revoke` ends all of it for a run.

## 1. Policy

```
require warden 1.28
proxy on
proxy inspect
credential openai from file:/etc/varek/creds/openai
credential github from vault:secret/data/agents/github#token
credential stripe from aws-sm:arn:aws:secretsmanager:us-east-1:111122223333:secret:stripe-AbCdEf
allow host api.openai.com:443
allow request POST https://api.openai.com/v1/chat/completions credential=openai header=Authorization:Bearer
allow request GET https://api.github.com/repos/acme/** credential=github header=Authorization:token
```

- `credential NAME from STORE:REF` names a credential. Names are
  `[a-z][a-z0-9_]{0,31}`, each once.
- `credential=NAME header=HEADER[:SCHEME]` on an **allow** request rule:
  the request may carry that credential, in that header, after that
  scheme word (`Authorization: Bearer <value>`). Without `:SCHEME` the
  value is the whole header value (`X-Api-Key: <value>`).
- Refused at load: a credential no rule uses (a warning), a rule naming an
  unknown credential, `credential=` on a deny rule, `credential=` on a host
  that is not inspected (a passthrough host, or `proxy inspect` off), a
  header that is a framing header (`Host`, `Content-Length`,
  `Transfer-Encoding`, `Connection`), and a credential under `require
  warden` below 1.28.
- The three parsers (decision procedure, certificate checker, cross-check
  oracle) read the new clauses and must agree, as for `require warden
  1.27`; the Warden refuses to start if they do not.

*Tests:* each form and each refusal in the three parsers; a 1.27 policy
with a credential refused; `varek policy check` and lint.

## 2. Fetching: `warden-secrets`

- A separate binary, like `warden-proxy`: the Warden opens it at startup,
  records its SHA-256 in `run_start`, and starts it with `fexecve`. It
  links OpenSSL (for Vault and AWS over HTTPS); the Warden still does not.
- It runs under its own user, non-dumpable, with no capabilities, and
  holds the credentials it needs for the stores themselves (a Vault token
  or AppRole file, the host's AWS role), which the agent cannot read.
- **Stores:**
  - `file:PATH`: a file owned by root, mode 0600 or 0400, not under any
    path the policy lets the agent open (the start is refused if it is).
  - `vault:PATH#FIELD`: a KV v2 read, or a dynamic secret with a lease.
  - `aws-sm:ARN`: `GetSecretValue`, the version id recorded.
- Each value is fetched at startup; the start is refused if one cannot
  be. A dynamic secret is renewed before its lease ends.
- Values go to `warden-proxy` over a socket pair the Warden makes, never
  through the Warden. Neither process writes a value anywhere.

*Tests:* each store against a local test server (a Vault dev server; an
AWS endpoint stand-in); a store that fails refuses the start; a file store
the policy lets the agent read refuses the start; neither helper's memory
nor files are reachable from the agent.

## 3. Placeholders and the swap

- **The placeholder.** For each credential, 32 random bytes from the
  kernel, as `varek_ph_<name>_<base64url>`, made at startup and never
  reused. The agent's environment gets `VAREK_CRED_<NAME>` (upper case) set
  to it. The Warden records each placeholder's SHA-256 (it is not secret;
  the hash lets the audit link it to a run without keeping it).
- **The verdict.** `WP_MSG_REQVERDICT` gains the credential's index and the
  header and scheme from the deciding rule. A request no credential rule
  allows gets none.
- **The swap.** In the request head, the proxy looks for the named header.
  It must occur once, and its value must be exactly `SCHEME placeholder`
  (or the placeholder alone). Then the value replaces the placeholder and
  the head is written. If the header is missing, repeated, or holds
  anything else, the request is refused (`credential_mismatch`) and nothing
  is sent. The value is checked once, at fetch, to contain no CR, LF or
  NUL.
- **Everywhere else** a placeholder is just bytes: in another header, the
  query, the body, a request to another host, or a request whose rule
  names no credential, it is sent unchanged.
- **Memory.** The proxy holds each value in `mlock`ed memory, writes it
  only into the outgoing head buffer, and clears that buffer after the
  write.

*Tests:* the swap with and without a scheme; each refused shape (missing,
repeated, extra text, the wrong placeholder, another credential's); a
placeholder in a query, a body and another header sent unchanged; a
redirect to another host carrying the header gets no value; a server that
logs what it receives sees the value only where a rule allowed it.

## 4. Revocation

- `varek revoke <run>` (and `--all`) writes to a root-only control socket
  the Warden opens for the run (`/run/varek/<run>.ctl`).
- On revocation the Warden records `revoked` (who asked, when), answers
  every later mediated call UNSATISFIED (`rule: revoked`), and tells the
  proxy to clear every value it holds; the proxy refuses every later
  request. `warden-secrets` revokes the run's Vault leases.
- What is already sent stays sent. Revocation does not end the run: the
  agent goes on, held to refusals, and the run ends as it would.

*Tests:* revocation in mid-run: the next file open, connect and request
are refused and recorded; the proxy's memory no longer holds the values
(checked through a test hook); a Vault lease is revoked; a revoke for a
run that has ended, or by a user who is not root, is refused.

## 5. Records, audit and tools

- `run_start` gains `credentials`: each name, store kind, reference,
  version (Vault's version or lease id, AWS's version id, a file's
  inode and modification time), the placeholder's SHA-256,
  and `warden-secrets`'s SHA-256. Never a value.
- Each `net.request` that carried a credential records its name and
  header. A refused swap is `credential_mismatch`.
- `varek_audit.py`: every credential a request carried is one its
  deciding rule names, on an inspected connection, and none after
  `revoked`; every decision after `revoked` is UNSATISFIED; the credential
  list matches the policy.
- `varek refusals` explains `credential_mismatch` and `revoked`; the
  CycloneDX export carries `varek:credentials.*`; `varek doctor` and the
  preflight check each store can be reached (as root); `varek policy show`
  lists credentials and the rules that use them.

*Tests:* forged streams the audit must refuse (a credential on a rule that
names another, on a passthrough connection, after `revoked`; an allowed
decision after `revoked`); the tools' outputs.

## 6. Cost and real traffic

The swap is a search of one header in a head of at most 8 KB; it should
not show beside the request round trip. Fetching adds startup time per
store. To measure: `varek bench --proxy` with and without a credential; a
24-hour soak with real requests carrying a credential to a local server
that checks it, a probe sending the placeholder where no rule allows it
(the server must see the placeholder, never the value), and a revocation.

## Ship gates

- `make test-v1280`: sections 1 to 5, and a regression count against
  v1.27.1.
- The earlier suites pass unchanged (or each change is explained).
- `make crosscheck` with credential clauses, 0 disagreements.
- A 24-hour soak on the droplet.
- A review by AI review agents, including one that tries to get the value
  into the agent's process or the stream.

## Decisions before building

- **D1. Scope.** (a) Credential release and revocation in v1.28.0, the
  delegation chain (OAuth token exchange, SPIFFE IDs, the on-behalf-of
  chain in every verdict) in v1.28.1; (b) all three in v1.28.0.
  *Recommended: (a).* The delegation chain is its own identity design;
  together they would double the release.
- **D2. The first stores.** (a) File, HashiCorp Vault, AWS Secrets
  Manager; (b) file only, the others in a patch release. *Recommended:
  (a)*: the roadmap names Vault and Secrets Manager, and a file store alone
  would not meet a real deployment. Keycard and other stores later, behind
  the same interface.
- **D3. Who fetches.** (a) A new helper, `warden-secrets`; (b) the proxy
  fetches; (c) the Warden fetches. *Recommended: (a).* The Warden does not
  link OpenSSL and should not; the proxy faces the agent's connections and
  should not also hold the credentials for the stores.
- **D4. Where a value may go.** (a) Only into a header the rule names, in
  place of the placeholder; (b) also queries and bodies. *Recommended:
  (a).* A query is recorded in the stream as sent, and a body cannot be
  rewritten without changing its length and hash.
- **D5. A server that echoes the value back.** (a) A known limit, and the
  policy author's to avoid; (b) scan responses for the value and refuse.
  *Recommended: (a).* A scan cannot see through compression or an encoded
  echo, so it would promise more than it holds.
- **D6. After revocation.** (a) The run goes on with every decision
  UNSATISFIED; (b) the Warden ends the run. *Recommended: (a)*, which keeps
  the record of what the agent tried after it; the operator can still stop
  the run.
- **D7. The version.** The Warden reports `1.28.0`; the grammar becomes
  1.28 (`require warden 1.28`; `1.29` refused).

## Implementation plan

1. **Grammar** (done) in the three parsers, lint and `policy check`; the
   version. Tests of section 1.
   As built:
   - The decision procedure (`smt_decide.c`), the certificate checker
     (`checker/vdp_checker.c`, written separately) and the cross-check
     oracle (`tools/smt_crosscheck.py`) read `credential NAME from
     STORE:REF` and `credential=NAME header=HEADER[:SCHEME]` to one
     definition, in `smt_decide.h`: a name of `[a-z][a-z0-9_]{0,31}`, at
     most 32; a reference of 1 to 1,024 printable ASCII bytes; `file:` an
     absolute path with no `.`, `..` or empty segment; `vault:` one `#`
     between a path not starting with `/` and a field of letters, digits,
     `_`, `.` and `-`; `aws-sm:` an ARN holding `:secretsmanager:`; a header
     and scheme each an HTTP token (64 and 32 bytes at most). A credential
     must be named before a rule uses it.
   - Framing headers refused for a credential: `Host`, `Content-Length`,
     `Transfer-Encoding`, `Connection`, and also `Upgrade`, `TE`,
     `Trailer`, `Keep-Alive`, `Proxy-Connection` and
     `Proxy-Authorization` (the plan named the first four).
   - Each C tool has a `credentials` mode printing what its parser read;
     the cross-check compares both with the oracle on every policy, and its
     generator now writes credentials and credential rules, valid and
     malformed. Lint notes a credential no rule carries.
   - The Warden compares the two C parsers' credentials and each rule's
     credential, header and scheme at load and refuses to start if they
     differ. Until steps 2 and 3, it refuses to start a policy that names a
     credential at all ("credential release is not built in this Warden
     yet"): fail closed.
   - Version: the Warden reports `1.28.0`; the grammar is 1.28 and `require
     warden 1.29` is refused (D7). The earlier suites' checks that a later
     grammar is refused move from 1.28 to 1.29, and their checks of this
     Warden's own version accept 1.27 or later.
   - `make test-v1280` section 1 (45 checks); in CI.
2. **`warden-secrets`** (done) and the three stores; startup and
   refusals. Tests of section 2.
   As built:
   - `warden_secrets_helper.c` (the binary, linking OpenSSL) and
     `warden_secrets.c` (the Warden's side, linking none); the messages are
     in `warden_secrets.h`. The Warden loads the binary into a sealed,
     hashed copy (as `warden-proxy`), starts it through an intermediate so
     it is not the Warden's child, and gives it the configuration's path
     and each credential's store and reference. No message carries a
     value: the helper answers with each credential's version and length,
     the local files it read, and a ready message whose SCM_CREDENTIALS
     prove its user.
   - As root it reads only files: its configuration (`--secrets-conf`,
     default `/etc/varek/secrets.conf`; `vault_addr`, `vault_token_file`,
     `vault_ca`, `aws_region`, `aws_endpoint`, `aws_ca`,
     `aws_credentials_file`, `aws_imds`), the Vault token, the AWS key
     file and each file store, each a regular file owned by root and
     readable by no group or other user. Then it drops to its own user
     (`--secrets-as`, default `varek-secrets` or 65531:65531, never the
     agent's or the proxy's; no groups, no capabilities,
     no-new-privileges, not dumpable) and fetches over HTTPS, verified
     against the host's trust store or the CA the configuration names
     (which its own user must be able to read). Plain HTTP only to a
     loopback address or to the instance metadata service.
   - Vault: KV version 2 (`kv2:N`), version 1 (`kv1`) and a leased secret
     (`lease:<id>`). AWS: `GetSecretValue` signed with SigV4, from a key
     file or the instance's role through IMDSv2 (`aws:<version id>`); only
     `SecretString`. A file: its inode and mtime. A value is 1 to 8,192
     bytes with no CR, LF or NUL (it goes in one header); one trailing
     newline in a file or token file is dropped.
   - Values sit in one `mlock`ed, `MADV_DONTDUMP` arena and are cleared
     when the control socket closes, which happens when the Warden exits;
     the transient buffers that held them are cleared too. OpenSSL's own
     buffers are not under the helper's control: a copy may remain in its
     freed memory until reused (the process is not dumpable, and runs as
     its own user).
   - The Warden refuses to start when a fetch fails (naming the credential
     and the reason), when the policy would let the agent open any file the
     helper read (`vdpc_path_openable`, after `realpath`), or when the
     helper does not prove its user. `--check-startup` lists the
     credentials and fetches nothing.
   - Renewing a leased secret before its lease ends came with revocation
     (step 4); handing the values to `warden-proxy` with step 3.
   - `tests/v1280_stores.py`: stand-ins for Vault (KV 2, KV 1, a lease, a
     chunked answer), AWS Secrets Manager (checking each request's SigV4
     signature with its own implementation) and IMDSv2, over HTTPS with a
     CA made for the test. `make test-v1280` section 2 (30 checks): each
     store, the version recorded, no value in the Warden's output, the
     helper gone after the Warden, its user, and 18 refusals. CI installs
     `python3-cryptography` for it.
3. **Placeholders and the swap** (done) in the Warden's environment for
   the agent and in `warden-proxy`. Tests of section 3.
   As built:
   - Placeholders: `varek_ph_<name>_` and 32 random bytes in URL-safe
     base64 (55 bytes for a two-letter name), made by the Warden at
     startup, in the agent's environment as `VAREK_CRED_<NAME>`; their
     SHA-256 is kept for `run_start` (step 5).
   - The values go from `warden-secrets` to `warden-proxy` over a socket
     pair the Warden makes and only passes on (one end to each,
     SCM_RIGHTS); the helper clears its copies once they are written. The
     proxy keeps them in memory it locked while still root (locked pages
     stay locked after the drop), out of any dump, and tells the Warden it
     holds all of them, or none: then the start is refused.
   - On an allowed request whose deciding rule names a credential, the
     verdict carries its index, header and scheme, and the request record
     carries `credential` and `credential_header`. In the head, the header
     (its name in any case) must occur once and hold exactly the scheme
     (in any case), one space and the placeholder, or the placeholder
     alone, with spaces or tabs around it; then the placeholder's bytes are
     replaced in place (the buffer grows once if the value is longer; what
     follows the head in the buffer, a body or a pipelined request, moves
     with it). Anything else refuses the request with a 403, sends nothing
     to the server, and is recorded as `credential_refused` with why; the
     connection takes no more requests.
   - Bytes that held a value are cleared once sent, and the buffer when it
     is freed.
   - **Added beyond the plan:** a credential rule must be `https://`: all
     three parsers refuse `credential=` on an `http://` rule, so a value is
     never written in the clear.
   - `make test-v1280` section 3 (15 checks), with a TLS server that logs
     what it receives: a value longer and one shorter than its placeholder,
     a scheme in another case, the body after the head intact, five refused
     shapes (no header, twice, another credential's placeholder, extra
     text, no scheme), placeholders elsewhere sent as they are, and no
     value in the agent's environment or the verdict stream. Section 1
     gains the `http://` refusal; section 2's runs now go on to the proxy
     holding the values.
   - The cross-check (`tools/smt_crosscheck.py`, whose generator writes
     credentials and credential rules, valid and malformed): four batches
     of 400 generated policies, the last with the `https://` rule, 0
     disagreements among the three parsers.
4. **Revocation** (done): the control socket, `varek revoke`, the proxy's
   clear, Vault leases. Tests of section 4.
   As built:
   - When it runs as root, the Warden opens `/run/varek/<run>.ctl` (a
     sequenced-packet Unix socket, 0600, in a directory it makes 0700; both
     root's) and says so at the start: `[warden] revocation: varek revoke
     <run>`. It is closed and removed when the run ends. Without root, or
     without `/run/varek/`, the run starts and the Warden says it cannot be
     revoked.
   - `varek revoke <run>` (a run id, or a running run's verdict log) and
     `varek revoke --all` need root. The kernel refuses a connection from
     any other user (the directory), and the Warden refuses a peer that
     `SO_PEERCRED` does not name as uid 0. A run that has ended, or never
     was, has no socket: refused, exit 1.
   - On `revoke` the Warden records `revoked` (`by_uid`, `by_pid`) and from
     then on refuses every mediated call with rule `revoked`: in the
     supervision loop before anything else, and in the decision itself, so
     the proxy's name and request decisions are refused too.
   - `warden-proxy` clears every value and placeholder, closes every
     connection it holds (`proxy_close`, why `revoked`), and refuses every
     later swap; it answers with the number of value slots in its locked
     memory that still hold a byte other than zero (it scans them),
     recorded as `revocation_proxy` (`values_held`, 0).
   - `warden-secrets` keeps the Vault token, in its locked arena, only
     while the run holds a lease. On revocation it revokes each lease
     (`PUT /v1/sys/leases/revoke`), then clears the token; recorded as
     `revocation_leases` (`revoked`, `failed`).
   - Renewal: a renewable lease is renewed at two thirds of its duration
     (`PUT /v1/sys/leases/renew`, the same increment), recorded as
     `lease_renewed` (the new `ttl`) or `lease_renewal_failed` (why).
   - Limits: what was sent stays sent; a connection the agent opened
     outside the proxy before the revocation stays open (later connects are
     refused); a renewal Vault refuses is recorded and not retried, and the
     secret is not fetched again, so the value lapses when Vault says;
     leases are not revoked when a run ends without `varek revoke` (they
     end at their duration, no longer renewed).
   - `make test-v1280` section 4 (24 checks): a run revoked in mid-run;
     before it a request with its credential and a file open are allowed;
     after it the connection the proxy held is closed and its request never
     reaches the server, a file open and a connect are refused and recorded
     with rule `revoked`; `revoked`, `revocation_proxy` (0 held),
     `proxy_close` (`revoked`) and `revocation_leases` (2, 0 failed) are
     recorded; the stand-in got both lease revokes with the token; a lease
     renewed (increment and new duration 3 s), one whose renewal Vault
     refuses (recorded once, not retried), and no renewal after the
     revocation; the agent goes on to finish; `varek revoke` by a user who
     is not root, a raw connection by one, a run that has ended and one
     that never was, all refused; `--all` answers "already revoked". The
     audit accepts the revoked run as it stands (its checks of revocation
     are step 5).
5. **Records, audit and tools.** Section 5.
6. **Tests and the regression count** against v1.27.1 (`make test-v1280`).
7. **Soak and latency.** A trial and 24 hours on the droplet; `varek bench
   --proxy` with credentials.
8. **Review by AI review agents**, fixes, README, threat model, spec paper,
   release notes.
