# v1.36.3: confirming the container a connection names (design note)

**Status:** For decision. Measured November 4 (below); nothing of the fix is built. It answers the first of the
three items left open after v1.36's runs
(`docs/security/v1.36-kubernetes-parity.md`, step 12, "Open after the runs,
for v1.37") and section 4's first item of
`docs/roadmap/production-readiness.md`.
**Author:** Kenneth Wayne Douglas, MD
**Last updated:** November 4, 2026 (Central)

## The finding

When a runtime starts a container under VAREK's filter, it connects to the
node agent's socket and sends two things: the filter's descriptor, and the
container's state (OCI's container process state, JSON). The node agent
checks who sent them and which process the descriptor is for
(`node_admit`, `node_tie` in `varek/v1_4/warden_node.inc.c`). It does not
check that the rest of the state is that process's. Everything else it
takes from the state, as the sender wrote it (`node_state`, `node_policy`,
`node_plan`, `node_inputs`):

- the container's **id**, which names its stream, and the root-only files
  of its user's token and its SVID;
- its **bundle**, whose `config.json` gives the command it launches and the
  credential placeholders in its environment (`node_config`);
- the **annotations**: the pod's namespace, name and uid, the container's
  name, the policy's name and SHA-256, the plan's, the on-behalf-of
  Secret, the dry run, the trust bundle, the flow policy's SHA-256 and the
  service account.

So the policy a process is held to, the identity its stream is signed
under, the credentials released for it and the user token read for it all
come from the sender's word.

That was safe while the sender was always the runtime. Through v1.35 the
node agent took a connection only from a root process running where the
runtime runs (in the node agent's user, PID and mount namespaces), or from
a runtime that had ended leaving a root parent there. v1.36's step 12
added two ways for a container's runtime to be taken without being read,
both found on the matrix (runc 1.2 creating a container in a mount
namespace of its own; crun under CRI-O reaped by conmon at once):

1. a peer **in a mount namespace of its own**, root, in the node agent's
   user and PID namespaces, whose parent is root where the runtime runs;
2. a peer **already reaped** when the node agent reads it, where the
   process the state names has a root parent where the runtime runs.

In both, the kernel ties the descriptor to the process the state names:
the first call on that listener must come from that process (`node_tie`).
That shows which process the listener is for. It does not show which
container that process is, so the bundle and annotations are still the
sender's.

**Who can use it.** A process that can connect to the node agent's socket
(`node.sock`, in a root-only directory on the node), as root. Root on the
node can do this and much else, and is outside VAREK's threat model. The
case that matters is weaker: **a pod allowed a hostPath of the socket's
directory, running as root**, without `hostPID`. Through the second path,
such a pod can have a process of its own supervised as another pod's
container: held to **the other pod's policy**, its stream signed as **the
other pod's container**, with **the credentials given to the other pod's
namespace** and **the other pod's user token** (on-behalf-of), read by the
pod uid it names. The steps are kept out of this note until the fix is
released (`SECURITY.md`, coordinated disclosure); the test that shows them
is D7's, added with the fix.

**Rating** (`SECURITY.md`): **High**. A pod held to another pod's policy
and identity, with another pod's credentials, needing a precondition (a
hostPath of the socket's directory, as root).

**Affected:** v1.36.0 to v1.36.2, by reading. v1.35.0 is to be confirmed by
the test below (D7): its refusal of a reaped peer whose parent was not read
suggests it is not.

## What can confirm the container

| Source | Who writes it | Can the sender change it |
|---|---|---|
| The state's JSON | the sender | Yes: it is the sender's word |
| The process's **cgroup** (`/proc/<pid>/cgroup`) | the kernel, placed there by the runtime before the container's process runs | Only with write access to the node's cgroup filesystem, which a pod does not have (it is mounted read-only in containers) |
| The **bundle's path** | the runtime, under its own state directory, named by the container's id | No, once the id is confirmed |
| The bundle's **`config.json`** | the runtime, root-owned, from the pod's spec and the NRI plugin's adjustments; the OCI state's annotations are a copy of its | No |
| A record from the **NRI plugin**, written as it adjusts the container | the plugin, in a root-only directory it shares with the node agent | No; but it is the same author as `config.json`'s annotations, by another channel |

Under both cgroup drivers, the container's own cgroup names its id, and
the pod's names the pod's uid:

- systemd: `…/kubepods-<qos>-pod<uid, - as _>.slice/cri-containerd-<id>.scope`,
  or `…/crio-<id>.scope` under CRI-O;
- cgroupfs: `…/kubepods/<qos>/pod<uid>/<id>`.

## Decisions proposed

- **D1. The container is confirmed by its process's cgroup.** As the
  connection is taken, the node agent reads the cgroup of the process the
  state names (by its pidfd, so the pid cannot be reused between). The
  state's id must be the container's id in that cgroup, and the pod uid
  must be the pod's in its parent. The container's cgroup is its scope
  (`crio-<id>.scope`, `cri-containerd-<id>.scope`), or, under crun, the
  leaf named `container` directly below that scope, where crun puts the
  container's process (measured, below): the id is read from the last
  component, or from the one above a last component that is exactly
  `container`, and from nowhere else. Otherwise the connection is refused,
  with both in the node's log. This holds on **every** path, not only the
  two step 12 added: it costs one small read, and it stops resting the
  identity on how the runtime was read.
- **D2. The bundle is the confirmed id's.** The bundle's path must be the
  runtime's own for that id: containerd's
  `<state>/io.containerd.runtime.v2.task/k8s.io/<id>`, CRI-O's
  `<root>/overlay-containers/<id>/userdata` (the roots read from the
  chart's `runtime` value, or found once at the node agent's start). It is
  opened without following links, and must be a directory owned by root
  and writable by no one else.
- **D3. The annotations come from the bundle's `config.json`**, not from
  the state's JSON. The node agent already reads that file for the command
  (`node_config`); `node_state`, `node_policy`, `node_plan` and
  `node_inputs` read the same keys from it. If the state's copy differs
  from it in any key VAREK reads, the connection is refused, since only a
  sender other than the runtime makes them differ.
- **D4. Refused means refused.** A connection that fails D1 to D3 is
  refused as any other is today: the container does not start
  unsupervised, and its pod shows the reason.
- **D5. No plugin record, for now.** It would repeat what `config.json`
  already holds, from the same author, by a second channel to keep
  consistent. It is the fallback if measurement M1 finds a cell where the
  cgroup does not name the container.
- **D6. Defense in depth, in the webhook (proposed, separate).** VAREK's
  admission webhook refuses, in the namespaces it serves, a pod that is not
  VAREK's own and has a hostPath volume at or above the socket's
  directory. A read-only mount does not stop a connect to a socket, so
  `readOnly` is not an exception. This narrows who can reach the socket at
  all; it is not the fix, since a namespace the webhook does not serve
  could still hold such a pod.
- **D7. The test is the attack.** A new section in
  `varek/v1_4/tests/test_v1340.sh` makes a forged sender, through
  each path (a peer read, one in a mount namespace of its own, one
  reaped), naming another container's id, bundle and annotations, and
  shows each refused, with no stream written under that id and no
  credential or token file made. Run against v1.36.2, it fails; against
  v1.35.0, it shows whether that release is affected. The kind and matrix
  suites start their pods as before, so a change that refuses the real
  runtime fails there.

## Measurements before building

- **M1.** On every cell of the matrix (CRI-O 1.35 to 1.37 under runc and
  crun; containerd 2.2 and 2.3; amd64 and arm64) and on kind: when the
  listener arrives, the container's process is already in its own cgroup,
  and the cgroup names its id and its pod's uid in one of the forms above.
  This includes the cgroup as the node agent reads it from its own cgroup
  namespace (the DaemonSet's pod may have one of its own, making the paths
  relative). Measured by a report-only build (the node agent logs one
  `MEASURE v1.36.3` line for each container it admits, refusing nothing;
  `v1340_kind.sh` prints them), started November 4 on the matrix and kind.
  **EKS and OpenShift** are not given clusters of their own for it: their
  runtimes are the matrix's (containerd with `SystemdCgroup` on EKS,
  Amazon Linux 2023's setting; CRI-O under OpenShift), so the cgroup and
  bundle forms are the matrix's to measure. What is theirs alone (CRI-O's
  roots as OpenShift configures them, the DaemonSet's cgroup namespace
  there) is checked on the v1.36.3 release candidate before the tag, on
  the EKS cluster milestone 1's scale tests use and the OpenShift cluster
  its timed install uses: a container the candidate refuses there shows
  in the node's log with both values.
- **M2.** The bundle's path for a container on each cell, against D2's
  forms, and where each runtime's root is configured.
- **M3.** The state's annotations against `config.json`'s, for each key
  VAREK reads, on each cell: equal, as OCI says.
- **M4.** The time D1 to D3 add to a container's start, against v1.36.2
  (the burst check's 20 pods).

## Measured (November 4, 2026)

The report-only build on pull request #121 (head `3b72aaf`): every cell of
the matrix on amd64 and arm64 (CRI-O 1.35, 1.36 and 1.37 under runc and
crun; containerd 2.2 and 2.3 under runc) and kind on both, 18 cells, 387
containers admitted, every cell's chart test passing. Both paths step 12
added were taken: 99 containers whose runtime was reaped before it could
be read (most under crun), and one whose runtime was read in a mount
namespace of its own (CRI-O 1.36, runc).

- **M1, the cgroup.** On all 387, the container's process was in its own
  cgroup when the listener arrived, the path absolute (the node agent
  reads the node's cgroup tree), and the pod's uid in it, with `-` as `_`
  (the systemd driver, every cell). The id matched the scope's name on
  every runc and containerd container (`crio-<id>.scope`,
  `cri-containerd-<id>.scope`; kind's tree starts at `kubelet.slice`, the
  scope the same). **Under crun** (126 of 126) the process is one level
  lower, in `crio-<id>.scope/container`: crun's own leaf. D1 now names it.
  No cell used the cgroupfs driver; its form stays in D1 untested.
- **M2, the bundle.** CRI-O's always `<root>/overlay-containers/<id>/userdata`
  (the root `/run/containers/storage` on every cell), containerd's always
  `/run/containerd/io.containerd.runtime.v2.task/k8s.io/<id>`. Every
  bundle a directory, root's, mode 700.
- **M3, the annotations.** The state's and `config.json`'s equal on every
  container, for every key VAREK reads that either held (10 keys, or 14
  for a pod with a plan or a user's token): none only in one, none
  different.
- **M4, the time.** The cgroup's read and check: median 72 µs (26 to
  2,545); the bundle's: median 9 µs (4 to 533); reading `config.json` a
  second time and comparing: median about 1 ms (240 µs to 42 ms). Built,
  D3 reads `config.json` once, where `node_config` reads it now, so what
  the fix adds to a container's start is the cgroup and bundle checks:
  under 0.1 ms at the median. containerd's medians were about half
  CRI-O's.

**Result:** D1 to D3 hold on every cell, with D1's crun form added. D5
stands: no cell needs the NRI plugin's record. EKS and OpenShift are
checked on the release candidate, as M1 says.

## What changes

- `varek/v1_4/warden_node.inc.c`: the cgroup read and check (D1), the
  bundle's check (D2), the annotations from `config.json` (D3).
- `varek/v1_4/tests/test_v1340.sh`: D7's section; the existing forged
  sender (section 5) kept.
- `docs/security/threat-model.md`: the node agent's trust in the runtime,
  restated; the review line says what was found and fixed.
- `RELEASE-v1.36.0.md` and the parity note's "Open after the runs": the
  item marked answered, with the release.
- `RELEASE-v1.36.3.md`: a **Security** section, and the GitHub advisory
  with a CVE that `SECURITY.md` asks for, saying the versions affected,
  that no pod ran unsupervised, and that streams recorded by v1.36.0 to
  v1.36.2 on a node where such a pod could run are worth auditing again
  with `varek audit --node-keys`.

## Release

A patch release, **v1.36.3**, as `SECURITY.md` says a security fix is
released: it changes no policy line or decision, only which connections
the node agent takes. If D7 shows v1.35.0 affected, the same fix goes to
**v1.35.1**, since 1.35 is still a supported line. The other two open items
(the accept loop's 5 s receive, the plugin's memory on OpenShift) and the
named capabilities (R9) stay in v1.37's first steps, where they are
measured on the same matrix.
