# v1.41: VAREK's cryptography — where every call goes

Status: v1.41.0 (unreleased), branch `claude/v1.41.0-fips-crypto-backend`.
Written for the export-control documents (v4) and the Defense build's FIPS
claim. It lists every cryptographic operation VAREK's shipped code performs,
the file it is in, and the library that performs it.

## The claim, and how far it holds

**VAREK implements no cryptographic algorithm of its own.** Every hash,
signature, key operation, random byte and TLS session is computed by a
library on the host: OpenSSL 3 for the Warden, its helpers and its tools
(directly, or through Python's `hashlib`, `ssl` and `cryptography`, which
are bound to it), and Go's standard library for the Kubernetes components.

**In the Defense build (`make DEFENSE=1`), every hash and signature the
Warden, warden-secrets and varek_keygen perform goes through the host's
OpenSSL FIPS provider**, which on RHEL 9 is the FIPS 140-3 validated module;
they refuse to start unless that provider services them. Two parts of the
repository are outside that sentence today, and the documents should say so
until they are settled (section 4): the Kubernetes components (Go, built
with `CGO_ENABLED=0`), and the Python audit tools, which use the host's
OpenSSL but run wherever an auditor runs them, FIPS mode or not.

What was removed in v1.41:

| Removed | Was in | Was |
|---|---|---|
| libsodium | the Warden (`warden.c` and six included files, `warden_proxy.c`), `tools/varek_keygen.c`, `tools/varek_cyclonedx.py` (by `ctypes`) | SHA-256 chain, Ed25519 stream and node-key signatures, Ed25519 BOM signatures, random bytes, base64, guarded memory |
| VAREK's own SHA-256 | `checker/vdp_checker.c` | a FIPS 180-4 implementation (the policy digest) |
| VAREK's own Ed25519 verifier | `tools/varek_ed25519.py` | RFC 8032, in pure Python |
| EPEL | RHEL/UBI builds, the container image, the VM provisioning | the repository libsodium came from |

## 1. The C programs

All of the Warden's cryptography is in one file, `varek/v1_4/varek_fips.c`
(the backend), which calls OpenSSL 3 through EVP with no property query, so
the library's default properties choose the implementation (`fips=yes` once
the FIPS provider is active). No other Warden source calls OpenSSL.

| Binary | File | Operation | Algorithm | Library | Core | Defense |
|---|---|---|---|---|---|---|
| warden | `warden.c` (`rec_end`, `log_init`) | verdict-stream hash chain | SHA-384 | OpenSSL, via `varek_fips.c` | yes | yes (FIPS provider) |
| warden | `warden.c` (`rec_end`) | run_start, checkpoint, run_end signatures | ECDSA P-384 with SHA-384 | OpenSSL, via backend | yes | yes |
| warden | `warden.c` (`load_sign_key`) | load the signing key (PKCS#8 PEM) | EC P-384 | OpenSSL, via backend | yes | yes |
| warden | `warden.c` (`plan_snapshot`, `sha256_file_hex`), `warden_node.inc.c` | plan, shared-domain lists, node policy files hashed | SHA-256 | OpenSSL, via backend | yes | yes |
| warden | `warden.c` (credentials) | placeholder made, hashed | DRBG bytes, SHA-256, base64url | OpenSSL, via backend | yes | (credentials refused) |
| warden | `warden_exec.inc.c` | launchable files hashed (`allow exec`) | SHA-256 | OpenSSL, via backend | yes | yes |
| warden | `warden_names.inc.c` | a connect's candidate names hashed | SHA-256 | OpenSSL, via backend | yes | yes |
| warden | `warden_proxy.c` (`wp_load`) | the sealed helper binaries hashed | SHA-256 | OpenSSL, via backend | yes | yes |
| warden | `warden_node.inc.c` (`node_key_prepare`) | the node agent's key made and loaded | EC P-384 keygen | OpenSSL, via backend | yes | yes |
| warden | `warden_trust.inc.c` | inspecting mode's trust views hashed; the CA's PEM decoded | SHA-256; base64 | OpenSSL, via backend | yes | not built in use (inspect refused) |
| warden | `checker/vdp_checker.c` | the policy digest (`sha256=`) | SHA-256 | OpenSSL, via backend | yes | yes |
| varek_keygen | `tools/varek_keygen.c` | the signing key made | EC P-384 keygen | OpenSSL, via backend | yes | yes |
| vdp_cert_check | `checker/vdp_checker.c` | the policy digest | SHA-256 | OpenSSL, via backend | yes | yes |
| warden-secrets | `warden_secrets_helper.c` | HTTPS to Vault, AWS, IdPs, JWKS | TLS 1.2+ (the host's crypto policy) | OpenSSL (libssl) | yes | yes (FIPS provider) |
| warden-secrets | `warden_secrets_helper.c` | AWS SigV4 | SHA-256, HMAC-SHA256 | OpenSSL | yes | yes |
| warden-secrets | `warden_secrets_helper.c` | user-token (JWT) signatures checked | RS256, PS256, ES256, EdDSA | OpenSSL | yes | yes (EdDSA: if the provider offers it) |
| warden-secrets | `warden_secrets_helper.c` | the agent's SVID checked (X.509 chain) | X.509 path validation | OpenSSL | yes | yes |
| warden-proxy | `warden_proxy_helper.c`, `warden_proxy_mcp.inc.c` | inspecting mode: TLS terminated both ways; server certificate, request and MCP bodies, tokens hashed | TLS 1.2+; SHA-256 | OpenSSL (libssl) | yes | **not compiled in** |
| warden-proxy | `proxy_ca.c` | inspecting mode: the run's CA and leaf certificates made and signed; a PKCS#12 trust store (certificates only, neither encrypted nor MAC'd) | ECDSA P-256, SHA-256; DRBG serials | OpenSSL | yes | **not compiled in** |

In the Defense build `warden-proxy` links no TLS or crypto library at all
(its `ldd` shows libc alone; `make test-v1410` checks it, and that none of
inspecting mode's code is in it). The Warden starts warden-secrets for
credentials (refused in the Defense build) or for `--on-behalf-of` and
`--svid`, which it can still be given.

Random bytes: credential placeholders and everything OpenSSL makes (keys,
ECDSA nonces, CA serials) come from OpenSSL's DRBG, the FIPS provider's in
FIPS mode. The run's id (16 bytes, which the agent never sees and which tell
its records from foreign ones) comes from `getrandom(2)`, the kernel's CSPRNG,
in `warden.c` (`log_init`); it is not a key. Not cryptography, and not listed
above: hex, base64 and memory clearing (`OPENSSL_cleanse`; `explicit_bzero` in
the Defense proxy).

## 2. The Python tools

They use the host's OpenSSL through Python's standard `hashlib` and `ssl`
and the `cryptography` package. On RHEL 9 in FIPS mode those run in the FIPS
provider (Python then refuses MD5 for security, which the acceptance checks).

| Tool | Operation | Algorithm | Library |
|---|---|---|---|
| `varek_audit.py`, `varek_cyclonedx.py`, `varek_ocsf.py` | the stream's chain recomputed | SHA-384 (chain-2), SHA-256 (chain-1) | `hashlib` |
| `varek_ed25519.py` (used by both) | stream, anchor and node-key signatures checked | ECDSA P-384 SHA-384; Ed25519 for logs of v1.40 and earlier | `cryptography` |
| `varek_cyclonedx.py` | CycloneDX evidence signed (JSF) | ES384 (ECDSA P-384, SHA-384; R‖S) | `cryptography` |
| `varek_cyclonedx.py` | evidence signatures checked | ES384; Ed25519 (v1.40 evidence) | `cryptography` |
| `varek` (CLI), `varek_audit.py`, `varek_baseline.py`, `varek_bench*.py`, `varek_plan.py`, `smt_crosscheck.py` | policy, plan, baseline and file digests | SHA-256 | `hashlib` |
| `varek_falcon.py`, `varek_sentinel.py`, `varek_splunk.py`, `varek_otel.py`, `varek` | exports and license checks over HTTPS | TLS (the host's policy) | `ssl` / `urllib` |
| `varek_bench_proxy.py`, `varek_bench_mcp.py` | benchmark TLS servers (measuring inspecting mode) | TLS | `ssl` |
| `varek_vm.py` | a VM's token | random bytes | `secrets` (the kernel's CSPRNG) |

The Ed25519 verifier keeps the v1.16 one's strictness in front of OpenSSL
(no small-order key, canonical encodings, S below the group order): OpenSSL
alone accepts trivial "signatures" under a small-order key (506 of 4,096
tried). On a host in FIPS mode Ed25519 is not offered; a v1.40 log is then
reported as not checkable there, never as forged.

## 3. The Kubernetes components (Go)

`varek-nri`, `varek-admission`, `varek-svid` and `internal/kube` use Go's
standard library (`crypto/tls` for the admission webhook's server and the API
server client, `crypto/sha256`, `crypto/rand`), built with `CGO_ENABLED=0`
(`packaging/container/Containerfile`): Go's own implementation, not VAREK's
and not the host's OpenSSL. The v1.41 change does not touch them, beyond
accepting P-384 node keys (`internal/kube/nodekeys.go`, the VarekNodeKey CRD).

## 4. Open items for the documents

1. **Kubernetes components.** For "every hash and signature through the
   host's FIPS 140-3 module" to cover them, build them with Red Hat's Go
   toolset (cgo, OpenSSL as the crypto backend in FIPS mode) or Go's own FIPS
   140-3 module (`GOFIPS140`, its CMVP status checked), or keep them out of
   the Defense build's scope. A decision, not done here.
2. **Inspecting mode, and what goes with it.** Request rules, MCP tool-call
   rules, credential release and passthrough hosts need it, so the Defense
   build refuses them. Returning it later, on the FIPS provider, is a counsel
   question (a TLS-intercepting proxy).
3. **JWT algorithms.** warden-secrets accepts RS256, PS256, ES256 and EdDSA
   (the IdP's choice); none is CNSA-aligned. ES384 and RS384 would let a CNSA
   IdP be used. EdDSA tokens are refused where the FIPS provider does not
   offer EdDSA.
4. **Verification is no longer independent of signing.** Through v1.40 the
   audit checked libsodium's Ed25519 with its own pure-Python code; now the
   Warden signs and the audit verifies with the same library, as FIPS
   requires of both. The off-host anchor is unchanged.
5. **The audit's host.** Verifying v1.40 logs needs a host whose provider
   offers Ed25519 (one not in FIPS mode). `varek_audit.py --require-fips`
   fails a run whose signed run_start does not say `crypto_provider: fips`.
6. **Random generation, if the documents count it.** The run id is the
   kernel's (`getrandom`), not the FIPS provider's DRBG; moving it to the
   backend (`vfips_rand`) is a one-line change if wanted.
7. **RHEL 9 FIPS-mode acceptance: passed** on November 22, 2026 (section 6).
   FIPS mode was enabled on that host after installation (`fips-mode-setup
   --enable`), not at install time; a run on a host installed in FIPS mode
   would close that difference, if the documents need it.

## 5. Formats and compatibility

- **Verdict stream, chain-2** (the Warden from v1.41): run_start says
  `"log":"chain-2"`, `"sigalg":"ecdsa-p384-sha384"` and `"crypto_provider"`;
  chain = SHA-384(chain ‖ record), IV SHA-384("VAREK-LOG-CHAIN-2"); signatures
  DER ECDSA P-384 over "VAREK-LOG-SIG-2" ‖ chain (48 bytes). chain-1 streams
  (v1.16 to v1.40: SHA-256, Ed25519, "VAREK-LOG-SIG-1") are still audited.
  A run_start naming a Warden of 1.41 or later in chain-1 is refused (a
  downgrade).
- **Keys**: PKCS#8 PEM, EC P-384; public keys as the uncompressed point (194
  hex characters, `04` first). The Warden refuses a v1.40 Ed25519 key; `sudo
  varek init` replaces it and keeps its public half as `log.key.v140.pub`,
  which `varek audit` and `varek export` use for the runs it signed.
- **Evidence (CycloneDX)**: JSF ES384; JSF Ed25519 evidence still verifies.
- **Anchor lines and node keys**: both formats pass the forwarder and the
  receiver; the VarekNodeKey CRD and `internal/kube` accept both key forms.

## 6. How it was checked

On a Linux 6.18 VM (root, seccomp user notification, Landlock ABI 7, not in
FIPS mode), with libsodium removed from the machine before the final build:

- the core and Defense builds, without a warning; the Defense warden-proxy
  links no library but libc; the Defense Warden and varek_keygen refuse to
  start (the host is not in FIPS mode);
- `make test-cli` (253 passed, 1 skipped) and every `make test-v*` suite,
  v1.12 to v1.35 and v1.41 (`test-v1410`, this change), including
  `test-v1160` (the audit chain: 59 checks) and the forge and tamper suites
  (v1.24 to v1.27), whose editors now re-chain in the stream's own format.
  Checks skipped for want of the machine: musl, Squid, IPv6, AppArmor,
  the node agent's containers. One check failed for the same reason: v1.35's
  "a code adapter is not run unconfined", because this VM's `python3` is a
  /usr/local build, which the CLI refuses as an environment first; with the
  distribution's Python it passes;
- a log, anchor and BOM written by the v1.40.0 Warden, built from its tag,
  verified by the v1.41 tools (`tests/v140_fixture`), and the upgrade of a
  v1.40 host by `varek init`.

On RHEL 9 in FIPS mode, `sudo make fips-acceptance`: **RESULT: PASS**, on
November 22, 2026, at commit `bbd90b5`:

- the host: RHEL 9.8 (Plow), kernel 5.14.0-687.45.1.el9_8.x86_64, on Amazon
  EC2 (t3.medium); FIPS mode enabled after installation (`fips-mode-setup
  --enable` and a reboot): `/proc/sys/crypto/fips_enabled` = 1,
  `fips-mode-setup --check` "FIPS mode is enabled", system crypto policy
  FIPS;
- the module: openssl-libs 3.5.9-1.el9_9 with openssl-fips-provider
  3.0.7-11.el9_8, its fips provider active (3.0.7-cda111b5812c30d4); the CMVP
  certificate is the one Red Hat names for that provider version;
- the Defense build (`make DEFENSE=1`) without a warning, no binary linking
  libsodium, the egress proxy linking no TLS or crypto library;
- `test_v1410` (22 checks) and a Defense run audited with `--require-fips`;
  `test_v1160` with the Defense binaries (58 checks: the Ed25519 check is
  skipped, as the provider does not offer it), its `run_start` saying
  `crypto_provider: fips`; `test_v1161` with the Defense binaries;
- the audit in FIPS mode: hashlib refuses MD5; ECDSA P-384 verifies RFC
  6979's vector; a v1.40 log is reported as not checkable there, not as
  forged.

The run before it, at `aa3de69`, failed, and its findings were fixed in
`bbd90b5`: that host's OpenSSL hands out the P-384 public key compressed, so
`varek_keygen`'s `.pub` did not match the stream's key (the point is now
built from the key's coordinates, whatever the library's default); the
v1.40 fixture's log was missing from the repository; and the test probes need
a static C library (`glibc-static`, from CodeReady Builder), which the
acceptance script now asks for at the start.

The evidence (`SUMMARY.txt` and the files behind it, SHA-256
`074e479eefc4e8b23b1ccbcef7ec3d92bbeced318ec83c7fc955b57506fac833` for the
tarball) is kept with the export-control documents.
