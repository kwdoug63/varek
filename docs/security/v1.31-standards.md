# v1.31.0 — Standards: OCSF export, MCP servers and MCP tokens, and the Agent Baseline mapping (plan)

Status: **planned**, target **v1.31.0**. Decided 2026-10-13: the
recommendation for each decision below (D1 to D12). Nothing is built. To be developed on its own branch from v1.29.0's (proposed:
`claude/varek-v1310-01dbw5`). Each section ends with what must be tested
before it ships. The roadmap entry is in `docs/roadmap/v1.28-v1.31.md`.

Ship gate (decided for v1.28.1, v1.29.0 and v1.31.0 together): one 24-hour
soak on the droplet covers the three releases' changes on the final build,
before any of them is tagged.

The standards this note builds on, as read on 2026-10-13:

- **OCSF 1.9.0** (released August 3, 2026; the schema's main branch is
  1.10.0-dev). Its AI additions are new in 1.9.0: the `ai_agent` object,
  `ai_agent` and `delegation` in the `ai_operation` profile (which 1.9.0
  adds to the System, Network, Application and IAM base classes), and the
  `record_integrity` profile with its `attestation` object.
- **MCP, revision 2026-07-28** (the current one; read from the
  specification's own repository). Its authorization part (OAuth 2.1, RFC
  9728 protected resource metadata, RFC 8707 resource indicators,
  audience-bound tokens, no token passthrough) applies to HTTP transports
  only; a stdio server takes its credentials from its environment. The
  Streamable HTTP transport now requires `Mcp-Method` and `Mcp-Name`
  headers that mirror the JSON-RPC body, which the server must check
  against the body.
- **Agent Baseline v1.0-draft** (agentbaseline.org; its repository at
  commit f686aeb, 2026-10-13): 35 controls under six outcomes (Discover,
  Constrain, Authorize, Observe, Validate, Respond), with identifiers such
  as `AUT-04`. Public comment closed on September 30, 2026. The identifiers
  freeze at v1.0 and may change until then.

## What v1.29.0 leaves open

- **Evidence a SIEM can read.** VAREK's evidence is its own stream (one
  chained JSON record per decision) and a CycloneDX 1.6 export (a summary
  of a run: the objects reached and an attestation). A SIEM ingests
  events, one per action, in a schema it already parses. CycloneDX is not
  that: it describes a run after the fact, and a SIEM has no parser for
  VAREK's records. OCSF is the schema Amazon Security Lake requires and
  the other SIEMs (Splunk, Microsoft Sentinel, Elastic, Google SecOps) map
  from.
- **MCP servers on the host.** A local MCP server is a program the agent
  launches and talks to over stdio. Under v1.27 its launch is decided; under
  v1.28.1 it can be a sub-agent, in its own control group, with every one
  of its calls attributed to it. But it is decided by the agent's rules: a
  filesystem server can read whatever the agent can, and a GitHub server
  can reach every host the agent can. Nothing narrows a server to what it
  is for, and nothing names it as an MCP server in the records. v1.28.1
  left rules that depend on who is calling to "a release of its own" (its
  D6).
- **MCP servers over HTTP.** Under inspecting mode (v1.26.1) a call to a
  remote MCP server is a `POST` to one URL: every tool call is the same
  request object. Bodies are not decided (v1.26.1 §2), so a policy cannot
  allow `tools/call` of `get_issue` and refuse `delete_repository` on the
  same server.
- **MCP tokens.** An MCP server is an OAuth 2.1 resource server, and the
  token a client sends it must have been issued for that server (its
  canonical URI as the audience). v1.28.0 can release a credential from a
  store into a header, and v1.28.1 verifies the user's token at start, but
  VAREK cannot: hold an MCP access token so that it reaches only the
  server it was issued for; refuse a token the agent sends to a server it
  was not issued for (the passthrough the specification forbids); or
  accept, as the run's user, a token found through an MCP server's
  protected resource metadata rather than OpenID discovery.
- **Agent Baseline.** Buyers are starting to ask which of its controls a
  product meets. No mapping exists.

## What it gains, and what it does not

With v1.31.0:

- **An OCSF export.** `varek export --format ocsf` writes each record of a
  stream as an OCSF 1.9.0 event (JSON Lines): file, process, network,
  HTTP and DNS activity, with the decision in the `security_control`
  profile, the agent, its user and its sub-agents in the `ai_operation`
  profile, and every event linked back to its record in the stream. With
  `--follow`, it writes events as the Warden writes records, for a
  forwarder to ship.
- **MCP servers confined to their own rules.** `mcp server NAME exec PATH`
  declares a server the agent may launch. It runs as a sub-agent (v1.28.1),
  and its calls are decided by the rules written for it (`for=NAME`) and
  nothing else: the filesystem server reads the project, the GitHub server
  reaches GitHub with a credential the agent never holds, and neither gets
  the other's reach or the agent's.
- **MCP calls decided by method and tool.** Under inspecting mode, `allow
  mcp URL METHOD [NAME]` decides each JSON-RPC request to a remote MCP
  server on its method and the tool, resource or prompt it names, read from
  the body the server will act on.
- **MCP tokens.** A token issued under MCP's authorization specification
  can be a v1.28.0 credential bound to its server's canonical URI, released
  only into calls to that server; a bearer token the agent sends to an MCP
  server that was issued for another audience is refused; and the run's
  user may be named by a token whose issuer was found through the server's
  protected resource metadata.
- **The Agent Baseline mapping.** `docs/standards/agent-baseline.md`: each
  of the 35 controls, what in VAREK addresses it (and from which release),
  how far, and what is left to the operator or to other products. It is a
  document, and can be published before v1.31.0 (D11).

It does not:

- change any verdict outside what the new lines decide. An OCSF event
  reports a decision; it decides nothing. The token checks only add
  refusals. No extension may move a genuinely unsafe action to SATISFIED,
  and none does here;
- decide the calls an agent makes to a stdio MCP server. Those are bytes
  on a pipe between two processes the Warden supervises; v1.31 confines
  what the server does, not what the agent asks it (D4). The agent can ask
  a server for anything the server's rules allow: confinement bounds a
  server that is compromised or malicious, and keeps the server's reach
  and the agent's apart, but a server's tools remain the agent's to call;
- decide a call's arguments, or anything in a server's responses (a tool
  list that changes, a result that carries an injected instruction);
- make VAREK an OAuth client of an MCP server's authorization server. It
  does not run the authorization code flow, register clients, or refresh
  tokens; a token comes from a store, as v1.28.0's credentials do (D8);
- make VAREK a registry, an approval workflow or a testing product. Most
  of Agent Baseline's Discover and Validate controls are met elsewhere;
  the mapping says which, rather than claiming them;
- add enterprise sign-in (OIDC, SCIM). There is no admin console to sign
  in to (D12).

## The design in one paragraph

`tools/varek_ocsf.py` (called by `varek export --format ocsf`) reads a
stream, checks it as `varek audit` does, and maps each record to an OCSF
1.9.0 class by its `action`, carrying the decision as `action_id` and
`disposition_id`, the policy line as `policy`, the run and its chain as
`ai_agent` and `delegation`, and the record's report id, sequence number
and chain hash in `unmapped.varek`, so each event can be checked against
the stream. Under `require warden 1.31`, `mcp server NAME exec PATH
[sha256=HEX]` names a program as an MCP server: it is a sub-agent whose
launch the line allows, and its calls are decided by the SMT decision
procedure against the rules marked `for=NAME` only (and the hard denies
and the Warden's own files, as for every call). Under `proxy inspect`, a
URL that an `mcp` rule names is an MCP endpoint: `warden-proxy` reads each
request's body (within a limit), parses it as one JSON-RPC message with a
strict parser, refuses one whose `Mcp-Method` or `Mcp-Name` header
disagrees with it, and sends the Warden the method and the name, which
it decides as the object `mcp:URL#METHOD[/NAME]`. A credential with
`audience=URL` is checked at fetch to be a token for that URL and is
released only into calls to it; a bearer token the agent sends to an MCP
endpoint is refused if its audience is another, if it has expired, or if
it is the run's user token.

## 1. The OCSF export

- **Format.** OCSF 1.9.0 events, one JSON object per line, each with
  `metadata.version` `1.9.0`, `metadata.product` (VAREK, the Warden's
  version), `metadata.profiles` (`security_control`, `ai_operation`, and
  `host`), `metadata.uid` (the record's report id) and
  `metadata.correlation_uid` (the run id).
- **Classes.** By the record's action:

  | VAREK record | OCSF class | Activity |
  |---|---|---|
  | `file.open`, `file.access`, `file.stat`, `file.readlink` | File System Activity (1001) | Open (14), Read (2), Get Attributes (8) |
  | `file.mkdir`, a creating `file.open` | 1001 | Create (1) |
  | `file.unlink`, `file.rmdir` | 1001 | Delete (4) |
  | `file.rename_from` / `file.rename_to` (one event per pair) | 1001 | Rename (5) |
  | `file.chmod`, `file.utime`, `file.truncate` | 1001 | Set Attributes (6), Update (3) |
  | `file.chdir` | 1001 | Other (99) |
  | `process.exec` (and v1.27 launches) | Process Activity (1007) | Launch (1) |
  | `net.connect`, `net.send`, `net.proxy` | Network Activity (4001) | Open (1); Refuse (5) when refused |
  | `net.bind` | 4001 | Listen (7) |
  | `net.request` | HTTP Activity (4002) | by method: Get (3), Post (6), ... |
  | `net.mcp` (section 3) | API Activity (6003) | Read (2) for `*/list`, `resources/read`, `prompts/get`; Other (99) for `tools/call` |
  | `dns_question` | DNS Activity (4003) | Query (1) |
  | `run_start`, `run_end` | Application Lifecycle (6002) | Start (3), Stop (4) |
  | `revoked`, `on_behalf_of_expired` | Application Lifecycle (6002) | Disable (7) |
  | a system call decided by the baseline filter (v1.29) | Process Activity (1007) | Other (99), the call's name in `unmapped` |

  Records with no OCSF counterpart (`checkpoint`, `resolution`,
  `exec_result`, `request_body`, `proxy_close`, `synthetic_address`, lease
  events) are not exported as events; what they say is folded into the
  event they belong to (`request_body` into its `net.request`, an
  `exec_result` into its launch) or into `unmapped`.
- **The decision.** `security_control`: `action_id` 1 (Allowed) for
  SATISFIED, 2 (Denied) for UNSATISFIED and UNKNOWN; `disposition_id` 1
  (Allowed) or 2 (Blocked); `status_id` from the kernel's outcome
  (`kernel_verdict`, `errno`). The three-state verdict itself is kept as
  `unmapped.varek.decision` (`SATISFIED`, `UNSATISFIED`, `UNKNOWN`) and the
  raw decision as `decision_raw`: OCSF has no UNKNOWN, and a refused
  UNKNOWN is not the same finding as a refused UNSATISFIED. A dry run's
  would-be refusal (v1.29, `"enforced":false`) is `action_id` 2 with
  `disposition_id` 15 (Detected), never Blocked, and `unmapped.varek.mode`
  `dry_run` (D2).
- **The policy.** `policy`: `name` the policy file, `uid` its SHA-256,
  `version` the grammar (`1.31`), `is_applied` true, and `desc` the rule
  text of the deciding line; `unmapped.varek.policy_line` the line number.
  The certificate and the checker's answer go in `unmapped.varek`.
- **Who.** `actor.process` is the calling process (its pid and Unix
  user); `ai_agent` names the agent (`uid` its program's SHA-256, `name`
  its file name, `instance_uid` the run id, `type_id` 99 Other). With a
  v1.28.1 chain, `actor.user` is the verified user (the token's subject
  and issuer) and `delegation` the authority it gave (`uid` the token's
  SHA-256, `issuer_uid` the issuer, `parent_uid` for each actor of a token
  exchange), as OCSF puts the principal in `actor.user` and the delegate
  in `ai_agent`; a run with no chain has no `actor.user`. A sub-agent's or
  MCP server's event names it in `ai_agent` (`type` `mcp_server` for a
  server), and the chain it was decided for in `unmapped.varek.obo`.
- **Linking back.** Every event carries `unmapped.varek.report_id`,
  `seq` and `chain` (the stream's running SHA-256 after this record), and
  the run's signed checkpoints are exported as they occur. `varek export
  --format ocsf --verify STREAM EVENTS` checks that each event is the one
  the exporter would write from that record and that the stream is intact
  (D1).
- **Batch and follow.** By default the exporter reads a finished stream,
  audits it first (a stream the audit refuses is not exported, as for
  CycloneDX), and writes the events. `--follow` tails a live stream and
  writes each record's event as it is chained; the audit's whole-stream
  checks then run at `run_end`, and the last event says whether they
  passed (D5).
- **The schema's names.** CycloneDX's export says what it is not (not
  certified by the OWASP Foundation); the OCSF export says the same of the
  OCSF project in its header and the NOTICE file.

*Tests:* each record kind against the OCSF 1.9.0 schema (the schema's own
JSON files, vendored with their license, checked by a validator in the
tests, with no network); a dry run's events never Blocked; UNKNOWN kept;
every event's link back verified against its stream, and an edited event
or a removed one found; `--follow` on a live run, and a run that ends
early; a stream the audit refuses is not exported; Amazon Security Lake's
and Splunk's OCSF parsers accept the output (a fixture checked by hand
once, recorded in the notes).

## 2. MCP servers on the host

```
require warden 1.31
launches on
mcp server files  exec /opt/mcp/bin/mcp-server-filesystem sha256=3f1a...
mcp server github exec /opt/mcp/bin/github-mcp-server
allow read /home/ken/proj/** for=files
allow write /home/ken/proj/** for=files
allow host api.github.com:443 for=github
allow request GET https://api.github.com/repos/acme/** credential=github header=Authorization:Bearer for=github
```

- `mcp server NAME exec PATH [sha256=HEX]`: `PATH` is the server's own
  launch file (a binary, or a script with `#!`), never an interpreter or a
  launcher (`node`, `python3`, `npx`, `uvx`, `docker`): lint refuses those,
  since a rule on `node` would make every Node program the server (D4). The
  line is also the rule that lets the agent launch it. `sha256=` pins the
  file: a launch whose file has another hash is refused (the launch set
  already hashes it, v1.29).
- **A sub-agent.** A server is a v1.28.1 sub-agent: at its launch the
  Warden makes its control group, and it and every process it starts stay
  in it. Its records' `obo` ends in `mcp:NAME#n`, and its launch record
  says `mcp_server`.
- **Its own rules.** Every call from a server's control group is decided
  against the rules marked `for=NAME` and no others (D3). The agent's
  rules (unmarked) do not apply to it, and its rules do not apply to the
  agent. The hard-denied system calls, the Warden's protected objects,
  revocation and the token's expiry hold for it as for the agent.
  `for=NAME` may name a server, or a v1.28.1 sub-agent declared with
  `subagent=NAME confined`; a `for=` naming neither is refused at load.
- **What crosses between them.** Only the pipes the agent gave the
  server at launch, and files both sets of rules allow. The calls that
  reach into another process (`ptrace`, `process_vm_readv` and
  `process_vm_writev`, `pidfd_getfd`) are hard-denied already; v1.31 also
  refuses, whatever the rules say, an open by one subject of another
  subject's `/proc/<pid>/` entries (`mem`, `environ`, `fd`, `cwd`,
  `root`, `map_files`). A server whose launch file, or a directory above
  it, is writable under the agent's rules is refused at load: the agent
  could otherwise rewrite the server it is confined from. Modules the
  server loads from elsewhere (a `node_modules` tree) are the operator's
  to keep out of the agent's reach; `varek doctor` checks the server's
  package directory, and lint notes a server rule that lets the agent
  write there.
- **What a server needs to start.** A confined server needs its loader,
  libraries and interpreter like any program. `varek run` (v1.29) writes
  the baseline's system reads for each server it is given (`--mcp
  NAME=PATH`), and `varek policy suggest --for NAME` drafts the rest from
  a dry run, as for the agent.
- **The decision procedure.** The subject is an input to the decision:
  the SMT decision procedure decides a call against the rules of the
  calling subject, and the certificate names the subject, so the checker
  replays the decision against the same rules. All three parsers (the
  decision procedure, the certificate checker, the cross-check's oracle)
  read `mcp server`, `for=` and `confined` alike, and the cross-check's
  generator writes them; a v1.29.0 Warden refuses them as unknown.
- **Credentials.** A v1.28.0 credential used only by rules `for=NAME` is
  released only into that server's requests. The agent, which launches
  the server, still cannot read the value: it is in the proxy, not in the
  server's environment (a server that needs it in its environment gets the
  placeholder, as the agent does).

*Tests:* each form and refusal in the three parsers; a server reading what
its rules allow and refused what only the agent's rules allow, and the
agent refused what only the server's rules allow; a server's child (a
fork, a double fork, a launched `git`) decided by the server's rules; a
server launched by a second name or a changed file (`sha256=`) refused;
the agent refused the server's `/proc/<pid>/mem` and `environ` (and the
server the agent's); a server file under an agent-writable rule refused
at load; lint on `node`, `npx` and `docker` as a server's file; a credential `for=`
a server released into its request and not the agent's; the certificate
names the subject, and a certificate replayed under another subject is
refused by the checker.

## 3. MCP calls over HTTP

```
proxy on
proxy inspect
allow host mcp.example.com:443
allow mcp https://mcp.example.com/mcp server/discover
allow mcp https://mcp.example.com/mcp tools/list
allow mcp https://mcp.example.com/mcp tools/call get_*
allow mcp https://mcp.example.com/mcp resources/read file:///projects/app/**
deny  mcp https://mcp.example.com/mcp tools/call delete_*
```

- `allow|deny mcp URL METHOD [NAME]`: `URL` is the server's canonical URI
  (scheme, host, optional port and path; no query or fragment), `METHOD` a
  JSON-RPC method or a glob over methods, `NAME` a glob over the tool,
  prompt or resource URI the request names (`params.name` or
  `params.uri`). A URL that any `mcp` rule names is an MCP endpoint, and
  every `POST` to it is decided by `mcp` rules only; other methods on it
  (a `GET` an older server uses for its stream) by request rules.
- **The body is read.** For a `POST` to an MCP endpoint the proxy reads the
  body before sending anything, up to the rule's `max_body` (default 1
  MiB; a larger body is refused), and parses it as JSON with a strict
  parser: UTF-8 only, no duplicate member names at any depth, nesting at
  most 64 deep, numbers and strings within fixed bounds. It must be one
  JSON-RPC 2.0 request or notification: a batch (an array, allowed by the
  2025-03-26 revision) is refused, as is anything else. The method and
  `params.name` / `params.uri` are read from the parsed body (with JSON
  escapes decoded); a name over 4,095 bytes, or with a control character,
  is refused.
- **The headers agree.** When the request carries `Mcp-Method` or
  `Mcp-Name` (required from 2026-07-28; a Base64-sentinel value decoded as
  the specification says), each must equal the body's value, or the
  request is refused (`mcp_header_mismatch`). The decision is always on
  the body, which is what the server acts on; a server that routes on the
  header and does not check it cannot be sent a header the body
  contradicts.
- **The decision.** The proxy sends the Warden the method and the name
  (`WP_MSG_MCPREQ`); the Warden decides the object
  `mcp:URL#METHOD/NAME` (or `mcp:URL#METHOD`) with the SMT decision
  procedure, the certificate checker accepts it, and the record is
  written, as for a `net.request`. A refused call gets a JSON-RPC error
  response (code -32000, in the range JSON-RPC leaves to implementations,
  with a one-line reason and the request's `id`) in an HTTP 403, and
  nothing reaches the server.
- **What is recorded.** `net.mcp`: the URL, method, name, request id, the
  body's length and SHA-256, the `MCP-Protocol-Version` header, the
  W3C `traceparent` from `_meta` when the request carries one (for
  correlation; it decides nothing), the decision and the rule. Arguments
  are not recorded.
- **Responses are not decided.** A server's results, its tool list and
  its input requests (2026-07-28's multi round-trip pattern: the client
  retries the original request with the input, and the retry is decided
  again) pass as they are.

*Tests:* each method and name form, first match wins, default refusal; the
parser on duplicate keys (`{"method":"tools/list","method":"tools/call"}`
refused), escaped names (`"get_issue"` decided as `get_issue`), deep
nesting, invalid UTF-8, a batch, a body over the limit, a chunked body; a
header that disagrees with the body; a Base64-sentinel header; the
refusal's JSON-RPC error; the 2025-06-18 and 2026-07-28 revisions against
a stand-in server built for the test; the proxy's time per call.

## 4. MCP tokens

- **A token the run holds.** `credential NAME from STORE:REF
  audience=URL`: a v1.28.0 credential that is an MCP access token for the
  server at `URL`. At fetch, `warden-secrets` checks that it is a JWT whose
  `aud` holds `URL` exactly (RFC 8707's canonical URI, compared without
  normalization) and whose `exp` is in the future; a token that is not a
  JWT is refused unless the line says `opaque` (D7). Its value is released
  only into the `Authorization: Bearer` header of a call that an `allow
  mcp` rule for that `URL` with `credential=NAME` allowed. When the store
  gives a new token (a file rewritten, a Vault secret with a lease), the
  helper reads it again before the old one expires; VAREK does not refresh
  tokens itself (D8).
- **A token the agent sends.** On a call to an MCP endpoint whose
  `Authorization: Bearer` value is not a placeholder, the proxy decodes the
  token's claims if it is a JWT (without checking its signature: the
  result can only refuse) and the Warden refuses the call when the token's
  `aud` does not hold the endpoint's URL, when it has expired, or when its
  SHA-256 is the run's user token's (v1.28.1; the agent never holds that
  token, but a copy of it would be passthrough). The record says which
  check refused it and never holds the token. An opaque token is recorded
  as `opaque` and decided by the rules alone (D6).
- **The user, found through MCP.** `trust mcp-resource URL [audience
  AUD]`: an issuer for the run's user token (v1.28.1's `--on-behalf-of`)
  found as an MCP client finds one: `warden-secrets` fetches the protected
  resource metadata for `URL` (RFC 9728), takes its
  `authorization_servers`, fetches each one's metadata (RFC 8414, or
  OpenID discovery), requires its `issuer` to be identical to the
  identifier it was fetched for, and checks the token against that
  issuer's keys with `URL` (or `AUD`) as the audience. Everything else is
  v1.28.1's check (algorithms, time, `act` chain, expiry and revocation).

*Tests:* a stand-in authorization server and MCP server (metadata,
JWKS, tokens made for the test); a token for another audience, an expired
one, an opaque one with and without `opaque`; the value released only to
its URL and not to another MCP endpoint or a plain request rule; the
agent's own token for another audience refused, the run's user token
refused, a placeholder passed to the swap; metadata whose `issuer`
differs from the identifier refused; no token value in any record or in
the agent's environment.

## 5. The Agent Baseline mapping

`docs/standards/agent-baseline.md`, written against the control list at a
named commit of the Agent Baseline repository, with one row per control:

- **Addressed**: VAREK enforces it for what it supervises (named: the
  release and the mechanism).
- **In part**: VAREK covers part of it; the row says which part, and what
  is not covered.
- **Evidence**: VAREK records what another system needs to meet it, and
  the row says which record or export.
- **Not addressed**: a registry, a workflow, testing or detection VAREK
  does not do.

A first reading, to be checked control by control when the document is
written:

| Outcome | Addressed or in part | Evidence | Not addressed |
|---|---|---|---|
| Discover | DIS-06 (the policy is the run's effective access; credentials by name and destination, v1.28.0; the delegated chain, v1.28.1) | DIS-01, DIS-04, DIS-05 (`run_start`: the agent's and each launched program's SHA-256, sub-agents, MCP servers from v1.31) | DIS-02, DIS-03, DIS-07 |
| Constrain | CON-03 (files, network destinations, launches, credential delivery, system calls; not compute, duration or process count), CON-01 and CON-04 in part (pinned launch sets and MCP servers; the baseline and profiles, versioned by SHA-256) | | CON-02 |
| Authorize | AUT-01 (every decision: run, user, agent, sub-agent, target, time), AUT-04 (placeholders; values only into requests decided SATISFIED, v1.28.0), AUT-06 (UNKNOWN refused; a start refused without a required identity; expiry revokes), AUT-05 in part (the plan gate, a decision point independent of the agent), AUT-03 in part (each hop recorded; attenuation not enforced) | AUT-02 | AUT-07, AUT-08, AUT-09 (a stolen placeholder is useless outside the run, but the released value is a bearer token) |
| Observe | OBS-01 in part (no model or task), OBS-06 (chained, signed, anchored, audited for completeness), OBS-02 (run ids; OCSF; MCP `traceparent` from v1.31) | OBS-05 | OBS-03, OBS-04 |
| Validate | | VAL-01 (a dry run shows what a policy would refuse; the testing is the operator's) | VAL-02, VAL-03, VAL-04 |
| Respond | RES-01 (`varek revoke`: later actions UNSATISFIED, credentials withdrawn, leases revoked), RES-04 in part (unverified actions refused; no fallback), RES-02 and RES-05 in part (pins and deny rules for later runs; MCP servers by hash from v1.31; remote tool definitions not covered) | RES-03 | |

The document states the standard's status (a draft, identifiers not
frozen), cites the bare identifiers as the standard asks, and is reviewed
again at the v1.0 freeze. It names no conformance: Agent Baseline has no
conformance program.

*Tests:* none in code. A review by AI review agents of every "Addressed"
and "In part" row against the code and the threat model, looking for a
claim the code does not support.

## 6. Audit, export and tools

- `varek_audit.py`: every `for=` decision was made for a call from that
  subject's control group (the launch that started it, by its `mcp server`
  line); no server's decision cites a rule without its `for=`, and no
  agent decision a rule with one; every `net.mcp` belongs to an inspected
  connection to an MCP endpoint, in sequence, with its certificate
  re-checked; a released MCP credential only on an allowed call to its
  audience; no token value anywhere.
- `varek refusals --for NAME` and `varek runs` show MCP servers;
  `varek policy show` lists servers, their rules and their credentials;
  `varek doctor` checks each server's file (owner, mode, pin);
  `varek policy suggest --for NAME`.
- The CycloneDX export gains each MCP server as a component (name, file,
  SHA-256) and each remote MCP endpoint reached, with its methods and
  names.
- `varek export --format ocsf` (section 1).

*Tests:* forged streams the audit must refuse (a server's decision on an
agent rule, a `net.mcp` on a passthrough connection, a credential
released to another URL); the tools' outputs.

## 7. Cost

- Deciding by subject partitions the rules: a call is decided against
  fewer rules, so a server's decisions should cost no more than the
  agent's. `varek bench --for` measures it.
- An MCP call over HTTP costs the body's read and parse before the first
  byte is sent: the body is held, not streamed. `varek bench --mcp`
  measures calls of 1 KB to 1 MiB; the latency script reports the
  proxy's added time per call.
- The OCSF export is offline, or a tail of the stream; it adds nothing to
  a decision.

## Decisions before building

Decided 2026-10-13: the recommendation for each, D1 to D12.

- **D1. How an OCSF event is tied to the evidence.** (a) Each event
  carries its record's report id, sequence number and chain hash, and
  `--verify` checks events against the stream; (b) also an OCSF
  `record_integrity` attestation on each event, signed at export with the
  log key; (c) only (b). *Recommended: (a)* in v1.31.0. The stream is the
  evidence and its signatures are the Warden's; an attestation made at
  export would be the exporter's signature over a translation, and
  `record_integrity` is new in 1.9.0, with few readers. (b) can follow
  when SIEMs check it.
- **D2. A dry run's would-be refusals in OCSF.** (a) `action_id` Denied,
  `disposition_id` Detected, labelled `dry_run`; (b) exported as Allowed
  (what happened); (c) not exported. *Recommended: (a).* (b) hides what
  the dry run is for; Blocked would claim an enforcement that did not
  happen; (c) loses the record.
- **D3. How a confined subject is decided.** (a) By its own rules only;
  (b) its own rules first, then the agent's; (c) both must allow.
  *Recommended: (a).* (b) leaves every server as broad as the agent, as
  today. (c) means the agent must be allowed the server's hosts and
  credentials, which is what a server is for keeping from it. (a) means a
  server needs its system reads written for it; `varek run` and `suggest`
  do that. It does not give attenuation (AUT-03): a server's rules may
  allow what the agent's do not, by the operator's choice, and lint notes
  each.
- **D4. Which MCP servers v1.31 decides.** (a) Local servers by what they
  do (section 2), remote servers by method and tool (section 3); the
  agent's calls to a local server are not decided; (b) also a relay the
  Warden places on a local server's stdio, deciding each JSON-RPC message;
  (c) local servers only. *Recommended: (a).* (b) means the agent's MCP
  configuration must name the relay instead of the server, and a relay
  between two supervised processes adds a parser in the Warden's trusted
  computing base; a confined server already bounds what any call to it can
  do. (b) can follow if operators ask for tool-level rules on local
  servers.
- **D5. Following a live stream.** (a) `--follow` writes each event as its
  record is chained, and reports the whole-stream audit at the end; (b)
  batch only. *Recommended: (a).* A SIEM that receives a run's events
  only after it ends cannot alert during it; the record-level checks
  (chain, signature, certificate) run on each record as it arrives.
- **D6. A bearer token the agent sends.** (a) A JWT checked for audience,
  expiry and being the user's token, refusal only; an opaque one decided
  by the rules; (b) every bearer token on an MCP call refused unless VAREK
  released it; (c) not checked. *Recommended: (a).* (b) breaks every
  agent that signs in to a server itself, which the 2026-07-28
  specification expects; (c) leaves the passthrough the specification
  forbids unchecked when VAREK can see it.
- **D7. An MCP credential that is not a JWT.** (a) Refused unless the line
  says `opaque`, and then released by its rules without an audience check;
  (b) checked by token introspection (RFC 7662). *Recommended: (a).* (b)
  needs client credentials at each authorization server and a round trip
  per fetch.
- **D8. Getting MCP tokens.** (a) From stores only (v1.28.0's file, Vault
  and AWS Secrets Manager), with something outside VAREK keeping the token
  there current; (b) VAREK runs the OAuth flow or exchanges the
  user's token (RFC 8693) for one with the server's audience.
  *Recommended: (a).* (b) makes VAREK an OAuth client of every
  authorization server, which v1.28.1's D7 also deferred. It is the
  natural next step for an agent calling an MCP server as its user.
- **D9. The OCSF version.** (a) 1.9.0 only; (b) 1.9.0 and 1.8.0 (without
  the AI attributes, moved to `unmapped`). *Recommended: (a)*, with the
  version an option for later releases. 1.9.0 is the first with
  `ai_agent` and `delegation`, which is most of why the export is worth
  having.
- **D10. The version.** (a) The Warden reports 1.31.0 and the grammar is
  1.31: `mcp server`, `for=`, `confined`, `mcp` rules and `audience=`
  need `require warden 1.31`; v1.30.0's macOS work does not change the
  grammar. (b) Grammar 1.30. *Recommended: (a).* Grammar versions follow
  the release that adds the lines, and v1.30.0 adds none.
- **D11. When the Agent Baseline mapping is published.** (a) Now, against
  the current draft, marked as such, and revised for v1.31.0 and at the
  standard's v1.0 freeze; (b) with v1.31.0. *Recommended: (a).* The
  roadmap says it can go out before v1.31; its rows for v1.31 say "from
  v1.31.0, planned" until then.
- **D12. Enterprise sign-in.** (a) Not in v1.31.0: VAREK Enterprise has no
  admin console; (b) OIDC sign-in and SCIM for one. *Recommended: (a)*, as
  the roadmap says: revisit when a console is planned.
