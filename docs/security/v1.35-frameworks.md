Status: **decided, not built**, target **v1.35.0** (numbered so on October
18, 2026, when macOS became v1.33.0). Drafted and decided October 18, 2026
(Central): the recommendation for each decision below (D1 to D10), D8 on

Ship gate (the roadmap's, extended by D2, decided): for each framework, a sample

## What there is today

The plan gate dates from v1.6.2. As built through v1.32 (file and line
references are to the v1.32 branch):

- **The format** is line-oriented text: `action LABEL KIND TARGET
  [key=value ...]` and `edge FROM TO`, at most 256 actions and 1,024 edges,
  the edges a DAG (`v1_6/plan_parser.h`, `v1_6/README.md`). Three kinds are
  known (`warden.c:1254`): `file_open` (a read or a write by its `open=`
  field), `net_connect` (an address, a Unix socket, or a host name where the
  policy has host-name rules) and `process_exec`. Any other kind is
  UNKNOWN. There is no kind for an MCP call, a credential or a sub-agent.
- **The check** is the Warden's own: `varek run --plan FILE` passes the file
  through; the Warden decides each step with the same procedure and the
  same certificate check as a call (`warden_plan_decider`, `warden.c:1425`),
  after `run_start` and before the agent is forked, and starts the agent
  only if every step is SATISFIED. A refusal prints each step's reason and
  exits 1.
- **It is a check of the plan, not of the run.** Nothing holds the agent to
  the plan once it starts: every call is decided by the policy alone, as
  without a plan (`warden.c:1271`, `threat-model-dataflow.md` L5). A plan's
  fields and edges are the agent's own declarations, not evidence.
- **One plan per launch**, decided once. (`threat-model.md` says plans are
  "re-verified as the agent revises it"; no code does. To be corrected.)
- **Steps are decided as the agent's**, never under a sub-agent's or a
  confined MCP server's rules (the decider's action has subject 0).
- **What a team sees of a refusal is little.** The basic gate's refusal is
  an unchained line on standard error. `varek refusals` reads no plan
  record, so after a refused plan `varek run` says "0 refused"; `varek
  policy check`, which the CLI's and the Warden's messages name for
  checking a plan, takes none. (The flow gate, `--flow-policy`, writes a
  chained `plan_gate` record, but `varek run` cannot pass it.)
- **`process_exec` steps are always UNSATISFIED** (`warden.c:1467`: "the
  Warden refuses every launch after the first"), true before v1.27 and not
  since: with launches decided, the Warden decides each launch by the
  policy. `docs/security/v1.27-program-launches.md` says such steps are
  "now SATISFIED when the policy allows"; the code was not changed.
- **No adapter exists.** Nothing outside the tests writes a plan. The
  in-process integrations at the repository's root (`varek_guardrails/`,
  the notebooks and scripts 04 to 16) are from v1.1, use none of the
  Warden, and two of them import names that no longer exist.

## What v1.35 gains, and what it does not

- **A plan without writing one.** An adapter reads what the framework
  already says about the agent (its tools, its MCP servers, its sub-agents
  or handoffs, the files and hosts its tools are configured with) and
  writes the plan. The team changes no agent code.
- **A refusal before the agent starts, explained**: which step, which rule,
  in `varek refusals` and the verdict stream.
- **A run held to its plan** (D2): the plan narrows the policy for that run
  to what the framework said the agent is for, and the Warden refuses, while
  the agent runs, a call the policy allows but the plan does not name.
- **Plans that name MCP servers, sub-agents and credentials** (D4), decided
  under the rules each is subject to.

It does not make the framework trusted. An adapter's plan is the
framework's description of the agent, written from the agent's own code
and configuration; a plan can only narrow what the policy allows, never
widen it. Every call is still decided by the Warden as now.

## The design in one paragraph

A framework adapter is a small MIT-licensed program, one per framework,
run as its own step before the agent starts (`varek plan generate`), and
confined like an agent (D5), since reading an agent's definition often
means importing its code. It writes a plan in the existing format with the
new kinds (D3, D4), one step for each thing the agent is given: each file
or directory a tool is configured with, each host, each MCP server and the
tools of it the agent may call, each sub-agent, each credential. `varek run
--plan` checks it as now. With `--hold-to-plan` (or the policy's `require
plan`, D7), the Warden also keeps the run's decisions inside the plan: a
call the policy allows is refused if no step of the plan covers it
(`outside_plan`), and the record names the call and the plan. The plan
gate's refusals become chained records that `varek refusals` explains.

## 1. What carries, and what must be built

- **Carries:** the parser, the decider, the certificate check, the DAG and
  the aggregation (UNSATISFIED over UNKNOWN over SATISFIED).
- **To fix first** (D9): `process_exec` decided by the policy when
  launches are decided; the plan gate's records chained; `varek refusals`
  reading them; `varek policy check --plan`; the threat model's sentence on
  re-verification.
- **New:** the kinds of D4; steps decided under their subject; the hold of
  D2 (a per-run narrowing applied after the policy's decision, so the
  decision procedure does not change); `varek plan generate` and the
  adapters; `require plan` (D7).

## 2. The adapters

Each reads a framework's own description of an agent; each is to be
checked against the framework's current release in step 1, as the
frameworks change faster than VAREK:

- **Amazon Bedrock AgentCore** (first, decided October 14): an agent on
  AgentCore Runtime is a container image AWS runs per session; its tools
  come through AgentCore Gateway as MCP servers, and its credentials
  through AgentCore Identity. The adapter writes the Gateway's servers and
  tools and the agent's outbound hosts. Two things to measure (step 1, D8):
  whether AgentCore Runtime lets a container hold what the Warden needs
  (v1.32: ten capabilities, a cgroup namespace of its own), and the
  architecture: AWS documents AgentCore Runtime's containers as arm64,
  and v1.32's image is x86_64 only (v1.33 builds the arm64 Warden).
- **IBM watsonx Orchestrate:** agents and their tools and collaborators
  declared in the Agent Development Kit's files; read as data, without
  importing the agent's code where they suffice.
- **LangGraph:** the compiled graph's nodes and the tools bound to them.
  A LangGraph graph may loop; a plan may not, so a loop is written as its
  steps once (the plan names what may happen, not how often).
- **OpenAI Agents SDK:** an agent's tools, MCP servers and handoffs (a
  handoff is a sub-agent).
- **Claude Agent SDK:** the allowed tools, MCP servers and sub-agents of the
  agent's options.

## 3. Tests

Per framework, the ship gate's two sample agents, run in CI with the
framework pinned; a plan per new kind passed and refused; a run held to its
plan refusing a call outside it, with the policy allowing it; the regression
count against v1.34.0; the 24-hour soak with a framework agent held to its
plan.

## Decisions before building

- **D1. What a plan is for a framework agent.** (a) The agent's capability
  set for the task (every tool, server, sub-agent, file, host and credential
  it is given), one plan per launch, as the gate checks now; (b) a plan per
  step, sent by the agent to the Warden as it decides each step.
  *Recommended: (a).* A framework knows its agent's tools before the agent
  starts, not its steps; a per-step plan comes from the agent's own process,
  which the Warden does not trust, so it could only ever narrow, and (a)
  with D2 already does.
- **D2. Holding the run to its plan.** (a) Opt-in, `--hold-to-plan`: the
  plan narrows the policy for the run, enforced on every call; (b) advisory
  only, as now. *Recommended: (a).* An advisory plan from a framework
  tells the team what the policy would allow, which the policy already
  says; held, it limits a run to what this agent was given, under a policy
  shared by many agents.
- **D3. The format.** (a) The existing line format with new kinds and a
  first line `plan 1.35` (a plan without it is read as now); (b) JSON.
  *Recommended: (a):* the parser, its limits and its tests exist, and the
  adapters, not people, write it.
- **D4. The new kinds.** (a) `mcp_call` (a server and a tool, decided as
  v1.31 decides MCP calls over HTTP; a stdio server's calls are not decided
  in v1.31, so a step for one is UNKNOWN), `subagent` (a name, decided by
  the policy's `subagent=` rules, and the sub-agent's own steps under its
  rules), `credential` (a name, decided as v1.28 releases it); (b)
  `mcp_call` only. *Recommended: (a).*
- **D5. Where an adapter runs.** (a) `varek plan generate --from FRAMEWORK
  ENTRY`, a step of its own before the run, itself run under the Warden
  with the baseline and no network, since importing an agent's module runs
  its code; read as data where the framework's files suffice; (b) inside
  the agent's process at its start. *Recommended: (a);* (b) is the agent
  writing its own plan, which the Warden must check before the agent
  starts, so it cannot come from the agent.
- **D6. Steps decided under their subject.** (a) A step for a sub-agent or
  a confined MCP server is decided under that subject's rules, as its calls
  are; (b) every step as the agent's, as now. *Recommended: (a).*
- **D7. A policy that requires a plan.** (a) A policy line `require plan`
  (grammar 1.35): a run without a plan, or not held to it, is refused at
  start; useful with v1.34's admission, where the cluster says which
  policy a pod runs under; (b) the command-line flag only.
  *Recommended: (a).*
- **D8. If AgentCore Runtime cannot carry the Warden.** (a) Keep AgentCore
  first: the adapter for agents built for AgentCore, run under the Warden
  elsewhere (an EKS cluster with v1.34, or v1.32's image), stated plainly,
  while AgentCore Runtime itself is taken up with AWS; (b) move LangGraph or
  the Claude Agent SDK first, which run anywhere. *Recommended: (a)*, as the
  partnership value is why AgentCore is first; to be settled by step 1's
  measurement.
- **D9. The present mismatches.** (a) Fixed first in v1.35 (step 2): the
  `process_exec` decision, the chained plan records, `varek refusals`,
  `varek policy check --plan`, the threat model; (b) a patch on v1.32.
  *Recommended: (a)*, the `process_exec` refusal being on the safe side; the
  release notes of v1.32 to name the mismatch as a known limit.
- **D10. The in-process integrations from v1.1.** (a) Marked legacy where
  they are, their README pointing to the adapters; (b) removed.
  *Recommended: (a)*, as removing them would break any copy someone has.
- **D11. Plans under the node agent.** v1.34's node agent carries no plan,
  yet D7's `require plan` is meant for v1.34's admission, and D8 (a) runs
  agents built for AgentCore on EKS. (a) v1.35 carries plans in the node
  agent: a pod's plan is given by name, as its policy is (v1.34's D7), the
  node agent checks it before the container's command launches and holds
  the run to it (D2), and `require plan` is enforced at admission and by
  the node agent. A step of a kind the node agent does not carry yet
  (`mcp_call`, `subagent`, `credential`: v1.36) is UNKNOWN there, so its
  plan is refused, never passed; (b) v1.35 states the limit, and v1.36
  carries plans with the rest. *Decided (a)* (October 24, 2026), since
  `require plan` with admission is the cluster use v1.35 is for.

## Implementation plan

1. **Measure:** each framework's current description of an agent (the
   fields each adapter reads); AgentCore Runtime's container (the
   capabilities, the cgroup namespace, arm64) for D8.
   **First reading, each framework's description** (October 19, 2026,
   Central; by an AI research agent, from each framework's released
   packages on PyPI and npm, its repositories and AWS's API definition in
   botocore; AWS's, IBM's and LangChain's documentation sites were out of
   the agent's reach, so what they say is from search excerpts, said so
   below):
   - **Amazon Bedrock AgentCore** (SDK 1.24.1; AgentCore CLI 0.31.1): the
     starter toolkit, and its `.bedrock_agentcore.yaml`, is no longer
     supported; the AgentCore CLI's `agentcore/agentcore.json` is the
     current file: runtimes (protocol, network mode, environment),
     credentials, gateways and their targets (MCP servers, OpenAPI and
     Smithy schemas, Lambda functions, each with its outbound credential
     kind). Both are data. **Neither lists the agent's own tools**: they
     are the inner framework's (Strands, LangGraph, the OpenAI Agents
     SDK), so the AgentCore adapter writes the runtime's, the Gateway's
     and the credentials' steps and calls the inner framework's adapter
     for the rest. A gateway target without a tool schema lists its tools
     from the live server, so its step names the server, not its tools.
     **AgentCore Runtime's API gives a container no settings but its
     image** (`containerConfiguration` has `containerUri` only): no
     capability, privileged mode, seccomp or AppArmor profile can be asked
     for, and no page or field reached says what the container holds. Its
     microVMs take arm64 images, and the "Instances" compute type x86_64
     and arm64 (AWS's pages, from search excerpts). D8 stays open until a
     session in an AWS account shows the container's capabilities,
     `NoNewPrivs`, whether it may load a filter, make namespaces and
     groups, whether its root is writable, and whether a supervisor can run
     the agent as its child while the session is served;
   - **IBM watsonx Orchestrate** (ADK 2.18.2): agents, toolkits and
     connections are YAML or JSON: `tools`, `toolkits` (an MCP server's
     transport, `url` or `command`, and a `tools` allow-list),
     `collaborators`, and connections by name and kind (their secrets are
     set apart). All data. But a native agent runs on IBM's platform, not
     where the Warden is; the plan can be checked, the run cannot be held
     there (the agent's inference, to be confirmed with IBM);
   - **LangGraph** (1.2.16): `langgraph.json` only points at code; the
     graph, its nodes and tools exist only as Python objects, and a graph
     may be built per run by a factory. The adapter imports the module,
     confined (D5); `MultiServerMCPClient` has no per-server allow-list;
   - **OpenAI Agents SDK** (0.24.0): code only: `Agent.tools`,
     `mcp_servers` (each with a static `tool_filter` of allowed and blocked
     names, or a callable) and `handoffs`; imported, confined. Its traces
     go to `api.openai.com` by default, a host the agent's definition does
     not name, which the plan has to;
   - **Claude Agent SDK** (Python 0.2.168, TypeScript 0.3.303): the
     settings files, `.mcp.json` and `.claude/agents/*.md` are data
     (permission rules, MCP servers, sub-agents and their tools); the
     options passed in code are not. Servers can be added and modes
     changed mid-session (`setMcpServers`, `setPermissionMode`), which a
     held run refuses as outside its plan.
   So D5's order holds: read as data where the framework allows
   (AgentCore, watsonx Orchestrate, the Claude Agent SDK's files), import
   under the Warden where it does not (LangGraph, the OpenAI Agents SDK);
   and a server whose tools are found when it is connected is a step
   naming the server, its tools then decided as v1.31 decides MCP calls.
   **Second reading, AgentCore Runtime's container** (October 24, 2026,
   Central; `packaging/agentcore/`, in us-east-1, AgentCore Runtime's
   default compute, two sessions, the probe standing alone, as the
   Warden does not build for arm64 on this branch):
   - arm64 (`aarch64`), Linux 6.1 (Amazon Linux 2023's kernel); the
     container's root filesystem an overlay, writable; `/sys` and the
     cgroup filesystem (cgroup v2) read-only.
   - The entrypoint runs as root (uid 0) with Docker's default
     capabilities and `CAP_SYS_ADMIN` (no `CAP_SYS_PTRACE`), `NoNewPrivs`
     already set, and no seccomp filter of its own.
   - **What the Warden needs holds:** a filter with a listener loads
     (`SECCOMP_FILTER_FLAG_NEW_LISTENER`); user, mount, PID, network,
     cgroup, IPC and UTS namespaces are all made; from a parent,
     `pidfd_open`, `pidfd_getfd` and `process_vm_readv` on its child all
     succeed.
   - **Landlock is absent** (`ENOSYS`: not in this kernel). Decided
     launches (`require warden 1.27`) are held by Landlock, so there
     every launch after the agent's own is refused, as on any host
     without it; plans and policies that need launches decided do not
     run there.
   - **A group cannot be made in place** (`EROFS`; no controller
     delegated in `cgroup.subtree_control`). Sub-agents and confined MCP
     servers need one; the Warden's bind remount (v1.32.1), with
     `CAP_SYS_ADMIN` in its own mount namespace, may lift it there. Not
     measured until the Warden runs there.
   So AgentCore Runtime can carry the Warden's supervision, which
   settles D8 at (a), and better than (a) assumed: the agent can run
   under the Warden on AgentCore Runtime itself, not only elsewhere,
   once the Warden builds for arm64 and without decided launches until
   AWS's kernel has Landlock. A run under the Warden there, with
   sub-agents, is the measurement left.
   **Decided** (October 24, 2026): the Warden's arm64 port is taken onto
   v1.35 from the macOS branch (`claude/varek-v1300-01dbw5`, v1.30's
   Graviton sweep and v1.33's review), rather than waiting for macOS to
   ship: the Warden, its filter, the open flags translated to VAREK's
   encoding (x86_64's) where they are decided and recorded, `run_start`'s
   `arch`, `getpgid(0)` admitted (glibc's `getpgrp()` on arm64), the arm64
   job in CI, `make test-v1300`; macOS itself (the VM, `varek vm`, the Mac
   checks, the Warden's 1.33.0) stays on its branch. Every x86_64 suite it
   touches passes; on arm64, every source compiles and the open-flag
   translation's test passes (under emulation here; CI's arm64 runner
   runs the rest).
2. **The present mismatches** (D9).
   **As built** (October 24, 2026, Central; `tests/test_v1350.sh`, `make
   test-v1350`):
   - **`process_exec`.** Under `require warden 1.27` a step is decided as
     the launch would be (`plan_exec_decide`, `warden_exec.inc.c`): an
     absolute path, opened and named by its canonical path, so a symlink
     is decided on the file it names; the policy's exec rules and the
     certificate; then Landlock and the launch set built at startup. A
     relative path, or a program that is not a file on this host, is
     UNKNOWN; a deny rule, no Landlock, or a file outside the set is
     UNSATISFIED. Without the opt-in the step is UNSATISFIED as before,
     the runtime refusing every launch after the first. Each step not
     SATISFIED is logged with its reason.
   - **The records.** Each step either gate does not find SATISFIED is a
     chained `plan_step` record (label, kind, target, the resolved name,
     decision, the deciding rule's line or -1, the reason), and the basic
     gate's outcome a chained `plan_gate` record (`"gate":"plan"`, the plan,
     its actions and edges, the verdict, and `error` when the plan could
     not be read). The flow gate's `plan_gate` record gains
     `"gate":"flow"`. A changed record fails the audit's chain like any
     other. The OCSF export does not map them yet (step 7).
   - **`varek refusals`** on a refused plan says the plan was refused and
     the agent did not start, then each step with its reason and the
     policy line's text; `varek run --plan` says the plan was refused, not
     "0 refused".
   - **`varek policy check --plan PLAN`** decides the plan as the run
     would, on this host (`warden --check-startup --plan`, which now
     decides the plan and writes no record), with each step's reason;
     exit 1 if refused. With a flow policy a check decides the steps only:
     it does not step the flow policy or the breaker.
   - **The threat model's sentence** was corrected in v1.32.0 ("verified
     … once per launch. The agent is not held to it once it starts"); it
     changes again with the hold (step 4).
3. **The format and kinds** (D3, D4, D6) in the three parsers.
   **As built** (October 24, 2026, Central; `tests/test_v1350.sh` section
   5, `v1_6/tests/test_plan_parser.c`). There is one plan parser
   (`v1_6/plan_parser.c`; the three parsers are the policy's, and the
   policy's grammar does not change in this step). Each new kind is decided
   on what the Warden decides at run time, so a step and the call it stands
   for cannot be decided differently:
   - **`plan 1.35`**, the plan's first line, once (comments may come
     first). Another version refuses the file. A plan without it is read
     as through v1.34, and in it the new kinds and `as=` are UNKNOWN, each
     said why.
   - **`mcp_call URL [method=M] [name=N]`**: the object
     `<canonical URL>#<M>#<N>` (`vdp_mcp_object`), decided by the mcp rules
     and certified, as a call over HTTP is, after its server's host and
     port, decided by the host rules as the proxy decides the connection
     (a call is decided only on a connection they allow). `method` defaults to
     `tools/call`. Without `name=` the step is the server, decided on the
     empty name: SATISFIED only where a rule allows any name. A server that
     is not an `http://` or `https://` URL (a stdio server) is UNKNOWN, its
     calls not being decided; its launch is a `subagent` step.
   - **`subagent NAME [exec=PATH]`**: decided as its launch (as a
     `process_exec` step is, step 2), and SATISFIED only when the rule that
     allows the program carries `subagent=NAME`; a confined MCP server
     (`mcp server NAME exec PATH`) is one. Without `exec=`, the program is
     the one exact rule with `subagent=NAME` names.
   - **`credential NAME`**: SATISFIED when the policy names the credential
     and an allow request or mcp rule of the step's subject carries
     `credential=NAME`; the requests that carry it are decided when made.
   - **`as=NAME`** on any step (D6): decided under a confined subject's own
     rules (and certified under them), as its calls are; for an unconfined
     sub-agent, under the rules of the subject that launches it. A name the
     policy does not give is UNKNOWN.
   - Found while building it: a step the policy itself refused or did not
     allow printed no reason (only its record said why), so `varek policy
     check --plan`, which writes no record, showed nothing for it. Every
     step not SATISFIED now prints its reason.
4. **The hold** (D2) and `require plan` (D7); its records; both under
   the node agent and at admission (D11).
   **As built, the hold on a host** (October 24, 2026, Central;
   `warden_hold.inc.c`; `tests/test_v1350.sh` section 6). `--hold-to-plan`
   (with `--plan`; `varek run --hold-to-plan`) holds the run to its plan
   once the gate passes it: a call the policy allows, and the checker
   certifies, is refused if no step covers it, with the rule
   `outside_plan`. Its record keeps the policy's verdict
   (`decision_raw` ALLOW, `decision_final` DENY) and names the plan;
   `run_start` names the plan and its SHA-256 (`hold`). The decision
   procedure is unchanged: the hold is applied after it, where each kind of
   call is finally allowed, so it can only refuse. What covers a call,
   each step only for its own subject (`as=`, else the agent's):
   - a file open, stat, access, readlink or change by name: a `file_open`
     step for the path, or for a directory above it (a target ending in
     `/`, decided on the directory's name with its `/`); `open=read`
     covers reads only (no write access, no `O_CREAT`, `O_TRUNC` or
     `O_APPEND`, no change by name). A stat, access or readlink of a
     directory above a covered path is covered (a program checks its way
     there), never its listing;
   - a connection (a connect, or a name and port the egress proxy reads):
     a `net_connect` step for the destination, or an `mcp_call` step for a
     server there;
   - a launch after the agent's own: a `process_exec` or `subagent` step
     for the program, matched on the launch set's file (its canonical
     path), not the name given, which may be a link;
   - an MCP call over HTTP: an `mcp_call` step for its object, or, naming
     no tool, for its server and method;
   - a request or MCP call carrying a credential: a `credential` step for
     it (a request is otherwise held by its connection).
   Not held: the agent's own launch, the Warden's synthetic views, the stub
   resolver's answers (names the policy allows), binds. So a held agent's
   runtime is a step too (`file_open /usr/ open=read` and the like);
   writing those is `varek plan generate`'s (step 5). The audit accepts an
   `outside_plan` refusal only in a held run, as a refusal of a call the
   policy allowed, naming the run's plan; `varek refusals` lists it as
   OUTSIDE_PLAN. Tested on files, writes under a read-only step, the
   metadata of a directory above, launches and connections; the MCP call
   and credential paths are built the same way and are tested with the
   proxy in step 8.
   **As built, `require plan` on a host** (October 24, 2026, Central;
   `tests/test_v1350.sh` section 7). A policy line `require plan`
   (grammar 1.35: after `require warden 1.35`, at most once) refuses to
   start a run that has no plan or is not held to it (`--plan PLAN
   --hold-to-plan`), and says why; `--check-startup` notes it. The three
   parsers read it alike (`identity` lists it; the crosscheck's generator
   writes it). The Warden is 1.35.0. Until step 4c the node agent refuses
   a policy with it (`--oci-filter` and admission: "plans (require
   plan)"), as it cannot yet hold a pod to a plan. (Found in step 4c: the
