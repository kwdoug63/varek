# v1.33.0 on an EC2 Mac: the checks and the 24-hour soak

The run that `docs/security/v1.30-macos.md` steps 5 and 7 call for, in one
allocation of an EC2 Mac's dedicated host (billed for 24 hours at least,
about $0.65 an hour in us-east-1): the Mac's checks (`tests/mac_check.sh`),
every suite inside the VM, the soak's trial, then the 24-hour soak
(`tests/mac_soak.sh`). Each step says where it runs. Times are Central.

| When (Central) | What | Where |
|---|---|---|
| Day 1, 8:00 | Allocate the host, launch the Mac | the AWS console |
| 8:30 to 9:00 | The Mac reachable; its tools | the Mac (over ssh) |
| 9:00 | The RHEL image, the checkout | the Mac |
| 9:15 | `mac_check.sh` makes the VM; you register it | the Mac, then the VM |
| 9:45 to 11:30 | `mac_check.sh --sweep --soak-trial` (every suite: an hour or more) | the Mac |
| about 11:30 | `mac_soak.sh start` | the Mac |
| Day 2, about 11:30 | `mac_soak.sh check`; send the results | the Mac |
| after that | Unregister the VM; terminate the Mac; release the host | the VM, the console |

## 1. The host and the Mac (the AWS console, us-east-1)

1. EC2 → Dedicated Hosts → Allocate Dedicated Host: instance family
   `mac2`, instance type `mac2.metal`, an Availability Zone that offers it
   (if one has no capacity, try another), quantity 1.
2. EC2 → Instances → Launch instances:
   - AMI: macOS Sequoia 15 (Apple silicon, "64-bit (Mac-Arm)");
   - instance type `mac2.metal`;
   - key pair `varek-sweep-key`; security group `launch-wizard-3` (it must
     allow ssh, port 22, from where you will connect);
   - Advanced details → Tenancy: Dedicated host; Target host: the host
     from step 1;
   - Advanced details → Metadata version: V2 only (token required), and
     Metadata response hop limit: 1. Root in the VM reaches the instance
     metadata service through the Mac's NAT (October 19: `mac_check.sh`
     reported it); with tokens required and one hop, a token's answer
     cannot come back past the NAT, so the Mac's role is not the VM's;
   - Advanced details → IAM instance profile: a role with
     `AmazonSSMManagedInstanceCore` (`varek-mac-ssm`), for a terminal on
     the Mac in the browser (Systems Manager → Session Manager), without
     the `.pem`. There, first `sudo -iu ec2-user`; and raise Session
     Manager's idle timeout to 60 minutes (its Preferences), or a quiet
     session ends what it runs;
   - storage: the AMI's default is enough.
3. Wait until the instance shows 2/2 status checks passed (often 10 to 20
   minutes for a Mac). Note its public IPv4 address.

### If no host is free: a watcher that allocates one

On October 19 no zone of us-east-1 had a `mac2.metal` host free. A small
function in your own account (`varek/v1_4/tests/mac_watch/varek-mac-watch.yaml`,
made with CloudFormation) tries every 10 minutes, in order: us-east-1
`mac2.metal`, us-east-1 `mac2-m2.metal`, us-east-2 `mac2.metal`, us-west-2
`mac2.metal`, each zone that offers it. A region whose Mac host limit is not
approved yet just fails and is tried next time. Once the host it allocated
is available (a later run: on October 19 a launch the moment the host was
allocated was ended by AWS, `Server.InsufficientInstanceCapacity`, and the
host then spent hours being wiped), it launches the newest macOS 15 AMI there (the key pair
`varek-sweep-key`, imported in each region beforehand; `launch-wizard-3`
where it exists, elsewhere a group allowing ssh from your address only),
emails you, and turns itself off. It never allocates a second host (any Mac
host in those regions stops it), and it stops after 36 hours. No keys are
involved: it runs under a role of its own.

1. Your laptop's address (Git Bash, on the laptop):

   ```
   curl -s https://checkip.amazonaws.com
   ```

2. In AWS CloudShell (us-east-1), the template:

   ```
   curl -fsSLO https://raw.githubusercontent.com/kwdoug63/varek/refs/heads/claude/varek-v1300-01dbw5/varek/v1_4/tests/mac_watch/varek-mac-watch.yaml
   ```

3. In CloudShell, the watcher, with the address from step 1 in place of
   ADDRESS (keep the `/32`) and your email in place of EMAIL:

   ```
   aws cloudformation deploy --region us-east-1 --stack-name varek-mac-watch --template-file varek-mac-watch.yaml --capabilities CAPABILITY_IAM --parameter-overrides SshCidr=ADDRESS/32 Email=EMAIL
   ```

4. Confirm the subscription in the email AWS sends ("AWS Notification -
   Subscription Confirmation"), or the email when the Mac is up will not
   come.
5. After 10 minutes, what it tried (CloudShell):

   ```
   aws logs tail /aws/lambda/varek-mac-watch --region us-east-1 --since 15m
   ```

When it is done (or no longer wanted), remove it (CloudShell; the host and
the Mac are not touched):

```
aws cloudformation delete-stack --region us-east-1 --stack-name varek-mac-watch
```

A host allocated overnight is billed from then; the run after it is the
same.

## 2. On the Mac

Connect from where `varek-sweep-key.pem` is kept (as for the Graviton
instance), with the Mac's address for ADDRESS:

```
ssh -i varek-sweep-key.pem ec2-user@ADDRESS
```

Everything in this section runs on the Mac, as `ec2-user` (not root).

1. Its tools:

   ```
   eval "$(/opt/homebrew/bin/brew shellenv)" && brew install vfkit qemu python git
   ```

2. The checkout of the v1.33 branch:

   ```
   git clone -b claude/varek-v1300-01dbw5 https://github.com/kwdoug63/varek.git ~/varek
   ```

3. The RHEL image. In your browser, sign in at access.redhat.com →
   Downloads → Red Hat Enterprise Linux 9 → version 9.6 or later,
   architecture aarch64 → "Red Hat Enterprise Linux 9.x KVM Guest Image".
   Copy that row's "Download Now" link (it is good for a short time), and
   note its SHA-256 (shown on the same page). On the Mac, with the link for
   LINK:

   ```
   curl -fL -o ~/rhel-9-aarch64-kvm.qcow2 'LINK'
   ```

4. The checks, the first time with the image and its SHA-256 for HEX:

   ```
   ~/varek/varek/v1_4/tests/mac_check.sh --image ~/rhel-9-aarch64-kvm.qcow2 --sha256 HEX
   ```

   It makes the VM, and stops (exit 3) for you to register it with your own
   Red Hat login. In the VM (the first command, on the Mac, opens a shell
   there):

   ```
   python3 ~/varek/varek/v1_4/tools/varek vm ssh
   ```

   ```
   sudo subscription-manager register
   ```

   Then `exit`, back on the Mac.

5. The checks again, carrying on, with every suite and the soak's trial
   (an hour or more). In the background, so a dropped session does not
   stop it (macOS's `nohup` refuses to run without a console, as under
   Session Manager, so the hangup is ignored by hand):

   ```
   /bin/zsh -c 'trap "" HUP; ~/varek/varek/v1_4/tests/mac_check.sh --sweep --soak-trial' > ~/mac_check.out 2>&1 < /dev/null &!
   ```

   To see where it is:

   ```
   tail -3 ~/mac_check.out
   ```

   It must end `mac_check.sh: PASS`. Send me its summary in pieces:

   ```
   sed -n '1,20p' ~/varek-mac-check/summary.txt
   ```

   ```
   sed -n '21,45p' ~/varek-mac-check/summary.txt
   ```

   ```
   sed -n '46,90p' ~/varek-mac-check/summary.txt
   ```

   If a check fails, stop here and send the summary: we fix it before the
   soak, in the same allocation.

6. The 24-hour soak. It starts the VM again (`mac_check.sh` stops it at
   its end) and runs in the background in the VM; the Mac is kept awake.
   Do not stop the VM, or run `mac_check.sh`, until it ends:

   ```
   ~/varek/varek/v1_4/tests/mac_soak.sh start
   ```

   You can close ssh. To look at it later (on the Mac):

   ```
   ~/varek/varek/v1_4/tests/mac_soak.sh status
   ```

7. After 24 hours (the start's output says when it ends):

   ```
   ~/varek/varek/v1_4/tests/mac_soak.sh check
   ```

   It prints the report and ends with `soak_check: PASS` or `FAIL`; the
   report and the soak's files are copied to `~/varek-mac-soak/` on the
   Mac. Send me the report in pieces:

   ```
   sed -n '1,25p' ~/varek-mac-soak/report.txt
   ```

   ```
   sed -n '26,60p' ~/varek-mac-soak/report.txt
   ```

## 3. Afterwards

1. In the VM (opened from the Mac with `python3 ~/varek/varek/v1_4/tools/varek vm ssh`),
   take the VM out of your Red Hat account:

   ```
   sudo subscription-manager unregister
   ```

   (or delete its record later at console.redhat.com → Inventory).
2. The AWS console: terminate the Mac instance. AWS then scrubs the host
   (an hour or more; the host shows "pending"); once it is "available",
   and 24 hours after it was allocated, Dedicated Hosts → the host →
   Actions → Release host. Check that EC2 → Volumes shows none left.
