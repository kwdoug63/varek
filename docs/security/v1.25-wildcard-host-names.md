# v1.25 — wildcard host names, opt-in (plan)

Status: **in progress**, target **v1.25.0** (decided 2026-10-05). Builds on
v1.24.0 (exact host names, [design](./v1.21-stage2-host-names.md)). Sections 1
(grammar), 2 (shared domains refused at load), 3 (the stub resolver) and 4
(budgets and question records) are implemented, and section 5 (the 24-hour
run) has passed ("Implementation notes" at the end). Each section ends with what must
be tested before it ships.

## Why, and why opt-in

v1.24.0 lets a policy name hosts exactly (`allow host api.salesforce.com:443`)
and keeps the agent off DNS entirely: the Warden resolves every allowed name
before the agent runs and serves a hosts view. That works because the list of
names is known in advance. A wildcard (`allow host *.example.com:443`) has no
list. The names under it are only known when the agent asks for one, so they
have to be resolved on demand, and the agent's lookups become queries that
leave the host.

Two consequences, which is why wildcards are a separate, opt-in rule form
rather than a variant of exact names:

1. **The name itself is a channel.** An agent that looks up
   `<encoded-data>.example.com` delivers that label to the authoritative DNS
   servers for `example.com` (and to the host's recursive resolver). That is a
   party the policy already trusts with HTTPS traffic, but it is still a path
   out that exact names do not have. v1.25 bounds it (section 4); it does not
   close it. The v1.26 egress proxy decides on the name without any query from
   the agent.
2. **Some domains let anyone create names under them.** `*.s3.amazonaws.com`,
   `*.cloudfront.net`, `*.herokuapp.com` and `*.github.io` each cover names an
   attacker can register, and `*.my.salesforce.com` covers every company's
   Salesforce org, not only the buyer's. Allowing such a pattern allows the
   attacker's endpoint. v1.25 refuses those patterns at load (section 2).

## 1. Policy grammar

- `allow host *.<suffix>:<port> acknowledge=dns-channel` and
  `allow host *.<suffix> acknowledge=dns-channel` (any port). Every wildcard
  allow rule carries `acknowledge=dns-channel`; without it the policy is
  refused (see "The acknowledgment" under Implementation notes).
  `*.` appears once, as the whole leftmost label; `<suffix>` follows the
  v1.24 name rules (lowercase, A-labels only, no trailing dot).
- `*.example.com` matches any name with one or more labels before
  `.example.com` (`a.example.com`, `a.b.example.com`), never `example.com`
  itself. A policy that wants both writes both rules.
- `deny host *.<suffix>` and `deny host <name>` carve exceptions as usual,
  first match wins, decided by the existing suffix matcher (v1.14), so both
  parsers already agree on the matching; only the name validation is new.
  (v1.25 review: a deny wildcard holds on the names under it the agent asks
  for, not on their addresses, which cannot be resolved in advance; see "After
  the review".)
- `require warden 1.25` for a policy with a wildcard rule; earlier Wardens
  refuse it (`policy requires Warden 1.25`). The policy-grammar version moves
  to 1.25 in both parsers.

*Tests:* parser refusals (`*` mid-name, `**.`, bare `*`, `*.` with one label
after it, uppercase, U-labels), both parsers agree, the cross-check oracle
extended with wildcard constants, first-match order between exact and
wildcard rules.

## 2. Patterns refused at load

- A pattern whose `<suffix>` is a public suffix, or lies under an entry in the
  Public Suffix List's private section, is refused with the matching entry
  named (`*.s3.amazonaws.com: s3.amazonaws.com is a shared domain where anyone
  can register names`). `*.com` and `*.co.uk` are refused by the same rule.
- The list is a pinned snapshot shipped with the release; its SHA-256 is in
  `run_start`, so an audit knows which list a policy was checked against.
  `varek policy check --explain` names the entry for each refusal.
- A short VAREK list adds multi-tenant domains the Public Suffix List does not
  carry (for example `my.salesforce.com`, `force.com`, `salesforce-sites.com`),
  reviewed per release and recorded the same way.
- An operator who needs a refused pattern writes exact names instead, or uses
  the v1.26 proxy, where the decision is on the name the client sends and the
  same refusal applies.

*Tests:* every private-section entry refuses a pattern at and under it; the
VAREK list; `--explain` output; the snapshot hash in `run_start` and checked
by the audit.

## 3. On-demand resolution by the Warden

- The `/etc/resolv.conf` view names a Warden-owned stub address, and
  `/etc/nsswitch.conf` reads `hosts: files dns`. Connects to that address on
  port 53 (UDP and TCP) are handed by the Warden to its own stub resolver;
  every other connect to port 53 stays refused, as in v1.24.
- The stub answers only A and AAAA questions (and the empty answer for
  others), one question per message, no EDNS options beyond the payload size.
- A question for a name that matches an exact or wildcard allow rule (and no
  earlier deny) is resolved by the Warden through the host's resolver; the
  answer goes into the v1.24 resolution table with its TTL, and the agent gets
  those addresses. Any other name gets NXDOMAIN at once, and no query leaves
  the host.
- The hosts view still lists the exact names, so libraries that read only
  `/etc/hosts` keep working for them.
- Connect decisions, certificates and audit are as in v1.24: the decision is
  on `name:port` for the names that resolved to the address dialed, and the
  record carries the resolution it relied on.

*Tests:* glibc, musl, Go, Java and Node (`dns.lookup` and `dns.resolve4`)
resolve a wildcard-matched name and connect; a name outside every rule gets
NXDOMAIN within 50 ms and produces no upstream query (checked with a
recording upstream); non-A/AAAA questions; TCP fallback; no connect to any
other port-53 destination.

## 4. Bounding the name channel

- Each wildcard rule has a budget of distinct new names per run (default 256)
  and per minute (default 30), and a cap on the length of the part matched by
  `*` (default 63 bytes). A question past a budget is answered NXDOMAIN and
  recorded as `rule: wildcard_budget` with the rule's line.
- Every question the stub receives is a chained record in the verdict stream
  (`event: dns_question`: name, type, the rule that matched or none, the
  answer), signed by the next checkpoint. `varek refusals` lists budget hits.
- Budgets are set per rule in the policy
  (`allow host *.example.com:443 names=64 rate=10 acknowledge=dns-channel`) and shown by
  `varek policy show`.
- What remains, and is stated in the threat model: within the budget, the
  labels an agent chooses reach the domain's authoritative servers.

*Tests:* a DNS-tunnel style client is held to the budget and recorded;
budgets per rule; records chained and audited; tampering fails the audit.

## 5. A real wildcard workload

Before v1.25 ships, an agent runs for 24 hours against a SaaS API reached
through per-tenant names under one suffix, fetching every minute, and shows no
refused connect from a stale table, every question recorded, and no budget hit
in normal use at the default budgets.

## 6. What changes for operators

- `allow host *.example.com:443 acknowledge=dns-channel` works, with the refusals of section 2 and the
  budgets of section 4.
- The stub resolver is the Warden's; the host keeps its own resolver, which
  the Warden uses.
- Policies with only exact names behave exactly as on v1.24 (no stub, no DNS
  for the agent).

## Open questions

- Default budgets: decided 2026-10-07, 256 names per run and 30 per minute
  (see "Default budgets" under Implementation notes).
- The `acknowledge=dns-channel` token: decided 2026-10-07, required on every
  wildcard allow rule (see "The acknowledgment" under Implementation notes).

## Implementation notes

### Sections 1 and 2

Decided 2026-10-06. Tests: `make test-v1250` and `make crosscheck`.

**Grammar.**
- After `require warden 1.25`, `*.<suffix>[:port]` is a wildcard host rule.
  `<suffix>` must be a valid v1.24 name of at least two labels.
- Each parser converts the rule to the existing glob atom: `?*.<suffix>:<port>`,
  or `?*.<suffix>:*` without a port. These are the decision procedure, the
  certificate checker and the cross-check oracle, each written separately.
  So the rule is decided, certified, checked for reachability and fuzzed like
  any glob, with no new matcher. The plan said "the existing suffix matcher";
  a suffix cannot express "any port", and the glob can.
- The glob is exact on the strings a connect is decided on, which are always
  valid names with a port. `?*` needs at least one byte before
  `.<suffix>`, and the name rules rule out a leading dot.
- A wildcard before `require warden 1.25` is refused, naming the directive it
  needs. Under 1.24 it is refused rather than given the v1.21 meaning, because
  1.24 already refused `*` in a name.
- The Warden compares the two C parsers' readings, now including the wildcard
  bit. A wildcard names no host to resolve in advance, so it adds nothing to
  the resolution table.

**Shared domains** (`varek/v1_4/shared_domains.c`).
- The lists are pinned files in `varek/v1_4/data/`:
  - `public_suffix_list.dat`: fetched 2026-10-06 from the publicsuffix/list
    repository, MPL-2.0, with its header kept. SHA-256
    `102b252c18b5f87f4c81f017e75282a82c18e00cd0c2e601b5b02a0f7a601f2c`. It
    holds 6,949 ICANN rules and 3,384 private rules.
  - `varek_shared_domains.txt`: domains the list lacks. It started with 11:
    `my.salesforce.com`, `force.com`, `salesforce-sites.com`,
    `visualforce.com`, `my.site.com`, `amazonaws.com`, `zendesk.com`,
    `atlassian.net`, `freshdesk.com`, `service-now.com` and `sharepoint.com`.
    On 2026-10-06, choosing the section 5 workload showed that sites anyone
    can create a name under were missing too. Twenty were added:
    - blogs, newsletters and site builders: `wordpress.com`, `substack.com`,
      `fandom.com`, `tumblr.com`, `medium.com`, `squarespace.com`,
      `ghost.io`, `beehiiv.com`, `hashnode.dev`, `livejournal.com`,
      `neocities.org`, `glitch.me`, `railway.app` and
      `hubspotpagebuilder.com`;
    - tenants anyone can sign up for: `slack.com`, `zoom.us`, `okta.com`,
      `auth0.com`, `freshservice.com` and `typeform.com`.
  - `make install` copies both to `<prefix>/data/`.
- **ICANN section:** the suffix is refused when it is itself a public suffix,
  by the list's normal, `*` and `!` rules. So `*.com` and `*.co.uk` are
  refused, and `*.example.co.uk` is not.
- **Private section and the VAREK list:** the suffix is refused when it is an
  entry or is under one. So `*.s3.amazonaws.com`,
  `*.bucket.s3.amazonaws.com` and `*.myorg.github.io` are refused. A private
  `!` rule does not lift its parent's refusal.
- **Unicode entries** are compared in A-label form. An RFC 3492 encoder in
  `shared_domains.c` matches Python's punycode on all 440 Unicode labels in
  the list.
- **Where it applies:** only allow rules are refused; a deny wildcard over a
  shared domain is harmless. The Warden refuses such a policy at startup
  (`--check-startup` too), naming the entry. `vdp_check lint`, and so
  `varek policy check`, names it too.
- **Missing lists:** when the lists cannot be read, a policy with wildcard
  rules is refused. Use `--psl` and `--shared-domains` to point elsewhere.
  `run_start` carries `psl_sha256` and `shared_domains_sha256`.
- **Checked against an independent statement:**
  `tests/v1250_psl_oracle.py` states the same rule in Python. It agrees with
  `shared_domains.c` on 17,800 suffixes: every private entry and a name under
  it, the ICANN public suffixes, and the `*` and `!` rules.

### Section 3

Decided 2026-10-06. Code: `varek/v1_4/warden_stub.inc.c`; tests: section 3 of
`make test-v1250`.

**Where the stub is.**
- The stub is at `127.53.53.53:53`, UDP and TCP, bound by the Warden inside
  the agent's own network namespace. The Warden brings that namespace's
  loopback up for it; nothing else is in the namespace. Every other connect
  is still dialed by the Warden in the host's namespace, so a stub in the
  agent's namespace cannot reach anything, and the host's own resolvers
  (`127.0.0.53`, dnsmasq) are never in the path.
- Without a network namespace of its own for the agent there is no stub. The
  Warden says so, and names only a wildcard allows do not resolve.
- `run_start` carries `"dns_stub":"127.53.53.53:53"` whenever the policy has
  a wildcard allow rule.

**Reaching it.**
- A connect to `127.53.53.53:53` (or its IPv4-mapped form) on a UDP or TCP
  socket is made by the Warden on the agent's own socket, to the Warden's
  copy of the address. It is not dialed from the host and not handed over,
  because the destination is in the agent's namespace. The agent then sends
  and receives on that socket itself. glibc, Go and c-ares connect their UDP
  sockets this way.
- musl sends with `sendto()` on an unconnected socket. A `sendto()` naming the
  stub on a UDP socket is read once and sent by the Warden from the agent's
  socket, so the answer comes back to it.
- Both are records with rule `dns_stub` (no certificate: they reach nothing
  outside the agent's namespace). `varek_audit.py` accepts `dns_stub` only to
  the address `run_start` names.
- Every other connect to port 53 is refused (`dns_refused`), as in v1.24.

**Views.**
- With the stub up, `resolv.conf` reads `nameserver 127.53.53.53` and
  `options attempts:2 timeout:5`, and `nsswitch.conf` says
  `hosts: files dns`. The hosts view still lists the exact names, so they
  never reach the stub through glibc.
- Two more views, both empty, are served only with the stub up:
  `/etc/netsvc.conf` (`netsvc_view`) and `/etc/svc.conf` (`svc_view`). c-ares
  reads them after `resolv.conf` and `nsswitch.conf`. The Warden answers
  EACCES for a file it does not allow, whether or not it exists, and c-ares
  takes that as a broken configuration: it discarded everything it had read
  and asked 127.0.0.1, so Node's `dns.resolve4` failed.

**Answering.**
- One question per message, class IN. A message that is not a query is
  dropped. A malformed one gets FORMERR, as do one with more than one
  question and a non-standard opcode.
- A name that is not a valid host name gets NXDOMAIN.
- A name is answered only when a connect to it could reach an allow rule. The
  Warden decides `name:port`, with the decision procedure, for every port a
  host rule names and for one port no rule names; if any of these is
  SATISFIED the name may be resolved. Anything else gets NXDOMAIN at once,
  and no question leaves the host. A port that only a glob over ports allows
  is not tried; such a name gets NXDOMAIN, the safe side.
- A name an exact rule names is answered from the table, as the hosts view
  is.
- A name a wildcard matches becomes a dynamic entry of the resolution table.
  The resolver helper looks it up, A and AAAA. The result is a `resolution`
  record with `"dynamic":true`, and the agent's waiting questions are
  answered from it. NXDOMAIN on both types gives NXDOMAIN. A failed lookup
  with no address gives SERVFAIL.
- Questions other than A and AAAA for an allowed name get an empty answer and
  send nothing upstream.
- The answer's TTL is the time left until the entry's refresh is due. A UDP
  answer is at most 512 bytes; the rest of the addresses are left out with TC
  set, so the client can ask over TCP.

**Dynamic entries.**
- A dynamic entry is looked up only when the agent asks. It is never
  refreshed on its own, so no upstream query happens that the agent did not
  cause.
- While its TTL lasts, further questions are answered from the table.
- When the TTL passes with no new question, its addresses go into grace (the
  TTL, at most `--dns-grace-max`), and the next question looks it up again.
  This retirement writes no record. An audit that reads the last
  `resolution` record therefore accepts a connect slightly longer than the
  Warden would, never shorter.
- Dynamic entries are not in the hosts view.
- At most 1,024 dynamic names per run; past that, SERVFAIL. Section 4
  replaced this with per-rule budgets and a 4,096-name backstop.

**Known, for section 4 and 5.**
- An address could carry at most 15 names (NAMES_MAX_CAND). Per-tenant names
  under one suffix often share a CDN's addresses. With more than 15 such
  names resolved and current, a connect to that address was refused
  (`too_many_names`). Lifted on 2026-10-06; see "Many names on one address"
  below.
- Stub questions are not yet records; `dns_question` records come with the
  budgets in section 4. (Done: see below.)

### Section 4

Decided 2026-10-06. Code: `varek/v1_4/warden_stub.inc.c` (budgets and
records), the three policy parsers (grammar), `tools/varek_audit.py`,
`tools/varek`; tests: sections 1 and 4 of `make test-v1250`.

**Grammar.**
- `allow host *.example.com:443 names=64 rate=10 acknowledge=dns-channel`.
- `names=` is 1 to 100,000 and `rate=` is 1 to 10,000, decimal with no
  leading zero, each at most once.
- They are allowed only on a wildcard allow rule. On an exact name, a deny,
  or out of range, the policy is refused.
- The decision procedure, the certificate checker and the cross-check oracle
  each parse them separately. The Warden compares the two C parsers'
  readings, budgets included. Budgets take no part in any decision.
- Defaults: 256 names a run and 30 a minute. The label budget is fixed at 63
  bytes, the most one DNS label holds; it counts every byte before the suffix,
  dots included.

**Charging.**
- A question charges a rule only when it would add a name, that is, one the
  table does not hold. The name is charged to the rule `name:port` was decided
  on: an exact allow rule if one decides some port (no charge), otherwise the
  first wildcard rule that does.
- A name asked again is never charged again against names=. The budgets
  count names, not questions. (v1.25 review: but a name asked again after
  its TTL, which goes upstream again, counts against rate=; see "After the
  review".)
- The checks, in order, are the label budget, then names, then rate. Rate
  counts lookups sent upstream in the last 60 seconds, a sliding window.
- A question past a budget gets NXDOMAIN, the name is not added, and nothing
  is looked up. Its record has rule `wildcard_budget`, the rule's line and
  `budget: names|rate|label`.
- A global backstop of 4,096 dynamic names per run remains.

**Records.**
- Every question the stub receives is a chained `dns_question` record:
  - `name`, `type` and `transport`;
  - `rule`: `policy_match`, `exact_name`, `wildcard_budget`, `no_rule`,
    `not_a_host_name` or `malformed`;
  - `policy_line`, and `budget` for a budget refusal;
  - `new`, when the question charged a name;
  - `answer`: `noerror`, `nxdomain`, `servfail`, `formerr` or `lookup`;
  - `addresses`, the answer's addresses for a NOERROR answer;
  - the table generation.
- `lookup` means the resolver helper was asked; the next `resolution` record
  for that name is the answer.
- A name that is not a valid host name is not quoted in the record (it may
  hold any byte).
- `run_start` carries `wildcard_budgets`: each wildcard allow rule's line,
  names, rate and label budgets, with the defaults filled in.

**Audit** (`varek_audit.py`, check 7). The audit fails a stream unless:
- `run_start`'s budgets are the ones the policy file sets, read by the audit
  itself;
- each charged name is charged once, under its rule's suffix, and within its
  rule's names, rate and label budgets;
- each budget refusal, and each question no rule allows, is NXDOMAIN and
  charges nothing;
- each name looked up on demand was asked for first and charged;
- each NOERROR answer carries only addresses the name's latest resolution
  lists.

A forged stream with the chain recomputed fails in three tested cases: a
question removed, run_start budgets changed, and a budget refusal turned into a
sixth charge to a `names=5` rule.

**CLI.**
- `varek refusals` lists budget refusals as BUDGET, with the policy line and
  which budget ran out.
- `varek policy show` lists each wildcard rule's budgets.

**Defaults.** 256 names a run and 30 a minute, decided 2026-10-07
("Default budgets" below). The `acknowledge=dns-channel` token was decided
the same day ("The acknowledgment" below).

### Many names on one address

Decided 2026-10-06, while choosing the section 5 workload. Every Wikipedia
language edition (`*.wikipedia.org`) resolves to one address, as per-tenant
names behind a CDN do. Under the 15-name limit, every connect to that address
would have been refused once 16 languages had been resolved.

- **No limit.** A connect is decided over the address and every name it
  belongs to, current or in grace, however many there are. The candidates
  are held in a growable array outside `struct action`, used before the
  connect is dialed or left pending. The certificate checker's earlier-rule
  check covers every one of them.
- **The record.** Up to 16 candidates (the address and 15 names) are listed,
  as in v1.24. Past that the record carries `candidates_n` and
  `candidates_sha256`: the SHA-256 of all the candidates, sorted bytewise
  and joined with newlines.
- **The audit** rebuilds the candidates from the resolution records before
  the connect: every name whose latest record lists the address, or holds it
  in grace. It checks the count and the hash, that the deciding candidate is
  among them, and that no earlier host rule holds on any other.
  - A record gives grace in whole seconds, while the Warden keeps it to the
    millisecond. So a name within about a second of its grace ending may be in
    or out, and the audit tries each way.
  - More than 12 such names at once on one connect cannot be checked, and
    the audit says so.
- **Names that expire unasked.** A dynamic entry whose TTL passes with no new
  question moves its addresses into grace. That move now writes a
  `resolution` record with `"a":"retired"` and `"aaaa":"retired"`.
  - Without it, the audit read the name's last answer as still current and
    refused a later connect to the same address under another name: the name
    "resolved to it but is not a candidate".
  - `check_dns` does not count a retired record as a lookup.
- **Tests:** section 4b of `make test-v1250`.
  - 40 names on one address all fetch, their connects are hashed past 15, and
    the audit accepts the run.
  - A forged resolution record, with the chain recomputed, fails the audit.
  - A name that expires unasked is recorded, and a later connect under
    another name is accepted.
  - Against the build before this change, 5 of its 7 checks fail.

### Default budgets

Decided 2026-10-07: 256 names a run and 30 a minute, unchanged. The
section 5 run, below, used 40 names and at most 2 a minute.

**What a budget bounds.** Only names that reach the domain's servers carry
data out. A name the stub sends upstream is lowercase letters, digits,
hyphens and dots; any other byte makes it a non-host name, which no rule
matches and nothing looks up. So each charged name carries at most about
5.25 bits a byte over its 63 label bytes, about 41 bytes. Per wildcard rule:

| Budget | Names | Most data in the names chosen |
|---|---|---|
| Per run (`names=`, default 256) | 256 | about 10.5 KB |
| Per minute (`rate=`, default 30) | 30 lookups | about 1.2 KB a minute, until `names` runs out (about 9 minutes) |

Re-asking a name already charged adds nothing to names=, and sends a lookup
only after its TTL. (v1.25 review: such a lookup counts against rate=, so
which names are re-asked carries at most about 8 bits a lookup, 30 bytes a
minute at the default, about 43 KB a day; the timing of each lookup a few
bits more. Through d69e330 it counted against nothing.)

**What the run shows.** The section 5 workload is 40 names, asked in turn,
one fetch a minute. Figures from `report.txt`:

- names charged: 40 of 256; most in any minute: 2 of 30;
- budget refusals: 0;
- lookups on demand 1,440, retirements 1,440; most names on one address 4.

(2026-10-07 to 2026-10-08, 1,440 of 1,440 fetches OK, 0 refused connects;
see `RELEASE-v1.25.0.md`.)

The run shows whether the defaults are hit in normal use. It does not show
where a ceiling should be: an agent with more tenants, or one that reaches
them all at startup, asks more.

**Why these.**
- An allowed wildcard host is already a channel for whatever the agent sends
  it over HTTPS. The names reach the same domain's own servers, since shared
  domains are refused at load, so the budgets bound a second, narrower
  channel to the same party.
- 256 is more than six times the run's names, and an agent that needs more
  says so in its policy (`names=`), where a reviewer sees it.
- 30 a minute lets an agent reach 30 tenants at startup at once; a burst
  past that is refused, recorded as `wildcard_budget` and listed by
  `varek refusals`, and the agent may retry a minute later.

### The acknowledgment

Decided 2026-10-07. Code: the three policy parsers, `tools/varek`; tests:
section 1 of `make test-v1250`.

**Why.** A wildcard rule looks like a broader exact name, but it changes
where the agent's lookups go: under an exact name the agent sends no DNS,
and under a wildcard its lookups leave the host. They reach the host's
resolver and the domain's DNS servers, which may be run by a DNS provider
rather than the party behind the API. The policy is what a reviewer reads,
so the trade-off is written in the rule itself.

**Grammar.**
- Every wildcard allow rule carries `acknowledge=dns-channel`, in any position
  among its options (`allow host *.example.com:443 names=64
  acknowledge=dns-channel`). Without it the policy is refused: "a wildcard
  rule sends the agent's lookups out of the host; add
  acknowledge=dns-channel to allow it".
- It is on each rule, not once a policy, so a rule copied between policies
  carries it, and a later rule is not covered without its own.
- Refused: any other `acknowledge=` value, the token given twice, and the
  token on an exact name, a deny or a path or exec rule.
- The decision procedure, the certificate checker and the cross-check oracle
  each parse it separately; the fuzzed policies include it missing,
  misspelt, twice and misplaced. It takes no part in any decision.
- `varek policy show` says, for each wildcard rule, that the agent's lookups
  under it leave the host.

### After the review

Decided 2026-10-07, after the review by AI review agents (the findings are
in `RELEASE-v1.25.0.md`, "Found in review").

- **Parents of shared domains.** A suffix with any list entry under it, or
  the base of an ICANN `*.x` rule, is refused (`shared_domains.c`,
  `mark_above`), naming the entry: `*.salesforce.com` would cover
  `my.salesforce.com`. Chosen over refusing such names at run time, which
  would have changed what a rule matches in all three parsers.
- **Pinned lists.** `shared_domains.h` holds the release's SHA-256 values;
  `make test-v1250` checks they match `data/`. Lists in `data/` that differ
  stop the Warden; lists named on the command line are used and recorded
  (`"shared_lists_pinned":false`). A Public Suffix List needs its END marker
  and at least 1,000 ICANN and 100 private rules. The audit checks each
  wildcard again with `vdp_check lint` against the release's lists.
- **Re-lookups charge rate=.** Every lookup sent upstream counts in the
  rule's sliding minute; a lookup already on its way is shared. Questions
  that send one are `"upstream":true`, with the Warden's monotonic time
  (`"mono_ms"`), on which the audit counts the window.
- **Exact grace.** The Warden writes a resolution record when an address's
  grace ends (`"a":"grace_end"`), before a connect decided at that time
  (`wr_grace_due`), and `wr_apply` drops only its own entry's ended grace. A
  lookup out at the end of the run is recorded `"unanswered"`. So the audit
  rebuilds hashed candidates exactly, with no guessing from grace in whole
  seconds.
- **Stub connects.** A TCP connect to the stub is non-blocking; if still in
  progress, it waits as a pending operation (`PEND_STUB`).
- **The audit** takes the policy's rules from the checker's `rules` mode
  (now with wildcard, line, budgets and constant), checks each question's
  rule against the stub's own choice (`holds`), accepts `dns_stub` only with
  a wildcard rule and only to `127.53.53.53:53`, and requires every lookup
  sent upstream to be answered.
- **Deny wildcards** hold on names only, documented rather than changed: a
  CNAME chain could be followed, but two names merely sharing an address
  could not be caught without resolving the deny's names in advance, which
  a wildcard does not allow.
