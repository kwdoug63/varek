# v1.28.1 — the on-behalf-of chain: who each decision was for (plan)

Status: **in progress**, target **v1.28.1**. Decided 2026-10-13: the
recommendation for each decision below (D1 to D9). Built: step 1 (see "As

soak on the droplet covers the three releases' changes on the final build,
before any of them is tagged.

## What v1.28.0 leaves open

The verdict stream says what was decided, under which policy, by which
Warden, for which run. It does not say for whom. An agent acts for a
person (the user who asked it to do the task), and often hands parts of the
task to other agents (sub-agents) it starts. Today:

- **The user is not recorded.** `run_start` names the run and the policy,
  and the operator can be inferred from the host, but nothing says on whose
  behalf the agent acted, or with what authority. An auditor asking "what
  did the agent do for Alice?" has no field to filter on.
- **A sub-agent is indistinguishable from its parent.** A program the agent
  launches (from v1.27.0) that is itself an agent runs under the same run;
  its decisions are recorded with its process id only, and a process id says
  nothing about which agent a process belongs to.
- **Identity systems already exist and are not read.** Enterprises issue
  users OAuth 2.0 / OpenID Connect tokens, record delegation with OAuth
  token exchange (RFC 8693: an `act` claim naming the actor, nested for each
  further delegation), and give workloads SPIFFE IDs. VAREK accepts none of
  them.

## What it gains, and what it does not

With the on-behalf-of chain, every decision record names the chain it was
made for: the user (from a token the Warden verified at start), the agent
(the run, and its workload identity if it has one), and the sub-agent (if
the call came from one), so:

- **Each decision answers "for whom".** The audit and the export can
  filter, count and attest by user and by sub-agent.
- **The chain is verified, not asserted.** The user's token is checked
  against its issuer's keys, its audience and its expiry; a SPIFFE ID
  against its trust bundle. What the run records is what was verified, and
  a link that was not verified says so.
- **A sub-agent cannot pass as its parent.** Its processes are held in
  their own control group from launch, which they cannot leave; each call is
  attributed by the kernel's record of that group, not by anything the
  process says.

It does not (in v1.28.1):

- make decisions depend on the chain (no rule says "only for Alice"): the
  chain is recorded and audited, and the decisions are unchanged (D6);
- give a sub-agent less authority than its parent (the same policy holds);
- mint tokens, exchange them, or act as an identity provider: VAREK reads
  identities others issue (D7);
- prove the user meant the agent to do any particular thing: a token says
  the user delegated to the agent, not what for.

## The design in one paragraph

The operator starts a run with the user's token (`--on-behalf-of FILE`, a
root-owned file holding an OAuth 2.0 / OIDC JWT, possibly the result of a
token exchange) and, optionally, the agent's SPIFFE identity. Before the
agent starts, `warden-secrets` (already the Warden's verified-HTTPS helper,
and the only process that sees a token) checks the token against an issuer
the policy trusts: signature against the issuer's keys (JWKS), audience,
time, and the `act` chain inside it. The Warden records the verified claims
in `run_start` (issuer, subject, audience, expiry, the actors of a
delegation, the token's SHA-256; never the token) as the run's chain. A
program the policy names as a sub-agent is put, at its launch, in its own
control group (cgroup v2) that it and its children cannot leave; every
decision record carries `obo`, the chain it was made for: the run's, or the
run's with that sub-agent appended. The audit checks the chain against the
policy's trusted issuers and every record's `obo` against the launches
that started each sub-agent. When the user's token expires, the run is
revoked (v1.28.0's revocation), unless the operator chose otherwise.

## 1. Policy

- `trust issuer URL audience AUD [jwks URL]` (after `require warden 1.28`):
  an issuer whose tokens the run accepts for the user, the audience they
  must carry (the agent's own client id, as the IdP issued it), and where
  its keys are (default: the issuer's OpenID discovery document). More than
  one issuer may be named.
- `trust spiffe TRUST_DOMAIN bundle PATH`: a SPIFFE trust domain and the
  bundle (a root-owned PEM file) its SVIDs are checked against.
- `allow exec PATH subagent=NAME`: a launch rule whose program is a
  sub-agent; `NAME` (`[a-z][a-z0-9_]{0,31}`) names it in the chain. A
  `deny` rule or a rule without `exec` may not carry it.
- `require on-behalf-of`: a run without a verified user token refuses to
  start. Without it, a run with no token records the chain as the agent
  alone.
- All three parsers (the decision procedure, the certificate checker and
  the cross-check's oracle) read the new lines alike; a v1.28.0 Warden
  refuses them as unknown (D8).

*Tests:* each form and each refusal in both C parsers and the oracle; the
cross-check's generator writes them; lint notes a `trust` line no token
uses and a `subagent=` on a program never launched.

## 2. Verifying the identities: `warden-secrets`

- `--on-behalf-of FILE`: a root-owned file (mode 0600/0400, one name, under
  directories no other user can write, as v1.28.0's file stores) holding
  one JWT. `--agent-svid FILE`: an X.509-SVID (certificate chain and key)
  or a JWT-SVID for the agent.
- The helper reads them as root, then, as its own user, fetches each named
  issuer's keys over verified HTTPS (the discovery document, then its
  `jwks_uri`; or the `jwks` URL the policy names) and checks:
  - the JWT's signature (RS256, PS256, ES256, EdDSA; `none` and every
    HMAC algorithm refused), its `iss` among the policy's issuers, its
    `aud` holding that issuer's audience, `exp` in the future and `nbf` /
    `iat` not after now (with a leeway of 60 s);
  - an `act` claim, if present, as a chain of actors (RFC 8693), each
    with its `sub` (and `iss` when given), nested at most 8 deep;
  - an SVID against the policy's bundle for its trust domain (the SPIFFE
    ID in the certificate's URI SAN, the chain to the bundle, the key
    matching).
- The helper sends the Warden the verified claims only: issuer, subject,
  audience, expiry, `jti`, the actors, the SPIFFE ID, and each input's
  SHA-256. The token never reaches the Warden, the agent or the stream; the
  helper clears it once checked.
- A token that fails a check refuses the start, naming the check. A token
  that is fine but close to expiry (under 60 s) is refused too.

*Tests:* a stand-in IdP (discovery, JWKS, keys of each type) and tokens
made for the test: each check failing on its own (signature, issuer,
audience, expiry, `nbf`, algorithm `none`, an HMAC token signed with the
public key as secret, a key id not in the JWKS, nesting past 8); a token
from token exchange with two actors; an SVID valid, expired, from another
trust domain, with a key that does not match; no token in the Warden's
output, the agent's environment or the stream; the files' second names
refused as in v1.28.0.

## 3. Sub-agents

- At startup the Warden makes a control group for the run (cgroup v2,
  under its own, `varek-<run>`), and moves the agent into it before it
  runs. A launch the policy allows by a rule with `subagent=NAME` is
  decided as any launch; before the Warden answers it, it makes
  `varek-<run>/NAME-<n>` and moves the launching process there. The
  process and every child it makes stay there: the agent runs unprivileged
  and cannot write a control group's `cgroup.procs`.
- On every notification, the Warden reads the calling process's control
  group (`/proc/<pid>/cgroup`, read through the pidfd it already holds for
  the request) and attributes the call: the run's group, the agent; a
  sub-agent's group, that sub-agent. A sub-agent that launches another
  sub-agent nests (`NAME-<n>/NAME2-<m>`), so the chain grows by one.
- Nothing the process sends is believed: not its argv, its environment or
  its name.
- A host without cgroup v2, or a Warden that cannot make groups, refuses to
  start a policy that names a sub-agent; one that names none runs as
  before.

*Tests:* a sub-agent and its children (a fork, a double fork that
reparents, a thread) all attributed to it; a nested sub-agent; the agent
itself never attributed to a sub-agent; a sub-agent's process cannot move
itself out (`cgroup.procs` refused); a launch of the same program by a rule
without `subagent=` is the agent's; no cgroup v2, refused at start.

## 4. Records

- `run_start` gains `on_behalf_of`: the user (`issuer`, `subject`,
  `audience`, `expires`, `jti`, `token_sha256`, `verified: true`), the
  actors of a delegation in order, and the agent (`run`, and `spiffe_id`
  with `svid_sha256` when given). With no token, the user is absent and
  the chain is the agent alone.
- Each decision record gains `obo`: the chain it was made for, as a short
  list of names: `["user", "agent"]`, or with a sub-agent's
  `"subagent:NAME#n"` appended (n: which launch of it). The full entries
  are in `run_start` (and, for a sub-agent, its launch record, which gains
  `subagent` and `cgroup`), so each record stays small (D4).
- When the user's token expires during the run the Warden records
  `on_behalf_of_expired` and, by default, revokes the run (v1.28.0): every
  later call UNSATISFIED, the proxy's values cleared, leases revoked (D5).

*Tests:* the records of a run with a token, without one, with a SPIFFE ID,
with sub-agents; expiry during a run revokes it and is recorded; no token
or claim beyond those named in any record.

## 5. Audit, export and tools

- `varek_audit.py`: `run_start`'s chain names an issuer the policy trusts,
  is marked verified and was not expired at the run's start; every
  decision record has an `obo` that resolves (the user only if the chain
  has one, a sub-agent only after a launch that started it, by a rule with
  that `subagent=`); after `on_behalf_of_expired` every decision is
  UNSATISFIED when the run was revoked.
- `varek runs` and `varek refusals` show the user and the sub-agent;
  `varek refusals --subagent NAME` and `--user SUB` filter. The CycloneDX
  export carries `varek:on_behalf_of.*` (issuer, subject, actors, SPIFFE
  ID, decisions per sub-agent). `varek doctor` checks cgroup v2 and the
  issuers' keys; `varek policy show` lists the trusted issuers and
  sub-agents.

*Tests:* forged streams the audit must refuse (an issuer the policy does
not trust, an unverified user, a sub-agent's decision before its launch, a
sub-agent the policy does not name, an allowed decision after expiry with
the run revoked); the tools' outputs.

## 6. Cost

Attribution reads one small file per notification through a descriptor
the Warden already holds; it should add a few microseconds to a decision.
Verifying the token adds one HTTPS round trip per issuer at startup (keys
are not cached between runs, D9). `varek bench` must show the decision
time with sub-agents named.

## Decisions before building

- **D1. The user's identity.** (a) Only a JWT the run verifies against an
  issuer the policy trusts; (b) also the operator's login (the uid that
  ran `varek run`), recorded unverified. *Recommended: (a)*, with the
  operator's uid and login recorded in `run_start` as a new field,
  `operator`, not as the user: a chain entry should be something an issuer
  vouched for.
- **D2. SPIFFE.** (a) An SVID from a file, checked against a bundle file;
  (b) also the SPIFFE Workload API (a local SPIRE agent's socket).
  *Recommended: (a)* in v1.28.1, (b) in a later patch: the Workload API
  adds a long-lived connection and rotation the Warden would have to follow.
- **D3. Attributing sub-agents.** (a) A control group per sub-agent,
  which its processes cannot leave; (b) the process tree (`PPid`), which a
  double fork escapes by reparenting. *Recommended: (a).* (b) would let a
  sub-agent's work be counted as the agent's.
- **D4. The record.** (a) `run_start` holds the full chain, each decision
  a short `obo` list; (b) the full chain on every record. *Recommended:
  (a)*: a day's stream holds hundreds of thousands of records, and the
  audit (which holds the stream in memory) is already the largest cost on
  a small host.
- **D5. When the user's token expires.** (a) The run is revoked; (b) it is
  recorded and the run goes on; (c) the operator chooses, (a) by default
  (`--on-behalf-of-expiry revoke|record`). *Recommended: (c).* An agent
  acting after the user's authority lapsed should stop, but a long task
  started with a short-lived token may be meant to finish.
- **D6. Decisions on the chain.** (a) Recorded and audited only in
  v1.28.1; (b) rules may require a user, issuer or sub-agent (`allow ...
  for=subagent:NAME`). *Recommended: (a).* (b) changes the decision
  procedure, the certificate format and all three parsers; it is a release
  of its own, best planned once the chain has run in practice.
- **D7. Token exchange.** (a) Accept tokens that came from a token
  exchange (read the `act` chain); (b) also perform one: `warden-secrets`
  exchanges the user's token for one scoped to a downstream API, and the
  proxy puts it in as a v1.28.0 credential. *Recommended: (a)* in v1.28.1.
  (b) is the natural next step (the agent would call an API as the user
  without ever holding the user's token) but it makes VAREK a token-exchange
  client of each IdP, with its own design and tests.
- **D8. The version.** (a) The Warden reports 1.28.1; the grammar stays
  1.28, and the new lines are refused by a v1.28.0 Warden (fail closed);
  (b) a grammar 1.28.1 with `require warden 1.28.1`. *Recommended: (a).*
  `require warden` takes a major and minor version, and a patch that adds
  lines an older Warden refuses changes nothing an older policy means.
- **D9. Issuers' keys.** (a) Fetched at each start; (b) cached on the host
  between runs. *Recommended: (a)*: no cache to protect or expire, at the
  cost of a round trip at start; a cache can follow if starts are slow.

## Implementation plan

1. **Grammar** (done): `trust issuer`, `trust spiffe`, `subagent=`,
   `require on-behalf-of`, in the decision procedure, the certificate
   checker and the oracle; lint; the version 1.28.1. Tests of section 1.
   As built:
   - The forms of section 1, after `require warden 1.28`. An issuer and a
     `jwks` URL are `https://` with a host (at most 255 and 1024 bytes), an
     audience 1 to 255 printable bytes; a trust domain is `[a-z0-9._-]`,
     starting with a letter or digit; a bundle is an absolute path as a file
     credential's. At most 8 of each, each once. `subagent=NAME`
     (`[a-z][a-z0-9_]{0,31}`) only on an allow exec rule, once; one name may
     sit on several rules. `require on-behalf-of` once. A matcher keyword
     followed by `subagent=...` keeps its earlier meaning (the constant),
     in all three parsers.
   - `vdp_check` and `vdp_cert_check` gain an `identity` mode (`issuer ISS
     AUD JWKS|-`, `spiffe DOMAIN BUNDLE`, `subagent LINE NAME`, `require
     on-behalf-of`), which the cross-check compares with the oracle's
     reading. The Warden compares the two C readings at load (each rule's
     sub-agent, and the issuers, trust domains and `require on-behalf-of`).
   - The Warden reports 1.28.1 (`VDP_WARDEN_PATCH 1`); the grammar stays
     1.28 (D8), so a v1.28.0 Warden refuses the new lines.
   - Until steps 2 and 3, the Warden refuses to start a policy with
     `require on-behalf-of` or a `subagent=`, naming the step that builds
     it, so no run claims attribution it does not have. `trust` lines alone
     change nothing.
   - Lint: the plan's note on a `trust` line no token uses cannot be made
     at lint time (the token is the operator's, at the run); lint instead
     notes `require on-behalf-of` with no trusted issuer, which no run could
     meet.
   - `make test-v1281` section 1 (49 checks); `test-v1280`'s version check
     accepts any 1.28 patch.
2. **Verifying**: `warden-secrets` checks the JWT and the SVID against a
   stand-in IdP and bundle; `run_start`'s `on_behalf_of`. Tests of section 2.
3. **Sub-agents**: the run's control group, a group per sub-agent at its
   launch, attribution on every notification, `obo` on every record.
   Tests of section 3.
4. **Expiry**: `on_behalf_of_expired`, revocation by default. Tests of
   section 4.
5. **Audit, export and tools.** Section 5.
6. **Tests and the regression count** against v1.28.0 (`make test-v1281`).
7. **Latency**: the decision time with sub-agents; startup with a token.
   The soak is shared (above).
8. **Review by AI review agents**, fixes, README, threat model, spec
   paper, release notes.
