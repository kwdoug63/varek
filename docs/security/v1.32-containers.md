# v1.32.0 — Containers: an official image, Docker and Podman (plan)

Status: **in progress**, target **v1.32.0**. Decided 2026-10-16: the
recommendation for each decision below (D1 to D12). Step 1 measured
on both hosts, rootful (every suite passes; the result below); rootless
Podman (D10) measured, 25 of 30 before its fixes and 31 of 31 after. Built: the image's Containerfile (step 2), the
AppArmor profile and the SELinux module (step 3), the Warden's cgroup
remount in a container, `varek doctor` and the preflight in a container
(step 4, D11), CI (step 5), the release workflow (step 6), the version
(D12) and `make test-v1320` (step 7); reviewed (step 8, below). Developed on its own branch
(`claude/varek-v1320-01dbw5`, from v1.31.1's, so the image carries the
calls glibc and bash make that v1.31.1 admits). Each section ends with
what must be tested before it ships. The roadmap entry is in
`docs/roadmap/v1.32-v1.35.md`.

Ship gate: the existing suites pass inside a container under the
documented settings, each setting is shown needed by a check that fails
without it, and a 24-hour soak runs inside a container on a droplet.

## What v1.31 leaves open

Most production agents run in containers. The Warden runs as root on the
host and asks more of its host than a container allows by default, so a
first attempt in Docker fails: with Docker's default settings the Warden
refuses to start (it needs CAP_SYS_ADMIN for the agent's PID namespace),
and the usual answer, `--privileged`, grants everything and turns off the
container's own seccomp profile and AppArmor or SELinux confinement. A
buyer who must write "privileged" in a security review stops there.

## What v1.32 gains, and what it does not

- **An official image** with the Warden, its helpers and the `varek`
  command; an agent runs under VAREK by building on the image and naming
  its own command.
- **A published, minimal set of container settings**, each with the reason
  the Warden needs it, never `--privileged`: the capabilities, the seccomp
  profile, AppArmor or SELinux, and the control groups.
- **Docker and Podman**, each covered by a release suite; rootless Podman
  where the host allows it, and a clear refusal naming the missing setting
  where it does not.
- **A signed image with a software bill of materials (SBOM).**

It does not change a decision, a rule or a record: the Warden inside a
container is the Warden on a host. The agent itself never holds a
capability: the Warden empties its bounding set and drops it to its own
user before the filter, as on a host (unless run `--run-as root`, which
the Warden warns of). It does not run the Warden outside
the agent's container (a node agent is v1.34's).

## The design in one paragraph

The image's entrypoint is `varek run`, so the container's first process is
the Warden and the agent is its child, in the agent's own PID, network and
mount namespaces made by the Warden inside the container, exactly as on a
host. The container is started with every capability dropped and only the
ones the Warden needs added; the container runtime's own default seccomp
profile stays on, since with those capabilities it already allows every
call the Warden makes, and the Warden's own filter on the agent is far
stricter. Where the host confines containers with AppArmor or SELinux, a
profile is shipped that allows the Warden's mounts and nothing more.
`varek doctor` in the container checks each setting and names the one
missing with the flag that grants it.

## 1. What the Warden asks of its container

Measured on 2026-10-16 (Central) with the v1.31.1 Warden in an Ubuntu
24.04 image, Docker 29.6.2, starting from `--cap-drop ALL` and adding one
capability at a time, two runs: a policy with no `require` line running
`/bin/true`, and a 1.31 policy (launches held by Landlock, the writable
directory mounted noexec, files opened as the agent) running Python as
`nobody`.

| Setting | Why the Warden needs it | Without it |
|---|---|---|
| CAP_SYS_ADMIN | the agent's PID, network and mount namespaces; the noexec mounts (v1.27.1) | the Warden refuses to start |
| CAP_SYS_PTRACE | `pidfd_getfd` for the agent's listener descriptor and handed-over sockets; reading the agent's memory for paths | `pidfd_getfd` refused (Docker's default seccomp profile admits it only with this capability) |
| CAP_SETPCAP | emptying the agent's capability bounding set at its launch | the agent's setup fails: "cannot drop to uid 65534" |
| CAP_SETUID, CAP_SETGID | dropping the agent, the egress proxy and `warden-secrets` to their own users; opening files as the agent (v1.29) | the drop fails |
| CAP_DAC_OVERRIDE | opening files for the agent, as root, wherever the policy allows | the agent cannot load its libraries; CAP_DAC_READ_SEARCH alone is not enough |
| CAP_KILL | ending the agent's processes, which run as another user (found by the sweep: `test-lifecycle` hangs without it) | the Warden cannot signal the agent |
| CAP_NET_ADMIN | bringing the loopback up in the agent's network namespace, for the DNS stub (v1.25) | "cannot bring the loopback up": no stub; names under a wildcard do not resolve |
| CAP_NET_BIND_SERVICE | binding the stub on port 53 in that namespace | "cannot bind the UDP stub": no stub |
| CAP_CHOWN | `varek run` giving the agent its temporary directory, `/tmp/varek-<uid>` (v1.29) | `varek run` stops: the directory cannot be the agent's |
| Docker's default seccomp profile | (kept on) | — |

**Docker on Ubuntu, AppArmor** (2026-10-17, Central; a 1-vCPU droplet,
Ubuntu 24.04, kernel 6.8, Docker 29.1.3, cgroup v2, `docker-default`
applied; commit `ed2f11c`): with the ten, 21 of the 30 suites pass, and the
z3 and CycloneDX checks with them (PyPI reached). Nine fail, seven for one
reason: `docker-default` has `deny mount,`, so the first of the noexec
mounts, the Warden's new mount namespace made private, is refused
(EACCES: "cannot make the mount namespace private (Permission denied);
refusing to start"), and every policy from 1.27 that names a writable
directory stops there (`test-v1270`, `-v1271`, `-v1280`, `-v1281`,
`-v1290`, `-v1310`, `test-cli`'s two end-to-end runs); `test-v1170` and
`-v1180` fail at their own setup, a bind mount. The suites whose policies
mount nothing (`test-lifecycle`, `-v1124`, `-v1250`, ...) pass: the
namespaces, `pidfd_getfd`, the drop and the stub are as on a host. A
`deny` rule is not logged, so the kernel's log shows nothing.

So D5's first part is needed: `packaging/container/apparmor/varek-container`,
`docker-default` with its `deny mount,` replaced by the Warden's three
kinds of mount (`/` made `rprivate`; `rbind` of a directory; `remount,
bind` with `noexec` and the mount's own flags, which from v1.32 also makes
the container's cgroup filesystem read-write) and no other, loaded on the
host and named with `--security-opt apparmor=varek-container`. AppArmor
cannot tie a bind's target to its source nor require a remount to keep a
flag, so the rules bound what is mounted, not where: a process with
CAP_SYS_ADMIN in the container (the Warden; a root shell `docker exec`
starts with the same capabilities) may bind any path and make a bind mount
read-write. That is the Warden's trust, as on a host; the agent holds no
capability and its filter refuses `mount(2)`.
`tests/container_sweep.sh --apparmor` runs the suites under it (a copy
that adds the suites' own tmpfs and bind mounts, as MKNOD is added).

**Podman on RHEL, SELinux** (2026-10-17, Central; t3.large, RHEL 9.8,
kernel 5.14, Podman 5.8.2 rootful, cgroup v2, enforcing; commit
`ed2f11c`): 24 of the 30 suites pass with the ten, the bind mounts and most
noexec mounts among them; each of the ten is again shown needed by
`--drop-each`. The causes of the rest, each found and handled (the last
three items from later runs, on commits up to `090c902`, there and on the
Docker host under the AppArmor profile):

- **`/dev/mqueue`.** A writable name under `/dev` (`allow path /dev/null`
  admits `/dev/null2`) has the Warden mount `/dev` noexec with every mount
  beneath it, and SELinux refuses a container the remount of the
  `mqueue` filesystem (unaudited). The runtime mounts it noexec already;
  the Warden now leaves a mount that is noexec as it is (the check pass
  still confirms each), so it is not remounted (`test-v1270`, `-v1271`).
- **Control groups** (`test-v1281`, `-v1310`, and the same counts on the
  Docker host): the runtime mounts the cgroup filesystem read-only, so the
  run's group cannot be made ("Read-only file system"), and SELinux refuses
  `container_t` writes to `cgroup_t`. **Decided 2026-10-17: make it work.**
  With `--cgroupns=private` the Warden is at its cgroup namespace's root
  and the filesystem shows the container's own groups only; the Warden
  remounts it read-write in a mount namespace of its own
  (`sub_container_cgroup`; the container's mount stays read-only, and the
  agent, its own user without capabilities, can write none of it, as on a
  host). The remount is a bind remount, which changes that one mount's
  flags (noexec and the others kept), never the filesystem's, which every
  cgroup2 mount on the machine shares (the review, below). Without
  `--cgroupns=private` it refuses and says so. The AppArmor
  profile's bind remount rule allows it. On SELinux the container runs as `container_init_t`,
  the distribution's type for containers that manage their control groups
  (`--security-opt label=type:container_init_t`), and
  `packaging/container/selinux/varek_container.cil`, D5's SELinux half, is
  four rules, each measured refused without it, two here and two for
  rootless (below): that type may remount the `cgroup_t` filesystem
  (`{ remount }`, which SELinux asks for any remount, a bind remount too),
  and mount on the container's character devices (`{ mounton }` on
  `container_file_t` `chr_file`: the noexec mount of `/dev/null`, which
  `container_t` allows). `container_init_t` has more than `container_t`
  besides the control groups (container-selinux's `container.te`): it
  may mount on and unmount the cgroup filesystem, sysfs and `/proc`,
  remount `/proc` and `device_t` filesystems, unmount tmpfs, and its
  network is unconfined; that is the distribution's type for systemd in a
  container, used as is. Other containers keep `container_t`, where the host-wide
  `container_manage_cgroup` boolean would change them all. (Tried first:
  udica's base container type with the cgroup rules added. It has far
  less than `container_t`, no ports, memfd files or PAM, and every suite
  failed under it; not pursued.)
  `test-v1281` checks the remount on any host: a read-only cgroup
  filesystem in a cgroup namespace of its own, the check and the run, and
  the refusal outside the namespace's root.
- **Process events.** The kernel's process events do not reach a listener
  in a container's own network namespace on RHEL 9's 5.14 nor Ubuntu's 6.8
  (no SELinux denial; they did on 6.18). The Warden says so and falls back,
  as it does on a host without them: a launch known by the image a process
  runs. Until step 9, a sub-agent of the image its launcher runs was then
  refused (`subagent_same_image`), so a Python agent could not launch a
  Python MCP server confined in a container (the soak's run A does; found
  preparing it, 2026-10-17). **Decided 2026-10-17: fix it.** Such a launch
  is now told from a failed one by the process's memory layout (where its
  code, stack, heap, arguments and environment begin and end, from
  `/proc/<pid>/stat`): every new program gets a new one, randomized, and
  the process cannot change it but by a launch (the agent's filter refuses
  `prctl(PR_SET_MM)`, every form, under every policy, and the build fails
  if it is admitted), so a failed launch cannot
  pass for one that happened; the same layout is a failed launch, the safe
  side. Where layouts are not randomized (`kernel.randomize_va_space` not
  2) or the layout cannot be read, such a launch is still refused. The
  settling is recorded `"how":"layout"`. A process may itself turn off its
  next program's randomization (`personality(ADDR_NO_RANDOMIZE)`); its
  launch then most likely settles failed (its process is the launcher's
  subject), never the other way. `test-v1281` checks it on any host
  (process events turned off for the test): a launch that happened, a
  failed one (E2BIG), and the refusal without randomization. It skips
  in a container the four checks that need the process events themselves
  (three lines) and says why; on a host, their lack fails. The shared
  soak's 6-minute trial with the process events turned off (here, kernel
  6.18): `fs` and `gh`, Python servers the Python agent launches, settled
  launched by their layout, every check of run A held (`soak_check:
  PASS`).
- **`O_TMPFILE`.** The container's `/tmp` (overlayfs) has none on either
  host: `test-v1290`'s check and the Landlock table's two rows (`test-v1270`)
  skip where the filesystem has none.
- **A tmpfs the container mounts itself** is `tmpfs_t`, which SELinux does
  not let the container remount, so the Warden cannot mount it noexec and
  refuses to start, saying which. Only `test-v1271`'s own setup makes one;
  a tmpfs the runtime mounts (`--tmpfs`, `/dev/shm`) is the container's and
  is mounted noexec (measured: `--tmpfs /work`). Where one cannot be
  remounted, `test-v1271` makes its cases from directories bound onto
  themselves with the same flags.

## 2. The image

- Built from the release's source in a multi-stage build: the Warden,
  `warden-proxy`, `warden-secrets`, the tools and the shipped policies and
  profiles, with their runtime libraries (libseccomp, libsodium, OpenSSL)
  and Python for the tools. No compiler in the final image.
- Entrypoint `varek run --`, so `docker run ... IMAGE <agent command>`
  runs the agent under the baseline (v1.29) with the profile its command
  names, the working directory the mounted project.
- A user builds their own image `FROM` it, adding the agent (Claude Code,
  a Python agent, ...); the documented Dockerfile shows it. A policy of
  their own is mounted read-only or built in.
- The verdict stream goes to a volume, and the signing key, if any, comes
  from a mounted secret, never baked in.

**Tests:** the image builds reproducibly from a tag; `varek version` in it
names the release; the documented Dockerfile with a Python agent runs.

## 3. Docker and Podman

- **Docker** with the settings of section 1, on a host with AppArmor
  (Ubuntu) and on one without.
- **Podman, rootful**, on RHEL 9 with SELinux enforcing.
- **Podman, rootless**: the container's root is the user's own in a user
  namespace. Namespaces, Landlock and seccomp user-notify work there; the
  noexec mounts work inside the user namespace's mount namespace; cgroup v2
  needs systemd's delegation to the user. Where something is missing,
  `varek doctor` says what, and the Warden refuses as it does on a host.

**Tests:** every suite in the image under each runtime and host
(`tests/container_sweep.sh`: Docker with AppArmor, Podman rootful and
rootless with SELinux), and in CI (GitHub's Ubuntu runners have Docker
with AppArmor and cgroup v2). `make test-v1320` checks the rest on any
host: the version, doctor's container section, the preflight's share, and
the packaging and workflows (step 7).

## 4. `varek doctor` and the preflight in a container

`varek doctor` gains a container section: it detects that it runs in one
and checks each setting of section 1 (each capability in the effective
set, seccomp mode, the AppArmor or SELinux label and whether a test mount
succeeds, cgroup v2 writability), naming the one missing and the flag that
grants it (`--cap-add SYS_PTRACE`, ...). The preflight refuses a run the
container cannot carry before the agent starts.

**Built (2026-10-17, D11 (a)):** `tools/varek_container.py`, called by
`varek doctor` when it finds itself in a container (`/.dockerenv`,
`/run/.containerenv`, `$container`): the ten capabilities in the bounding
set (each missing one a FAIL naming its `--cap-add`; any beyond them, or
`--privileged`, a WARN), seccomp on, the AppArmor profile (`docker-default`
a FAIL: it denies the noexec mounts) or SELinux type (`container_t` a WARN:
no control groups), the cgroup namespace (read-only and shared a FAIL:
`--cgroupns=private`), rootless said, and the Warden's mounts made in a
child (a namespace of its own made private, a directory bound and
remounted noexec, the cgroup filesystem remounted where a run would).
`tests/test_varek_container.py` checks each rule from the container's
state as text; run in containers here, the settings, two capabilities
left out, and Docker's defaults each read as they should.

**The preflight's share (built 2026-10-17):** in a container, `varek run`
refuses before the agent starts when the container cannot carry the run,
naming each lack and the flag for it: a missing capability always; the
mount test when the Warden will mount the writable directories noexec
(launches decided and a rule that writes: `vdp_check POLICY mounts`, since
the second review) or the policy names a sub-agent or an MCP server; the cgroup namespace only for those last.
`tools/varek_preflight.sh` has a section 2b with the doctor's checks in its
PASS/WARN/FAIL form, control groups counted when the policy needs them.
Run in containers here: the documented settings run the agent; without
SYS_PTRACE the run is refused with `--cap-add SYS_PTRACE`; Docker's defaults
are refused naming the three capabilities and the mount test. An AppArmor
profile that denies mounts (`docker-default`) is refused only for a run
that mounts (the noexec mounts, or control groups); for any other it is a
warning (the review, below).

## 5. Signing and the SBOM

The image is signed and carries a CycloneDX SBOM of its packages (syft's
catalog of the image), attached as an attestation. VAREK's own binaries
are not listed in it by their SHA-256; the Warden records `warden-proxy`'s
and `warden-secrets`' in each `run_start`.

## Ship gates

- Every suite passes inside the container under the documented settings,
  under Docker (AppArmor host) and rootful Podman (SELinux host).
- Each setting in the published list is shown needed.
- `--privileged`, `seccomp=unconfined`, `apparmor=unconfined` and
  `label=disable` appear nowhere in the documentation as a way to run it.
- A 24-hour soak inside a container on a droplet.

## Decisions before building

- **D1. Where the Warden runs.** (a) Inside the agent's container, as its
  entrypoint, the agent its child (the roadmap's plan); (b) in a sidecar
  sharing the PID namespace, which cannot work (the agent's filter and its
  listener must come from a process the Warden starts); (c) on the host,
  the agent's container started by a runtime hook (v1.34's node agent).
  *Recommended: (a).*
- **D2. Which capabilities.** (a) `--cap-drop ALL` and the exact list step 1
  settles (ten), each with its reason; (b) Docker's default set
  plus SYS_ADMIN and SYS_PTRACE (simpler, grants more).
  *Recommended: (a).*
- **D3. CAP_SYS_ADMIN.** (a) Required in v1.32, as on a host: it carries
  the PID namespace (the agent dies with the Warden), the empty network
  namespace and the noexec mounts; the agent never holds it (unless run
  `--run-as root`, which the Warden warns of); (b) a mode
  without it that gives those up. *Recommended: (a);* v1.34's node agent
  is where it can leave the agent's container.
- **D4. The seccomp profile.** (a) The runtime's default profile, unchanged
  (measured sufficient with the capabilities); (b) a profile of VAREK's
  own. *Recommended: (a),* with a test that would fail if a runtime's
  default profile stopped admitting a call the Warden makes.
- **D5. AppArmor and SELinux.** (a) Ship an AppArmor profile (Docker on
  Ubuntu) and an SELinux policy module (Podman on RHEL) that allow the
  Warden's mounts and nothing more, if step 1 shows the defaults refuse
  them; (b) document turning confinement off; (c) refuse the noexec mounts
  in containers (losing v1.27.1's guarantee there). *Recommended: (a).*
- **D6. The base image.** (a) Red Hat's Universal Base Image 9 (freely
  redistributable, the base Red Hat's container certification asks for,
  in line with the RHEL 9 and OpenShift work; RHEL 9.8 passes every suite);
  (b) Ubuntu 24.04 (what CI tests); (c) both. *Recommended: (a);* CI checks
