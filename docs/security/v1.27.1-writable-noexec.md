# v1.27.1 — nothing written during the run is mapped executable (plan)

Status: **in progress**, target **v1.27.1**. Decided 2026-10-11: the
recommendation for each decision below. Built: steps 1 to 7 (see "As built"); the
release notes and the spec paper's v1.27.1 edition are drafted, and the 24-hour soak of the
reviewed build is running. Each section
ends with what must be tested before it ships. Decisions to take before
building are listed at the end, each with a recommendation.

## What v1.27.0 leaves open

v1.27.0 decides launches: with `require warden 1.27` the kernel's Landlock
domain lets the agent launch only the files of the launch set, so a file
written during the run is never launched (design note
`v1.27-program-launches.md`). Landlock governs what the kernel launches, not
the executable mappings by which the dynamic loader maps shared libraries.
Where a policy lets the agent both write and read a directory, a shared
library written there may be mapped executable into an allowed program
(`LD_PRELOAD`, `LD_LIBRARY_PATH`, `dlopen`, an interpreter's native
extension). v1.27.0 states this as a limit ("Libraries are not decided").

## What it gains, and what it does not

The agent's own process already runs code the Warden did not decide: it is
the untrusted program the Warden contains, and it may make its own memory
executable (`mmap` and `mprotect` are admitted, as a JIT needs). A library
loaded into an allowed program runs under the same seccomp filter, Landlock
domain, file rules and network rules as the agent. So the library route
escapes no containment. What it breaks is two claims:

- **Nothing written during the run runs as a file.** v1.27.0 makes this
  true for launches only. v1.27.1 extends it to executable mappings: a file
  under a path the policy lets the agent write can be neither launched nor
  mapped executable.
- **The launch record means what it says.** "`git` ran" should mean git's
  code ran, not git's and a library the agent wrote.

v1.27.1 does not stop code the agent writes into memory and runs there, and
does not claim to.

## Why not a mount in the agent's namespace

The plan in v1.27.0's notes was to mount the writable paths `noexec` in the
agent's own mount namespace. That alone does nothing: the agent does not
open files itself. The Warden opens each file it allows in its own mount
namespace and hands the agent the descriptor (`resolved_fd_injection`), and
the kernel checks an executable mapping against the mount the file was
opened through (`path_noexec` on the file's own path). The mount has to be
where the Warden opens.

## The design in one paragraph

At startup, under `require warden 1.27`, the Warden gives itself a private
mount namespace before it starts any helper or the agent, makes it private
so nothing propagates to the host, and re-mounts each directory the policy
lets the agent write on itself with `MS_NOEXEC` (keeping the flags the
mount already has). Every file the Warden later opens under those
directories, for the agent or for itself, is opened through a `noexec`
mount: the kernel refuses to map it executable (`mmap` with `PROT_EXEC`
gives `EPERM`; `mprotect` adding `PROT_EXEC` gives `EACCES`) and to launch
it. The agent inherits the same view. The host's mounts are untouched, and
the namespace ends with the run.

## 1. Which paths

- A path is **writable** when an `allow path` rule, as the decision
  procedure reads it, allows some open for writing on its constant (the
  same test lint uses for "may be both launched and written": `O_WRONLY`,
  `O_RDWR`, with and without `O_TRUNC`, and `O_CREAT`). `readonly` rules
  are not writable; `access=ro` alone is (it admits `O_TRUNC`).
- Each writable rule is turned into the directory to mount:
  - a prefix rule ending in `/` (`allow path /work/`): that directory;
  - a prefix rule not ending in `/` (`/work/out`, which admits
    `/work/out2`): its parent directory;
  - a glob: the literal directory before its first wildcard;
  - an exact path: the file itself when it exists at startup (a file can be
    bind-mounted), else its parent directory.
- A directory inside another one already in the list is dropped. A
  directory that does not exist at startup is listed as missing and
  reported; nothing is mounted for it, and if the host makes it during the
  run the agent's opens under it are refused (the step-7 review found the
  earlier "skipped" wrong: such a directory is writable and not `noexec`).
- **Refused at startup:** a writable directory that is `/`, or that holds
  the operator's own program (its launch would fail). A launch-set file
  under a writable directory is reported and will not launch (decision D4).
- Each directory's submounts are re-mounted `noexec` too (a writable
  `/tmp/work` with a tmpfs below it).

*Tests:* the list for prefix, glob and exact rules, with and without a
trailing `/`; nested rules; a missing directory; `/` refused; the operator's
program under a writable directory refused; a submount.

## 2. The mounts

- `unshare(CLONE_NEWNS)` in the Warden, which is single-threaded at that
  point (the resolver is a process for that reason), then `mount(NULL, "/",
  NULL, MS_REC | MS_PRIVATE, NULL)`, so nothing reaches the host's
  namespace.
- For each directory: a bind of the directory on itself, then a remount
  with `MS_BIND | MS_REMOUNT | MS_NOEXEC` and the flags the mount already
  has (`statvfs`), since a remount may not drop locked flags such as
  `nosuid` or `nodev`. The same for each submount.
- Done before the launch set is built, the resolver and `warden-proxy` are
  started, and the agent is forked, so all of them see the same view.
- Needs `CAP_SYS_ADMIN`, which the Warden already requires (its PID
  namespace). A failure refuses the start.

*Tests:* the agent's `/proc/self/mountinfo` shows each directory `noexec`;
the host's does not change during or after the run; a mount with `nosuid`
keeps it.

## 3. What the agent sees

- A file under a writable directory: readable and writable as the policy
  says; `mmap(PROT_EXEC)` of it refused `EPERM`; `mprotect` to add
  `PROT_EXEC` to a mapping of it refused `EACCES`; a launch of it refused
  by the kernel (`EACCES`) even where the launch set holds it.
- Everything else unchanged: anonymous memory may still be made
  executable; files outside writable directories map as before.

*Tests:* a copy of an existing system library placed in a writable
directory cannot be loaded (`dlopen` fails, the process goes on); the same
library at its own path loads; `mmap` and `mprotect` of a file under the
directory are refused; anonymous executable memory still works; the v1.27
suite passes unchanged except where it launches from a writable directory.

## 4. Records, audit and tools

- `run_start` gains `noexec`: the list of directories mounted, or `null`
  when the mounts are off (decision D2). The Warden reports `1.27.1`.
- `varek_audit.py`: a `require warden 1.27` run from a Warden of 1.27.1 or
  later must record `noexec`; a run recording it off says so as a finding
  of its own, not a failure (D2).
- `varek policy show` lists the directories the Warden would mount on this
  host; `varek doctor` and the preflight check the Warden can make a mount
  namespace. The CycloneDX export carries `varek:noexec.*`.

*Tests:* `run_start`'s list; forged streams the audit must refuse (a list
naming a directory the policy does not let the agent write, a missing list
from a 1.27.1 Warden); `policy show`.

## 5. What it may break (to measure before deciding D1)

- A package installed during the run into a writable directory (a `venv`,
  `pip install --target`) whose compiled extensions are then imported: the
  import fails. Pure-Python packages are unaffected.
- A program that maps executable code from a temporary file (libffi does
  so only where anonymous executable memory is refused; not on these
  hosts). To check with CPython's `ctypes` callbacks.
- A compile writes and reads its temporary files only (the v1.27 soak's
  gcc tasks); to confirm under the mounts.
- A workflow that builds a program in a writable directory and runs it:
  already refused by v1.27.0 (not in the launch set).

*Measure:* the v1.27 soak's tasks under the mounts; `ctypes` callbacks;
startup time with 1, 10 and 50 writable directories.

## 6. Ship gates

- `make test-v1271`: sections 1 to 4 above, and a regression count against
  v1.27.0.
- The v1.27 suite and the earlier suites pass unchanged (or each change is
  explained).
- The soak harness (`tests/soak_v1270`) re-run under 1.27.1 on the droplet

- A review by AI review agents.

## Decisions before building

- **D1. Which policies.** (a) Every `require warden 1.27` policy, with an
  operator's opt-out (D2); (b) only a policy that asks for it, which needs
  grammar; (c) every policy, v1.26 included. *Recommended: (a).* The opt-in
  already promises that nothing written during the run is launched; this
  completes it. A v1.26 policy keeps its behaviour, which includes loading
  compiled extensions from writable directories.
- **D2. The opt-out.** (a) A Warden option, `--writable-exec`, recorded in
  `run_start` (`noexec: null`) and reported by the audit; (b) a policy
  directive. *Recommended: (a)*: no grammar change in a patch release, and
  the operator, not the policy author, knows whether a run installs
  compiled packages.
- **D3. An exact path that does not exist at startup.** (a) Mount its
  parent directory; (b) skip it and report it. *Recommended: (a)*, which
  holds when the file is created later; the parent's other files are then
  not mapped executable either, which the report says.
- **D4. A launch-set file under a writable directory.** (a) Report it at
  startup and leave it unlaunchable (the kernel refuses it); (b) refuse to
  start. *Recommended: (a)*: lint already notes a file both launched and
  written, and a launch of it then fails closed. The operator's own program
  under a writable directory is refused at start either way.
- **D5. The version.** The Warden reports `1.27.1`; the policy grammar
  stays 1.27 (`require warden 1.27`; `1.28` still refused). The version
  string gains a patch number from a new `VDP_WARDEN_PATCH`.

## Implementation plan

1. **Paths and version** (done). The writable-directory list from the policy (both
   parsers agree on it, as on the rules), `VDP_WARDEN_PATCH`, the
   `--writable-exec` option, the startup refusals and reports. Tests of
   section 1.
   As built:
   - `warden_noexec.inc.c`: a rule is writable when an open its flag clause
     admits writes (an access mode of write or read-write, `O_TRUNC` or
     `O_CREAT`); computed from each rule's verb, kind, matcher, constant and
     flag clause, which the Warden already requires both parsers to read the
     same way at load, so the two agree on the list by construction.
   - The target of each rule as in section 1. A path rule without a matcher
     is a prefix, so `allow path /dev/null` (which admits `/dev/nullX`) names
     `/dev`; that is the safe direction (more is mounted `noexec`), and the
     report shows it. Canonical paths (`realpath`); one inside another
     dropped; at most 256.
   - Refused at start, each with its remedy: a writable rule no directory
     bounds; a writable `/`; the agent's own program under a writable
     directory (from the step-7 review, also the interpreter or loader a
     launch needs). Reported: a missing directory (listed, opens under it
     refused if it appears); a launch-set file under one.
   - Only with `require warden 1.27` (D1); `--writable-exec` turns it off and
     the Warden says so (D2). The Warden reports `1.27.1`
     (`VDP_WARDEN_PATCH`); the grammar stays 1.27 (D5).
   - `--check-startup` lists each directory with the line that makes it
     writable. Nothing is mounted yet (step 2).
   - `make test-v1271` section 1 (19 checks); in CI. `test-v1270`'s version
     check accepts any 1.27 patch release.
2. **The mounts** (done). The private namespace and the re-mounts, before the
   helpers and the agent. Tests of section 2.
   As built:
   - `noexec_mount()` in `warden_noexec.inc.c`: `unshare(CLONE_NEWNS)`, the
     whole tree made private (`MS_REC | MS_PRIVATE`), then for each
     directory (or file) a recursive bind on itself and a remount, with
     `MS_NOEXEC` and the flags each mount already has (`statvfs`), of every
     mount at or under it (read from `/proc/self/mountinfo`, so a mount
     beneath one is `noexec` too). A failure refuses the start.
   - Called right after the list is built, before the run starts, the
     resolver helper starts and the agent is forked; not under
     `--check-startup`. The egress proxy, started earlier, keeps the host's
     view: it opens no file for the agent.
   - Checked by hand before writing the tests: under the Warden, a copy of
     `/usr/bin/true` in a writable directory cannot be mapped executable
     (`mmap` with `PROT_EXEC`: `EPERM`), the original can, and with
     `--writable-exec` both can. A Warden-opened descriptor carries the
     Warden's mount, which is now `noexec`: the design holds.
   - A local soak trial (2 minutes, a task every 5 s) with the work directory
     mounted `noexec`: 20 tasks (6 compiles, 7 `git`, 7 `python3`) all ok,
     2 probes refused, the audit passed. gcc's temporary files are only read
     and written.
   - `make test-v1271` section 2 (9 checks): each directory, a mount beneath

7. **Review by AI review agents** (done), fixes (done), README, threat
   model, spec paper, release notes.
   As built: three AI review agents read `45294a6..bd44694`: the mounts and
   list, coverage (what still reaches executable memory), and the audit,
   tools and soak. Each finding below was reproduced here before it was
   fixed, and each fix has a check in `test_v1271` that fails on the Warden
   before it.
   - **High: the working directory led around the mounts.** The Warden's
     working directory, which the agent inherits, was taken before the bind
     mounts; inside a writable directory (as `soak.sh` runs it) it still
     pointed at the exec-allowed mount beneath, so a copy opened by a
     relative name loaded, mapped executable and launched. Two fixes, each
     closing it alone (shown with the other turned off): `noexec_mount`
     walks the working directory again after the mounts; and every
     descriptor the Warden hands over for a path under a listed directory
     must be on a `noexec` mount (`fstatvfs`), or the open is refused.
     (53cb771)
   - **Medium: a glob with no wildcard** naming a file not there yet got no
     mount; it is now an exact path (its directory, or the file).
   - **Medium: a mount beneath whose `mountinfo` line was over 8 KB** was
     left exec-allowed. Lines are read whole (`getline`), and a second pass
     confirms every mount at or under each directory is `noexec`, or the
     start is refused.
   - **Medium/low: the host changing a writable path during the run.** A
     writable directory missing at start, then made by the host, was
     writable and not `noexec`; a file an exact rule names, replaced by the
     host, was reached through its parent's exec mount. Both are refused by
     the descriptor check; a missing directory is listed (`"missing": true`).
     The agent itself cannot do either (no `mkdir`, `rename` or `link`).
   - **Low: a descriptor the agent inherits** (its standard input from the
     operator's shell) open for reading on a file there was opened before
     the mounts: the start is now refused.
   - **Low: the interpreter or loader a launch needs**, under a writable
     directory, only got a note and then a misleading failure; the start is
     now refused, as for the program itself.
   - **Low:** a remount dropped `nosymfollow` (kept now); a relative glob was
     refused with the wrong reason (it matches nothing and is skipped); the
     Makefile did not rebuild the Warden when `warden_noexec.inc.c` changed.
   - **Medium (audit): an entry's path was never checked against its rule.**
     A re-chained stream could list `/etc`, or a read-only directory, for a
     writable line. Each entry now records its rule's own directory
     (`target`); the audit works that out from the rule (the checker's new
     `matches` mode gives each rule's matcher) and requires it, the path
     spelled canonically and equal to it, none inside another, and `file`
     only for a rule naming one file.
   - **Medium (audit): a list leaving a directory out passed**, even when
     the stream recorded writes there. Now every writable rule's directory
     must be covered by an entry, and every open the stream records the
     agent making for writing under a policy rule must fall under one.
   - **Low (audit):** a `noexec` record from a Warden before 1.27.1 is
     refused. `varek policy show` names a missing directory instead of
     saying the agent writes nowhere. The soak's library probe records the
     loader's words and requires the mapping refusal, and `soak.sh` refuses
     a work directory the host already mounts `noexec`.
   - **Limitation (recorded, not fixed):** a path that reaches a writable
     directory's files through another mount the host made before the run
     (a bind of it elsewhere) is not under a listed directory, so a read
     there is not checked; the policy must also allow that path. An offline
     audit cannot repeat the Warden's `realpath`, so an entry for a rule
     that names its directory through a link is refused by the audit (the
     Warden notes it at start; such a rule matches no path the Warden
     resolves).
   - Suites after the fixes: `test-v1240` to `test-v1271` and `test-cli`
     pass; a 3-minute soak trial (here) passed with the audit's new write
     check over every recorded write.
