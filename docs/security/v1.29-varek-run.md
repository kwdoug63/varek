# v1.29.0 — `varek run` with nothing set up first, a dry run, and `varek policy suggest` (plan)

Status: **plan; decisions pending** (D1 to D11 below, each with a
recommendation), target **v1.29.0**. Each section ends with what must be
tested before it ships. The roadmap entry is in
`docs/roadmap/v1.28-v1.31.md`.

Ship gate (decided for v1.28.1, v1.29.0 and v1.31.0 together): one 24-hour
soak on the droplet covers the three releases' changes on the final build,
before any of them is tagged.

## What v1.28.1 leaves open

`varek run -- <agent>` exists from v1.22.0. Before it does anything, an
operator has to:

- **Run `varek init --pack NAME`.** Without `/etc/varek/varek.conf`,
  `varek run` stops ("no configuration"). The five packs are written for
  sector workloads (a SOC agent, a claims agent), not for a coding agent in
  a project directory, so the first run of, say, Claude Code under any of
  them is refused at its first read of its own configuration.
- **Write or adapt a policy by hand.** Nothing tells the operator what an
  agent needs. The only way to find out is to run it, read `varek
  refusals`, add a rule, and run it again, once per refusal; an agent that
  stops at its first refusal shows one refusal per run.
- **Accept that files the agent creates belong to root.** The Warden opens
  every file it hands the agent itself, as root (§2.12 of the spec paper;
  threat model §6). A file the agent creates is root's, and a root-owned
  file under a tree the policy lets the agent write is writable by the
  agent whatever its mode. Under a sector pack, with the agent writing only
  scratch space, this was a stated limit; for an agent working in a user's
  own project, it leaves the project full of root-owned files and lets the
  agent write files the user could not.

## What it gains, and what it does not

With v1.29.0:

- **One command.** `sudo varek run -- claude` (or `-- python3 agent.py`)
  starts the agent under the Warden with a built-in baseline policy for the
  working directory, with no `varek init` and no policy written by hand.
  The policy it ran under is an ordinary file, recorded by SHA-256 in
  `run_start` like any other, so the audit and the tools work unchanged.
- **A dry run.** `varek run --dry-run -- <agent>` decides and records every
  call exactly as an enforcing run would, and then lets the agent go on
  where an enforcing run would have refused: one run shows everything the
  policy would refuse. It is labelled as not enforcing everywhere it
  appears: on the terminal, in the stream, in every record it did not
  enforce, in the audit's result and in the export.
- **`varek policy suggest`.** From a run's stream (a dry run's, or an
  enforcing run's refusals), a draft policy: the run's policy with a rule
  for each object it refused, commented with how often and by whom, for the
  operator to read, edit and install. It installs nothing.
- **Files opened as the agent.** Under `require warden 1.29`, the Warden
  opens each file it hands the agent with the agent's own user, group and
  supplementary groups: a file the agent creates is the agent's, and a file
  the agent's user could not write is not writable whatever rule allows it.
- **The free tier named.** The MIT build is VAREK Core (D9), as the
  `varek` command and the AWS Marketplace image have called the open-source
  packs since v1.23.

It does not:

- change any verdict. A dry run's decisions are the same SATISFIED,
  UNSATISFIED and UNKNOWN an enforcing run would reach; what changes is
  whether the Warden holds the agent to them. No extension may move a
  genuinely unsafe action to SATISFIED, and none does here;
- make a dry run safe. Its whole purpose is to let through what the policy
  would refuse. It is for a host and an agent the operator would run
  without VAREK; a dry run gives the agent no more than it would have had
  then (D1), and in a few places less (D2);
- make a suggested policy right. `suggest` writes down what the agent did;
  whether the agent should have done it is the operator's call, and the
  draft says so in its first lines;
- install anything for the agent, or reach the network for VAREK (no
  telemetry, no policy download).

## The design in one paragraph

`varek run` without a configuration makes what it needs on first use (the
log directory and a signing key, each step printed; no `varek.conf`),
writes the baseline policy for the working directory and the agent (a
generic baseline, plus a profile chosen by the agent command's name: its
configuration directory and its model provider's API host) to a root-owned
file under `/var/lib/varek/policies/`, and runs the agent as the user who
ran `sudo`. The baseline says `require warden 1.29`, so the Warden opens
files with the agent's credentials. With `--dry-run` the Warden runs
exactly as it does when enforcing, with one difference at the end of each
decision: an UNSATISFIED or UNKNOWN call is carried out (by the kernel, as
the agent's own user, for files, launches and system calls; by the Warden's
dial, as for an allowed connect, for connects) and its record says
`"enforced":false`. The Warden's own files, the hard-denied system calls,
`varek revoke` and the user token's expiry still refuse in a dry run.
`varek policy suggest LOG` reads the stream and writes a draft policy.

## 1. Opening files as the agent (`require warden 1.29`)

- Under `require warden 1.29`, the Warden opens every file it hands the
  agent (`materialize_target`, the launch's file, the `noexec` view of
  v1.27.1) in a thread whose filesystem user, group and supplementary
  groups are the agent's (`setfsuid`, `setfsgid` and `setgroups` as raw
  system calls: credentials are per thread in the kernel, and the Warden's
  other threads keep root's). The kernel's own permission checks then
  apply on top of the decision: an open the policy allows but the agent's
  user could not make fails with the kernel's error (`EACCES`), recorded
  as the decision it was (SATISFIED) with the kernel's result.
- A file the agent creates is owned by the agent's user and group, with
  the mode it asked for under its umask.
- The protected objects (the Warden's key, anchor, stream, `warden-secrets`'
  files, control-group files) are refused by identity, as before; opening
  as the agent is in addition, not instead.
- Without `require warden 1.29`, files are opened as before (as root): a
  v1.28 policy decides and opens the same (D4).
- The grammar version is 1.29: a v1.28.1 Warden refuses `require warden
  1.29`. No other line is added (D11).

*Tests:* a file the agent creates is the agent's, with its mode and
umask; a root-owned 0644 file under a writable tree is not writable (the
kernel's `EACCES`, recorded); a file readable by a supplementary group of
the agent's user is readable; the protected objects still refused; a
v1.28 policy opens as root as before; `noexec` mounts and launches under
the agent's credentials; the thread's credentials never leak into the
Warden's other work (the stream, the key, `warden-secrets`' socket still
written as root).

## 2. The baseline policy and the agents' profiles

- `varek run` without a configuration (or with `--baseline` when one
  exists) writes the baseline for this run:
  - `require warden 1.29`; launches decided (v1.27) and the writable
    directories `noexec` (v1.27.1), unless `--writable-exec`;
  - the system read-only: `/usr/`, `/lib*/`, `/etc/` less its secrets
    (`/etc/shadow`, `/etc/gshadow`, `/etc/sudoers*`, `/etc/ssh/`, private
    keys), the dynamic loader's cache, the CA store;
  - the working directory read-write, and a private `/tmp/` for the run;
  - in the user's home, nothing but the profile's directories; credential
    stores refused by name wherever they appear (`.ssh/`, `.aws/`,
    `.config/gcloud/`, `.kube/`, `.docker/config.json`, `.netrc`,
    `.git-credentials`, `*.pem`, `id_*`, and the packs' existing key
    patterns), first in the file so no later allow reaches them;
  - launches of the programs under `/usr/bin/`, `/bin/`, `/usr/local/bin/`
    and the profile's own directories;
  - no network, except the profile's hosts on 443 (named, v1.24).
- **Profiles** (`policies/agents/NAME.profile.txt`, shipped and shown by
  `varek policy show --profile NAME`): rules added to the baseline for a
  known agent. v1.29.0 ships profiles for Claude Code (`claude`), the
  OpenAI Codex CLI (`codex`), the Gemini CLI (`gemini`), Aider (`aider`),
  and plain Python and Node.js (no rules of their own; their package
  caches read-only). Each profile is built by the method this release
  provides: a dry run of the agent, `varek policy suggest`, and review.
  The profile is chosen by the agent command's name (after `env`,
  `npx`/`uvx` and an interpreter, the script's name), or by `--profile
  NAME`; `--profile none` uses the baseline alone. An unknown command gets
  the baseline alone, and `varek run` says so.
- The written policy is a complete, ordinary policy file: root-owned, 0644,
  named by its SHA-256 under `/var/lib/varek/policies/` so the audit and
  `varek refusals` find it, never rewritten. Its first lines say which
  baseline, profile and working directory it was made for. `varek run
  --show-policy` prints it without running.
- `run_start` gains `baseline` (the baseline's version, the profile's name
  and SHA-256, the working directory) when the policy came from one.

*Tests:* the baseline lints, and passes `make crosscheck` (the three
parsers agree on it and on each profile); a Python agent and a Node.js
agent that read their packages, write in the working directory, launch
`git` and `sh`, and connect to a local stand-in for a model API named in a
test profile; each credential store in a test home refused; a profile
chosen by each spelling of the command; the written policy recorded and
audited; each shipped profile run as a dry run against its CLI where the
CLI installs without an account (refusals listed in the test's output, not
failed on: the CLIs change).

## 3. The dry run

- **Chosen per run, on the command line only** (D3): `varek run
  --dry-run`, which passes the Warden `--dry-run`. A policy cannot ask for
  it, and `varek.conf` has no setting for it.
- **Decided as when enforcing.** Every mediated call goes through the same
  path: resolution, the decision procedure, the certificate checker for a
  SATISFIED verdict, the record. Only the last step differs (D1):
  - an allowed call is carried out as when enforcing;
  - a file open, lookup or launch that would be refused is let through
    to the kernel (`SECCOMP_USER_NOTIF_FLAG_CONTINUE`), which carries it
    out as the agent's own user in the agent's own mount namespace: the
    agent gets what its user would get without VAREK, never what the
    Warden's root could;
  - a connect that would be refused is dialed by the Warden as it dials an
    allowed one (the agent has no network of its own); the stub resolver
    answers a name no rule allows, from upstream, and the egress proxy
    relays a request no rule allows (no credential is put in it: a swap
    needs a SATISFIED verdict, as in v1.28.0);
  - the Landlock execute set (v1.27) and the `noexec` mounts (v1.27.1) are
    not applied: a launch outside the set is let through and recorded;
  - a system call outside the allowlist is sent to the Warden instead of
    refused, recorded (`syscall_refused`, with its number) and let
    through, except the hard-denied ones (D2);
  - budgets (v1.25) and the bounded-refusal breaker are counted and
    recorded when they would act, and do not act.
- **Still refused in a dry run** (D2), each recorded `"enforced":true`:
  the hard-denied system calls (those that would let the agent reach the
  Warden or the kernel's configuration: `ptrace`, `process_vm_writev`,
  `bpf`, `mount`, `setns`, `unshare`, module loading and the like); the
  protected objects (the Warden's key, anchor and stream, `warden-secrets`'
  files, the trust bundles, control-group files); every call after `varek
  revoke` or the user token's expiry (v1.28.0, v1.28.1). The first two keep
  the dry run's own stream trustworthy; the third is an operator's act, not
  the policy's.
- **Labelled.** `run_start` says `"mode":"dry_run"`; every record whose
  verdict was not enforced says `"enforced":false` (the verdict itself is
  unchanged); `run_end` counts them. The Warden prints `DRY RUN: NOT
  ENFORCING` on its first line and in its summary; `varek run` prints it
  before and after the agent's output; `varek runs`, `varek status` and
  `varek refusals` mark the run and say "would refuse"; the audit and the
  export below.
- **Not with** `--plan` (the plan gate refuses a plan before the agent
  starts; a dry run of a plan is `varek policy check`'s job) and not with
  credentials named in the policy (a dry run would hand the proxy real
  values for an agent the policy does not yet hold; D2).

*Tests:* each kind of call that would be refused (an open, a create, a
lookup, a launch outside the set, a connect, a name, a request, a system
call outside the allowlist) carried out and recorded `enforced:false`; the
same run enforcing refuses each; an open the agent's user could not make
fails with the kernel's error and is recorded so; each hard-denied call,
each protected object, and every call after a revocation refused and
recorded `enforced:true`; the breaker and the budgets recorded and not
acting; the label in each place it must appear; `--dry-run` with `--plan`
or with credentials refused; no `dry_run` setting read from a policy or
`varek.conf`.

## 4. `varek policy suggest`

- `varek policy suggest [LOG] [-o FILE]`: from a stream (default: the
  latest run's), the run's policy followed by a block of suggested rules,
  one for each object the run refused (an UNSATISFIED or UNKNOWN verdict,
  enforced or not), grouped by kind, each with a comment: how many times,
  which process and which sub-agent (v1.28.1), the first and last time.
- **Exact by default** (D8): a rule names the object it saw, with the
  narrowest form that admits it (`readonly` for reads, the flags seen for
  writes; `allow exec` with the path; a connect by the name the agent used
  when it used one, else the address). Where five or more files under one
  directory were refused, a directory rule is offered as a commented-out
  alternative.
- **Never suggested as active rules** (each written commented out, with
  the reason): an object a deny rule of the policy matched (the operator
  wrote that deny); a credential store or key by the baseline's patterns;
  anything in another user's home; a write under `/etc/`, `/usr/` or a
  directory on the system's `PATH`; a launch of a shell, an interpreter or
  `sudo` by a path the agent wrote. `suggest` never removes or weakens a
  rule of the policy.
- The draft begins by saying it is a draft from one run, not a reviewed
  policy, and by naming the run, its mode and its policy's SHA-256. It
  lints (`vdp_check lint`) before it is written; one that does not lint is
  a bug. Output is deterministic for a given stream.
- `varek policy use FILE` installs a reviewed draft as today; `varek run
  --policy FILE --dry-run` checks it.

*Tests:* a dry run with known refusals of each kind gives the expected
draft, byte for byte; the draft lints; a second dry run under it refuses
nothing the first did (the commented-out lines aside); each never-active
case written commented out; a deny rule of the policy never undone; a
stream from an enforcing run; a stream with sub-agents.

## 5. Audit, export and tools

- `varek_audit.py`: a dry run's stream is checked as an enforcing one is
  (chain, signatures, every decision re-made, certificates), plus: every
  `enforced:false` record is in a stream whose `run_start` says
  `dry_run`, holds a verdict other than SATISFIED, and is not of a kind
  D2 keeps refused; in a stream that is not a dry run, no record says
  `enforced:false`. A dry run that passes these ends `VERIFIED: DRY RUN,
  NOT ENFORCED` and exits 3, so a script treating exit 0 as "enforced"
  cannot mistake it (D10).
- The CycloneDX export of a dry run says `varek:mode=dry_run` in its
  metadata and on every authorization it lists, and counts "would refuse"
  separately; it is never written without it.
- `varek runs` (a MODE column), `varek status`, `varek refusals` ("would
  refuse", and `--enforced`/`--not-enforced`), `varek policy show` (the
  baseline and profile a policy was made from), `varek doctor` (Landlock,
  which the baseline needs, and `SECCOMP_USER_NOTIF_FLAG_CONTINUE`, which a
  dry run needs; the agent's user exists and has a home).

*Tests:* forged streams the audit refuses (an `enforced:false` record in
an enforcing run; one with a SATISFIED verdict; one on a protected object;
a dry run that claims to be enforcing in `run_end`; a `run_start` whose
`dry_run` was dropped); the exit code; the export's marks; each tool's
output.

## 6. Running the agent as its user (D6), and its environment (D7)

- With no configuration, the agent runs as the user who ran `sudo`
  (`SUDO_UID`, `SUDO_GID` and that user's groups), so its files are its
  own (with §1). Run as root without `sudo`, or by `sudo` from root, it
  runs as `nobody` and `varek run` says so. `--run-as` overrides; root is
  refused as in v1.17.
- The agent's environment: what `sudo` passed, with `HOME`, `USER`,
  `LOGNAME` and `SHELL` set to the agent's user's, and `PATH` to the
  system's. A variable an agent needs (an API key) is passed by name with
  `--env NAME` (repeatable) and recorded by name, never by value. v1.28.0's
  placeholders remain the way to keep a key out of the agent (D7).

*Tests:* the agent's uid, gid and groups under `sudo`, as root, with
`--run-as`; its environment; `--env` passes the variable and the stream
holds its name only.

## 7. Cost

The baseline and a profile add rules, and the decision procedure's time
grows with the rules a call must pass: `varek bench` measures the decision
time under the baseline with each profile against a sector pack. Opening
as the agent adds a hand-off to the opening thread per open, measured the
same way. A dry run costs what an enforcing run does, plus a notification
for each system call outside the allowlist.

## Decisions before building

- **D1. How a dry run carries out a call the policy refuses.** (a) The
  kernel carries out a file open, lookup, launch or unlisted system call as
  the agent's own user (CONTINUE); the Warden dials a connect as it dials
  an allowed one. (b) The Warden carries out every call itself, as it
  does an allowed one. (c) The agent gets the host's network namespace,
  and connects are CONTINUEd too. *Recommended: (a).* (b) would open files
  as root for the agent: a dry run would give the agent more than it has
  without VAREK. (c) loses the names the Warden decides connects on (v1.24
  to v1.26.1), so the dry run would not report what the policy would do.
  CONTINUE has a race (the agent can change the call's memory after the
  Warden read it), so a would-be refusal's record says what the agent
  asked, not certainly what the kernel did; in a dry run, which enforces
  nothing, that is a limit of the report, not a hole in enforcement.
- **D2. What a dry run still refuses.** (a) The hard-denied system calls,
  the protected objects, and every call after a revocation or the token's
  expiry; and a policy with credentials is refused a dry run. (b) Nothing:
  a dry run lets everything through. *Recommended: (a).* The first two keep
  the stream the dry run is for out of the agent's reach; a revocation is
  the operator saying stop; a dry run with credentials would release real
  values to an agent whose policy is not settled.
- **D3. How a dry run is chosen.** (a) Only per run, on the command line;
  (b) also in `varek.conf` or a policy line. *Recommended: (a).* A setting
  that makes every run non-enforcing, or a policy that switches its own
  enforcement off, is too easy to leave in place.
- **D4. Opening files as the agent.** (a) Under `require warden 1.29`
  only; (b) always; (c) not in v1.29.0. *Recommended: (a).* (b) would
  change what existing policies do: a sector pack that lets `nobody` read
  a root-only file through a rule would stop working. (c) leaves root-owned
  files in the user's project and the agent able to write files its user
  could not, which the baseline must not.
- **D5. The baseline.** (a) A generic baseline plus a profile per known
  agent, chosen by the command's name; (b) the generic baseline only.
  *Recommended: (a).* Under (b) every coding agent is refused at its first
  read of its own configuration, which is the experience v1.29 is meant to
  end. The profiles are made with the dry run and `suggest`, so they are
  the release's own first use of them.
- **D6. The agent's user with no configuration.** (a) The user who ran
  `sudo`; (b) `nobody`, as `varek init` sets. *Recommended: (a)*, with
  `nobody` when there is no such user (root without `sudo`). An agent in a
  user's project, running as `nobody`, cannot read the user's files the
  kernel guards, and with §1 cannot create files there.
- **D7. The agent's credentials (API keys).** (a) As without VAREK: its
  configuration directory (the profile) and variables passed by name with
  `--env`; (b) v1.28.0 placeholders by default, the key in a root-owned
  file. *Recommended: (a)* in v1.29.0: (b) needs a key file and inspecting
  mode set up first, against "nothing set up first". `varek policy suggest`
  notes a key it can see the agent sending, and the release notes say how
  to move it to a placeholder.
- **D8. How `suggest` generalizes.** (a) Exact objects, a directory rule
  only as a commented-out alternative; (b) directory rules whenever
  several files in a directory were refused. *Recommended: (a).* A
  suggested rule wider than what was seen grants what nobody saw the agent
  need; the operator can widen it knowingly.
- **D9. The free tier's name.** (a) VAREK Core, the name the `varek`
  command, the Marketplace image and the spec paper have used for the
  open-source packs since v1.23; (b) a new name (for example, VAREK
  Community). *Recommended: (a).* A new name would leave the image's
  messages and the documentation disagreeing with the listing. The site
  and the Marketplace listing are Ken's to change; the repository's README
  gains a short "VAREK Core and VAREK Enterprise" section.
- **D10. The audit's result for a dry run.** (a) Verified and labelled,
  with its own exit code (3); (b) exit 0 with a label; (c) refused (exit
  1). *Recommended: (a).* (b) lets a script that checks only the exit code
  take a dry run for an enforced one; (c) makes a dry run's stream, which
  is meant to be read and kept, look tampered with.
- **D11. The version.** (a) The Warden reports 1.29.0 and the grammar is
  1.29 (`require warden 1.29` turns on opening as the agent); no other line
  is added; the baseline and the profiles are policies in the existing
  grammar. (b) New lines for the baseline (a variable for the working
  directory or the home). *Recommended: (a).* Writing a concrete policy for
  each run keeps the three parsers, the certificates and the audit as they
  are, and a written policy can be read, kept and audited like any other.

## Implementation plan

1. **Opening as the agent**: `require warden 1.29`, the opening thread's
   credentials, the version 1.29.0 in the three parsers. Tests of section 1.
2. **The baseline and the profiles**: the generator, `/var/lib/varek/policies/`,
   `run_start`'s `baseline`, `varek run` with no configuration (first-use
   setup, the agent's user and environment, `--env`, `--profile`,
   `--show-policy`). Tests of sections 2 and 6.
3. **The dry run**: `--dry-run` in the Warden (CONTINUE, the dial, the
   stub and the proxy, no Landlock set or `noexec`, unlisted system calls
   notified, the breaker and budgets), what still refuses, the records and
   labels. Tests of section 3.
4. **`varek policy suggest`.** Tests of section 4.
5. **Audit, export and tools.** Tests of section 5.
6. **The profiles**: a dry run of each agent, `suggest`, review, shipped.
7. **Tests and the regression count** against v1.28.1 (`make test-v1290`).
8. **Latency**: the baseline and profiles against a pack; opening as the
   agent; a dry run's unlisted system calls. The soak is shared (above).
9. **Review by AI review agents**, fixes, README (VAREK Core and VAREK
   Enterprise), threat model, spec paper, release notes.
