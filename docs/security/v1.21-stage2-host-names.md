# v1.21 stage 2 — host names without agent DNS (plan)

Status: **released in v1.24.0** (2026-10-07; retargeted 2026-10-03 from
v1.21.2: v1.22.0 shipped the `varek` command and `varek bench`, and v1.23.0 is
the first VAREK Enterprise AMI), after the outside review of v1.21.0. Sections
1 to 4 are implemented ("Implementation notes" at the end says what was decided
while building them). Section 5, the 24-hour run against CDN-hosted APIs,
passed on 2026-10-06 and again on 2026-10-07 (results in RELEASE-v1.24.0.md).
This file is the design the implementation will be measured against; each
section ends with what must be tested before it ships.

## Where stage 1 leaves off

v1.21.0 decides each connect on the numeric destination the Warden dials
(`a.b.c.d:port`, `[IPv6]:port`, `unix:<path>`). A policy therefore names
addresses, and an agent that wants `api.salesforce.com` must be given an
address by someone else: the operator (hard-coded), or a resolver the policy
lets it reach (`allow host 10.0.0.2:53`), which also lets it send arbitrary
data to that resolver in DNS queries. Neither is what a buyer means by "allow
the Salesforce API". Host rules with names parse, but a load-time note says
they can never match (`deny host evil.example.com` never fired through v1.20).

## The design in one paragraph

Policies name hosts: `allow host api.salesforce.com:443`. The Warden resolves
the names the policy allows, itself, and keeps a table of the addresses each
name resolved to. When the agent looks a name up, it reads `/etc/hosts`, and
the Warden answers that open with a view it builds from the table: the allowed
names and their current addresses, nothing else. The agent never sends a DNS
query (no resolver is allowed), so a name the policy does not allow does not
resolve, and DNS cannot carry data out. At connect time the destination must
be an address the Warden itself resolved for an allowed name; the decision is
made on `name:port`, certified like any host rule, and recorded with the
resolution it relied on.

## 1. Policy grammar

- `allow host <name>:<port>` and `allow host <name>` (any port), where
  `<name>` is a DNS name: lowercase letters, digits, hyphens and dots, labels
  of 1 to 63 bytes, at most 253 bytes, no trailing dot (a trailing dot is
  refused at load, not stripped), internationalized names as A-labels
  (`xn--…`) only. A name in any other form is refused at load.
- `deny host <name>` carves an exception out of a broader allow, as today.
- No wildcards (`*.salesforce.com`) in stage 2: the Warden cannot enumerate
  the names under a wildcard to resolve them, and resolving on demand would
  make the agent's lookups queries the Warden sends for it (a DNS channel
  again). Wildcards are planned as an opt-in rule form in v1.25.0, with
  shared domains refused and the name channel bounded
  ([design](./v1.25-wildcard-host-names.md)), and without any agent DNS in
  the v1.26.0 egress proxy ([design](./v1.26-egress-proxy.md)).
- Numeric rules keep working and keep their meaning.
- `require warden 1.24` for a policy with name rules, so an older Warden
  refuses the policy rather than loading name rules it cannot match. The
  directive takes `<major>.<minor>`, so no patch component is needed: every
  earlier Warden refuses it with `policy requires Warden 1.24; this is 1.21`
  (the policy-grammar version, which v1.22 and v1.23 leave at 1.21). Stage 2
  raises that version to 1.24 in both parsers. (Through 2026-10-02 this plan
  targeted v1.21.2 with a patch-form `require warden 1.21.2`.)
- Both parsers (decision procedure and certificate checker) validate names
  independently and must agree rule by rule, as for every other rule.

*Tests:* parser refusals (uppercase, trailing dot, empty label, 64-byte label,
U-label, wildcard), agreement of both parsers, lint notes, the cross-check
oracle extended with name constants.

## 2. The Warden's resolution table

- At startup, before the agent runs, the Warden resolves every name an allow
  rule names, A and AAAA, through the host's resolver
  (`res_nquery`, so the answer's TTL is known). A name that does not resolve is
  reported and retried; it does not stop the Warden (the agent's lookups of it
  fail until it does).
- Each entry is refreshed at its TTL, clamped to [30 s, 1 h] (configurable),
  between notifications, never while an agent thread waits on an answer.
- An address that drops out of a name's answer stays valid for a grace period
  (default: the old TTL, at most 5 min), because the agent may have read it
  from the view just before. After that a connect to it is refused.
- Every resolution is a chained record in the verdict stream (`event:
  resolution`: name, addresses, TTL, the resolver used, time), signed by the
  next checkpoint like any record.
- The Warden trusts the host's resolver. DNSSEC validation is not in stage 2;
  a host that needs it points the Warden at a validating resolver.

*Tests:* refresh on TTL against a local authoritative test server that
rotates answers; grace period; an unresolvable allowed name; resolution
records chained and audited; the Warden never blocks an answer on a lookup.

## 3. The hosts view

- An open of `/etc/hosts` (by its canonical path, after resolution, like any
  open) is answered with a read-only descriptor on a sealed memfd holding
  `127.0.0.1 localhost`, `::1 localhost` and one line per current address of
  each allowed name. It is served whenever the policy has a name rule, without
  an allow rule for the path, unless a deny rule covers `/etc/hosts` (then the
  agent resolves nothing). Each open is recorded (`rule: hosts_view`) with the
  view's generation number, so an audit can tie what the agent could resolve
  to the resolution records. The same holds for the two views below.
- `/etc/resolv.conf` is answered with a view that names no reachable server
  (`nameserver 192.0.2.1`, an address reserved for documentation that is never
  assigned, with `options attempts:1 timeout:0`; see the implementation notes), and `/etc/nsswitch.conf` with
  `hosts: files`. Not `127.0.0.1`: since v1.21.0 the Warden dials an allowed
  connect in the host's namespace, where `127.0.0.1:53` may be a real resolver
  (dnsmasq, a local cache). While the policy has a name rule, the Warden
  refuses every connect to port 53, TCP or UDP, whatever the numeric rules say
  (`rule: dns_refused`), so a library that skips `/etc/hosts` fails at once
  instead of waiting, and cannot reach any resolver by any address.
- Clients that must work, each tested as the agent: glibc `getaddrinfo`
  (curl, Python `socket`/`requests`, Node's `dns.lookup` and `http`), musl
  (an Alpine-built binary), Go's pure-Go resolver (reads `/etc/hosts` itself),
  Java (`InetAddress`). Clients that query DNS directly (Node's `dns.resolve*`,
  c-ares, `dig`) fail: that is the point, and is documented.

*Tests:* each client resolves an allowed name and connects; a name the policy
does not allow fails to resolve within 100 ms; no connect to port 53 is ever
made, including with `allow host 127.0.0.1` and a resolver listening there;
the view's contents are exactly the allowed names.

## 4. Deciding a connect

- The destination is spelt canonically, as in stage 1. The Warden looks it up
  in the resolution table (current and grace entries) and finds the names that
  resolved to it.
- The decision is made on `name:port` for each such name, first match wins
  as always; an address no allowed name resolved to is decided on its numeric
  form (so numeric rules still apply, and are the only way to reach it).
- The certificate is over the string decided (`api.salesforce.com:443`); the
  record also carries the address dialed and the resolution record it relied
  on, so `varek_audit.py` can check that the address was in that name's answer
  at that time.
- The plan gate decides a `net_connect api.salesforce.com:443` step on the
  name, without resolving it (the step is a declaration; the runtime decides
  the address).

*Tests:* the stage 1 suite unchanged; a name rule allows its current and grace
addresses and nothing else; a deny rule on a name wins over a numeric allow of
its address, in rule order; audit re-checks name certificates and the
name-to-address binding; tampering with a resolution record fails the audit.

## 5. A real CDN-hosted API

Content networks change addresses often and put many names on one address.
Before stage 2 ships it is run for at least 24 hours against real CDN-hosted
APIs (one Fastly-, one Cloudflare- and one CloudFront-hosted), with the agent
fetching every minute, and must show: no refused connect caused by a stale
table, every refresh recorded, and the addresses the agent used all present
in the resolution records.

What stage 2 cannot do, and says so: on a shared CDN address, allowing
`api.example.com` also lets the agent reach any other site served from that
address, by sending another name in TLS SNI or the HTTP Host header. Stage 2
decides the address a name resolves to, not the name the agent asks the
server for. The v1.26.0 egress proxy, which sees SNI and Host
([design](./v1.26-egress-proxy.md)), is where that line is drawn. The threat model will state this next to the stage 1 note that
an allowed host is a channel.

## 6. What changes for operators

- A policy can say `allow host api.salesforce.com:443` and mean it.
- The Warden needs to reach the host's resolver; the agent needs none.
- `/etc/hosts`, `/etc/resolv.conf`, `/etc/nsswitch.conf` and `/etc/host.conf`
  need not be in the policy's allow rules for the views to be served; a `deny` covering them
  still wins (the agent then resolves nothing).
- The preflight resolves each allowed name and reports ones that fail.

## Open questions

- Wildcards (`*.salesforce.com`): decided 2026-10-05 — opt-in in v1.25.0
  ([design](./v1.25-wildcard-host-names.md)) and DNS-free in the v1.26.0
  egress proxy ([design](./v1.26-egress-proxy.md)).
- Should a refresh that changes a name's addresses be signed at once (a
  checkpoint), rather than at the next scheduled one?
- Per-name TTL overrides in the policy, or a Warden-wide clamp only?

## Implementation notes

### Sections 1 and 2

Decided while building them, 2026-10-05. Tests: `make test-v1240`
(`varek/v1_4/tests/test_v1240.sh`) and `make crosscheck`.

**Grammar.**
- A host constant is in *name form* unless it starts with `[` or `unix:`, or
  the part before its first `:` is empty or only digits and dots (those are the
  v1.21 numeric forms, unchanged, still with load-time notes for spellings no
  connect produces). So `010.1.2.3` is a non-canonical address, not a name.
- After `require warden 1.24` a constant in name form must be a valid name or
  the policy is refused. Besides the rules in section 1: a label may not start
  or end with `-`; the last label may not be all digits (`a.123`); the name
  `unix` is reserved (`allow host unix` would otherwise match every
  `unix:/path`); a port is decimal, 0 to 65535, without leading zeros.
- Without the directive, a constant in name form keeps its v1.21 meaning (an
  exact string no connect produces) and the note says so, so every v1.21
  policy loads unchanged. A `require warden 1.24` that comes after such a
  constant is refused, so one policy cannot hold names under both meanings.
- A name without a port matches every port (`host(c, s)` with `portless(c)`),
  decided once at load in all three parsers (decision procedure, certificate
  checker, cross-check oracle); the Warden compares the two C parsers'
  readings, including that bit, at startup.
- The policy-grammar version is 1.24 in both parsers and the oracle.

**Resolution table** (`varek/v1_4/warden_resolve.c`).
- Lookups are A and AAAA through `res_nquery`, the name sent fully qualified
  (no search list), CNAME chains followed (at most 8 links), the answer's TTL
  the smallest over the chain.
- Refreshes run in a **resolver helper process**, not a thread: after
  `unshare(CLONE_NEWPID)` the kernel refuses new threads, and a thread started
  before the agent is forked would make that fork unsafe. The helper is the
  Warden re-executed (`--resolver-helper`) over a socket pair, started after
  the startup lookups and before the agent's PID namespace exists, as a
  grandchild (its exit raises no SIGCHLD in the Warden). It never holds the log
  signing key, and the resolver library's parsing of network data runs outside
  the Warden. It exits when the Warden's end of the socket closes. If it dies
  during a run, the Warden stops the run (the table would go stale).
- A refresh that fails (timeout, SERVFAIL) keeps that family's current
  addresses and is retried after the TTL floor; an authoritative empty answer
  (NXDOMAIN, or no record of the type) replaces them, the old ones going into
  grace. An unresolved name is retried at the floor.
- Options: `--dns-ttl-min` / `--dns-ttl-max` (default 30 s / 1 h),
  `--dns-grace-max` (default 300 s), `--dns-server a.b.c.d[:port]` (a
  validating resolver, or the test server). `--check-startup` resolves each
  name and reports the ones that fail, without writing records.
- Records: `run_start` carries `host_names` and `resolver`; each lookup is a
  chained `resolution` record (`name`, `a` and `aaaa` status, `addresses`,
  `grace` with seconds left, `ttl`, `refresh_s`, `resolver`, `generation`).
  The generation counts changes to any name's current set, for the section 3
  views. Signing a checkpoint at once when an answer changes (an open question
  above) is not done yet: the next scheduled checkpoint signs it.

### Sections 3 and 4

Decided 2026-10-05. Code: `varek/v1_4/warden_names.inc.c`; tests: section 4
of `make test-v1240`.

**Views.**
- While the policy has a host name rule (allow or deny), a read-only open of
  `/etc/hosts`, `/etc/resolv.conf`, `/etc/nsswitch.conf` or `/etc/host.conf` is
  answered with a read-only descriptor on a sealed memfd. The open is matched by
  the path the agent gave, when it is exactly one of the four (whether or not
  the host has the file), or by the canonical path it resolves to: one of the
  four, or what
  each resolved to on the host when the Warden started (`/etc/resolv.conf` is
  often a symlink into `/run`).
- The policy is asked about the view's path. An explicit deny wins (the agent
  then resolves nothing); anything else, an allow or no rule, serves the view.
  The record's rule is `hosts_view`, `resolv_view`, `nsswitch_view` or
  `hostconf_view`, with
  `view_generation`. There is no certificate: no file is opened, and what the
  agent reads is the Warden's own text. `varek_audit.py` accepts such a record
  only for the view's own path, a read-only open, and a run whose `run_start`
  says the policy has host name rules (`host_name_rules`).
- `nsswitch.conf` reads `passwd: files`, `group: files`, `hosts: files`.
- `host.conf` reads `multi on`, and the hosts view lists each name's IPv4
  addresses before its IPv6 ones. Added 2026-10-06, after the first 24-hour
  soak. Without `multi on` (the file absent, or not readable under the
  policy, as in the soak), glibc returns only the first `/etc/hosts` line for
  a name. The table appends a new address after the ones it keeps, so after
  CloudFront rotated its IPv4 addresses an IPv6 one came first. The agent then
  got that single address, which the IPv4-only droplet could not reach. That
  happened on 4 of 1,440 fetches; `make test-v1240` now recreates it.
- `resolv.conf` says `timeout:0`, not the `timeout:1` planned above. musl has
  no nsswitch, so it queries the nameserver after `/etc/hosts`. The Warden
  refuses that send, but musl ignores the error and waits out its timeout.
  With `timeout:0` it gives up at once. glibc, Go and Node never query through
  the view (`hosts: files`), and glibc treats 0 as its own 1 s minimum.
- The legacy `open(2)` is now mediated, as `openat(AT_FDCWD, …)`. A static musl
  program calls `open`, never `openat`, and through v1.23 that fell to the
  filter's default deny: a musl agent could open no file at all, so it could
  not read the hosts view either.
- Lookups by `stat` and `access` on the four paths are decided as before (no
  view); glibc, Go, Node and Java resolve correctly without them.

**Port 53.** With a host name rule in the policy, a connect to port 53 is
refused before the policy is asked (rule `dns_refused`), TCP or UDP, any
address. A send naming a destination was already refused in v1.21.

**Deciding a connect.**
- The candidates are the numeric destination and `name:port` for every table
  name whose current or grace addresses include it. The first rule, in policy
  order, that holds on any candidate decides. So a deny on a name wins over a
  later numeric allow of its address, and a numeric deny wins over a later name
  allow. The record's `resolved` is the deciding candidate; it also carries
  `dialed`, `candidates` and `resolution_generation`.
- An address that more than 15 names resolve to is refused (`too_many_names`):
  a name left out could hold an earlier deny.
- The certificate is over the deciding candidate. The checker then confirms,
  with its own matchers, that no earlier host rule holds on any other
  candidate (`vdpc_holds`).
- `varek_audit.py` rechecks all of it. Each name candidate must be bound to the
  dialed address by the latest resolution record before the connect (current,
  or in grace). Every name whose latest record lists the address must be a
  candidate. No earlier host rule may hold on another candidate
  (`vdp_cert_check … kinds` and `holds`). A stream edited to leave a name out,
  with its chain recomputed, fails the audit.
- The plan gate decides a `net_connect <name>:<port>` step on the name when the
  policy has host name rules.

**Clients tested as the agent** (section 4 of `make test-v1240`):
- Python's `socket` and `http.client` (glibc).
- Node's `dns.lookup` and `http`. Node's `dns.resolve4` fails at once, as
  intended.
- Go with `CGO_ENABLED=0` (its own resolver).
- Java's `InetAddress` and `HttpURLConnection`.
- A static musl client (built with `musl-gcc -static`).
- curl.

### After the AI-agent review

Decided 2026-10-07. Findings and fixes: `RELEASE-v1.24.0.md`, "Found in
review"; tests: section 5 of `make test-v1240`.

- **Special addresses.** A connect to a loopback, link-local, unspecified or
  multicast address (IPv4 0/8, 127/8, 169.254/16 and 224/3; IPv6 `::`, `::1`,
  fe80::/10 and ff00::/8, with IPv4-mapped forms as IPv4) is decided on its
  address alone. Its record has `"special_address": true` and the address as
  its only candidate. Only a numeric rule reaches these addresses, whatever a
  name resolves to. Private ranges are not special.
- **Deny rules' names** are resolved too, after the allow rules' names, so
  `deny host <name>` holds on the name's addresses. A name that only deny
  rules name is left out of the hosts view.
- **The resolver files cannot be written.** An open of one of the four view
  paths, or what each resolved to at startup, that could write is refused
  (`view_write_refused`), whatever the policy says.
- **The resolver helper does every lookup**, at startup too. An answer longer
  than the lookup's buffer is a failure.
- **The table.**
  - An AAAA answer `::ffff:a.b.c.d` binds `a.b.c.d`.
  - Grace comes from the last answered TTL, not from a failure's retry
    interval.
  - A full request queue to the helper does not make the supervise loop spin.
- **The audit** (`varek_audit.py`, check 6):
  - Every connect in a run whose policy file has name rules must carry its
    candidates. The policy's name rules are read through `vdp_cert_check …
    rules`.
  - Names bound by grace count, unless their grace ends within the
    1.2 seconds the record's rounding allows.
  - Destinations and ports must be spelt as the Warden spells them, and the
    dialed address must be the target.
  - `resolution_generation` must be the latest resolution record's.
  - A view must not contradict a deny on its path.
