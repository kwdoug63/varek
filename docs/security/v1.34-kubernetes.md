# v1.34.0 — Kubernetes: a node agent, a Helm chart, OpenShift and EKS (plan)

Status: **decided; steps 1 to 7 built** (October 21, 2026: the measurements,
the node agent, the NRI plugin and the launcher, the pod's network, policies,
admission and evidence, the Helm chart and its release, the tests; `kind` in
CI written, not yet run), steps 8 and 9 not, target
**v1.34.0** (numbered so on
October 18, 2026, when macOS became v1.33.0). Decided October 18, 2026:
the recommendation for each decision below (D1 to D11), D6 on step 1's
measurement. The measurements of step 1 settle the parts marked *to be
measured*; it starts after v1.32.0 and v1.33.0. The roadmap entry is in
`docs/roadmap/v1.32-v1.35.md`.

Ship gate: a 24-hour run with a real agent on Amazon EKS and on OpenShift,
the agent pods running with no added capabilities, every guarantee the
Warden gives on a host either held or refused with the reason named.

## What v1.32 leaves open

v1.32 runs the Warden inside the agent's container. In a Kubernetes pod
that means the pod is given ten capabilities, CAP_SYS_ADMIN among them, an
AppArmor profile or SELinux type of VAREK's, and `--cgroupns=private`. A
cluster's admission policy (Pod Security Standards' "restricted" and
"baseline" levels, OpenShift's default security context constraints)
refuses such a pod, and a platform team will not grant it to every agent.
The agent itself holds none of those capabilities, but the pod does, and
the pod's process is the Warden: one Warden per pod, each privileged.

## What v1.34 gains, and what it does not

- **A node agent:** one Warden per node (a DaemonSet), privileged on the
  node as Falco or Tetragon are, which supervises the agent containers of
  labelled pods from outside them. The agent pods get no added capability,
  no custom profile, and pass the "restricted" level.
- **A Helm chart** that installs it, with policies as cluster resources,
  so a policy change goes through the cluster's review and GitOps flow.
- **The v1.32 image as a fallback,** in the pod, where the node agent
  cannot run (a cluster whose runtime has no hook for it, or no
  DaemonSets allowed).
- **OpenShift and EKS:** the chart tested on both; the OpenShift operator
  certification and the EKS add-on listing are business steps that follow
  (D9).

It does not change a decision procedure, a rule or a record's meaning: a
decision made by the node agent is the decision the Warden makes on a host.
Where a guarantee cannot be carried into a pod from outside, the node agent
refuses the pod and says which (D3 to D6), never runs it with less.

## The design in one paragraph

The container runtime starts every container under a seccomp filter its
OCI configuration names. The OCI runtime specification (v1.1) lets that
filter return `SCMP_ACT_NOTIFY` and names a Unix socket
(`linux.seccomp.listenerPath`) to which the runtime (runc from v1.1, crun)
sends the filter's notification descriptor, with the container's state,
when the container is created. The node agent is that listener: it
receives the descriptor for each container of a pod VAREK supervises, and
from then on decides the container's calls as the Warden decides an
agent's, under the policy the pod is labelled with. The OCI configuration
is changed for those pods only, by a plugin of the Node Resource Interface
(NRI), which containerd and CRI-O call as each container is created: it
sets the filter and the listener, and adds what the Warden would have done
itself at the agent's start (the noexec mounts, the launch set, D3 and D4).

## 1. What carries, and what must be built another way

Each of the Warden's guarantees assumes today that it starts the agent.
Under the node agent, the runtime starts it:

| Guarantee | On a host (and v1.32) | Under the node agent |
|---|---|---|
| Calls decided | the Warden's filter, installed by its child, which then launches the agent | the same filter, given in OCI form by the NRI plugin; the runtime installs it at the container's start, so the container's first instruction runs under it (*to be measured: that the Warden's filter can be written in OCI's seccomp form without loss*) |
| The listener | the Warden's own | the descriptor handed over by the runtime (`listenerPath`); the node agent checks it is the container's (the state's pid and its pidfd) |
| Files opened as the agent | names resolved in the Warden's own view | resolved inside the container's root: `openat2` with `RESOLVE_IN_ROOT` on `/proc/<pid>/root`, as the agent's user (*to be measured*) |
| Descriptor handover (`pidfd_getfd`), reading the agent's memory | CAP_SYS_PTRACE in the Warden's namespace | the node agent's, from the host (*to be measured: across the pod's user namespace, where one is used*) |
| The agent's network | an empty network namespace, the stub resolver and the egress proxy the Warden's | the pod's network namespace (the cluster's network): connects are decided as now; the stub resolver and the proxy run in the pod's namespace, entered by the node agent (D5) |
| Decided launches (Landlock) | the agent applies the launch set to itself before it launches anything | cannot be added to a running process from outside: a small launcher the plugin puts first in the container's command applies it, then runs the container's own (D3) |
| Writable directories noexec | the Warden's own mount namespace, which the agent inherits | the container's mounts, set noexec by the plugin; the container's root read-only (D4) |
| Lifecycle, revocation, the token's expiry | the run ends with the agent; the Warden ends every process | the run is the container's life; the node agent ends it by its control group (`cgroup.kill`) |
| Sub-agents and confined MCP servers | control groups under the run's | groups under the container's, which the runtime and the kubelet manage (D6, *to be measured*) |
| The verdict stream | the Warden's, signed | the node agent's, one stream per container, signed with the node's key (D8) |
| The on-behalf-of chain | the user's token, the agent's SPIFFE ID | the same, the token from a projected volume and the SPIFFE ID from the node's SPIRE agent where the cluster runs one |

## 2. The node agent

- A DaemonSet, privileged on the node: the Warden's code with a listener
  socket in place of a launch, one supervision per container, each its own
  policy, stream and decisions. A container is supervised from the moment
  its descriptor arrives until it ends; nothing it does reaches the node
  agent but its notifications.
- The NRI plugin, in the same pod, sets each supervised container's OCI
  configuration: the filter and `listenerPath`, the noexec mounts, the
  launcher (D3), and a refusal (the container is not created) when the pod
  asks for what the node agent cannot carry, with the reason in the pod's
  events.
- A pod is supervised when it carries a label naming a policy
  (`varek.io/policy: NAME`); a namespace can require it (an admission
  check the chart installs, D7).
- If the node agent is not running, a supervised container is not created
  (the plugin fails closed), never created unsupervised.

## 3. The Helm chart

- The DaemonSet, the plugin, the CRD (D7), the admission check, the
  node's signing key from a Secret, and where streams go (D8).
- Values for containerd 2.x, containerd 1.7 with NRI turned on, and CRI-O;
  OpenShift's security context constraint for the node agent.
- Published as an OCI artifact beside the image (`ghcr.io/kwdoug63/charts/varek`),
  signed as the image is (v1.32's workflow).

## 4. Tests

- `kind` (Kubernetes in Docker) in CI: containerd 2.x with NRI, the chart
  installed, a labelled pod's calls decided and refused, a pod refused for
  what cannot be carried, the stream audited; on every change.
- The suites, where they apply, against a container supervised by the node
  agent (a sweep like v1.32's).
- The ship gate: 24 hours on EKS and on OpenShift with a real agent.

## Decisions before building

- **D1. The architecture.** (a) The node agent primary, the v1.32 image in
  the pod as the fallback; (b) the v1.32 image in the pod only, documented
  for clusters that allow its settings; (c) the node agent only.
  *Recommended: (a).* It is what the roadmap names, and the fallback keeps
  clusters without NRI covered.
- **D2. Runtimes.** (a) containerd 2.x (NRI on by default) and CRI-O
  (OpenShift's) first, containerd 1.7 with NRI turned on by its
  configuration; (b) containerd only. *Recommended: (a)*, as EKS's nodes
  run containerd and OpenShift's CRI-O.
- **D3. The launch set in a pod.** (a) A small static launcher,
  `varek-init`, put first in the container's command by the plugin and
  mounted read-only: it applies the Landlock launch set and executes the
  container's own command; a pod whose command cannot be found (none in
  the image or the spec) is refused; (b) launches decided by the filter
  only, without Landlock (the file decided could be swapped between the
  decision and the launch). *Recommended: (a);* (b) gives up v1.27's
  guarantee.
- **D4. Writable directories noexec in a pod.** (a) The pod's root file
  system read-only (`readOnlyRootFilesystem: true`, refused otherwise),
  and each writable volume mounted noexec by the plugin; (b) best effort.
  *Recommended: (a);* a pod that cannot have it is refused and told why.
- **D5. The network.** (a) The pod's own network namespace, connects
  decided as now, the stub resolver and the egress proxy run by the node
  agent inside it; (b) an empty namespace as on a host, which Kubernetes'
  networking does not allow a pod. *Recommended: (a);* the difference (the
  pod has the cluster's interfaces, and every connect is still decided) is
  stated in the threat model.
- **D6. Sub-agents and confined MCP servers under the node agent.** (a)
  Supported if step 1 shows a container's group can hold groups of the
  run (the runtime leaving it delegable); (b) under the node agent in a
  later release, the v1.32 image in the pod meanwhile. *Recommended: (a)
  if measured possible, else (b),* decided on step 1's result.
- **D7. Policies in the cluster.** (a) A namespaced custom resource,
  `VarekPolicy`, its text the policy as written today, selected by the pod
  label, and an admission check that refuses a labelled pod whose policy
  does not load; (b) ConfigMaps. *Recommended: (a);* GitOps tools review
  custom resources like any other, and the admission check fails a bad
  policy at deploy, not at run.
- **D8. Evidence.** (a) Each container's stream written by the node agent
  under the node's `/var/log/varek`, signed with the node's key (a
  Secret), forwarded by the existing anchor forwarder and exported as OCSF
  to the cluster's collector; (b) streams in the pod. *Recommended: (a);*
  the agent pod never holds its own evidence.
- **D9. Where it is published.** (a) The chart in v1.34 (the GitHub
  Container Registry, signed); the EKS add-on on AWS Marketplace and the
  OpenShift operator certification as their own steps after it; (b) all
  three in v1.34. *Recommended: (a);* each listing has its own process and
  review.
- **D10. The version.** (a) The Warden reports 1.34.0; the grammar stays
  1.31 unless the node agent needs a policy line (none is foreseen: the
  selection is the cluster's); (b) a `require warden 1.34`.
  *Recommended: (a).*
- **D11. Clusters to test on.** (a) `kind` in CI; Amazon EKS for the ship
  gate (a small managed cluster for a day); OpenShift on Red Hat OpenShift
  Service on AWS or a single-node OpenShift, decided when its cost is
  known; (b) EKS only. *Recommended: (a);* OpenShift's CRI-O and its
  security constraints are what its buyers check.

## Implementation plan

1. **Measure** on a `kind` cluster (containerd 2.x) and on a CRI-O host:
   an NRI plugin setting `listenerPath` and a filter that notifies; the
   descriptor arriving at the node agent with the container's state; the
   Warden's filter written in OCI's form and compared, call by call, with
   the one it builds today; `pidfd_getfd` and memory reads from the host;
   `RESOLVE_IN_ROOT` opens as the agent's user; noexec mounts and a
   read-only root through the plugin; the launcher applying Landlock; and
   whether a container's group can hold groups of the run (D6).
   **First measurement, the filter in OCI's form** (October 18, 2026,
   Central; done early, without a cluster): `tests/v1340_oci_filter.c` runs
   the Warden's own filter builder with every libseccomp call recorded,
   writes the rules as an OCI seccomp profile, and builds the filter again
   from the recorded rules in the profile's order, as runc does; `tests/v1340_bpf_compare.py` runs both compiled
   filters in a BPF interpreter over every system call number (0 to 599)
   with each value and mask the rules compare against, their neighbours and
   each multi-argument rule met and missed, for the three filters the
   Warden builds (a policy before 1.29, one from 1.29 with changes by name,
   and a dry run; 292, 337 and 449 rules, about 246,000 calls each). Every
   native call is decided the same. The one difference: the Warden kills
   the whole process for a call from another architecture (i386, or x32's
   bit), and OCI's profile has no field for that action, so runc's filter
   kills only the calling thread. The launcher of D3, already first in the
   container's command, can add a filter of its own whose only effect is
   that action (the kernel takes the stricter of two filters), so nothing
   is lost; to be checked when the launcher is built. (runc also answers a
   call number beyond its libseccomp's table ENOSYS, where the Warden's
   default is EPERM: both refuse.) The actions and comparisons the filter
   uses (allow, errno, kill-process, notify; equal, masked-equal,
   not-equal) are all in OCI's profile.

2. **The node agent:** the Warden's supervision driven by a received
   descriptor, one per container. **As designed** (October 19, 2026,
   Central, from a map of `warden.c`'s start and its supervision loop):
   - **one supervisor per container**, forked by the node agent for each
     descriptor it receives: the Warden keeps one run's state in globals
     (its stream, its policy's tables, the proxy's, the stub resolver's,
     the sub-agents'), single-threaded by design, so a process per
     container keeps each run's state its own and one container's failure
     from another's;
   - **the supervisor enters the container's mount and network
     namespaces**, not its PID namespace, after opening what is the node's:
     the policy, the signing key, the stream, the helpers (from sealed
     memory, as now), and a descriptor on the node's `/proc`. On a host the
     agent shares the Warden's mount namespace, so the Warden resolves a
     name as the agent would; entering the container's gives the same, its
     root, its mounts and their flags, without changing how names are
     resolved (section 1's `RESOLVE_IN_ROOT` at each name is the
     alternative, needing a change at each). Its PID namespace is not
     entered: the supervisor would be ended with the container's init
     before writing the run's end, and would be visible to the agent. So
     the agent's `/proc/<pid>` is reached through the node's `/proc` held
     before, its pid as the node numbers it (as the kernel reports it to
     the node agent), and an agent's `/proc/self` is rewritten with the
     pid as the container numbers it;
   - **connects are dialled from the pod's network namespace** (D5): the
     Warden never lets an agent's connect through as it is, but dials it
     and gives the agent the socket, so the supervisor, in the pod's
     namespace, dials from there; the stub resolver binds there as now; a
     dry run, which lets a refused call through, lets a connect reach the
     cluster's network, where on a host the agent's empty namespace
     stops it (said in the dry run's record);
   - **the run** is the container's: its id and pid in `run_start` with
     the pod's namespace, name and uid (the state's annotations); the
     agent's user from its process (`/proc/<pid>/status`), not
     `--run-as`; the first launch decided as the bootstrap is the
     container's command (the bundle's `config.json`); the run ends when
     the container's init ends (its pidfd) or the descriptor closes, its
     exit status from the runtime's state where it has one; the Warden
     ends the container through its control group (`cgroup.kill`);
   - **what cannot come from outside is refused at the start** until
     steps 3 and 5 bring it: the launch set (the launcher, D3), noexec
     mounts (D4), credentials' placeholders in the environment (the NRI
     plugin, step 5), and sub-agents (D6, measured possible).
   **As built** (October 19, 2026, Central; `warden_node.inc.c`,
   `node_json.c`, `tests/test_v1340.sh`, `make test-v1340`):
   - **2a, the node's `/proc`** (`warden.c`, `proc_openf` and the rest):
     every read of a process's state, the agent's (`mem`, `status`,
     `fdinfo`, `exe`, `cwd`, `cgroup`, `stat`, `environ`) or the Warden's

     - the node agent, privileged, its paths each at the node's own path (the
       runtime binds the launcher and dials the listener by the paths the
       plugin names), the runtime's state read-only, the policies and the
       launcher read-only, the node's key and anchor when given;
     - the plugin, as root (the policies and the NRI socket are root's) with
       no capability and a read-only root, `-sync` on;
     - the exporter, as root with no capability, reading the streams.
   - **the webhook**: a Deployment (two replicas, user 65532, read-only root,
     no capability, `RuntimeDefault`), a Service and the three hooks. Its
     certificate: the chart's own CA and certificate, kept across upgrades
     (`lookup`); or the operator's Secret (its `ca.crt`, or the CA given as
     `admission.tls.caBundle`; without either the install fails, not the
     webhook); or cert-manager (`cert-manager.io/inject-ca-from`). The
     chart's own namespace and `kube-system` are never checked, so the node
     agent's and the webhook's pods start while the webhook is down;
   - **RBAC**: the plugin `get`, `list` and `watch` on `varekpolicies`, the
     webhook `get`; nothing else;
   - **OpenShift** (`openshift.enabled`): a SecurityContextConstraints for
     the node agent's service account alone (privileged, the node's PID
     namespace, host paths, the init container's three capabilities). The
     webhook runs under `restricted-v2` as the namespace's user (the chart
     then sets none);
   - **found** writing the chart: the node agent checked that the runtime
     shares its mount namespace. In the DaemonSet it does not: the node agent
     is in its pod's, the runtime in the node's. It now takes either its own
     or the node's (PID 1's). On a host the two are one. In the pod no other
     process shares its own: each container has its own. The user and PID
     namespaces are still the node agent's own;
   - **the release** (`container-release.yml`, on a release tag):
     1. the node image is built and checked (`node_check.sh`: each command
        the chart names runs, the launcher has no interpreter, the Warden
        writes a filter as root and as the webhook's user, the exporter
        runs; the Warden is the tag's version);
     2. it is published as `ghcr.io/kwdoug63/varek-node:<version>`, signed
        and attested (CycloneDX) as the runtime image is;
     3. the chart's version and `appVersion` must be the tag's. A copy of the
        chart is given the digest just signed (`image.digest`), linted,
        rendered (the digest checked in every image), packaged and published
        as `oci://ghcr.io/kwdoug63/charts/varek`, then signed;
     4. all three are verified as a user would (`cosign verify`), and the
        node image's `:<major.minor>` and `:latest` move with the runtime
        image's.

     helm is built from source at a pinned version (`go install`, its
     modules checked against Go's checksum database);
   - **tested**: `make test-varek-chart` (16 tests): `helm lint --strict`,
     and the render under each setting:
     - each path the node agent and the plugin open is the node's own;
     - who may write what;
     - each runtime's state directory, and an unknown runtime refused;
     - signing and the anchor;
     - the exporter optional, a digest pinning every image;
     - the webhook's hooks, selectors and CA (its certificate names the
       Service and the CA's signature verifies), each of the three ways to
       its certificate;
     - RBAC, the OpenShift settings;
     - the CRD's name rule, the same as the node agent's (`kube.go`);
     - the workflows: CI builds and checks the node image and tests the
       chart; the release publishes, signs and verifies the node image and
       then the chart, in that order, before any tag moves.

     With `KUBECONFORM` each render is checked against Kubernetes 1.31's
     schemas (CI builds kubeconform pinned). `node_check.sh` ran against a
     stand-in image with the same layout (Red Hat's registry and package
     CDN are not reachable from where this was built; CI builds the real
     one, on every change). `test-v1340` passes again (121 checks) under
     runc 1.5.2 and 1.3.6;
   - **not run yet**: the chart installed on a cluster. That is step 7's
     `kind` in CI;
   - **known**:
     - containerd 1.7 (section 3) is not carried: its NRI cannot set a
       container's seccomp policy;
     - a new package on ghcr.io is private until its owner makes it public
       (`varek-node` and `charts/varek`, once, at the first release);
     - the CRD is installed with the chart and, by Helm's rule for
       `crds/`, never changed or removed by it: a new version is applied
       by hand.

   - **found by the sweep**:
     - *the audit refused every pod whose policy decides no launch*
       (`tools/varek_audit.py`). The launcher always applies Landlock, so
       run_start records a launch set (the command alone) and an empty
       noexec list, which the audit took for a launch-deciding run's. It now
       takes them when run_start names the launcher, with nothing but the
       command and what starts it in the set. `test-v1340` section 6 now
       audits such a stream. `test-v1340`'s own evidence check had run
       without the launcher;
     - *a container holding capabilities was supervised*. The Warden's
       agent holds none (`caps=none`). runc gives a user other than root
       the capabilities its spec names (three in its default), and neither
       the node agent nor the webhook checked them. The node agent now
       refuses a container whose effective, permitted or ambient set is not
       empty, naming them. The webhook refuses a container that does not
       drop `ALL`, or adds any back. Tested in `test-v1340` section 4, the
       webhook's unit tests and `v1340_apiserver.sh`; `test-v1340`'s own
       containers now drop them, as a pod's do;
     - the stand-in's own faults (the policy's name, the Warden's data
       files beside its binary, a signal handler's deadlock, the caller's
       umask, Python's ignored SIGPIPE and SIGXFSZ, a user namespace, the
       stream only at the end, `/tmp`'s submounts, the supervisor's anchor

     its 3 Python `requests` checks, as in every step before (where this

     - the plugin adds plain `noexec` to a pod's writable mounts, so a
       volume with mounts beneath it (a hostPath over a mount point) keeps

       runtime takes recursive mount options;

       `warden-build.yml` runs on the host, from 1.24 on.
