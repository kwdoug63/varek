# v1.34.0 — Kubernetes: a node agent, a Helm chart, OpenShift and EKS (plan)

Status: **decided; steps 1 to 3 built** (October 21, 2026: the measurements,
the node agent, the NRI plugin and the launcher), steps 4 to 9 not, target
**v1.34.0** (numbered so on
October 18, 2026, when macOS became v1.33.0). Decided October 18, 2026:
the recommendation for each decision below (D1 to D11), D6 on step 1's
measurement. The measurements of step 1 settle the parts marked *to be
measured*; it starts after v1.32.0 and v1.33.0. The roadmap entry is in
`docs/roadmap/v1.32-v1.35.md`.

Ship gate: a 24-hour run with a real agent on Amazon EKS and on OpenShift,
the agent pods running with no added capabilities, every guarantee the
Warden gives on a host either held or refused with the reason named.

## What v1.32 leaves open

v1.32 runs the Warden inside the agent's container. In a Kubernetes pod
that means the pod is given ten capabilities, CAP_SYS_ADMIN among them, an
AppArmor profile or SELinux type of VAREK's, and `--cgroupns=private`. A
cluster's admission policy (Pod Security Standards' "restricted" and
"baseline" levels, OpenShift's default security context constraints)
refuses such a pod, and a platform team will not grant it to every agent.
The agent itself holds none of those capabilities, but the pod does, and
the pod's process is the Warden: one Warden per pod, each privileged.

## What v1.34 gains, and what it does not

- **A node agent:** one Warden per node (a DaemonSet), privileged on the
  node as Falco or Tetragon are, which supervises the agent containers of
  labelled pods from outside them. The agent pods get no added capability,
  no custom profile, and pass the "restricted" level.
- **A Helm chart** that installs it, with policies as cluster resources,
  so a policy change goes through the cluster's review and GitOps flow.
- **The v1.32 image as a fallback,** in the pod, where the node agent
  cannot run (a cluster whose runtime has no hook for it, or no
  DaemonSets allowed).
- **OpenShift and EKS:** the chart tested on both; the OpenShift operator
  certification and the EKS add-on listing are business steps that follow
  (D9).

It does not change a decision procedure, a rule or a record's meaning: a
decision made by the node agent is the decision the Warden makes on a host.
Where a guarantee cannot be carried into a pod from outside, the node agent
refuses the pod and says which (D3 to D6), never runs it with less.

## The design in one paragraph

The container runtime starts every container under a seccomp filter its
OCI configuration names. The OCI runtime specification (v1.1) lets that
filter return `SCMP_ACT_NOTIFY` and names a Unix socket
(`linux.seccomp.listenerPath`) to which the runtime (runc from v1.1, crun)
sends the filter's notification descriptor, with the container's state,
when the container is created. The node agent is that listener: it
receives the descriptor for each container of a pod VAREK supervises, and
from then on decides the container's calls as the Warden decides an
agent's, under the policy the pod is labelled with. The OCI configuration
is changed for those pods only, by a plugin of the Node Resource Interface
(NRI), which containerd and CRI-O call as each container is created: it
sets the filter and the listener, and adds what the Warden would have done
itself at the agent's start (the noexec mounts, the launch set, D3 and D4).

## 1. What carries, and what must be built another way

Each of the Warden's guarantees assumes today that it starts the agent.
Under the node agent, the runtime starts it:

| Guarantee | On a host (and v1.32) | Under the node agent |
|---|---|---|
| Calls decided | the Warden's filter, installed by its child, which then launches the agent | the same filter, given in OCI form by the NRI plugin; the runtime installs it at the container's start, so the container's first instruction runs under it (*to be measured: that the Warden's filter can be written in OCI's seccomp form without loss*) |
| The listener | the Warden's own | the descriptor handed over by the runtime (`listenerPath`); the node agent checks it is the container's (the state's pid and its pidfd) |
| Files opened as the agent | names resolved in the Warden's own view | resolved inside the container's root: `openat2` with `RESOLVE_IN_ROOT` on `/proc/<pid>/root`, as the agent's user (*to be measured*) |
| Descriptor handover (`pidfd_getfd`), reading the agent's memory | CAP_SYS_PTRACE in the Warden's namespace | the node agent's, from the host (*to be measured: across the pod's user namespace, where one is used*) |
| The agent's network | an empty network namespace, the stub resolver and the egress proxy the Warden's | the pod's network namespace (the cluster's network): connects are decided as now; the stub resolver and the proxy run in the pod's namespace, entered by the node agent (D5) |
| Decided launches (Landlock) | the agent applies the launch set to itself before it launches anything | cannot be added to a running process from outside: a small launcher the plugin puts first in the container's command applies it, then runs the container's own (D3) |
| Writable directories noexec | the Warden's own mount namespace, which the agent inherits | the container's mounts, set noexec by the plugin; the container's root read-only (D4) |
| Lifecycle, revocation, the token's expiry | the run ends with the agent; the Warden ends every process | the run is the container's life; the node agent ends it by its control group (`cgroup.kill`) |
| Sub-agents and confined MCP servers | control groups under the run's | groups under the container's, which the runtime and the kubelet manage (D6, *to be measured*) |
| The verdict stream | the Warden's, signed | the node agent's, one stream per container, signed with the node's key (D8) |
| The on-behalf-of chain | the user's token, the agent's SPIFFE ID | the same, the token from a projected volume and the SPIFFE ID from the node's SPIRE agent where the cluster runs one |

## 2. The node agent

- A DaemonSet, privileged on the node: the Warden's code with a listener
  socket in place of a launch, one supervision per container, each its own
  policy, stream and decisions. A container is supervised from the moment
  its descriptor arrives until it ends; nothing it does reaches the node
  agent but its notifications.
- The NRI plugin, in the same pod, sets each supervised container's OCI
  configuration: the filter and `listenerPath`, the noexec mounts, the
  launcher (D3), and a refusal (the container is not created) when the pod
  asks for what the node agent cannot carry, with the reason in the pod's
  events.
- A pod is supervised when it carries a label naming a policy
  (`varek.io/policy: NAME`); a namespace can require it (an admission
  check the chart installs, D7).
- If the node agent is not running, a supervised container is not created
  (the plugin fails closed), never created unsupervised.

## 3. The Helm chart

- The DaemonSet, the plugin, the CRD (D7), the admission check, the
  node's signing key from a Secret, and where streams go (D8).
- Values for containerd 2.x, containerd 1.7 with NRI turned on, and CRI-O;
  OpenShift's security context constraint for the node agent.
- Published as an OCI artifact beside the image (`ghcr.io/kwdoug63/charts/varek`),
  signed as the image is (v1.32's workflow).

## 4. Tests

- `kind` (Kubernetes in Docker) in CI: containerd 2.x with NRI, the chart
  installed, a labelled pod's calls decided and refused, a pod refused for
  what cannot be carried, the stream audited; on every change.
- The suites, where they apply, against a container supervised by the node
  agent (a sweep like v1.32's).
- The ship gate: 24 hours on EKS and on OpenShift with a real agent.

## Decisions before building

- **D1. The architecture.** (a) The node agent primary, the v1.32 image in
  the pod as the fallback; (b) the v1.32 image in the pod only, documented
  for clusters that allow its settings; (c) the node agent only.
  *Recommended: (a).* It is what the roadmap names, and the fallback keeps
  clusters without NRI covered.
- **D2. Runtimes.** (a) containerd 2.x (NRI on by default) and CRI-O
  (OpenShift's) first, containerd 1.7 with NRI turned on by its
  configuration; (b) containerd only. *Recommended: (a)*, as EKS's nodes
  run containerd and OpenShift's CRI-O.
- **D3. The launch set in a pod.** (a) A small static launcher,
  `varek-init`, put first in the container's command by the plugin and
  mounted read-only: it applies the Landlock launch set and executes the
  container's own command; a pod whose command cannot be found (none in
  the image or the spec) is refused; (b) launches decided by the filter
  only, without Landlock (the file decided could be swapped between the
  decision and the launch). *Recommended: (a);* (b) gives up v1.27's
  guarantee.
- **D4. Writable directories noexec in a pod.** (a) The pod's root file
  system read-only (`readOnlyRootFilesystem: true`, refused otherwise),
  and each writable volume mounted noexec by the plugin; (b) best effort.
  *Recommended: (a);* a pod that cannot have it is refused and told why.
- **D5. The network.** (a) The pod's own network namespace, connects
  decided as now, the stub resolver and the egress proxy run by the node
  agent inside it; (b) an empty namespace as on a host, which Kubernetes'
  networking does not allow a pod. *Recommended: (a);* the difference (the
  pod has the cluster's interfaces, and every connect is still decided) is
  stated in the threat model.
- **D6. Sub-agents and confined MCP servers under the node agent.** (a)
  Supported if step 1 shows a container's group can hold groups of the
  run (the runtime leaving it delegable); (b) under the node agent in a
  later release, the v1.32 image in the pod meanwhile. *Recommended: (a)
  if measured possible, else (b),* decided on step 1's result.
- **D7. Policies in the cluster.** (a) A namespaced custom resource,
  `VarekPolicy`, its text the policy as written today, selected by the pod
  label, and an admission check that refuses a labelled pod whose policy
  does not load; (b) ConfigMaps. *Recommended: (a);* GitOps tools review
  custom resources like any other, and the admission check fails a bad
  policy at deploy, not at run.
- **D8. Evidence.** (a) Each container's stream written by the node agent
  under the node's `/var/log/varek`, signed with the node's key (a
  Secret), forwarded by the existing anchor forwarder and exported as OCSF
  to the cluster's collector; (b) streams in the pod. *Recommended: (a);*
  the agent pod never holds its own evidence.
- **D9. Where it is published.** (a) The chart in v1.34 (the GitHub
  Container Registry, signed); the EKS add-on on AWS Marketplace and the
  OpenShift operator certification as their own steps after it; (b) all
  three in v1.34. *Recommended: (a);* each listing has its own process and
  review.
- **D10. The version.** (a) The Warden reports 1.34.0; the grammar stays
  1.31 unless the node agent needs a policy line (none is foreseen: the
  selection is the cluster's); (b) a `require warden 1.34`.
  *Recommended: (a).*
- **D11. Clusters to test on.** (a) `kind` in CI; Amazon EKS for the ship
  gate (a small managed cluster for a day); OpenShift on Red Hat OpenShift
  Service on AWS or a single-node OpenShift, decided when its cost is
  known; (b) EKS only. *Recommended: (a);* OpenShift's CRI-O and its
  security constraints are what its buyers check.

## Implementation plan

1. **Measure** on a `kind` cluster (containerd 2.x) and on a CRI-O host:
   an NRI plugin setting `listenerPath` and a filter that notifies; the
   descriptor arriving at the node agent with the container's state; the
   Warden's filter written in OCI's form and compared, call by call, with
   the one it builds today; `pidfd_getfd` and memory reads from the host;
   `RESOLVE_IN_ROOT` opens as the agent's user; noexec mounts and a
   read-only root through the plugin; the launcher applying Landlock; and
   whether a container's group can hold groups of the run (D6).
   **First measurement, the filter in OCI's form** (October 18, 2026,
   Central; done early, without a cluster): `tests/v1340_oci_filter.c` runs
   the Warden's own filter builder with every libseccomp call recorded,
   writes the rules as an OCI seccomp profile, and builds the filter again
   from the recorded rules in the profile's order, as runc does; `tests/v1340_bpf_compare.py` runs both compiled
   filters in a BPF interpreter over every system call number (0 to 599)
   with each value and mask the rules compare against, their neighbours and
   each multi-argument rule met and missed, for the three filters the
   Warden builds (a policy before 1.29, one from 1.29 with changes by name,
   and a dry run; 292, 337 and 449 rules, about 246,000 calls each). Every
   native call is decided the same. The one difference: the Warden kills
   the whole process for a call from another architecture (i386, or x32's
   bit), and OCI's profile has no field for that action, so runc's filter
   kills only the calling thread. The launcher of D3, already first in the
   container's command, can add a filter of its own whose only effect is
   that action (the kernel takes the stricter of two filters), so nothing
   is lost; to be checked when the launcher is built. (runc also answers a
   call number beyond its libseccomp's table ENOSYS, where the Warden's
   default is EPERM: both refuse.) The actions and comparisons the filter
   uses (allow, errno, kill-process, notify; equal, masked-equal,
   not-equal) are all in OCI's profile.

   1.3.6, Linux 6.18, Ubuntu 24.04's root filesystem; a `kind` cluster

2. **The node agent:** the Warden's supervision driven by a received
   descriptor, one per container. **As designed** (October 19, 2026,
   Central, from a map of `warden.c`'s start and its supervision loop):
   - **one supervisor per container**, forked by the node agent for each
     descriptor it receives: the Warden keeps one run's state in globals
     (its stream, its policy's tables, the proxy's, the stub resolver's,
     the sub-agents'), single-threaded by design, so a process per
     container keeps each run's state its own and one container's failure
     from another's;
   - **the supervisor enters the container's mount and network
     namespaces**, not its PID namespace, after opening what is the node's:
     the policy, the signing key, the stream, the helpers (from sealed
     memory, as now), and a descriptor on the node's `/proc`. On a host the
     agent shares the Warden's mount namespace, so the Warden resolves a
     name as the agent would; entering the container's gives the same, its
     root, its mounts and their flags, without changing how names are
     resolved (section 1's `RESOLVE_IN_ROOT` at each name is the
     alternative, needing a change at each). Its PID namespace is not
     entered: the supervisor would be ended with the container's init
     before writing the run's end, and would be visible to the agent. So
     the agent's `/proc/<pid>` is reached through the node's `/proc` held
     before, its pid as the node numbers it (as the kernel reports it to
     the node agent), and an agent's `/proc/self` is rewritten with the
     pid as the container numbers it;
   - **connects are dialled from the pod's network namespace** (D5): the
     Warden never lets an agent's connect through as it is, but dials it
     and gives the agent the socket, so the supervisor, in the pod's
     namespace, dials from there; the stub resolver binds there as now; a
     dry run, which lets a refused call through, lets a connect reach the
     cluster's network, where on a host the agent's empty namespace
     stops it (said in the dry run's record);
   - **the run** is the container's: its id and pid in `run_start` with
     the pod's namespace, name and uid (the state's annotations); the
     agent's user from its process (`/proc/<pid>/status`), not
     `--run-as`; the first launch decided as the bootstrap is the
     container's command (the bundle's `config.json`); the run ends when
     the container's init ends (its pidfd) or the descriptor closes, its
     exit status from the runtime's state where it has one; the Warden
     ends the container through its control group (`cgroup.kill`);
   - **what cannot come from outside is refused at the start** until
     steps 3 and 5 bring it: the launch set (the launcher, D3), noexec
     mounts (D4), credentials' placeholders in the environment (the NRI
     plugin, step 5), and sub-agents (D6, measured possible).
   **As built** (October 19, 2026, Central; `warden_node.inc.c`,
   `node_json.c`, `tests/test_v1340.sh`, `make test-v1340`):
   - **2a, the node's `/proc`** (`warden.c`, `proc_openf` and the rest):
     every read of a process's state, the agent's (`mem`, `status`,
     `fdinfo`, `exe`, `cwd`, `cgroup`, `stat`, `environ`) or the Warden's
     own (`self/fd`, `mountinfo`, `cgroup`, `ns`), through a descriptor on
     the `/proc` the Warden started with; a Unix connect through a pinned
     descriptor made from it; an agent's `/proc/self` rewritten with its pid
     as its view numbers it (its `NSpid` entry for the container's PID
     namespace, in a container's). On a
     host nothing changes: every suite passes as on main;
   - **2b, the node agent**: `warden POLICY --node-agent SOCKET
     --node-streams DIR` listens (the socket made by root, mode 0600); for
     each connection, one descriptor and the container's state, it forks a
     supervisor, which writes its stream to `DIR/<container>.<pid>.jsonl`
     and reads the state with a strict reader (`node_json.c`: RFC 8259
     whole, and a member name given twice at any depth refused, since the
     runtime's reader takes the last; 25 unit checks, and two million
     mutated documents under AddressSanitizer without a fault). It takes the
     container's process by a pidfd at once (the container is ended through
     it, never by a pid that could be reused), requires no new privileges
     (the runtime then loads the filter after it takes the container's
     user, so the user read from the process is the agent's), and the
     container's command named by an absolute path (the bundle's
     `config.json`, the first launch decided as the bootstrap). It enters
     the pod's network namespace, starts as a run does (the policy, keys,
     stream, `run_start` with the container's id, pid, the profile's
     metadata, the pod's namespace, name and uid, the command and the
     user), then the container's mount namespace, and supervises. Until the
     command's launch, the calls of the container's init are the runtime's
     own (runc's checks of `/proc`, about 25), let through and counted in
     `run_end` (`runtime_calls_before_exec`), whose `exit_status` is -1, the
     runtime's to report. Every way out of a supervisor, a refusal at the
     start or the end of the run, ends its container;
   - **tested** here with runc 1.4 (CRI-O's), a static probe as the
     container's command, user 65534, no new privileges, a read-only root:
     a read the policy allows, one it does not name and a write it does not
     allow, the probe's own `/proc/self` in the container's `/proc`, a
     connect and a second launch, each decided in the container's view and
     recorded there; a second container under the same node agent with its
     own stream; refused at the start, the container ended: a policy with a
     host-name rule, a command named without an absolute path, a container
     with new privileges allowed (`test-v1340`, 25 checks; 31 after the
     review, below). Not yet tested
     under containerd or crun: with the NRI plugin (step 3), on `kind` and
     CRI-O as in step 1;
   - **known**: runc's masks of `/proc` entries (`/proc/keys`,
     `/proc/timer_list`, bound over with a writable device) are what the
     node agent's mount check sees as writable mounts without noexec, to be
     told apart from a volume when step 3 checks D4 at the descriptor's
     arrival.

   **Review** (October 19, 2026, Central): three AI review agents read
   step 2 (the node agent's security; the `/proc` change, `863a0bd`; the
   JSON reader). A human or third-party review has not been done. Found
   and fixed:
   - *Who may connect* (high). The listener took any root peer, and the
     process its state named: a forged state could have any process on the
     node killed (`node_fail`), or have another pod's calls answered as the
     forger's. Now, before a supervisor is forked: the peer is root, in the
     node agent's own user, PID and mount namespaces (so the node agent runs
     in the node's mount namespace, as the runtime does); the descriptor is
     a seccomp listener; the state's process is the peer's child (runc's
     init is its runtime's; crun's is not yet tested) and is under a
     filter. A refused connection kills nothing. The socket's directory must
     be root's, with no access for others. A call from any process but the
     container's init before its first launch ends the container.
   - *Files opened as the node's root* (medium). Only a policy of 1.29 or
     later had files opened as the agent, and every `require` past 1.26
     turns on the decided launches this step refuses: every open was
     root's, past the files' own permissions. Now files are opened as the
     container's user and groups whatever the policy's version, and a
     container running as root (uid 0) or with group 0 is refused.
     `run_start` says so (`"opens_as_agent": true`).
   - *A Unix connect's retry* (high, in host mode too). A connect retried
     after a full backlog resolved the pin's relative name from the
     Warden's own directory: a regression, and a way to a socket the policy
     does not name. Both go through one helper now; on a host the name is
     absolute again.
   - *Member names in another case* (high). Go's reader matches a member to
     a field in any case (and U+017F as s, U+212A as k): `"args"` and
     `"Args"` are one field to the runtime, which takes the last. Names are
     compared folded the same way; the check is linear (a 16 MB document
     took 16.6 s, now 0.13 s). The pod's annotations: containerd's and
     CRI-O's both present and different is refused.
   - *Smaller.* `NSpid`'s entry at the container's PID namespace's depth,
     not the last; the node's `/proc` opened once, at the start; the
     namespaces entered and the container's init watched through the pidfd
     held since the state arrived, and the process checked alive after each
     read of its `/proc/<pid>`; the run's control socket removed, and the
     anchor's lock opened, through directories held from before the mount
     namespace is entered; the listener reaps its supervisors and ends the
     container of any that ends (killed or crashed too), keeps at most 256,
     takes a state of up to 1 MiB within 5 s, and makes each supervisor the
     last the kernel ends when memory is short.
   - *The first launch refused, now and then* (found running `test-v1340`
     again after the fixes: 1 run in 5). runc's init is Go, whose runtime
     interrupts its threads with signals (preemption). One arriving while
     the init's exec of the command waited for the Warden voided the
     Warden's answer, and the kernel restarted the exec: the restarted one
     found the first launch spent, and was refused. The first launch is
     spent only once the kernel takes the answer now, and a call voided
     that way is not recorded (12 runs of 12 pass).
   `test-v1340` checks the new refusals and a supervisor killed (31
   checks).
3. **The NRI plugin** and the launcher (D3, D4). **As designed**
   (October 19, 2026, Central, from step 1's six measurements and step 2):
   - **the plugin** (`varek-nri`, Go, NRI v0.12, from `tests/v1340_nri`):
     for each container of a pod annotated `varek.dev/policy`, the
     Warden's filter in OCI's form as its seccomp policy with
     `listenerPath` the node agent's socket (the filter written by the
     Warden itself, `warden --oci-filter`, from step 1's converter, so the
     plugin carries no copy that could drift); `/varek/init` mounted
     read-only, nosuid, nodev, and put first in the command; every writable
     mount made noexec; the pod's policy name added to the container's own
     annotations (`varek.dev/policy`), since the state the node agent
     receives carries the container's annotations, not the pod's (step 1).
     A container without a command is refused. On a runtime with NRI before
     v0.10 (containerd before 2.2, CRI-O before 1.35) the plugin refuses
     to start, naming the version;
   - **the policy by name, for now**: the node agent reads
     `POLICY_DIR/<name>.policy` for the annotation's name (a name of
     `[a-z0-9-]`, at most 63 characters; one missing or not given is a
     refused container), until step 5's custom resource (D7);
   - **the launcher** (`varek-init`, C, static, from `tests/v1340_init.c`):
     it opens `/etc/varek/launch-set`, a view the supervisor serves (as it
     serves its other views: `warden_names.inc.c`), holding the launch set
     the supervisor built in the container's view with the Warden's own
     expansion (`exec_ruleset_build`: each program, its loader, a script's
     interpreter), one path a line; it applies Landlock to exactly those
     (each path, never a hardlink's other name: step 1's overlayfs
     measurement) and executes the container's command. A file changed
     between the view and the launch is refused at the launch, which the
     Warden decides by the file's device and inode (v1.27). Without
     Landlock, or without the view, it refuses to run the command;
   - **D4 checked by the node agent** when the descriptor arrives: the
     container's root read-only, and every writable mount noexec except a
     runtime's masks (a character device bound over a `/proc` or `/sys`
     entry, from which nothing can be executed); otherwise the container is
     refused, naming the mount;
   - **decided launches carried**: with the launcher, a policy that
     decides launches (`require warden 1.27`) is accepted under the node
     agent (step 2 refuses it), the bootstrap being `/varek/init`;
   - **tests**: the suite of step 2 with the launcher and the D4 check
     (runc, here and in CI), and the step 1 droplet run again with the
     plugin and the node agent instead of their stand-ins, on `kind` and on
     CRI-O under crun and runc.
   **As built** (October 21, 2026, Central; `warden_oci.c`, `varek_init.c`,
   `nri/`, `warden_node.inc.c`; `make test-v1340`, `make test-varek-nri`,
   `tests/v1340_crio.sh`):
   - **the filter, written by the Warden** (`warden POLICY --oci-filter`):
     the Warden's own builder run with every rule recorded, as step 1's
     converter did, and rule for rule the same (`test-v1340` compares them),
     then two things a pod needs. The launcher's three `landlock_*` calls
     are admitted. And each call the Warden's filter names no rule for is
     notified rather than refused. *Found* running a policy from before 1.29
     under the launcher: runc's last steps after it loads the filter (it
     reopens its exec FIFO) call `fstatfs`, which the Warden's filter admits
     only from 1.29, so runc failed before the command; step 2's tests had
     used the 1.29 filter. runc refuses a filter whose default action
     notifies, so each such call is named (248 under a policy from before
     1.29, on x86_64). Until the command's launch these are the runtime's and
     the launcher's, let through; from it the node agent answers each as the
     Warden's own filter for that policy would, by running that filter's
     compiled form on the call (`wd_bpf_run`, checked against step 1's
     interpreter on 118,800 calls for each of the two filters): EPERM,
     without a record, as on a host, and counted in `run_end`
     (`calls_not_admitted`);
   - **the launcher** (`varek-init`, static: `make varek-init`):
     `/varek/init -- COMMAND ...` reads the launch set from the view, applies
     Landlock to each path, adds a filter whose only effect is that a call
     from another architecture kills the whole process (step 1's open item:
     an i386 call from a second thread kills the process under the launcher,
     and only that thread without it, both in `test-v1340`), and launches
     the command. Without Landlock or the view, or if any step fails, it
     exits 126 without running the command;
   - **the node agent**: `warden POLICY_DIR --node-agent SOCKET
     --node-streams DIR --node-launcher FILE`. With a directory (root's,
     written by no one else) each container's policy is taken by its name;
     with a policy file, that one for every container. The launcher is
     root's, written by no one else, and known by its device and inode. When
     the descriptor arrives, in the container's view and before any of its
     code runs:
     - `/varek/init` must be the node's launcher (the same device and inode)
       on a read-only mount;
     - D4, when the policy decides launches: the root read-only; every
       writable mount noexec, except the kernel's file systems nothing
       written to can be run from (proc, sysfs, cgroup, mqueue, devpts) and
       a runtime's masks (a character device bound over a `/proc` or `/sys`
       entry: step 2's known item); and no mount that allows execution
       showing what a writable one can change (the same device, one root at
       or beneath the other). The last was *found* writing the check: a
       volume mounted twice, once writable and noexec and once read-only,
       would let the agent write a file through one and map it executable
       through the other. A writable hostPath of `/` is refused the same way;
     - the launch set is built in the container's view with the Warden's
       own expansion. The view holds every name the policy admits a file by.
       *Found* on CRI-O: busybox's commands are one file, and the set holds a
       file once, by its inode, so the view held `/bin/sh` alone; through
       overlayfs `/bin/cat` would then have been refused by Landlock. The
       paths are in `run_start` (`node.launch_paths`).

     Then the runtime's launch of `/varek/init` is let through (CONTINUE: the
     runtime's own), and the launcher's calls are let through too, its open
     of the view answered from a sealed memfd. The launcher's launch of the
     command is the bootstrap, answered with CONTINUE only when the caller
     runs the node's launcher and is single-threaded. Any other launch
     before the command ends the container. A policy that decides launches is
     carried with the launcher. One that does not runs with the launcher
     too, its launch set the command alone. A policy that would need a
     program kept executable under a directory it may write (v1.29) is
     refused, since in a pod every writable mount is noexec. The directories
     the policy may write are recorded in `run_start` as on a host but not
     mounted (the plugin does that); a file opened under one of them on a
     read-only mount is not refused, since D4 means the agent wrote nothing
     there. The pod's names come from the plugin's annotations
     (`varek.dev/pod-namespace`, `-name`, `-uid`, `varek.dev/container`):
     CRI-O run through `crictl` puts none in the container's, and in a
     cluster the kubelet's reach the container only as one JSON string. Every
     family present must agree;
   - **the plugin** (`varek-nri`, Go, NRI v0.12.3: `make varek-nri`): as
     designed. It runs `warden NAME.policy --oci-filter` once per policy
     (cached while the file is unchanged) and adds the pod's names. It
     refuses a container with no command, one named by a relative path, one
     that starts with `/varek/init` or has a mount there, a bad name, a
     missing policy, or a policy the Warden will not write a filter for. It
     refuses to start on containerd before 2.2, CRI-O before 1.35, or any
     other runtime. Its unit tests (`make test-varek-nri`) run in CI;
   - **tested**: `test-v1340` (59 checks; runc 1.4 here and in CI) runs
     step 2's checks and the refusals above. A container whose command is
     `/varek/init -- /probe launch` runs under a policy that decides
     launches: a program it allows and a hardlink of it ran, one it does not
     allow and a copy written to `/work` were refused, and an i386 call
     killed the process. `tests/v1340_crio.sh` runs the plugin, the node
     agent and the launcher under CRI-O 1.37.2 with runc, in this sandbox
     (vfs storage), with four busybox pods as Pod Security's `restricted`
     level has them; 8 of 8 checks pass. Pod A (annotated, read-only root):
     its reads and launches were decided as the policy says, and 14 calls
     its filter refuses were answered EPERM. Pod B (not annotated) was left
     as it was. Pod C (writable root) was refused by the node agent (D4). Pod
     D (no such policy) was refused by the plugin. Still to run: crun and
     overlay storage, which bring the hardlink names into play, on the
     droplet as step 1's sixth measurement, and `kind` (containerd 2.2 or
     later);
   - **known**:
     - The plugin alone gives a pod the filter and the listener. If the
       plugin is not running, an annotated pod runs as its spec says
       (RuntimeDefault), not supervised. NRI's validator requiring VAREK's
       plugin (step 6) and the admission check (step 5, D7) close this;
       until then the annotation alone is not enough.
     - The node agent cannot read the filter the runtime installed from
       the descriptor, so it cannot check that the filter is the Warden's
       for that policy. Every call that reaches it is answered by the
       Warden's filter, but what the runtime's filter admits in the kernel
       never reaches it. NRI's validator refusing other plugins' seccomp
       changes (step 6) is the check.
     - The command must be named by an absolute path (step 2), so an image
       whose command relies on `PATH` needs it spelled out in the pod.
     - crun has not yet run under the node agent itself (step 1 ran it with
       the stand-ins only). The node agent accepts only the runtime's
       `execve` of `/varek/init` by name, and only a state whose process is
       the connecting runtime's child; both are to be checked on the droplet.
