## v1.28.0 — Credential release

**Released 2026-10-15**, after its 24-hour soak (`RELEASE-v1.28.0.md`).

The design, with its decisions, is in
`docs/security/v1.28-credential-release.md`.

The agent holds only placeholder secrets. The egress proxy swaps in the real
credential only for a request the Warden has decided SATISFIED.

- **Credentials from existing stores:** a root-owned file, HashiCorp
  Vault or AWS Secrets Manager. VAREK does not become an identity
  provider.
- **Delegation:** the on-behalf-of chain (user → agent → sub-agent) recorded
  in every verdict and in the authorization log. OAuth token exchange and
  SPIFFE IDs accepted as identity inputs.
- **Revocation:** `varek revoke <session>` makes every later action in that
  session UNSATISFIED and withdraws any credential the proxy has already
  released.
- **What it needs:** swapping a header value means the proxy sees inside
  TLS. v1.26.1's inspecting mode already does: it terminates the agent's TLS
  with a CA made for the run and constrained to the policy's names, and the
  agent's usual clients (Python, curl, Node.js, Java) trust it without
  changes. Credential release is opt-in on top of it.

## The order of work, and the soak

Decided after v1.28.0's soak trial on the droplet:

1. **v1.28.0 ships on its own**, with its own 24-hour soak and review, as
   its design note sets out.
2. **v1.28.1, v1.29.0 and v1.31.0 are built one after another**, each with
   its own design note, decisions and review by AI review agents, and **one
   24-hour soak on the droplet covers them together**: a single harness
   that exercises each release's changes on the final build, run before
   any of them is tagged. Each design note names that shared soak as its
   ship gate. A failure in it holds all three until it is fixed and the
   soak is run again.
3. **v1.30.0 (macOS) is soaked on its own, on a Mac**: the droplet cannot
   run it. It does not hold the others.

**The 24-hour soaks start now** (decided October 14, 2026; earlier the
same day they had been deferred until v1.35.0, which this reverses, for
scheduling):

- v1.28.0's soak (`tests/soak_v1280`, on its branch's build) and the shared
  soak of v1.28.1, v1.29.0 and v1.31.0 (`tests/soak_shared`, on v1.31's
  build), each on the droplet, each after its 6-minute trial.
- A fault a soak finds is fixed on every branch it reaches, with a check,
  and that soak is run again.
- v1.30.0's soak runs on a Mac (an EC2 Mac) when v1.30 is built; v1.32 to
  v1.35 are each soaked before they are tagged.

**v1.27.2** (decided October 14, 2026): a patch release of v1.27.1 with
one fix, the checkpoint fault the shared soak's trial found, which is in
v1.26.1 to v1.27.1 too (`RELEASE-v1.27.2.md`, on its own branch, from
main). Its soak is v1.27.1's harness (`tests/soak_v1270`), signed, on the
droplet once one is free. It is tagged after its soak, apart from the order
below; if v1.28.0 is out first, README's "Current release" stays at v1.28.0.

Each release is tagged in this order, and its release commit (after its
soak) writes its CHANGELOG entry and its date, and moves README's
"Current release" line and its runtime badge to that release; until then
both stay at the last release tagged. A release candidate's notes, spec
paper and README entry are drafts on its own branch.

## v1.28.1 — The on-behalf-of chain

The design, with its decisions, is in
`docs/security/v1.28.1-delegation-chain.md`: the user (an OAuth 2.0 / OIDC
token, possibly from a token exchange, verified against an issuer the
policy trusts), the agent (and its SPIFFE ID) and each sub-agent (held in
its own control group from its launch) recorded with every decision and
audited.

**Released 2026-10-15**, after the shared 24-hour soak with v1.29.0 and
v1.31.0 (`RELEASE-v1.28.1.md`). Reviewed by AI review agents; `make
test-v1281`, 208 checks, 197 of which fail against v1.28.0.

## v1.29.0 — `varek run` (time to value)

The design, with its decisions, is in `docs/security/v1.29-varek-run.md`:
a baseline policy written for the working directory with a profile per
known agent, files opened with the agent's own credentials (`require warden
1.29`), a dry run that decides and records every call and enforces only
what keeps its own stream safe, `varek policy suggest`, and the free tier's
name (VAREK Core, already in use).

`varek run -- <agent>` exists from v1.22.0, with the policy `varek init`
installed. v1.29 makes it work in one command with nothing set up first.

**Released 2026-10-17**, after the shared 24-hour soak with v1.28.1 and
v1.31.0, run again on the reviewed build (`RELEASE-v1.29.0.md`). Reviewed
for correctness and by AI review agents; `make test-v1290`.

- **A built-in baseline policy,** so `varek run -- claude` wraps an agent
  without `varek init`.
- **A dry run** that reports what would be UNSATISFIED without blocking
  anything, labelled clearly as not enforcing, everywhere it appears.
- **`varek policy suggest`,** which drafts a policy from a dry run's
  session for the operator to review.
- **The free tier named:** the MIT build is the free tier; name it (for
  example, "VAREK Community") on the site and the Marketplace listing.

## v1.30.0 — macOS

- **A Linux VM on the Mac.** The agent runs inside a lightweight Linux VM
  (Apple's Virtualization framework, launched by Red Hat's `vfkit`, with a
  RHEL 9 guest, 9.6 or later: decided October 14, 2026), with the Warden
  inside the VM, so the guarantees are the same as on Linux.
- **An arm64 Warden first.** A Mac with Apple silicon runs an arm64 Linux
  in its VM, and the Warden is built for x86-64 only: it names the
  architecture in its filter and decides system calls that arm64 does not
  have (`open`, `stat`, `rename`, `unlink`, `mkdir` and others; arm64 has
  only their `*at` forms). The port, and every suite passing on arm64, can
  be done on an arm64 Linux host (an AWS Graviton instance), without a Mac.
- **Testing on a Mac without owning one:** an Amazon EC2 Mac (a bare-metal
  Mac mini, rented by the host-hour with a 24-hour minimum) in a US region,
  for building the VM integration and for v1.30.0's soak.
- **A native port is a separate, later program.** It would use Apple's
  Endpoint Security framework, which needs an entitlement Apple grants and
  covers fewer operations than seccomp. Apply for the entitlement now:
  approval takes time.

## v1.31.0 — Standards support

The design, with its decisions, is in `docs/security/v1.31-standards.md`
(decided 2026-10-13; not built): an OCSF 1.9.0 export of every decision, MCP servers
on the host confined to their own rules, calls to remote MCP servers
decided by method and tool, MCP tokens bound to their server, and the
Agent Baseline mapping (which can be published first).

- **OCSF:** authorization events exported in OCSF alongside CycloneDX, for
  SIEMs.
- **MCP:** enforcement on MCP server processes, and tokens issued under
  MCP's authorization specification accepted.
- **Agent Baseline:** a published mapping of VAREK to the six outcomes in
  Agent Baseline. It is a document, not code, so it can go out before
  v1.31.
- **Enterprise sign-in:** OIDC sign-in (and SCIM) only if VAREK Enterprise
  gains an admin console.

## Not releases

Some of what buyers ask for comes from the company, not the code: a SOC 2
audit, a support response-time SLA for self-hosted software, named
production customers, and standards participation. A release can support
these (signed releases, an SBOM, a vulnerability-disclosure policy) but not
deliver them.
