# VAREK v1.32 to v1.35 — connections after v1.31 (plan)

**Status:** v1.32.0 in progress (its decisions made); v1.33.0 to v1.35.0 planned, not built. These four releases follow v1.31.0, in this
order. Each gets its own design note, with decisions and ship gates, before
it is built, as v1.24 to v1.31 did, and is soaked for 24 hours before it
is tagged (`docs/roadmap/v1.28-v1.31.md`, "The order of work, and the
soak").
**Author:** Kenneth Wayne Douglas, MD
**Last updated:** October 16, 2026

The question was which connections, beyond Linux and macOS, would make
VAREK more competitive. The plan for v1.28 to v1.31
(`docs/roadmap/v1.28-v1.31.md`) already covers three of them: enforcement
on Model Context Protocol (MCP) servers and tokens, and an export in the
Open Cybersecurity Schema Framework (OCSF), in v1.31.0; and workload
identity (SPIFFE IDs, OAuth token exchange) with credentials from a file,
HashiCorp Vault or AWS Secrets Manager, in v1.28.0 and v1.28.1.

What that plan does not cover is where most production agents actually
run: containers and Kubernetes. This plan adds four releases after v1.31
and two separate programs. None of them changes the three-state decision
semantics: no extension may move a genuinely unsafe action to SATISFIED.

| Release | Connection | The buyer's question it answers |
|---|---|---|
| v1.32.0 | Containers: an official image, Docker and Podman | Can it run in our containers? |
| v1.33.0 | Kubernetes: node agent, Helm chart, OpenShift, Amazon EKS add-on | Can it run on our platform? |
| v1.34.0 | Agent frameworks: plans generated from the framework | Does it fit how we build agents? |
| v1.35.0 | Security operations: Splunk, Microsoft Sentinel, OpenTelemetry | Will our security team see it? |
| Program | Windows | Does it run on our developers' machines? |
| Program | Native macOS, without a VM | Can we skip the VM on Macs? |

## v1.32.0 — Containers

**Design note:** `docs/security/v1.32-containers.md` (decided 2026-10-16:
the recommendation for each of D1 to D12), with what the Warden was measured to need in
a Docker container: six capabilities and Docker's default seccomp profile,
never `--privileged`. Developed on its own branch
(`claude/varek-v1320-01dbw5`, from v1.31.1's).

The Warden runs as root and needs more from its host than most containers
allow by default. As built through v1.31 it uses:

- **seccomp user-notify**, the filter's answers on every mediated call,
  and descriptor handover (`pidfd_getfd`) and reads of the agent's memory
  (`/proc/PID/mem`), which need ptrace access to the agent's processes;
- **new PID and network namespaces** for the agent (its only network is
  the Warden's handover, or the egress proxy's);
- **a mount namespace and mounts**, for the agent's writable directories
  mounted noexec (v1.27.1), which needs CAP_SYS_ADMIN;
- **Landlock**, the launch set the agent applies to itself before it
  launches anything (v1.27);
- **cgroup v2, writable**, a group per run and per sub-agent or confined
  MCP server (v1.28.1, v1.31);
- **changing user**: the agent dropped to its own user, the egress proxy
  and `warden-secrets` each as their own, and files opened as the agent
  with per-thread `setfsuid` and `setfsgid` (v1.29).

Default container settings block several of these, so a buyer's first
attempt in Docker fails or ends with "run it privileged".

- An official container image with the Warden and the `varek` command, so
  an agent runs under VAREK by naming the image and its own launch command.
- A documented, minimal set of container settings: a published seccomp
  profile, the exact capabilities the Warden needs and why each, the
  cgroup and namespace settings; never "privileged".
- Docker and Podman, each covered by a release test suite, the way `make
  test-v1210` covers decided connections. Rootless Podman where the kernel
  allows it.
- A signed image with a software bill of materials (SBOM), which also
  serves the security-review pack.

**Ship gate:** the existing suites (conformance, decided connections, the
plan gate, program launches, credential release, the on-behalf-of chain,
`varek run`, MCP) pass inside a container, and the documented settings
grant nothing the Warden does not need.

**For the design note:** whether the agent's container must keep
CAP_SYS_ADMIN (the noexec mounts), or whether v1.33's node agent removes
that need; whether `varek doctor` checks each setting in the container
and names the one missing.

## v1.33.0 — Kubernetes

VAREK on a Kubernetes cluster, without giving agent pods extra privileges.

- **A node agent.** One Warden per node (a DaemonSet) receives seccomp
  user-notify for labelled pods from the container runtime, instead of
  running inside each pod. The pieces exist: the OCI runtime specification
  (v1.1) supports seccomp user-notify, runc has implemented it since v1.1,
  and the Node Resource Interface (NRI) in containerd and CRI-O lets a
  plugin adjust a container's seccomp policy and inject hooks when the
  container is created.
- **A fallback for clusters without NRI:** the v1.32 image as the pod's
  entrypoint.
- **A Helm chart** (Kubernetes' standard install package), with policy as
  a ConfigMap or custom resource, so policy changes go through the
  cluster's normal review and GitOps flow.
- **Where it sells:** OpenShift certification, the step after the RHEL 9
  certification under way with Red Hat, and an Amazon EKS add-on on AWS
  Marketplace, which lists third-party add-ons through a self-service flow.

**For the design note:** whether the node agent can carry everything the
Warden does today. Each of these assumes the Warden starts the agent:

- **Descriptor handover, the empty network namespace and the egress
  proxy:** the agent's network is the Warden's to give.
- **Lifecycle:** the run ends when the agent ends; revocation and the
  user's token's expiry reach every process of the run.
- **Decided launches:** the agent applies its Landlock launch set to itself
  before it launches anything, so the set cannot be added from outside a
  container that is already running; it would have to be applied by a hook
  at the container's start.
- **noexec mounts:** these are made in the Warden's own mount namespace,
  which the agent inherits; a container has its own, so they would have
  to be made there, for example by a hook.
- **Opening files as the agent:** the Warden resolves names in its own
  view of the file system; a node agent would have to resolve them inside
  each container's root.
- **Sub-agents and confined MCP servers:** their control groups are made
  under the run's; in a pod they would sit under the pod's group, which
  the kubelet owns.

**Ship gate:** a 24-hour run with a real agent on Amazon EKS and on
OpenShift, with agent pods running with no added capabilities (it needs
a cluster of each).

## v1.34.0 — Agent frameworks

The plan gate (`--plan`) needs the agent to write a plan file today, which
few teams will do by hand. Adapters would generate the plan from the
framework's own description of what the agent is about to do, so the gate
works without changes to the agent's code.

- **Order, by partnership value:** Amazon Bedrock AgentCore first (the
  AWS listing and pitch; decided October 14, 2026), IBM watsonx
  Orchestrate (IBM Partner Plus), then LangGraph, the OpenAI Agents SDK
  and the Claude Agent SDK.
- Each adapter is small and MIT-licensed. It writes a plan; the Warden
  decides it exactly as now.

**Ship gate:** for each framework, a sample agent whose plan passes and
one whose plan is refused, with the refusal explained in `varek refusals`.

## v1.35.0 — Security operations

v1.31's OCSF export makes the data available. This release delivers it
where security teams already look.

- A Splunk app and a Microsoft Sentinel connector, built on the OCSF
  events.
- OpenTelemetry export, for teams that route everything through a
  collector (Datadog, Grafana, Honeycomb and others).
- The CrowdStrike Falcon Foundry and Wiz integrations already in
  progress, released as supported.

**Ship gate:** a refusal appears in each tool within a minute, with the
policy line that decided it (each tested against a real instance: a
Splunk trial, a Sentinel workspace, an OpenTelemetry collector).

## Separate programs, not releases

**Windows.** Coding agents on developer laptops and some enterprise
servers run Windows. Native enforcement would be new code: a file-system
minifilter driver for files and the Windows Filtering Platform for
connections, signed by Microsoft through attestation signing, which
requires an extended-validation (EV) code-signing certificate. Start it
only when a buyer asks. Meanwhile, Windows users may be able to run agents
under VAREK inside WSL 2, which is a Linux VM, the same approach v1.30
takes on macOS; that should be tested and documented before it is offered.

**Native macOS.** The v1.28 to v1.31 plan describes it: a port to Apple's
Endpoint Security framework, which needs an entitlement Apple grants and
covers fewer operations than seccomp. That plan says to apply for the
entitlement now, because approval takes time.

**Business connections (no code).**

- Azure Marketplace and Google Cloud Marketplace, once the AWS listing has
  proven the motion. The v1.32 container image makes these simpler than
  building an AMI for each cloud. The Microsoft for Startups application
  is the first step toward Azure.
- What buyers check before code: the SOC 2 audit, OpenShift
  certification, and the CAIQ or SIG Lite questionnaire.

## Order and why

1. **v1.32, then v1.33.** They answer the most common technical objection,
   and both the EKS add-on and OpenShift use partnerships already in
   motion.
2. **v1.34.** Plans generated automatically turn the plan gate from a
   feature few will set up into a default.
3. **v1.35.** It depends on v1.31's OCSF export.
