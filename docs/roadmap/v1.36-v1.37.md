# VAREK v1.36 and v1.37, v1.11, and assurance before market (plan)

**Status:** Planned, not built. These follow the v1.32 to v1.36 plan
(`docs/roadmap/v1.32-v1.35.md`). One release is new (v1.36.0), security
operations moves from v1.36.0 to v1.37.0, and v1.11 gets a condition. As
before, each release gets its own design note, with decisions and ship
gates, before it is built, and is soaked for 24 hours before it is tagged.
**Author:** Kenneth Wayne Douglas, MD
**Last updated:** October 24, 2026

The question (October 24, 2026) was what else VAREK needs before it goes
to market. Two releases, one condition on v1.11, and an assurance program
that costs little or nothing. None of it changes the three-state decision
semantics: no extension may move a genuinely unsafe action to SATISFIED.

| Release | What it adds | The buyer's question it answers |
|---|---|---|
| v1.35.0 | Agent frameworks: plans generated from the framework (unchanged) | Does it fit how we build agents? |
| v1.36.0 | Kubernetes at parity with a host, and the platforms VAREK supports, tested | Does everything we bought work on our cluster? |
| v1.37.0 | Security operations: Splunk, Microsoft Sentinel, OpenTelemetry (was v1.36.0) | Will our security team see it? |
| v1.11 (candidate) | The bounded sequence fragment, revisited after v1.35, on measurement | Will more of our agents' safe plans clear? |

## v1.36.0 — Kubernetes at parity, and the platforms VAREK supports

v1.34 brings the Warden to Kubernetes, but not all of it. Its release
notes (Known limits) say what it leaves:

- **Not carried yet:** credentials (v1.28), sub-agents and `require
  on-behalf-of` (v1.28.1), confined MCP servers (v1.31), plans and the dry
  run (v1.29). The plugin and the admission check refuse a pod whose policy
  names any of them, so on a cluster VAREK is less than it is on a host,
  without its headline features.
- **amd64 only:** the node image is built for amd64 and the DaemonSet runs
  on amd64 nodes. Graviton is common on EKS, and AgentCore Runtime's
  architecture is one of v1.35's step 1 measurements.
- **The exporter audits each stream whole:** about 3.7 KB of memory a
  record, 2 GiB at most, so about 550,000 records. A busier agent's day is
  reported "not verified".
- **The node's signing key** is one Secret given to every node, so any
  node's key signs as any other's.

And step 9 of v1.34 (October 23, 2026) found three faults that no CI run
caught, because CI runs `kind` with containerd 2.3 and no SELinux:

- CRI-O 1.35 (OpenShift 4.22) crashed creating every supervised container:
  its NRI (v0.11) writes a seccomp rule's errno through a nil pointer.
  containerd before 2.3 has the same NRI.
- Under SELinux, the kernel refused to hand the agent a socket the node
  agent had made (the label is its maker's).
- The fix for that first opened `/proc` by path inside the container's
  mount namespace, where it is the container's, and silently did nothing.

Each would have reached the first OpenShift customer. What v1.36 does:

1. **Carry the rest.** Credentials, sub-agents, `require on-behalf-of`,
   confined MCP servers (built on sub-agents), plans and the dry run, each
   under the node agent as on a host. How each is carried is the design
   note's work. The hard one is sub-agents: a control group for each
   sub-agent inside the container's own, which needs the cgroup delegated
   to the pod (v1.32.1 solved the same question for rootless Podman with a
   bind remount).
2. **arm64.** A multi-architecture node image, the DaemonSet on arm64
   nodes, and the suites on an arm64 runner. v1.30's Graviton sweep fixed
   the host side.
3. **An audit in bounded memory.** A stream audited as it is read, in
   fixed memory, whatever its length. Streams are rotated on the node.
4. **A key for each node.** Each node signs with its own key. The design
   note decides how the audit learns which keys are the cluster's (each
   node's key signed by a cluster key, or listed in the anchor).
5. **The supported platforms, tested.** A CI matrix on every runtime
   VAREK names as supported: containerd 2.2 and 2.3 (kind node images by
   version), CRI-O 1.35, 1.36 and 1.37 under runc and under crun, one node
   with SELinux enforcing, and the hosts (RHEL 9, Amazon Linux 2023, Ubuntu
   24.04). What the matrix does not cover is not called supported. The
   README gets the table.

**Ship gate:** every cell of the matrix green on the release commit. Then
24 hours each on EKS (amd64 and Graviton) and on single-node OpenShift,
under a policy that names a credential, a sub-agent, a confined MCP server
and a plan. Each node's stream is audited under its own key, and a stream
of over 1,000,000 records is audited in fixed memory. **Cost:** as v1.34's
runs (about $25 for the day), plus a Graviton node.

### What v1.35 needs from it

v1.35's design note (`docs/security/v1.35-frameworks.md`) leans on the
node agent in two places:

- D8 (a) runs agents built for AgentCore under the Warden "elsewhere (an
  EKS cluster with v1.34, or v1.32's image)".
- D7's `require plan` is meant for v1.34's admission, where the cluster
  says which policy a pod runs under.

And D4 adds steps for MCP servers, sub-agents and credentials, none of
which v1.34's node agent carries. Until v1.36, v1.35's adapters work on a
cluster only for policies without them. v1.32's image is the full path
meanwhile. Decided (October 24, 2026): v1.35 carries plans under the
node agent (its D11), and v1.36 the rest.

## v1.37.0 — Security operations (was v1.36.0)

The scope is unchanged (`docs/roadmap/v1.32-v1.35.md`): a Splunk app and a
Microsoft Sentinel connector on v1.31's OCSF events, OpenTelemetry export,
and the CrowdStrike Falcon Foundry and Wiz integrations released as
supported. It moves after v1.36 because a refusal shown in Splunk is worth
little if the cluster cannot run the policy that made it. It depends only
on the OCSF export, so it can move ahead if a buyer asks for it first.

## v1.11 — the bounded sequence fragment: revisited after v1.35

The fragment (`docs/verification/bounded-sequence-fragment.md`) lets the
verifier decide predicates over every element of a bounded collection,
such as "every path in this list is under the allowed prefix". Today such
a case is UNKNOWN, and the step does not clear. It is sound by
construction: it composes on the string and bitvector fragments already
shipped, and anything longer than its bound stays UNKNOWN.

Not now, for three reasons:

- **It adds trusted code** to the verification chain (the encoder, the
  unroller and the length guard), with no outside review yet (below).
- **Its value depends on plans.** It only clears plan steps, and today
  "nothing outside the tests writes a plan" (v1.35's note). v1.35's
  adapters are what make plans common.
- **Nothing measures the need yet.** The v1.10 program's customer-derived
  corpus is still outstanding, so no figure says how many real steps are
  UNKNOWN on the collection stratum.

**The condition** (decided October 24, 2026): once v1.35's adapters
write plans from real agents (AgentCore first), run the
verdict-distribution harness on plans generated from at least 20 agents
across at least three frameworks. v1.11 is built if at least 10% of those
plans are refused only because of steps that are UNKNOWN on the
collection stratum, that is, plans v1.11 could let start. It is counted
per plan, not per step, because one step that does not clear refuses the
whole plan, so the share of plans is the share of runs that cannot start.
If fewer, v1.11 stays a candidate, measured again as the corpus grows. If
built, it ships under its note's own gate: `unsafe_allows == 0` across the
corpus and the collection adversarial pairs, and the length guard tested
at N and N+1.

## Assurance before market, without a paid audit

The threat model says what is true: "No human or third-party review has
been made." A paid review is not affordable before market, so none of the
following replaces one, and the docs keep saying so until one is made.
Most of it costs nothing:

1. **Continuous fuzzing.** The proxy's parsers and the MCP JSON parser
   have fuzz targets under ASan and UBSan (`make fuzz-proxy-parse`,
   `make test-mcp-json`), run by hand. Add targets for the other parsers
   that read input the Warden does not control: the node agent's JSON (the
   runtime's state, from its socket), the plan parser, the stub resolver's
   DNS parsing, and the three policy parsers. Run them in CI on each pull
   request (ClusterFuzzLite, a free GitHub Action), and apply to OSS-Fuzz,
   which fuzzes accepted open-source projects for free. VAREK is under the
   MIT license.
2. **Static analysis.** CodeQL on the C and Go code (free for public
   repositories), and Coverity Scan (free for open-source projects).
3. **The suites under sanitizers.** `test-v1340` and the sweep built with
   ASan and UBSan, run weekly in CI.
4. **OpenSSF Scorecard** (a free GitHub Action) and the **OpenSSF Best
   Practices badge** (self-assessed). Procurement checklists look for
   both.
5. **Funded reviews of open source.** Apply to OSTIF, which arranges
   security audits of open-source projects with sponsors' money, and to
   the Sovereign Tech Agency's programs. Whether a project a company owns
   is eligible is to be checked with each.
6. **Reviews that come with a sale.** A buyer's security team often tests
   a product before buying it: offer a test environment and ask for the
   findings. AWS's Foundational Technical Review, free for AWS partners'
   products, checks AWS practices, not the code's security. Some AWS
   partner programs require it.
7. **A public bypass challenge.** `docs/security/bypass-classes.md` says
   what is partial. Invite reports through `SECURITY.md` and credit them
   in the release notes.
8. **When the first contract allows:** a review scoped to the enforcement
   code in the trusted computing base, not the whole product. That means
   the Warden's decision and handover paths, the node agent and the egress
   proxy (`docs/security/TRUSTED-COMPUTING-BASE.md`). A narrow scope costs
   much less.

## Order and why

1. **v1.34** (its 24-hour runs end October 24), **v1.33** (macOS, in
   progress), then **v1.35**.
2. **v1.36.** Build its CI matrix during v1.35: the matrix is v1.36's
   ship gate, and it catches v1.35's regressions on runtimes CI does not
   run today.
3. **v1.37.**
4. **The assurance items from now.** Items 1 to 4 and 7 cost no money.
5. **v1.11 after v1.35's measurement**, if the condition holds. The
   measurement is a step of v1.35's own (its implementation plan, step 8),
   so the condition is checked when the adapters exist, not later.

## Decided

- **Release numbers are taken when a release is tagged** (October 24,
  2026). v1.34.0 ships before macOS, which then takes the next number;
  v1.35.0 to v1.37.0 above are the planned order, renumbered if another
  release ships between them (`docs/roadmap/v1.32-v1.35.md`, "Decided").
- **Kubernetes at parity and the supported platforms is v1.36.0, and
  security operations moves to v1.37.0** (October 24, 2026). Asked which
  order was better: parity first, since a platform that cannot run the
  policy is what loses a pilot.
- **v1.11 is revisited after v1.35, on measurement** (October 24, 2026),
  not built before.
- **v1.35 carries plans under the node agent** (October 24, 2026): a
  pod's plan checked and its run held to it as on a host, and `require
  plan` enforced at admission, so v1.35's cluster case works for plans
  whose steps v1.34 carries; v1.36 carries the rest (v1.35's D11).
- **v1.11's threshold** (October 24, 2026): built if at least 10% of the
  plans generated from at least 20 agents, across three frameworks, are
  refused only for steps UNKNOWN on the collection stratum.
- **No paid review before market** (October 24, 2026; cost). The
  assurance items above instead, with the docs saying plainly that no
  third-party review has been made.

## Decisions still open

- **The matrix's cost.** GitHub's hosted runners are Ubuntu. A node with
  SELinux enforcing, and CRI-O under crun, need a virtual machine in the
  runner (if it allows nested virtualization), a self-hosted runner, or a
  small cloud instance run for each release rather than each pull request.
